## Что обещает человеку

Человек, который открыл установщик, видит на карточке компонента бейдж «~222 МБ» и такой же список в попапе «Что попадёт на мой ПК». Эта фича обещает, что цифра не выдумана: она посчитана по тем самым файлам, которые физически лежат в `vendor` и поедут внутрь установщика (`src/renderer/app.js:1231-1251`, `componentSizeBytes` и `sizeBadgeHtml`). Если посчитать было нечего, человек увидит не круглое правдоподобное число, а пустое место или словесную пометку `sizeNote` — «скачивается во время установки», «размер задаёт магазин приложений».

Второе обещание — установщик вообще существует и собирается. Офлайн-издание Windows упирается в потолок 32-битного makensis; офлайн-кеш npm растёт сам собой, потому что `npm install --cache` добавляет версии и никогда не удаляет старые. Чистка кеша и пересчёт манифеста `vendor/checksums.json` — это то, что держит сборку под потолком и держит манифест целостности совпадающим с диском, чтобы гейт на машине ученика не отбил вшитый артефакт как подменённый.

Оба обещания адресованы не ученику напрямую, а тому, кто выпускает релиз: сами три инструмента в дистрибутив не попадают — `package.json` → `build.files` содержит только `src/**/*`, а общий `extraResources` (`package.json:66-104`) перечисляет ровно восемь записей: `scripts`, `agent`, `config.json`, `components.json`, `remote-components.json`, `packs.json`, `assets/starter-project`, `assets/START-HERE.html`. Каталог `vendor` в общий блок не входит — он объявлен только в `build.win.extraResources` (`package.json:117-128`, с фильтром «без `playwright-browsers` и без `apps/chatgpt.vsix`»); у `build.mac` блока `extraResources` нет вовсе, и `dist:mac` (`package.json:20`) даже не вызывает `fetch:vendor`. Каталога `tools` нет ни в одном из блоков.

## Как работает

Фича — это три независимых скрипта, каждый со своим входом и своим кодом возврата.

### 1. `tools/sync-sizes.js` — размеры компонентов

Единственный источник чисел в `components.json`.

1. `main()` (`:324`) разбирает аргументы: `--check`, `--json`, `--platform <win32|darwin>`, `--force`. Неизвестная платформа → `return 2`.
2. Гейт чужой платформы (`:339-345`): если запрошенная платформа не равна `process.platform` и нет `--force` — выход с кодом 2 и текстом «Часть путей vendor общая — измерение дало бы правдоподобные, но ЧУЖИЕ байты».
3. `computeSizes()` (`:247`) обходит все компоненты из `components.json`:
   - id есть в `NO_BUNDLED_PAYLOAD` (`:135-146`: `verify`, `bridge`, `claude-desktop`, `chatgpt-desktop`) → числа не будет вовсе, попадает в `skipped`. Пометка заводится не всем: в `notes` кладётся только непустой `note` (`:260`), а `applySizes` пишет его только при отсутствующем `sizeNote` (`:296`). У `verify` в карте стоит `note: null` (`:137`), поэтому пометки он не получает никогда;
   - иначе `measureComponent()` (`:191`) складывает размеры частей из `VENDOR_PARTS[platform][id]` (`:79-130`). Часть — это путь, каталог (считается рекурсивно через `sizeOf`, `:154`) либо glob-lite `{glob, pick:'max'}` для арх-вариантов одного артефакта: на mac едут обе арх, ставится ровно одна, поэтому суммировать нельзя — берётся больший;
   - результат `{missing}`, `{unmapped}` или `{timeout}` не даёт числа: такой id уходит в `skipped` и в `updates` не попадает.
4. Ветвление «чужая платформа с `--force`» (`:367-376`): из `updates` удаляются все id, кроме перечисленных в `PLATFORM_INDEPENDENT` (`:77`, сейчас там один `course` — закоммиченный `vendor/course/vibecoding-course.zip`).
5. `applySizes()` (`:287`) сносит легаси-поле `sizeHint` у всех компонентов, при необходимости проставляет `sizeNote` и пишет `c.sizeBytes[platform]` только для id из `updates`.
6. Исход:
   - `--check` и есть расхождения → сообщение в stderr и `return 1`, **до** `fs.writeFileSync` (`:428-433`);
   - расхождений нет и vendor не развёрнут → «ПРОПУЩЕНО: vendor не развёрнут — НИ ОДНО число не сверено», `return 0` (`:413-418`);
   - расхождений нет и vendor есть → «ОК: все сверенные числа совпали с vendor — файл не тронут»;
   - сериализация совпала с исходным текстом байт-в-байт → файл не переписывается (`:432`).

Куда это подключено: `npm run sizes` / `npm run sizes:check` (`package.json`), шаг «Проверка размеров компонентов (генератор жив и не врёт)» в `unit-tests.yml` на обеих ОС (`:131-132`, `:176-177` — на раннере vendor нет, шаг ловит сломанный генератор), шаг `npm run sizes` в `build-mac-lite.yml:221-222` (darwin-числа физически можно померить только там), и `checkSizes()` в `tools/release-check.js:135-155`, который считает тем же `computeSizes` (`:121`) и валит релиз блокером при расхождении.

### 2. `tools/regen-checksums.js` — манифест целостности без перекачки

Пересчитывает `vendor/checksums.json` по файлам, уже лежащим на диске.

1. Набор файлов (`:59-63`) повторяет `tools/fetch-vendor.ps1:524-555` дословно: всё непустое в `vendor/apps` рекурсивно (`walkFiles`, `:44`), плюс `course/vibecoding-course.zip`, `nomad-src.sha256`, `nomad-src/pyproject.toml`.
2. Пустой набор → `ОШИБКА: в vendor нечего хешировать` и `exit 2` (`:65-68`).
3. Сортировка по **базовому** имени файла (`:71`) — как `Sort-Object Name` в оригинале; ключ записи тоже базовое имя.
4. Формат собирается строкой вручную: `generatedAt`, `algorithm: sha256`, `files`, отступы и CRLF — чтобы очередной `npm run fetch:vendor` не давал шумный дифф (`:81-83`).
5. Сравнение с предыдущим манифестом идёт **только по полю `files`** (`:87-92`): `generatedAt` меняется всегда и о расхождении ничего не говорит. Совпало → «манифест уже соответствует диску — не трогаю», `exit 0`.
6. Разошлось → печатается построчный дифф `+ / - / ~`; с `--check` — `exit 1` без записи (`:113-116`), без него — запись файла.
7. **Перед записью — подписи издателей.** Скрипт зовёт `fetch-vendor.ps1 -VerifyOnly`: тот же пин (`Valid`, встроенная подпись, имя подписанта, корень цепочки в `LocalMachine\Root`) по всему `vendor/apps`, без загрузок и без удаления. Не подтверждено — `exit 3` и манифест не тронут; не Windows — тоже отказ; обход только явным `--skip-signer-check` с громким предупреждением в журнале. `--check` ничего не пишет и подписей не проверяет.

Ветвление по платформам у этого скрипта отсутствует: он работает с тем, что лежит в `vendor` на текущей машине.

### 3. `tools/prune-npm-cache.js` — чистка офлайн-кеша npm

1. `readCache()` (`:122`) разбирает `_cacache/index-v5` построчно, различая архивы (`parseTarballKey`, ключ вида `…/<пакет>/-/<имя>-<версия>.tgz`) и packument'ы (`parsePackumentKey`).
2. `resolveKeep()` (`:179`) вычисляет, что оставить: читает блоб packument'а корневого пакета `@anthropic-ai/claude-code`, берёт `dist-tags.latest` и `optionalDependencies` **этой** версии — так же, как резолвит `npm install --offline` без пина. Отсюда набор платформенных пакетов (win/mac/linux), а не из зашитой константы. Ветки-страховки: версии из `dist-tags` нет в кеше архивом → берётся самая новая имеющаяся плюс громкая нота; packument не прочитан → тоже самая новая имеющаяся.
3. `planPrune()` (`:254`) строит план и **проверки безопасности**: если под удаление попали все версии пакета или у оставляемой версии нет блоба на диске — в `blockers`. Блобы под удаление — те, на которые после чистки не сошлётся ни одна строка индекса (включая висячие ревизии packument'ов).
4. `main()` (`:352`): нет кеша → сообщение и `return 0`; есть blockers → «ОТКАЗ — чистка НЕ выполнена, кеш не тронут» и `return 1`; `--dry-run`/`-n` → печать плана без изменений; иначе `applyPrune()`.
5. `applyPrune()` (`:316`) удаляет **сначала строки индекса, потом блобы**. Обратной ссылки «блоб → индекс» в cacache нет: осиротевшая строка индекса заставила бы `hm_npm_cache_has_tarball` соврать установщику «офлайн-копия есть», и `claude.sh` ушёл бы в офлайн-ветку вместо честного онлайн-фолбэка.

Подключение: вызывается последним шагом наполнения кеша в обоих fetch-скриптах — `fetch-vendor.ps1:377` (после `npm install '@anthropic-ai/claude-code'`) и `fetch-vendor-mac.sh:135` (после `npm cache add` обеих darwin-арх, иначе прунер не увидит, что их надо сохранить). Оба скрипта на ненулевой код возврата печатают предупреждение и **продолжают** (`fetch-vendor.ps1:378-380`, `fetch-vendor-mac.sh:136`). Отдельный ранний сигнал — `checkNpmCacheDupes()` в `tools/preflight-build.js:205-234`: уровень бывает `skip` (`:211` — не подгрузился `prune-npm-cache.js`, `:215` — нет `vendor/npm-cache`, `:218` — кеш не разобрался), `ok` (`:221` — дублей нет) и `warn` (`:233` — дубли есть); `fail` не бывает никогда. В подсказке названа точная команда `npm run prune:cache`. Ручной запуск — `npm run prune:cache` (`package.json`).

## Инварианты

1. **Легаси-поле `sizeHint` не выживает ни при одном прогоне.** `applySizes` удаляет его у любого компонента безусловно (`tools/sync-sizes.js:292-295`); тест дополнительно проверяет, что renderer его не читает. Более сильного инварианта здесь НЕТ: число, которое реально видит человек, — это `sizeBytes[платформа]` (`src/renderer/app.js:1237`), и его `applySizes` не трогает, если id нет в `updates` (`tools/sync-sizes.js:301`). Рукописное `sizeBytes` у картированного компонента проходит все проверки, которые крутятся без vendor: сверочные тесты начинаются со `SKIP` при `!HAS_VENDOR` (`test/run-tests.js:9466`, `:8694`), а структурные (`:8548-8602`) проверяют форму — «есть запись в карте» (`:8561-8562`), «целое > 0» (`:8586`), «нет ключа `all`» (`:8590`), — но не само значение. Ловят такое только локальный прогон при развёрнутом vendor (`npm test`, `sizes:check`) и `release-check` на такой же машине; в CI сверки нет (`.github/workflows/unit-tests.yml:125-130`), а `release-check` без vendor даёт `warn`, а не `fail` (`tools/release-check.js:138`).
2. **Число есть только у компонента с записью в карте vendor.** Компонент из `NO_BUNDLED_PAYLOAD` числа не получает вовсе (`tools/sync-sizes.js:258-263`), а ВИДИМЫЙ компонент без числа не остаётся немым — у него есть `sizeNote`. Скрытого `verify` инвариант не покрывает по построению: в карте у него `note: null` (`tools/sync-sizes.js:137`), в `components.json` (`:98-106`) у него нет ни `sizeBytes`, ни `sizeNote`, а тест выводит скрытые компоненты из-под проверки первой же строкой (`test/run-tests.js:9351`, `if (c.hidden) continue;`). Это не недосмотр: `verify` в UI не показывается вовсе.
3. **`sizeBytes` — объект по платформам, целые положительные байты, ключа `all` не существует.** Держится тестами «размеры: sizeBytes — целые положительные байты под известные платформы» и картой `VENDOR_PARTS` (`tools/sync-sizes.js:79-130`); в коде рендерера число читается как `c.sizeBytes[STATE.platform]` (`src/renderer/app.js:1237`).
4. **Не измерил — не подставил.** `measureComponent` возвращает `{unmapped}` (`tools/sync-sizes.js:193`, компонента нет в `VENDOR_PARTS[platform]`) либо `{missing}` / `{timeout}` (`:199-223`) вместо числа, и такой id не попадает в `updates`, а значит `applySizes` его не трогает. Отсутствующий vendor не стирает уже записанные числа (`:301`, `:401-404`).
5. **`--check` не пишет файл никогда.** Ветка `if (check) { … return 1; }` стоит перед `fs.writeFileSync` (`tools/sync-sizes.js:428-433`); в `--json` то же самое через `return (check && changes.length) ? 1 : 0` без записи (`:381-388`).
6. **Прогон без vendor не выдаётся за успешную сверку.** При `!res.present` печатается «ПРОПУЩЕНО: vendor не развёрнут — НИ ОДНО число не сверено» (`tools/sync-sizes.js:413-418`), а не «ОК».
7. **Чужую платформу без `--force` не меряем; с `--force` пишем только переносимые артефакты.** Гейт `tools/sync-sizes.js:339-345` (exit 2) и покомпонентный фильтр `:367-376` по `PLATFORM_INDEPENDENT` (`:77`). Тест «sync-sizes: чужую платформу пишем ТОЛЬКО для переносимых артефактов» дополнительно запрещает объявлять переносимым то, что кладёт `fetch-vendor`.
8. **Набор файлов и формат `checksums.json` у генератора и у `fetch-vendor.ps1` совпадают.** `tools/regen-checksums.js:59-83` против `tools/fetch-vendor.ps1:1222-1255`: те же три добавки к `vendor/apps`, та же сортировка по базовому имени, тот же ключ, те же поля `sha256`/`bytes`, CRLF.
9. **Расхождение манифеста считается только по `files`.** `filesOf()` сравнивает `JSON.parse(text).files`, `generatedAt` в сравнение не входит (`tools/regen-checksums.js:85-92`); `--check` при расхождении даёт exit 1 и ничего не пишет (`:103-106`).
10. **Прунер удаляет только архивы `.tgz`.** В `removeEntries` попадают исключительно записи из `cache.tarballs` (`tools/prune-npm-cache.js:261-284`); packument'ы, включая чужие платформы, в удаление не кладутся — закреплено тестом «прунер удаляет ТОЛЬКО архивы…».
11. **Оставляемый набор версий вычисляется из метаданных кеша, а не из зашитой платформы.** `resolveKeep` берёт `dist-tags.latest` + `optionalDependencies` этой версии (`tools/prune-npm-cache.js:201-233`); тест требует, чтобы в KEEP оказались `darwin-arm64`, `darwin-x64` и `win32-x64`, и запрещает константу платформы в исходнике.
12. **Порядок удаления — строка индекса, затем блоб.** `applyPrune` сначала переписывает/удаляет файлы индекса, потом блобы (`tools/prune-npm-cache.js:316-333`).
13. **Повреждённый кеш не чистится вообще.** Любой blocker → `return 1` без вызова `applyPrune` в обеих ветках вывода (`tools/prune-npm-cache.js:379-380` для `--json`, `:390-395` для обычной).
14. **Отказ прунера не роняет наполнение vendor.** Оба fetch-скрипта печатают «чистка кеша ОТКАЗАЛА (кеш не тронут)» и продолжают (`tools/fetch-vendor.ps1:378-380`, `tools/fetch-vendor-mac.sh:135-136`); предполётная проверка накопления тоже никогда не `fail`, только `warn` (`tools/preflight-build.js:220-233`).
15. **Файл попадает в `vendor/apps` только с подписью ожидаемого издателя, выданной корнем машины.** `Assert-HmVendorFile` после загрузки и при пропуске готового файла, для распакованного uv до публикации и итоговый обход `Assert-HmVendorApps` до снятия сумм: Authenticode `Status = Valid`, встроенная подпись (не каталожная), общее имя подписанта ТОЧНО из `tools/vendor-signers.json`, назначение Code Signing у листа и корень цепочки в `LocalMachine\Root` (`Status = Valid` считает пользовательский движок цепочек, а он доверяет корням из HKCU; сертификат с нужным CN, выпущенный таким корнем, пройти не должен). Цепочка строится без оценки сроков, поэтому звено вне срока годности (любое: лист, промежуточный, корень) допустимо только с меткой времени, чья цепочка тоже в `LocalMachine\Root`. Провал — файл удалён и `exit 1`. Имя, которого нет в таблице ни как `signed`, ни как `unsigned` (с причиной), — тоже стоп, но файл не удаляется. Кэша «этот файл уже проверяли» нет: обход проверяет каждый файл заново прямо перед манифестом. Рабочие остатки оборванного прогона (`*.part`, `*.tmp`, `_jbmono.zip`, `_uv-stage`) обход убирает сам, а не считает неизвестными файлами. Нет `Get-AuthenticodeSignature` — стоп до первой загрузки. Тот же пин перед записью манифеста применяет `tools/regen-checksums.js` (через `fetch-vendor.ps1 -VerifyOnly`). Подробности — спека «Гейт целостности вшитых артефактов».
16. **Недоверенный код при сборке сведён к названному минимуму.** `npm install` ставит с `--ignore-scripts` (содержимое кеша от флага не зависит — проверено офлайн, побайтно): скрипты установки пакета с плавающей версией на машине подписи не исполняются. Каждый вызов `pip` идёт с `--only-binary=:all:`, единственное исключение — sdist pyaes: отдельным вызовом с `--no-binary pyaes --require-hashes` по пину `pythonSdists` из `tools/vendor-signers.json`, затем в общий вызов прямой ссылкой `file:///…#sha256=…`, так что индекс про него не спрашивают; в pywheels результат сверяется по файлу. Пакет без колеса роняет шаг громко (`pywheels/ … НЕПОЛНЫЙ`), а не собирается молча. Что этим НЕ закрыто — в разделе «Границы» (сборочный бэкенд setuptools из PyPI без хеша, playwright, плавающая версия claude-code).
17. **Личные паттерны экспорт-фильтра nomad-src не лежат в репозитории, а релиз без них не собирается.** В `tools/fetch-vendor.ps1` и `tools/fetch-vendor-mac.sh` только общие (ключи, токены); личные читаются из `tools/leak-patterns.local.json` (в `.gitignore`), из файла по `HM_LEAK_PATTERNS_FILE` или из переменной `HM_LEAK_PATTERNS`. Список есть, но битый или пустой (или `HM_LEAK_PATTERNS_FILE` указывает в пустоту) — стоп. Списка нет: локально печатается предупреждение и работают общие паттерны, а в РЕЛИЗНОЙ сборке (`CI=true`, `GITHUB_ACTIONS=true` либо явный `HM_RELEASE=1`) — стоп (`FATAL`, выход 1 / `return 1`); осознанный обход — `HM_ALLOW_NO_PRIVATE_LEAK_LIST=1` (флаг действует только в релизной сборке, в журнале громкий баннер). Каждый личный паттерн сканируется сам по себе (массив для `Select-String`, а не склейка через `|`), файлы с `[` `]` в имени и в пути сканируются по `-LiteralPath`.
18. **Экспорт-фильтр `nomad-src` называет файлы по пути от корня в том написании, в каком его обходит `Get-ChildItem`.** `Invoke-NomadSrcSanitize` приводит `$Src` к `(Get-Item -LiteralPath $Src).FullName` до первого среза по длине: правила «критичный файл» и строки журнала считаются по относительному пути, и с коротким 8.3-корнем (так выглядит `%TEMP%` на раннере GitHub и у людей с длинным именем профиля) он получал лишний каталог впереди. Тест «fetch-vendor.ps1 (прогон PS 5.1): экспорт-фильтр nomad-src при коротком (8.3) написании корня — относительные пути не съезжают, ключ в файле с [ ] в имени найден» ещё и проверяет путь, который фильтр сам пишет в журнал.

**Как CI получает личный список (описание, workflow не правятся здесь).** Рекомендуемый путь — секрет репозитория с JSON целиком, который шаг записывает ФАЙЛОМ во временный каталог раннера (`$RUNNER_TEMP`) и передаёт скрипту путь в `HM_LEAK_PATTERNS_FILE`: переменная `HM_LEAK_PATTERNS` наследуется всеми дочерними процессами шага (изолированная сборка pip, драйвер playwright). Для локального релиза на Windows файл `tools/leak-patterns.local.json` копируется в рабочее дерево, из которого идёт `npm run dist`, либо `HM_LEAK_PATTERNS_FILE` указывает на общий файл; `HM_RELEASE=1` в окружении превращает его отсутствие в стоп. Скрипты `dist` и `dist:win` в `package.json` зовут фетчер как `npm run fetch:vendor -- -Release`: ключ `-Release` сам выставляет `HM_RELEASE=1`, так что локальная релизная сборка без личного списка останавливается так же, как CI; обычный `npm run fetch:vendor` остаётся «предупредить и продолжить» (`dist:win:lite` фетчер не зовёт).

## Что ломается, если инвариант нарушить

1. Возвращается исходный дефект: рукописная строка размера, которую никто не пересчитывает. Человек видит «~50 МБ» рядом с файлом установщика на 1,9 ГБ и решает, что его обманывают, — ровно там, где интерфейс снимает страх «а не вирус ли это».
2. У компонента, который ничего не приносит с собой (`claude-desktop`, `chatgpt-desktop`, `bridge`), появляется бейдж с числом. Человек планирует загрузку по этой цифре, а реальный объём задаёт сторонний магазин или сайт.
3. Одно число на две ОС физически неверно: VS Code едет как 221,6 МиБ `setup.exe` на Windows и как 529,9 МиБ `.zip` на macOS (`components.json`, `vscode`: `sizeBytes.win32 = 232347808`, `sizeBytes.darwin = 555685401`). Пользователь Mac увидит вдвое заниженную сумму и решит, что установка зависла, а не идёт.
4. Пропавший из vendor файл превращается в тихий ноль или в старое число: попап обещает то, чего в сборке уже нет, и установка падает на шаге, который человек считал оплаченным заранее.
5. `npm run sizes:check` в CI начинает молча править рабочее дерево. Гейт перестаёт быть гейтом: расхождение «чинится» само и уезжает в релиз незамеченным.
6. Зелёный `sizes:check` на машине без vendor читается как «числа проверены», хотя не проверено ни одно. Именно так дефект и доживает до продакшена — сигнал есть, утверждения за ним нет.
7. Windows-байты записываются в darwin-поле. Живой случай 29.08.2026: `--platform darwin --force` переписал три числа (`claude` 135→103 МиБ, `nomad` 165→110, `mascot` 202→279) — все правдоподобны, ни одно не верно, код возврата 0. Пользователь Mac получает выдуманные цифры и никаких признаков подлога.
8. Манифест, собранный по другому набору или в другом формате, разъедется с тем, что генерит `fetch-vendor.ps1`. На установке `Confirm-HmArtifact` не найдёт записи по имени файла — вшитый компонент будет отбит как неподтверждённый, и человек увидит отказ на пустом месте.
9. Если в сравнение попадёт `generatedAt`, `--check` будет падать после каждого прогона генератора: гейт кричит всегда, к нему привыкают и перестают читать — а настоящее расхождение проезжает вместе с шумом.
10. Удалённый packument ломает резолв `optionalDependencies` для чужих платформ: офлайн-установка Claude Code на этой ОС не соберёт дерево и уйдёт в отказ у ученика, при формально «почищенном» кеше.
11. Прунер, зашитый на `win32-x64`, на macOS вычистит `darwin-arm64` и `darwin-x64` — ровно то единственное, ради чего кеш там и нужен. Офлайн-издание для Mac перестаёт ставить Claude Code.
12. Обратный порядок оставляет строку индекса без блоба. `hm_npm_cache_has_tarball` (грепом по `index-v5`) соврёт «офлайн-копия есть», `claude.sh` уйдёт в офлайн-ветку вместо онлайн-фолбэка и упадёт с `ENOENT`/`EINTEGRITY` **на машине пользователя**.
13. Чистка уже противоречивого кеша оставляет одну версию, которой физически нет: 12 архивов удалены, тринадцатый недостижим — офлайн-установка отказывает у ученика, а не у сборщика.
14. Если отказ прунера будет ронять `fetch-vendor`, наполнение vendor встанет из-за проблемы, которая сборку не ломает; если наоборот сделать `checkNpmCacheDupes` блокером — релиз будет отбиваться за лишние 80 МиБ, при том что настоящий отказ по размеру выносит отдельный гейт `nsis-limit`.
15. Без пина издателя подменённый по дороге установщик (CDN, DNS, TLS) становится «эталоном»: `checksums.json` снимается с того, что легло на диск, и все гейты Lite/Offline сходятся на подделке. С пином, но «предупредить и продолжить», — то же самое, только с зелёной строкой в журнале. С пином «Valid + имя», но без корня в `LocalMachine\Root`, — тоже: корень из HKCU (его кладёт процесс пользователя без UAC) даёт `Valid` сертификату с нужным именем. А если срок оценивать только у листа, лист, годный сегодня под просроченным промежуточным, проходит с чужой меткой времени.
16. Скрипты установки npm-пакета с плавающей версией и `setup.py` любого пакета без колеса исполняются на машине, где живёт сессия подписи Certum и боевые ключи S3: подменённая зависимость получает и то, и другое. Если pyaes качать без хеша, подмена в индексе выполнится так же. Закрыт именно этот класс («установочные скрипты и sdist без закрепления»); заявление шире — «чужой код на машине подписи не исполняется» — было бы неверным (см. «Границы»).
17. Личные паттерны в публичном файле публикуют ровно то, что фильтр должен не пропустить. Если при этом отсутствие списка сделать молчаливым — релиз с утечкой в `nomad-src` пройдёт «зелёным»; именно так выглядела первая редакция фикса, пока релизная сборка без списка не стала отказом.

## Границы

- **Ничего не качает.** `sync-sizes` меряет то, что уже лежит в `vendor`; `regen-checksums` не перекачивает артефакты (в этом и был смысл — раньше манифест обновляли только через `npm run fetch:vendor`); `prune` только удаляет. Восстановление после чистки — `npm run fetch:vendor`.
- **Размер докачки в lite-издании сюда не входит.** Он живёт в `remote-components.json` и приезжает в renderer как `bootstrap.remoteSizes`; второй копии в `components.json` нет сознательно (`tools/sync-sizes.js:21-23`, `src/renderer/app.js:1233-1236`). Кто именно записывает `sizeBytes` в `remote-components.json` — по прочитанному коду не подтверждено.
- **Не измеряется то, что качает сам компонент при первом запуске** (модель Handy, Chromium для Playwright, Python для Nomad) — это словами в `sizeNote`, числа там выдумывать запрещено.
- **darwin-числа берутся только на macOS.** На Windows гейт `:339-345` не даст их посчитать; практический путь — шаг `npm run sizes` в `build-mac-lite.yml:221-222` с коммитом `components.json` обратно в ветку.
- **`regen-checksums` фиксирует байты, лежащие на диске, и ничего не говорит об их подлинности.** Это генератор манифеста, а не проверка источника; сама проверка на установке — отдельная фича (гейт целостности, `scripts/windows/_verify.ps1`).
- **`prune` по умолчанию работает с `vendor/npm-cache`**, глобальный кеш пользователя не трогает (каталог задаётся `--cache`). Packument'ы не удаляются никогда, даже устаревшие по смыслу — удаляются только их висячие блобы.
- **Ни один из трёх инструментов не попадает к ученику.** `package.json` → `build.files` = `["src/**/*"]`, каталог `tools` не перечислен ни там, ни в `extraResources`. В дистрибутив едут результаты их работы: `components.json` и `vendor/checksums.json`.
- **Уступка по времени.** Обход каталогов на Windows упирается в антивирус, поэтому у `computeSizes` есть бюджет (`budgetMs`), и в тестах каталожные компоненты проверяются под ограничением (по умолчанию 8000 мс на компонент, полная сверка — `HM_SIZES_DEEP=1`). Что не успели — печатается как пропуск, а не как «ОК».

## Риски и открытые вопросы

- **У `tools/regen-checksums.js` нет ни одного теста и он нигде не вызывается автоматически.** Поиск по репозиторию даёт только четыре упоминания: `docs/INVENTORY.md`, `docs/specs/geyt-celostnosti-vshityh-artefaktov.md`, `docs/specs/_features.json` и сам файл. В `package.json` npm-скрипта под него нет (есть `sizes`, `sizes:check`, `prune:cache`, но не `checksums`), в `tools/release-check.js` и в workflow'ах он не упоминается. То есть единственный инструмент, который может разойтись с `fetch-vendor.ps1` по набору файлов и по формату, ничем не застрахован — расхождение обнаружится только отказом `Confirm-HmArtifact` на машине ученика.
- **Расхождение `regen-checksums.js` с `fetch-vendor.ps1` по фильтру пустых файлов.** PowerShell применяет `Where-Object { $_.Length -gt 0 }` только к рекурсии по `vendor/apps` и явно проверяет размер у курса, а `nomad-src.sha256` и `nomad-src/pyproject.toml` добавляет по одному лишь факту существования (`tools/fetch-vendor.ps1:1246-1249`). JS-версия применяет `size > 0` ко всем трём добавкам (`tools/regen-checksums.js:60-63`). Пустой `nomad-src.sha256` попал бы в манифест у одного генератора и не попал у другого. Практического случая в коде не видел.
- **Сравнение манифеста чувствительно к порядку ключей.** `filesOf()` сравнивает `JSON.stringify(...files)`, то есть порядок вставки; порядок задаётся `localeCompare(…, 'en')` в JS против `Sort-Object Name` в PowerShell. Совпадают ли эти два правила сортировки на всех именах из `vendor/apps` — не проверено ни тестом, ни прогоном; при расхождении `--check` сообщит о разошедшемся манифесте при идентичном наборе файлов.
- **`vendorPresent()` не ограничен бюджетом времени.** Он вызывает `measureComponent(id, platform, null)` (`tools/sync-sizes.js:230-237`) и возвращается на первом успешно измеренном компоненте. Порядок обхода — порядок ключей `VENDOR_PARTS`, где первым идёт файловый `git`; но если первые файловые артефакты отсутствуют, до успеха он дойдёт через каталог (`npm-cache`, `config-pack`). Замера не делал — потенциальная, не подтверждённая длительность.
- **`--force` у `sync-sizes` остаётся в интерфейсе, хотя его прежняя семантика признана опасной.** Сейчас он снимает только отказ, а покомпонентный фильтр всё равно оставит один `course`; сам комментарий в коде (`:351-366`) прямо говорит, что «`--force` сам по себе ничего не защищает». Открытый вопрос: нужен ли флаг вообще, раз единственный переносимый артефакт и так один.
- **Тесты прунера на реальном кеше молча вырождаются в no-op.** Три из пяти начинаются с `if (!cache.exists) return;` / `if (!versions.length) return;` (`test/run-tests.js:9687`, `:8920`, `:8931-8934`), то есть на чистом чекауте и в CI без `vendor` они зеленеют, ничего не проверив. Явного `SKIP` там, в отличие от размерных тестов, нет.
- **`sizes:check` в CI не сверяет ни одного числа** — это записано в самом workflow (`unit-tests.yml:138-143`): на раннере vendor не развёрнут, шаг ловит только сломанный генератор. Реальная сверка держится на локальном прогоне после `fetch:vendor`, на юнит-тестах при наличии vendor и на `release-check`.
- **Пин издателя не доказывает свежесть и продукт.** Настоящий, но старый или другой установщик ТОГО ЖЕ издателя пройдёт проверку (ProductName и версия файла не сверяются; публичная подпись Microsoft не отличает vscode-setup.exe от любого другого бинаря Microsoft); версию «latest» по-прежнему определяет API издателя. Сроки у самой метки времени не оцениваются (у настоящего python-setup.exe сертификат метки просрочен), а корень, лежащий только в `LocalMachine\AuthRoot`, не принимается — отказ громкий. macOS-вендор (`pkg`/`dmg`/`tar.gz`: python, node, VS Code zip, Cursor и Handy dmg, uv) подписью в фетчере не проверяется вовсе, там только пины dugite и Team ID скрепки: S-1 для macOS — отдельная задача (пины Team ID через `codesign`/`pkgutil`, таблица по образцу `vendor-signers.json`; на этой машине проверить значения нечем).
- **Что закрыто в S-6 и что нет.** Закрыто: скрипты установки npm-пакета (`--ignore-scripts`), `setup.py` подменённого pyaes и любого пакета без колеса (отказ по sha256 / `--only-binary` до сборки). НЕ закрыто, и заявление «чужой код на машине подписи не исполняется» неверно: (1) метаданные sdist pyaes pip собирает в изолированном окружении (современный pip, проверено на 26.2.1, изоляцию включает сам) и ставит туда сборочный бэкенд setuptools из PyPI без хеша — его код исполняется; `--no-binary` стоит только на pyaes, чтобы бэкенд приходил колесом, а не собирался из sdist, но хеша у него нет; (2) `playwright` и его драйвер ставятся из PyPI колёсами без хеша; (3) версия claude-code плавает (скрипты не исполняются, архивы берутся из реестра npm); (4) пин pyaes ни разу не прогонялся против настоящего PyPI — только на локальном индексе. Остаётся доверие к PyPI/npm и TLS до них. Полное закрытие — предустановить setuptools по хешу и добавить `--no-build-isolation`, либо один раз собрать колесо pyaes и вшивать его (заодно уходит сборка sdist на машине ученика); на macOS-раннере python.org 3.12 setuptools не содержит, поэтому там флаг не включён.
- **CI macOS без личного списка теперь падает, а не сканирует общими паттернами.** Релизная сборка (`CI=true`) без `HM_LEAK_PATTERNS_FILE` / `HM_LEAK_PATTERNS` / `tools/leak-patterns.local.json` — `FATAL` в `fetch-vendor-mac.sh`, пока workflow `build-mac*.yml` (файлы CI — отдельная правка, не этого фикса) не передаст список (секрет → файл в `$RUNNER_TEMP` → `HM_LEAK_PATTERNS_FILE`) либо не выставит `HM_ALLOW_NO_PRIVATE_LEAK_LIST=1` осознанно. Скрипты `dist*` в `package.json` `HM_RELEASE` не выставляют: релиз на Windows без файла списка предупредит, а не остановится, пока переменная не задана.
- **Тест живого pip идёт без сети и без изоляции сборки** (`PIP_NO_BUILD_ISOLATION=0` в окружении теста): он доказывает отказ по хешу ДО исполнения, запрет sdist и приоритет прямой ссылки, но не поведение изолированной сборки на настоящем PyPI.
