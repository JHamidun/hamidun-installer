## Что обещает человеку

После установки в домашней папке лежит готовая настройка Claude Code — `~/.claude` с правилами, агентами, командами, хуками и скиллами, плюс `~/CLAUDE.md` и шаблон файла ключей. Ничего не надо доносить руками: Claude при первом же запуске работает по этим правилам. Заодно в `~/HamidunStart` появляется стартовый проект с `PROMPTS.md`, на который ссылается памятка первого шага.

Второе обещание важнее первого и адресовано тем, у кого `~/.claude` уже есть. Установщик **никогда не переносит и не стирает** эту папку целиком. Ключи (`.credentials.master.env`), память (`memory/`, `MEMORY.md`), история сессий (`projects/`, `chats.db*`), локальные настройки (`settings.local.json`) и Telegram-сессия остаются нетронутыми в обоих режимах — и когда доустанавливается недостающее, и когда человек сам нажал «Переустановить начисто». Перед раскладкой снимается копия-бэкап `~/.claude.backup.<дата-время>` (хранятся три последние). Свои скиллы, которых не было в нашей базе, переживают даже переустановку начисто.

## Как работает

**1. Кто решает режим.** Режим выбирает main-процесс, а не интерфейс (`src/main.js:1174-1178`). Он вызывает `installMode.detectAdditive(os.homedir())` (`src/install-mode.js:47-61`), который проверяет семь признаков существующей настройки: `~/.claude/skills`, `agents`, `commands`, `rules`, `settings.json`, `.credentials.master.env` и `~/CLAUDE.md` (`additiveProbes`, строки 16-27). Проверка пути (`probePath`, строки 34-42) считает «нет» **только** при `ENOENT`; `EACCES`, `EIO`, `ELOOP`, `ENOTDIR` возвращаются как ошибка и трактуются как «возможно, есть». Дальше `decideConfigMode` (строки 75-79) отдаёт `clean` лишь в двух случаях: детекция доказала отсутствие кастомизаций, либо пользователь **и** включил repair, **и** отдельно подтвердил его. Всё прочее — `additive`. Результат едет в скрипт как `HM_ADDITIVE=1`; в режиме clean переменная удаляется из окружения (`main.js:1177-1181`). Но снятие регистрозависимое и по одному написанию — `delete childEnv.HM_ADDITIVE` (`main.js:1180`), — тогда как аллоулист renderer-env сверяет имя **регистронезависимо** (`install-env.js:35`, `RENDERER_ENV_ALLOW.has(String(k).toLowerCase())`) и кладёт ключ в результат в исходном регистре renderer'а (`install-env.js:43`, `out[k] = src[k]`). Поэтому кодом подтверждено лишь то, что подсказка renderer'а **в том же написании**, что эмитит наш `app.js:1295-1297`, решение переопределить не может. Ключ вида `hm_additive`/`Hm_Additive` аллоулист пропустит, `main.js:1180` не снимет, а `config.ps1:42` читает `$env:HM_ADDITIVE` через окружение процесса Windows, где имена переменных регистронезависимы. На macOS дыра не воспроизводится: `config.sh:29` читает `${HM_ADDITIVE:-}` регистрозависимо. Теста на этот конвейер нет — «P0-1 main.js: HM_ADDITIVE ставится АВТОРИТЕТНО…» (`test/run-tests.js:4570`) проверяет текст `main.js` пятью регулярными выражениями (`test/run-tests.js:4571-4576`), а сам env через фильтр не прогоняет.

**2. Подтверждение переустановки.** Кнопка «Переустановить начисто» в карточке компонента (`app.js:508-522`) при включении для `config` показывает `window.confirm` (`app.js:537-546`); только после согласия ставится `STATE.repairConfirmed`. В окружение уезжают два независимых списка: `HM_REPAIR` и `HM_REPAIR_CONFIRMED`, причём второй фильтруется по первому (`app.js:1299-1302`). Main требует оба (`main.js:1174-1176`).

**3. Источник базы.** Скрипт берёт вшитый в установщик пакет, если `HM_BUNDLED_CONFIG` указывает на каталог с `install.ps1` / `install.sh` (`config.ps1:58-59`, `config.sh:37-39`) — это офлайн-путь. Иначе делается `git clone --depth 1` с hardening-флагами `core.fsmonitor=false`, `core.hooksPath`, `core.symlinks=false`, пустым `credential.helper` и `credential.interactive=false` (`config.ps1:89-94`, `config.sh:90`); прежний каталог клона удаляется, клон всегда свежий. Адрес репозитория main форсирует из вшитого `config.json` и допускает только `https://github.com/JHamidun/…`, иначе подставляет умолчание `https://github.com/JHamidun/claude-code-config-pack` (`main.js:1190-1194`, сама проверка — регексп `/^https:\/\/github\.com\/JHamidun\//i` на `main.js:1192-1193`); `config.sh:74-77` дополнительно проверяет префикс `https://github.com/` уже на своей стороне. Нет ни вшитого пакета, ни работающего git — компонент падает с понятным сообщением (`config.ps1:75`, `config.sh:67`).

**4. Dry-run.** При `HM_DRY_RUN` скрипт печатает, что бы он сделал, и выходит с кодом 0 **до** клонирования и до бэкапа (`config.ps1:61-68`, `config.sh:41-55`). На диске не меняется ничего.

**5. Бэкап.** Если `~/.claude` существует, первой операцией снимается копия в `~/.claude.backup.<yyyyMMdd-HHmmss>-<8 hex>` (случайный хвост: имя нельзя угадать заранее). Windows: `robocopy /E /R:1 /W:1 /XJ` с `/XF` на секреты и на закрепку `.hm-pin-*` (`config.ps1:265-298`); перед папкой копии `~/.claude` закрепляется (инвариант 24). macOS: `rsync -a` с теми же исключениями, а без rsync — `cp -R` с последующей вычисткой секретов из копии; если вычистить не удалось, копия удаляется целиком (`config.sh:119-138`). Неполный бэкап печатает предупреждение и **не** останавливает установку — оригинал никуда не девался. Старые копии, кроме трёх последних, удаляются (`config.ps1:317-327`, `config.sh:154-158`).

**6. Раскладка (merge поверх).** Два режима отличаются одним флагом:
- **add-missing** (`HM_ADDITIVE=1`): Windows `robocopy /E /XC /XN /XO` — копируются только отсутствующие файлы (`config.ps1:226`); macOS `rsync -a --ignore-existing`, а без rsync — `hm_copy … missing`, которая пропускает существующие пути (`config.sh:250-255`, `167-193`).
- **repair** (переменной нет): Windows `robocopy /E` без `/XC` — наши базовые файлы перезаписываются свежими (`config.ps1:229`); macOS `rsync -a` без `--ignore-existing` либо `hm_copy … overwrite` (`config.sh:258-264`).

В обоих режимах preserve-list исключает пользовательское: имена и глобы `.credentials.master.env`, `.credentials.json`, `settings.local.json`, `MEMORY.md`, `chats.db*`, `tg_session.session*` и каталоги `memory`, `projects`, `todos`, `shell-snapshots` (`config.ps1:53-55`, `config.sh:105-106`, а для fallback-копира — `case` в `config.sh:176-179`). `settings.json` в preserve-list намеренно **не** входит: в add-missing он добавляется только если его нет, в repair перезаписывается. `~/CLAUDE.md` и `.credentials.master.env` из шаблона кладутся только при отсутствии — в обоих режимах (`config.ps1:243-254`, `config.sh:272-278`).

**4a. macOS: точечная правка `settings.json` прошлых версий пака.** Раз существующий файл в add-missing не трогается, исправления пака до тех, кто ставил раньше, не доходили: оставались плагины без токена, правила `Write(путь)`, опрос, HTTP-хуки `VSCODE_PORT`, `MCP_TIMEOUT=30000`. После раскладки `config.sh` зовёт `node scripts/macos/_cfgmigrate.js` — зеркало Windows-миграции: те же правила (`applyFixes`), та же отметка шага `student-defaults-2026-10` в `~/.hamidun-setup/config-migrations.json`, тот же формат записи `JSON.stringify(…, 2)`. Один раз на файл человека (под отметкой; у свежего файла пака, которого не было до раскладки или который repair перезаписал, — всегда): плагины с суффиксом `@claude-plugins-official` `true` → `false` из списка `OFF_PLUGINS` (пятнадцать: восемь из пака, Semgrep и шесть коннекторов июня–августа — Slack, Sentry, Figma, Hugging Face, LegalZoom, Adspirer), выключатель опроса и подъём `env.MCP_TIMEOUT` с ровно строки `"30000"` до `"120000"` (число, чужая строка и пробелы — выбор человека). На каждом запуске, по содержимому: правила `Write/MultiEdit/NotebookEdit/Glob(путь)` в `deny` и `ask` заменяются «близнецом» `Edit`/`Read` (запрет и вопрос только ужесточаются), а в `allow` убираются только дубли при уже стоящем близнеце — без близнеца правило остаётся как есть и в журнале установки появляется подсказка (замена превратила бы неработающее правило в разрешение, которого человек не давал); `Tool(*)`, голый `Write` и `mcp__*` не трогаются; `Bash(…*:*)` в `deny`/`ask` → `…*`; хуки `VSCODE_PORT` и раздел `mcpServers` убираются. Модель, effort, режим разрешений и прочие правила не трогаются (решение владельца 06.10). Запись: копия `settings.json.hamidun-bak-<время>` создаётся флагом `wx` с правами оригинала (занятое имя — файл, каталог или ссылка — не затирается и не прослеживается, берётся следующий суффикс), сам файл пишется во временный `wx`-файл и переносится `rename` поверх целевого (обрыв посреди записи не оставляет обрубок, ссылка на целевом имени заменяется, а не пишется насквозь; временный замок на целевом — антивирус или индексатор на Windows — переживается до восьми повторов с растущей паузой, постоянная ошибка и каталог на месте файла — отказ сразу); ссылка проверяется непосредственно перед записью и перед `rename`, то же для `~/.hamidun-setup`; файл-ссылка, `~/.claude`-ссылка, не-UTF-8 и не-объект не трогаются вовсе; BOM, CRLF и финальный перевод строки сохраняются; результат перед записью разбирается обратно. Движок — node (Node ставится раньше конфига; python3 на чистом маке — заглушка CLT с системным окном); нет node — правка пропускается понятной строкой. Проверено на настоящих файлах пака: `settings.json` 4223dd9 превращается ровно в 5cf4a39, повтор ничего не меняет.

**4b. macOS: профиль чинится на каждом прогоне (`touchup-config.sh`).** `config.sh` на повторном запуске не выполняется: компонент, уже отмеченный установленным, снимается с галочки, и всё из 4a, 4c и 4d до тех, у кого конфиг уже стоит, не дотягивалось. Для них есть автономный скрипт `scripts/macos/touchup-config.sh` (≤ 5 с, без сети, всегда код 0), который `verify.sh` зовёт на каждом прогоне (подключается отдельной правкой сборки) и который через `_cfgmigrate.js --touchup` делает то же над профилем. Если `config` НЕ выбран в этом прогоне (`HM_SELECTED`) и `~/.claude/settings.json` есть — миграцию (правила и отметка те же, поэтому повтор после `config.sh` ничего не меняет), `CATALOG.md` пака в `~/.claude` (только когда пак под рукой — `HM_BUNDLED_CONFIG`, в лёгком издании его нет, — и каталога там ещё нет: существующий не заменяется) и сводку для финального экрана (молча, и только если цифры изменились). При любых галочках, когда пак под рукой, — карту для Codex (4d): расширение могло встать позже `config.sh`, а повтор безвреден. Сухой прогон (`HM_DRY_RUN`) ничего не пишет и печатает одну строку `[dry-run] WOULD: …`. Ничего из профиля не исполняется. Нет файла настроек и нечего положить для Codex — молчит; изменилось — ровно одна строка `ОБНОВЛЕНО: …` со всем сделанным; нельзя или не вышло (ссылка, не-UTF-8, не объект JSON, нет node или он упал) — одна строка `[touchup-config] пропущено: <причина>`, чужие файлы целы.

**4c. macOS: опись поставленного (`CATALOG.md` и сводка).** После раскладки и фильтра наборов `config.sh` зовёт `_cfgmigrate.js --summary`: `CATALOG.md` пака кладётся в `~/.claude` (раньше он оставался в корне пака, и человек не находил, что вообще встало), а цифры — навыки (каталоги с `SKILL.md`), агенты и команды (`.md` без README, глубина 2) — в `~/.hamidun-setup/config-summary.json` в формате `JSON.stringify(…, 2)`: из него финальный экран пишет «установлено N навыков, M агентов». Сквозь ссылку (`~/.claude`, `CATALOG.md`, `~/.hamidun-setup`) не пишет; пака под рукой нет — каталог не кладётся, цифры пишутся. Сбой описи установку не валит. Зеркало `Write-HmConfigSummary` из `config.ps1`.

**4d. macOS: карта конфига для Codex (`~/.codex/AGENTS.md`).** Codex (расширение `openai.chatgpt-*` в `~/.vscode`, `~/.vscode-oss` или `~/.cursor`, либо каталог `~/.codex`) читает глобальный `AGENTS.md` из `~/.codex`; `AGENTS.md` пака туда никто не клал, и у тех, кто работает только через Codex, пак оставался невидимым. `config.sh` (после `~/CLAUDE.md`) и `touchup-config.sh` зовут `_cfgmigrate.js --codex`: Codex на машине нет — ничего не создаётся; файла нет — создаётся, содержимое пака лежит между метками `<!-- hamidun-pack begin -->` и `<!-- hamidun-pack end -->`; чужой файл остаётся байт в байт, а блок дописывается в конец один раз (BOM, CRLF и отсутствие финального перевода строки сохраняются); блок уже есть — не трогается ни повторно, ни «обновлением»; `~/.codex` или `AGENTS.md` — ссылка, `~/.codex` не каталог, файл не в UTF-8 — не пишется. Ссылка `](CATALOG.md)` в скопированном тексте переписывается на `](~/.claude/CATALOG.md)`. Переменная `CODEX_HOME` не читается: путь из окружения сделал бы запись произвольной.

**6а. Правка `settings.json` прошлых версий пака (только Windows).** `Invoke-HmSettingsMigration` (`scripts/windows/_cfgmigrate.ps1`) приводит `~/.claude/settings.json` к тому, что получает свежая установка из пака 5cf4a39 (его `guard_student_defaults.py --apply`), меняя ТОЛЬКО известные дефекты. Вызывается дважды: `config.ps1` сразу после раскладки и скрытый шаг `verify.ps1` на каждом запуске установщика, когда `config` не выбран (повторный запуск снимает у людей с готовым конфигом эту галочку, и без второго вызова правка до них не доходила бы). Что меняется:

- плагины без токена или входа и шумящий hookify: `greptile`, `sourcegraph`, `coderabbit`, `github`, `linear`, `notion`, `telegram`, `hookify`, ушедший из пака `semgrep` и коннекторы, которые старые версии пака отдавали включёнными, а без входа они только падают («needs authentication»): `slack`, `sentry`, `figma`, `huggingface-skills`, `legalzoom`, `adspirer-ads-agent` (все с суффиксом `@claude-plugins-official`) — `true` → `false`. Список сверен с историей `settings.json` пака, а не по памяти;
- правила, на которые Claude Code 2.1.283 ругается при каждом запуске (проверено запуском настоящего `claude -p` без входа на файлах всех версий пака): путь в `Write`/`MultiEdit`/`NotebookEdit`/`Glob` и Bash-правило, смешавшее `*` с хвостом `:*`. В `deny` и `ask` они заменяются на форму, которую советует сам Claude Code (`Edit(…)`/`Read(…)` на том же месте, `…*` вместо `:*`), — запрет и вопрос только становятся строже. В `allow` НИЧЕГО не заменяется: неработающее правило стало бы работающим разрешением, которого у человека на деле нет. Убирается только дубль (парное `Edit(…)`/`Read(…)` уже в списке), иначе правило остаётся, а в журнале пишется подсказка. `Tool(*)`, голый `Write` и `mcp__*` не трогаются (на `mcp__*` валидатор молчит);
- `env.CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY = "1"`, если не задан, и `env.MCP_TIMEOUT` `"30000"` → `"120000"` (пак отдавал 30000 с 19.08 по 06.09; любое другое значение, число или отсутствие ключа — выбор человека);
- HTTP-хуки с незаполненным `VSCODE_PORT` (опустевшие группы и события уходят вместе с ними) и top-level `mcpServers`.

Модель, effort, режим разрешений и всё прочее не трогаются. Запись осторожная. Файл, который не разбирается как JSON-объект, и файл или `~/.claude`, оказавшиеся ссылкой, не трогаются вовсе; текст пишется своим сериализатором в формате `JSON.stringify(…, null, 2)` с сохранением BOM, CRLF и финального перевода строки и до записи сверяется обратным разбором. Копия `settings.json.hamidun-bak-<дата>` создаётся режимом `CreateNew`: занятое имя — файл, каталог или ссылка — не затирается и не проходится насквозь, берётся следующее. Сам файл пишется во временный `CreateNew`-файл рядом и переносится поверх целевого; ссылка проверяется перед созданием временного файла и перед каждой попыткой переноса. Перенос повторяется до восьми раз (около 4 с): только что прочитанный файл на мгновенье держит антивирус или индексатор, и `File.Replace` падает с «Unable to remove the file to be replaced». То же относится к `~/.hamidun-setup` (отметка шага, сводка): ссылка — не пишем. Значения по умолчанию (плагины, опрос, `MCP_TIMEOUT`) к собственному файлу человека применяются один раз — отметка `student-defaults-2026-10` в `~/.hamidun-setup/config-migrations.json`; к файлу, который только что положили мы (его не было или repair его перезаписал), — всегда.

**6б. Карта конфига для Codex (только Windows).** Codex читает глобальный `AGENTS.md` из своего домашнего каталога `~/.codex` (в `codex.exe`: «Failed to read global AGENTS.md instructions»), а пак кладёт свой `AGENTS.md` только в корень пака, куда Codex не заглядывает: у тех, кто работает ТОЛЬКО через Codex, навыки пака оставались невидимыми. `Install-HmCodexAgents` (`scripts/windows/_cfgmigrate.ps1`) вызывается из `config.ps1` после `~/CLAUDE.md` и из блока починок `verify.ps1`, когда вшитый пак под рукой, — в том числе при выбранном `config`: расширение Codex могло встать позже него, а повтор безвреден (в лёгком издании пака на руках нет — файл появится при установке конфига). Условие: на машине есть Codex — каталог `~/.codex` или расширение `openai.chatgpt-*` в `~/.vscode/extensions`, `~/.vscode-oss/extensions` либо `~/.cursor/extensions`. Файла нет — создаётся (содержимое пака лежит между метками `<!-- hamidun-pack begin -->` и `<!-- hamidun-pack end -->`); файл человека есть, а блока в нём нет — блок дописывается В КОНЕЦ, остальное байт в байт как было (BOM, CRLF и отсутствие финального перевода строки сохраняются); блок уже есть — ни байта (ни повтора, ни «обновления»: нужен свежий — удали блок). Ссылка (junction/symlink) вместо `~/.codex` или `AGENTS.md` и файл не в UTF-8 — не пишем. Единственное изменение текста пака: относительная ссылка на `CATALOG.md` переписана на `~/.claude/CATALOG.md` — туда её кладёт опись (п. 11), а рядом с `~/.codex/AGENTS.md` каталога нет. Переменная `CODEX_HOME` не читается намеренно: установщик идёт под администратором, и путь из пользовательского окружения сделал бы запись произвольной. Если у человека есть `AGENTS.override.md`, Codex читает его вместо `AGENTS.md`.

**7. Ссылки внутри `~/.claude`.** Windows перечисляет все непосредственные дочерние элементы `~/.claude` и исключает из merge каждый, помеченный `ReparsePoint`: каталоги через `/XD`, файлы через `/XF` (`config.ps1:202-218`). Сбой этой проверки — fail-closed: пропускаются все наши подкаталоги, компонент помечается неуспешным. Если reparse-точкой оказался сам `skills`, он исключается целиком; если слинкован отдельный дочерний скилл — исключается только он, остальные раскладываются (`config.ps1:220-228`). macOS проверяет **только** `skills` — корень или любого ребёнка, включая скрытых (`config.sh:224-240`); при любом попадании исключается весь каталог `skills`.

**8. Фильтрация скиллов по наборам.** Работает только когда заданы обе переменные `HM_KEEP_SKILLS` и `HM_ALL_PACK_SKILLS` (их формирует renderer, `app.js:1285-1286`). Удаляется каталог скилла, который одновременно: входит в какой-то пак, не входит в выбранные, не является симлинком и был доложен нами. «Доложен нами» считается **по-разному на двух платформах**.

- **Windows** (`config.ps1:292-333`): отсутствовал в снимке `$preExisting`, снятом до merge, **или** записан нами в прошлый прогон в `~/.claude/.hamidun-skills.txt` — это дизъюнкция `$weAdded` на `config.ps1:323` (чтение списка — `config.ps1:176-181`, запись — `config.ps1:273-285`, удаление — `config.ps1:324-327`). Список наших скиллов обновляется только при полностью успешной раскладке (`config.ps1:273`).
- **macOS** (`config.sh:295-350`): механики `.hamidun-skills.txt` **нет вовсе** — такой строки в `config.sh` не существует, нет ни `ourPrev`, ни аналога. «Доложен нами» = только «имени нет в `PRE_EXISTING_SKILLS`» (`config.sh:319` `we_added=1`, `config.sh:320-324` `grep -qxF` → `we_added=0`); при отсутствии списка `we_added=0` и не удаляется ничего (`config.sh:329`). Следствие: прунинг паков на macOS срабатывает ровно один раз, на чистой машине — со второго прогона наши вчерашние скиллы уже попадают в `PRE_EXISTING_SKILLS` (`config.sh:215`), и снятие набора становится молчаливым no-op. Это ровно тот дефект, который комментарий `config.ps1:173-175` описывает как починенный: починен он только на Windows. macOS-аналога теста «config.ps1 ADD-MISSING ×3…» в наборе нет.

Fail-closed накрывает сбой перечисления `$preExisting` (`config.ps1:364-365`), reparse-скана (`config.ps1:400-404`), robocopy (`config.ps1:435-438`), копирования `~/CLAUDE.md` и шаблона ключей (`config.ps1:462`, `474`), а на macOS — `mktemp`, симлинк-реджект временного файла, перечисление и сбой `grep` (`config.sh:202`, `205`, `216-217`, `326`); тогда печатается «Удалено: 0» (`config.ps1:519`, `config.sh:297`). Сбой **чтения** `.hamidun-skills.txt` в fail-closed **не** входит: `catch` на `config.ps1:375` только обнуляет `$ourPrev` и `$pruneDisabled` не трогает — прунинг выполняется, просто консервативнее (удаляются лишь скиллы вне `$preExisting`), и печатает «убрано: N» (`config.ps1:557`). `mktemp` в `config.ps1` не используется вовсе — он есть только в `config.sh:200-206`.

**9. Стартовый проект.** Из вшитых ассетов `HM_ASSETS/starter-project` файлы докладываются в `~/HamidunStart` пофайлово: существующие не трогаются, отсутствующие копируются, счётчики печатаются (`config.ps1:335-387`, `config.sh:352-393`). Отдельно проверяется наличие `PROMPTS.md`, потому что памятка велит открыть именно его. Ассетов нет — об этом говорится вслух, а не молча.

**10. Доводка рантайма.** После успешной раскладки запускается `~/.claude/scripts/setup_runtime.py` — браузер Playwright, регистрация маркетплейсов плагинов, `node_modules` для `dev-browser` (`config.ps1:406-475`, `config.sh:412-468`). Python ищется и по PATH, и по абсолютным путям (Windows: `%LOCALAPPDATA%\Programs\Python\Python313|312|311`, `%ProgramFiles%\Python313|312`; macOS: `/Library/Frameworks/Python.framework/Versions/3.13|3.12|3.11`), заглушки `WindowsApps` и `/usr/bin/python3` без Command Line Tools отбрасываются. В окружение процесса добавляются `%APPDATA%\npm` и `~/.local/bin`, ставится `PYTHONIOENCODING=utf-8`. Провал доводки печатает совет «доделать», но компонент не валит.

**11. Завершение.** Маркер `~/.claude/.hamidun-config-complete` пишется последним шагом успешной раскладки (`config.ps1:493`, `config.sh:472`), и именно по нему детекция считает конфиг установленным, с легаси-фолбэком «есть `skills` И `settings.json`» (`main.js:2637-2640`). При неуспешной раскладке компонент выходит с кодом 1 и сообщением о том, что пользовательские данные не тронуты (`config.ps1:405-415`, `config.sh:401-409`). Перед маркером `Write-HmConfigSummary` кладёт `CATALOG.md` пака в `~/.claude` (раньше он оставался в корне пака, и человек не находил, что вообще встало) и пишет `~/.hamidun-setup/config-summary.json`: число навыков (подкаталоги `skills` с `SKILL.md`), агентов и команд (`*.md` без `README.md`, до двух уровней вглубь, ссылки не обходятся) — для финального экрана.

## Инварианты

1. **`~/.claude` не переносится и не стирается целиком** — ни `Move-Item`, ни `mv`, ни `rm -rf` дерева; раскладка идёт только merge-копированием (`scripts/windows/config.ps1:224-230`, `scripts/macos/config.sh:247-265`; тест «ИНВАРИАНТ: config.ps1/sh — НИ Move-Item/mv ~/.claude…»).
2. **`install.ps1` / `install.sh` из пакета конфига не запускаются** — раскладку делает сам скрипт компонента (`config.ps1:97-99`, `config.sh:93-95`).
3. **Режим установки решает main, а не renderer**: `childEnv.HM_ADDITIVE` либо ставится, либо удаляется по результату `decideConfigMode` (`src/main.js:1178-1183`). Инвариант держится **только для точного написания `HM_ADDITIVE`**: снятие регистрозависимо (`main.js:1180`), а аллоулист пропускает ключ регистронезависимо и сохраняет регистр renderer'а (`install-env.js:35`, `43`) — разбор в §1.
4. **Любая неопределённость детекции даёт additive.** «Нет файла» признаётся только по `ENOENT`; прочие ошибки и исключение в самой детекции возвращают `additive: true` (`src/install-mode.js:34-42`, `47-61`).
5. **Clean допустим только при доказанном отсутствии кастомизаций либо при паре repair + подтверждение** (`src/install-mode.js:75-79`; в UI подтверждение — отдельный `confirm`, `src/renderer/app.js:537-546`, и `HM_REPAIR_CONFIRMED` фильтруется по `HM_REPAIR`, `app.js:1301-1302`).
6. **Preserve-list не перезаписывается ни в одном режиме.** Одни и те же `/XF`+`/XD` (Windows) и `--exclude` (macOS) стоят в обеих ветках merge (`config.ps1:54-56` → `226`/`229`; `config.sh:105-106` → `250`/`259`; fallback-копир — `config.sh:176-179`).
7. **`~/CLAUDE.md` и `.credentials.master.env` создаются только при отсутствии** — в обоих режимах; сбой копирования помечает компонент неуспешным (`config.ps1:248-259`, `config.sh:272-278`).
8. **Бэкап — первая операция над `~/.claude` и это копия, а не перенос; его неполнота не фатальна** (`config.ps1:112-131`, `config.sh:119-149`).
9. **В бэкап не попадают ключи и Telegram-сессия, и копий хранится не больше трёх** (`config.ps1:123`, `134-138`; `config.sh:118`, `154-158`; на macOS при невозможности вычистить секреты копия удаляется — `config.sh:130-136`).
10. **Merge не пишет сквозь reparse-point/симлинк.** Windows исключает каждого помеченного непосредственного ребёнка `~/.claude`, macOS — каталог `skills` при ссылке на корне или на любом ребёнке (`config.ps1:202-228`, `config.sh:224-240`).
11. **Прунинг паков fail-closed**: сбой перечисления, копирования, `mktemp` или раскладки → ноль удалений и явное сообщение (`config.ps1:305-307`, `config.sh:296-297`).
12. **Скилл-симлинк не удаляется прунингом никогда** (`config.ps1:328`, `config.sh:314`), а пред-существующий скилл не удаляется, **если его имени нет в `~/.claude/.hamidun-skills.txt`** — в обоих режимах, включая repair. Абсолюта «пред-существующий не удаляется никогда» код не держит: `$weAdded` на `config.ps1:335` — дизъюнкция, и каталог, попавший в `$preExisting` (`config.ps1:166`), всё равно сносится на `config.ps1:337`, когда его имя числится в нашем инвентаре; этого прямо требует тест «config.ps1 ADD-MISSING ×3…» (`test/run-tests.js:2552`). На macOS абсолют выполняется буквально (`config.sh:320-330`, аналога `$ourPrev` нет), но ценой того, что прунинг там мёртв со второго прогона (§8).
13. **Список «наших» скиллов содержит только реально доложенное нами**: разность «источник минус `$preExisting`», объединённая с прошлым списком, и обновляется лишь при полностью успешной раскладке (`config.ps1:267-297`).
14. **Dry-run не меняет диск**: ветвление стоит до клонирования и до бэкапа, выход с кодом 0 (`config.ps1:62-70`, `config.sh:41-55`).
15. **Адрес репозитория конфига не управляется интерфейсом**: main перезаписывает `HM_CONFIG_REPO_URL` значением, прошедшим проверку `^https://github\.com/JHamidun/`, иначе умолчанием (`src/main.js:1205-1209`).
16. **Клон всегда свежий и неинтерактивный**: существующий каталог клона удаляется, git запускается с hooksPath/fsmonitor/symlinks-хардингом и запретом запроса кредов (`config.ps1:93-96`, `config.sh:83-90`).
17. **Маркер завершённости пишется только в конце успешной раскладки** и служит признаком «установлено» для детекции (`config.ps1:493`, `config.sh:472`, `src/main.js:2549-2552`).
18. **Провал раскладки даёт exit 1, а не ложный зелёный** (`config.ps1:405-415`, `config.sh:401-409`).
19. **Стартовый проект дополняется пофайлово**: существующие файлы в `~/HamidunStart` не перезаписываются, отсутствующие докладываются (`config.ps1:365-386`, `config.sh:363-382`).
20. **Доводка рантайма не может провалить компонент**: её ненулевой код превращается в совет, а не в ошибку установки (`config.ps1:471-482`, `config.sh:456-460`).
21. **Правка `settings.json` меняет только известные дефекты — с копией и самопроверкой.** Не разобрался как JSON-объект — не трогаем; ссылка — не трогаем; запись только после совпадения обратного разбора; копия до правки рядом (`scripts/windows/_cfgmigrate.ps1`).
22. **Выбор человека переживает повторные запуски.** Значения по умолчанию (плагины, опрос, `MCP_TIMEOUT`) применяются к его файлу один раз (отметка), к нашему свежему файлу — всегда; правила-«близнецы», хуки `VSCODE_PORT` и `mcpServers` проверяются по содержимому при каждом запуске (`Invoke-HmSettingsMigration`).
23. **В `allow` ничего не превращается в разрешение.** Правило с путём в `Write`/`MultiEdit`/`NotebookEdit`/`Glob` без парного `Edit`/`Read` остаётся как было (с подсказкой); убирается только дубль (`Get-HmWarnedRuleFix`, `Invoke-HmSettingsFixes`).
24. **Запись под администратором не идёт сквозь ссылку.** Копия — `CreateNew`, перенос — через временный `CreateNew`-файл, ссылка проверяется перед созданием временного файла и перед каждой попыткой переноса; то же для `~/.hamidun-setup` и `~/.codex` (`Write-HmFileSafe`, `New-HmBackupFile`, `Install-HmCodexAgents`). Корни `~/.claude` и `~/.hamidun-setup` и путь к ним от профиля (сам профиль — опора, ему доверяем) проверяются ДО первого действия и повторно впритык к каждому `robocopy` (`Get-HmLinkOnChain` в `_userpath.ps1`, `Assert-HmConfigNoLink` в `config.ps1`): ссылка на пути — отказ с кодом 1 и объяснением, что делать (`rmdir`), потому что `robocopy /XJ` пропускает ссылки только ВНУТРИ копируемого дерева, а корневой аргумент открывает как есть. Папка бэкапа носит случайный хвост (`.claude.backup.<время>-<8 hex>`), создаётся самим скриптом и на время копирования держит внутри открытый файл-замок (`DeleteOnClose`): подложить на неё ссылку или унести из-под `robocopy` нельзя. Сама `~/.claude` на всё время работы скрипта **закреплена** (`Lock-HmDir` в `config.ps1`): внутри лежит пустой файл `.hm-pin-<GUID>` (`CreateNew`, без общего доступа, `DeleteOnClose`), а пока в папке есть открытый файл, ОС не даёт переименовать ни её, ни родителей, то есть подменить ссылкой между проверкой и открытием корня `robocopy`-ом; проверка стоит до файла (чтобы он не лёг в подложенную ссылку), сразу после него и по имени с проверкой удержания (`Test-HmPinHeld`: подделка, которую никто не держит, и закрепка, оставшаяся в чужой папке, — отказ); закрепка держится до конца процесса (раскладка, список скиллов, прунинг, доводка рантайма), исключена из бэкапа (`/XF .hm-pin-*`) и из раскладки (`$excludeNames`), не вышло закрепить — отказ с кодом 1, а не «продолжаю без неё». Первый вызов — перед папкой копии, второй — сразу после `New-Item` (чистая машина). В онлайн-ветке так же закреплён `.claude` клона: он источник раскладки и лежит в профиле. Корень проверяется заново и перед прунингом. `~/CLAUDE.md`, шаблон ключей, файлы `~/HamidunStart`, маркер завершённости и список «наших» скиллов пишутся через `Write-HmFileSafe` (временный файл рядом и перенос по имени) теми же байтами, что давали `Set-Content` и `Copy-Item`: `Copy-Item` и `File.Copy(…, $false)` открывают само имя назначения на запись и на подложенной между проверкой и копией битой file-symlink СОЗДАЮТ файл-цель в чужой папке (проверено запуском на Windows PowerShell 5.1), а перенос по имени на ссылке отказывает и цель не трогает; в `~/HamidunStart` ссылка на самой папке или на подпапке внутри пропускает проект (или файл) со строкой в журнале.
25. **`~/.codex/AGENTS.md` человека не перезаписывается и не дублируется.** Нет файла — создаётся; чужой — дописывается отмеченный блок один раз; блок уже есть — файл не меняется (`Install-HmCodexAgents`).

## Что ломается, если инвариант нарушить

1. Человек теряет всё, что накопил в `~/.claude`: ключи, память, историю сессий, свои скиллы. Именно этот сценарий и был инцидентом, из-за которого механику переписали.
2. Возвращается `--backup`-режим пакета, который делал `mv` всего `~/.claude` в сторону, — тот же класс потери данных, только чужими руками.
3. Интерфейс (medium integrity, тот же пользователь) получает возможность подсунуть `HM_ADDITIVE=''` и превратить доустановку в перезапись без спроса.
4. Папка, которую не удалось прочитать из-за EDR, антивируса или прав, будет принята за «пусто», и установка пойдёт по clean-пути поверх реальных данных.
5. Кнопка, нажатая по ошибке или один раз залипшая в состоянии «начисто», перезаписывает базу без второго осознанного шага.
6. В repair-прогоне затираются ключи и память: человек теряет доступ ко всем интеграциям и всю накопленную историю, причём тихо — установка отрапортует «Готово».
7. Правки в `~/CLAUDE.md` (личный контекст) исчезают при каждой переустановке, а заполненный файл ключей затирается пустым шаблоном.
8. Если бэкап делать переносом, любой сбой посреди операции оставляет человека без обеих копий. Если считать неполный бэкап фатальным, установка будет падать всякий раз, когда открыт Cursor или Claude и залочен `chats.db`.
9. Ключи и Telegram-сессия размножаются по трём резервным копиям рядом с домашней папкой — утечка секретов в место, о котором человек не знает; без ретенции копии по несколько сотен мегабайт накапливаются молча и забивают диск.
10. Установщик уходит по симлинку в чужой каталог — личный git-репозиторий со скиллами или сетевую папку — и перезаписывает там файлы, которых вообще не касался запуск установщика.
11. Неполный снимок «что было до нас» превращается в приговор чужим скиллам: при снятом наборе удаляются каталоги, которые человек создавал сам.
12. Скилл пользователя, чьё имя совпало с именем из нашего пака, сносится вместе с его файлами при первом же снятии галки набора.
13. То же самое, но отложенно: на втором прогоне вчерашние «пред-существующие» каталоги считаются нашими, и снятие набора удаляет пользовательское. Либо обратная поломка — снятие набора перестаёт работать после первой установки.
14. Предпросмотр перестаёт быть безопасным: пользователь жмёт «посмотреть, что будет», а получает клон с сети и полный бэкап.
15. Подменённый адрес означает клонирование чужого репозитория прямо в `~/.claude` — то есть чужие `settings.json` и хуки, которые Claude исполнит.
16. Заранее подложенный `.git` с `core.hooksPath` выполняет чужой код под нашим процессом; включённый credential-helper поднимает графическое окно ввода логина, которое может всплыть за окном установщика, и установка виснет навсегда.
17. Оборванная установка (сон, перезагрузка, убитый антивирусом процесс) выглядит завершённой, галка компонента снимается автоматически, и повторный запуск не доразворачивает конфиг.
18. Частично разложенный конфиг отмечается как успех, человек уходит с нерабочей настройкой и без подсказки, что делать.
19. Работа человека в `~/HamidunStart` затирается — либо, при обратной ошибке, папка пропускается целиком и `PROMPTS.md`, на который прямо ссылается памятка, отсутствует.
20. Компонент падает целиком из-за отсутствующего браузера Playwright, хотя сами файлы конфига разложены и Claude уже работоспособен.
21. Установщик под правами администратора переписал бы настройки человека целиком или испортил бы файл, который не смог разобрать, — Claude Code при следующем старте показал бы «Settings Error» или потерял его правила.
22. Человек поставил токен и включил плагин (или вернул опрос или свой `MCP_TIMEOUT`), а следующий запуск установщика молча это откатил — и так на каждом повторе.
23. Правило `Write(~/проект/**)` в `allow`, которое Claude Code не применял, превратилось бы в `Edit(~/проект/**)` и выдало разрешение, которого человек никогда не получал.
24. Процесс обычного пользователя подменил бы `~/.claude`, `~/.hamidun-setup` или `~/.codex` ссылкой на системный каталог, и установщик под администратором записал бы в него файл. Без проверки корня ссылка вместо `~/.claude` заставила бы скопировать чужую папку (чужой профиль, `ProgramData`) в доступный пользователю бэкап и записать пак внутрь неё; по предсказуемому имени бэкапа подкладывалась бы ссылка в любую папку, куда администратору можно писать, и копия `~/.claude` (с тем, что процесс сам туда положил) уезжала бы туда под правами администратора. Без закрепки одной проверки мало: наблюдатель за профилем (`ReadDirectoryChangesW`) ждёт появления `.claude.backup.*`, за два переименования (20–30 мс) ставит junction на закрытую папку на место `~/.claude`, `robocopy` читает сквозь него, а скрытный вариант потом возвращает папку на место — шаг кончается кодом 0 и чистым журналом, и копия закрытой папки лежит там, где её прочтёт этот же процесс.
25. У тех, кто работает только через Codex, пак остаётся невидимым; а при повторной установке их собственный `~/.codex/AGENTS.md` был бы затёрт или обрастал копиями блока пака.

## Границы

- Спека описывает **компонент установщика**, а не содержимое пакета конфига. Что именно лежит в `.claude/` (какие правила, агенты, скиллы), сколько их и что делает `scripts/setup_runtime.py`, определяется репозиторием `claude-code-config-pack` и в этом репозитории не проверяется.
- Деинсталляции у компонента нет: `~/.claude` не удаляется установщиком, резервные копии `~/.claude.backup.*` чистятся только ретенцией до трёх штук. Кнопка «Удалить» рисуется лишь для компонентов из списка `REMOVABLE` с квитанцией (`src/renderer/app.js:510-513`), и этой парой ограничивается.
- Слияния JSON нет: `settings.json` целиком либо добавляется, либо перезаписывается; semver-мерж отклонён намеренно. Исключение — точечная правка известных дефектов на Windows (§6а). На macOS (`config.sh`) такой правки пока нет: исправления пака доходят туда только со свежим файлом. Карта для Codex (§6б) тоже только на Windows.
- Скиллы фильтруются только удалением каталогов уже разложенной базы; выборочного копирования по наборам нет.
- Компонент объявляет зависимости `git`, `node`, `claude` (`components.json:120-124`) и заявленный размер 233 358 780 байт для обеих платформ (`components.json:126-129`) — числа декларативные, скриптом не сверяются.
- В add-missing записанная версия компонента не продвигается до текущей — но под **двойным** условием, а не под одним `HM_ADDITIVE`: запуск аддитивный (`childEnv.HM_ADDITIVE === '1'`, `src/main.js:1349`) **и** в манифесте уже есть запись, строго старее текущей (`manifest.isOutdated(prevVer, ver)`, `src/main.js:1352`). Только тогда `ver = prevVer` (`src/main.js:1356`) и UI продолжает предлагать «Переустановить начисто». Если прежней записи нет (`prevVer === ''`) либо она не старее — выполняется `manifest.recordInstall(os.homedir(), id, ver, src)` с ТЕКУЩЕЙ версией (`src/main.js:1359`). Типовой случай «`~/CLAUDE.md` уже есть, конфиг ставится впервые» (`detectAdditive` вернёт additive по `src/install-mode.js:25`) пишет текущую версию как установленную.
- Онлайн-фолбэк требует git; офлайн-издание работает от вшитого пакета. Проверки целостности вшитого пакета (sha256) в самом `config.ps1`/`config.sh` нет — она, если есть, лежит вне этого кода и здесь **не подтверждена**.

## Риски и открытые вопросы

1. **Защита от записи сквозь ссылку на macOS уже, чем на Windows.** `config.ps1:197-213` исключает из merge каждого непосредственного ребёнка `~/.claude`, помеченного reparse-point, и комментарий прямо перечисляет `agents`, `commands`, `rules`, `hooks`, `tools`, `config`, `templates`. В `config.sh` такого перечисления нет вовсе — проверяется только `skills` (`config.sh:224-240`). Кодом подтверждена **сама асимметрия**; последствие для непокрытых детей (`agents`, `commands`, `rules`, `hooks`, `tools`, `config`, `templates`) кодом **не подтверждено** и различается между двумя ветками merge. Основная ветка — `rsync -a` (`config.sh:249-252`, `258-261`); флага `--keep-dirlinks`/`-K`, который заставил бы rsync трактовать симлинк-на-каталог у получателя как каталог, в `config.sh` нет, а без него rsync подменит симлинк реальным каталогом — то есть теряется ссылка пользователя, а не содержимое внешней цели. Запись **сквозь** ссылку кодом видна только в fallback-ветке `hm_copy`: `d="$(dirname "$dst/$rel")"; mkdir -p "$d"` и `cp -p "$src/$rel" "$dst/$rel"` (`config.sh:187-189`) пройдут по симлинку во внешнюю цель. Тестов на этот случай для macOS нет ни для одной из веток.
2. **Симметричная асимметрия в другую сторону.** Windows при слинкованном *дочернем* скилле исключает только его и раскладывает остальные (`config.ps1:414-417`, тест «config.ps1 REPAIR: слинкован ОДИН дочерний скилл…»). macOS при любом слинкованном ребёнке `skills` исключает **весь** каталог (`config.sh:230-235`), что зафиксировано тестом «config.sh REPAIR: скрытый (dot) дочерний skill-junction → skills исключён…». То есть поведение, которое на Windows признали дефектом («одна ссылка обнуляла раскладку всех ~330 скиллов», комментарий `config.ps1:346`), на macOS остаётся штатным.
3. **Маркер завершённости пишется даже тогда, когда скиллы не разложены.** При `skillsReparse` Windows пишет `.hamidun-config-complete` и только потом печатает предупреждение (`config.ps1:481-487`); macOS пишет маркер вообще без такого предупреждения (`config.sh:470-474`). Детекция в `main.js:2619-2622` увидит «установлено», и галка компонента снимется, хотя каталог скиллов пуст.
4. **Текст диалога подтверждения расходится с поведением кода.** `app.js:539-543` обещает, что ключи, память и история «будут сохранены и возвращены» — механики snapshot/restore больше нет, они просто не перезаписываются (это тот же результат, но другой механизм, и тесты требуют, чтобы snapshot/restore-машинерии не было вовсе). А вот вторая половина фразы — «Твои собственные скиллы и правки общих файлов при этом будут заменены свежей базой» (`app.js:542-543`) — для одного сценария **буквально верна**, и это отдельный риск, а не преувеличение диалога. Пред-существующий скилл защищён только от **удаления**: `$weAdded` на `config.ps1:323` и условие на `config.ps1:324` держат прунинг. Merge в repair — `robocopy $srcClaude $claudeHome /E /XJ /XF $excludeNames /XD $mergeXD` без `/XC` (`config.ps1:229`), а `$mergeXD` собран на `config.ps1:213` как `@($excludeDirs) + $reparseKids` (плюс `skills` при reparse корня, `config.ps1:216`); имён пред-существующих скиллов в исключениях нет, `$preExisting` (`config.ps1:164`) в merge не участвует вовсе. Значит, если имя каталога совпало с именем скилла из нашего пака (`git-workflow`, `security-audit` и т.п.), файлы пользователя внутри него будут перезаписаны паковыми. Тест «config.ps1 REPAIR: пред-существующий скилл юзера с ИМЕНЕМ снятого пака НЕ удаляется и НЕ перезаписан…» (`test/run-tests.js:2456`) эту ветку не покрывает: его сценарий кладёт `user-skill` в снятый пак, но **не** в clone (комментарий `test/run-tests.js:2460`), то есть коллизии имён с источником там нет. Ни один тест набора эту ветку не проверяет.
5. **Проверка адреса репозитория внутри скрипта есть только на macOS.** `config.sh:74-77` откатывает любой не-`https://github.com/` URL на умолчание; в `config.ps1:76` значение `HM_CONFIG_REPO_URL` берётся как есть. Защита держится исключительно на перезаписи в `main.js:1192-1193`; при запуске `config.ps1` в обход main этого рубежа нет.
6. **Строка `'0'` включает предпросмотр в двух местах сразу.** `$DRY = [bool]$env:HM_DRY_RUN` (`config.ps1:24`) истинно для любой непустой строки, включая `'0'`. В окружение скрипта main кладёт переменную только в dry-run (`if (isDryRun) childEnv.HM_DRY_RUN = '1';`, `main.js:1164`), поэтому до `config.ps1` подделка `'0'` из renderer'а не доезжает. Но сам `isDryRun` вычисляется раньше и по той же слабой логике: `!!(process.env.HM_DRY_RUN || (rendererEnv && rendererEnv.HM_DRY_RUN))` (`main.js:933`) — строка `'0'` здесь тоже истинна. Значит `HM_DRY_RUN=0` в окружении самого установщика превращает запуск в предпросмотр уже на уровне main (не качается remote, не пишутся лог/манифест/квитанция), не дожидаясь `config.ps1`. Дефект не ограничен приведением `[bool]` в PowerShell — он парный.
7. **Ошибки внутри блока прунинга подавляются.** Удаление идёт с `-ErrorAction SilentlyContinue` (`config.ps1:325`), а счётчик `$removed` увеличивается независимо от результата — отчёт «убрано: N» может быть больше фактического.
8. **Запись `.hamidun-skills.txt` (теперь через `Write-HmFileSafe`) завёрнута в пустой `catch { }`** (`config.ps1:509`). Это заявлено как fail-safe, но человек и лог не узнают, что список не записан, а без него снятие набора на следующем прогоне работать не будет.
9. **Код возврата `git clone` читается обоими скриптами — прежняя формулировка этого риска устарела.** `config.ps1:237-240` и `config.sh:101-105` печатают «Не удалось скачать конфиг с GitHub (git вернул код N)» и выходят с кодом 1, поэтому провал клонирования не маскируется под «источник не найден» (`config.ps1:256`, `config.sh:112`), как было до этих проверок. Остаётся только случай, когда git вернул 0, а `.claude` в клоне нет: тогда действительно печатается «источник не найден».
10. **Размер компонента в `components.json` (233 МБ) продублирован для обеих платформ** и ничем не сверяется с фактическим содержимым вшитого пакета — классическое место для расхождения документа с кодом.
11. **Хук статус-строки GSD (`gsd-statusline.js`) у старых установок обновляется только переустановкой начисто.** В add-missing существующий файл хука не перезаписывается, а правка §6а трогает только `settings.json`, поэтому «череп» в статус-строке у них остаётся до «Переустановить начисто». Свежие установки получают исправленный файл из пака.
12. **Окно между проверкой ссылки и открытием `~/.claude` самим `robocopy` закрыто закрепкой, а не проверкой; границы закрепки — ниже.** Проверка (`Assert-HmConfigNoLink`) стоит впритык к вызову, но между ней и тем, как `robocopy` откроет корневой аргумент, проходят десятки миллисекунд, и их хватало событийному наблюдателю за профилем (воспроизведено на сборке без закрепки: 3 прогона из 3, подмена за 20–30 мс; скрытный вариант возвращал папку и оставлял код 0). Раньше здесь стояло «папку раскладки нельзя прижать открытым файлом, в ней живут данные человека» — оба довода неверны: окно срабатывает по событию и не короче 20 мс, а временный файл-закрепка (`.hm-pin-<GUID>`, `CreateNew`, без общего доступа, `DeleteOnClose`) данных человека не касается и из копии исключён. Реальные события против исправленных скриптов: явная подмена и скрытная (повтор переименования 4000 раз) получают отказ ОС на переименование, утечки в копию нет, код 0; скрытный вариант мог подменить папку только после выхода скрипта. Что остаётся: (а) закрепка держит корень (и его родителей), а не содержимое: ниже верхнего уровня `~/.claude` (подкаталог, файловая или жёсткая ссылка на имени из пака) `robocopy` по-прежнему перезаписывает цель, существующая проверка охватывает только непосредственных детей (`$reparseKids`/`$reparseFiles`) и каталог `skills`; (б) прочие записи под администратором в профиль (`~/.hamidun-setup`: сводка и отметка миграции, `~/HamidunStart`, `~/CLAUDE.md`) не закреплены — они идут через `Write-HmFileSafe` с проверкой ссылки перед каждой попыткой, окно подмены остаётся, но пишется файл с фиксированным именем и содержимым из пака, а не читается чужое; (в) подделка закрепки, которую её автор сам держит открытой, по имени и по удержанию не отличима — для этого нужен дескриптор (`GetFileInformationByHandle`), а имя случайное и известно только тому, кто видит список файлов чужой папки; (г) закрепка не проверялась на томах, где переименование папки с открытым внутри файлом разрешено (профиль Windows на NTFS такого не допускает; ReFS, сетевые и FAT не пробовались); (д) под закрепкой нельзя переименовать `~/.claude` и профиль никому, пока идёт скрипт, включая доводку рантайма (минуты) — это цена защиты; остаток после аварийного выключения — пустой `.hm-pin-*`, который следующий прогон не трогает и не копирует.
