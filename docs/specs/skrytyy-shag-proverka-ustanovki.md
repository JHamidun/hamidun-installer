## Что обещает человеку

После установки человек получает не «зелёный экран, потому что скрипты не упали», а отдельный
чек-лист: Git, Node, Claude CLI, Конфиг, Python-пакеты, Расширение — каждый пункт с галочкой,
крестом или прочерком. Проверку он не выбирает и не может забыть включить: она добавляется сама
и идёт последним шагом. Крест значит «поставили, но не работает». Прочерк значит одно из трёх:
компонент не выбирали, его сняли из-за провала зависимости — **или** он установлен, но запуск не
подтверждён: `verify.ps1:122` печатает `CHECK skip Claude CLI (установлен, запуск не проверен)`
при вердикте `unverified`, который `claude.ps1:321` пишет на успешном пути (строка 322 печатает
«OK: Claude Code CLI установлен», выход `exit 0`). Третий случай на финальном экране подписывается
неверно — см. риск 1.

Заголовок «Установка завершена, но проверка нашла проблемы» с предложением отправить лог в бота
человек увидит **только когда все компоненты встали**: эта ветка стоит под условием
`failed.length === 0 && depSkipped.length === 0` (`src/renderer/app.js:1936-1939`). Если хоть один
компонент упал или был снят из-за провала зависимости, заголовок зависит от того, ЧЕМ упали: если
все провалы целостностные — «Файл не прошёл проверку подлинности» (`src/renderer/app.js:1940-1944`),
если все сетевые — «Сеть оборвалась при скачивании» (`src/renderer/app.js:1945-1948`), и только в
остальных случаях управление доходит до `else` и заголовок будет «Установка завершена с
предупреждениями» (`src/renderer/app.js:1949-1951`). Ни один из этих трёх заголовков не зависит от
того, есть крест в чек-листе или нет: крест влияет только на `okAll`
(`src/renderer/app.js:1931`), маскота (1958) и поле `ok` телеметрии (1984) — см. §9 и инвариант 10.

Второе обещание — обратное: сама проверка никогда не может испортить установку. Оба скрипта
заканчиваются безусловным `exit 0` (`scripts/windows/verify.ps1:245`, `scripts/macos/verify.sh:149`),
поэтому даже полностью сломанная диагностика не превращает удачную установку в красную.

## Как работает

**1. Компонент.** В `components.json:97-106` объявлен компонент `verify` («Проверка установки»)
с `"hidden": true`, `"default": true`, `"requires": []`, без `sizeBytes`. `hidden` означает
не «его не видно вообще», а шесть конкретных отсечек. Полный список мест, где читается
`.hidden`: `src/renderer/app.js` 232, 248, 371, 919, 1230; `src/main.js` 1335, 2765, 3257 —
других нет.

* карточка не рисуется на экране выбора — `renderGroups` фильтрует `!c.hidden`
  (`src/renderer/app.js:371`);
* он не попадает в счётчик выбранного (`src/renderer/app.js:1230`);
* попап «что попадёт/скачается на мой ПК» его не перечисляет — `showWhatInstalls` отсекает
  hidden (`src/renderer/app.js:919`, комментарий 904-906: «Служебные (hidden, напр. verify) не
  показываем»);
* детекция «уже установлено» его не видит — `detect-state` пропускает hidden
  (`src/main.js:2765`), поэтому автоснятие уже установленного его не касается
  (`src/renderer/app.js:232` требует `!c.hidden`);
* жёлтый баннер «часть компонентов уже установлена» не считает hidden установленными —
  `renderInstalledBanner` требует `!STATE.byId[id].hidden` (`src/renderer/app.js:248`);
* маркер установки и запись в `installed.json` для него не пишутся
  (`src/main.js:1335` → `receipts.shouldRecordInstall(code, isDryRun, !!(meta && meta.hidden))`),
  а `uninstall-component` для hidden отвечает отказом «Служебный компонент … не деинсталлируется»
  (`src/main.js:3257-3259`).

В списке шагов на экране установки он **виден** — `buildSteps` рисует все id прогона по
`STATE.byId[id].name` (`src/renderer/app.js:1445-1455`), то есть человек видит строку
«Проверка установки» последней.

**2. Порядок.** `ensureVerifyLast` выкидывает `verify` из списка и приклеивает в конец
(`src/renderer/app.js:358-361`). Вызывается дважды: при обычном старте — `ensureVerifyLast(installOrder())`
(`src/renderer/app.js:1853`), при повторе — `ensureVerifyLast(ids.concat('verify'))`
(`src/renderer/app.js:1895`), то есть на «Повторить» проверка догоняется, даже если её в списке
не было; дубликат снимает та же фильтрация.

**3. Запуск.** Скрипт выбирается по платформе: `scriptFor(id)` строит
`scripts/windows/verify.ps1` или `scripts/macos/verify.sh` (`src/main.js:568-573`). На Windows
процесс установщика запущен elevated (`package.json` → `build.win.requestedExecutionLevel:
"requireAdministrator"`), поэтому verify.ps1 исполняется под админом — из этого растут его
ограничения (см. инвариант 5).

**4. Что именно проверяется.** Обе платформы читают `HM_SELECTED` (список выбранных id через
запятую, собирается в `envForRun`, `src/renderer/app.js:1291`; допущен в elevated-скрипты явным
allowlist-ом `src/install-env.js:23`). Для каждого пункта — три исхода:

| Пункт | Windows (verify.ps1) | macOS (verify.sh) |
|---|---|---|
| Git | `Get-Command git` (46) + `git --version` (48), весь блок 42-53 | сначала проверка CLT (`xcode-select -p` или бинарь CLT), иначе git не из `/usr/bin`-шима — чтобы не всплыл системный диалог (29-40) |
| Node | `Get-Command node` + `node -v` (60-66) | `have node` + `node -v` (49-53) |
| Claude CLI | **переносит вердикт** из `~/.hamidun-setup/checks.json` (106-126) | `have claude` либо `-x ~/.local/bin/claude` (61-67) |
| Конфиг | `settings.json` И `skills` И запись `components.config` в `~/.hamidun-setup/installed.json` (145-167) | то же тремя свидетелями, но квитанция проверяется `grep -q '"config"'` (78-94) |
| Python-пакеты | найти python (два фиксированных пути в `%LOCALAPPDATA%`, затем PATH мимо WindowsApps) → `import playwright` → каталог `chromium*` в `%LOCALAPPDATA%\ms-playwright` (181-211) | кандидаты python3 из четырёх путей → `import playwright` → `~/Library/Caches/ms-playwright/chromium*` (104-121) |
| Расширение | каталоги `.vscode`, `.vscode-oss`, `.cursor` + regex `^<extId>-\d`, только каталоги (222-241) | `--list-extensions` у настоящих CLI Cursor/VS Code в `/Applications` и `~/Applications` (134-144) |

Не выбранный компонент даёт `CHECK skip <ярлык>` (`Test-Selected` / `is_selected`), а не крест.
Если `HM_SELECTED` не задана вовсе — проверяется всё (`verify.ps1:35`, `verify.sh:14`).

**5. Ветка Claude CLI (только Windows).** `claude.ps1` проверяет claude запуском и пишет вердикт
`works` / `broken` / `unverified` в `~/.hamidun-setup/checks.json` функцией `Write-HmCheck`
(атомарно, temp + `Move-Item`, `scripts/windows/claude.ps1:269-287`, вызовы на строках 307, 312,
318, 321). verify.ps1 читает этот файл и переносит вердикт: `works` → `CHECK ok`,
`unverified` → `CHECK skip Claude CLI (установлен, запуск не проверен)`, всё остальное (включая
отсутствие вердикта) → `CHECK fail`. Найденный путь бинаря (`Find-ClaudeBinary`) печатается
отдельной строкой и **не** влияет на вердикт.

**6. Приём результата в UI.** Подписка на лог в `runComponents` перехватывает строки с префиксом
`CHECK ` и разбирает их регуляркой `/^CHECK (ok|fail|skip)\s+(.*)$/`, складывая в `STATE.checks`
и не пуская их в общий лог (`src/renderer/app.js:1528-1536`). Перед самим запуском verify
накопленный чек-лист сбрасывается (`src/renderer/app.js:1588`), и то же делает `retryFailed`
(`src/renderer/app.js:1898`).

**7. Отсечка ложных крестов.** Компоненты, пропущенные в ходе прогона — осознанный `exit 120`
(`res.skipped`) или снятые из-за провала зависимости — копятся в `STATE.skippedEver` и
вычищаются из `HM_SELECTED` конкретно перед запуском verify
(`src/renderer/app.js:1620-1624`). Набор кумулятивный, поэтому переживает повторные прогоны.

**8. Отрисовка.** На финальном экране `renderNextSteps` строит блок «Проверка установки»:
`ok` → `✓`, `fail` → `✕`, `skip` → серый `–` с пояснением. Пояснение выбирается по карте
`CHECK_LABEL_TO_ID` (Git/Node/Claude CLI/Конфиг/Расширение) — если id в `depSkipped`, пишется
«не ставили: не встала зависимость», иначе «не выбрано» (`src/renderer/app.js:2140-2162`).
Ярлык со скобочным уточнением обрезается до первой скобки (`src/renderer/app.js:2154`).
Стили — `src/renderer/styles.css:477-499`.

**9. Влияние на исход.** `finishInstall` считает `checkFailed` как «есть хоть один `fail`» и
включает его в `okAll = failed.length === 0 && depSkipped.length === 0 && !checkFailed`
(`src/renderer/app.js:1927-1931`). Значит красный крест чек-листа меняет заголовок, маскота и
поле `ok` телеметрии, но не отменяет уже выполненную установку.

## Инварианты

1. **Проверка всегда последняя.** Любой прогон, содержащий `verify`, ставит его в конец —
   `ensureVerifyLast` (`src/renderer/app.js:358-361`), применяется и в `startInstall` (1853),
   и в `retryFailed` (1895).
2. **Проверка не проваливает установку.** Оба скрипта завершаются безусловным `exit 0`
   (`scripts/windows/verify.ps1:245`, `scripts/macos/verify.sh:149`); внутри Windows-скрипта
   стоит `$ErrorActionPreference = 'Continue'` (строка 4), а запись вердикта в claude.ps1
   обёрнута в пустой `catch` (`scripts/windows/claude.ps1:286`).
3. **Не выбранный компонент даёт прочерк, а не крест.** `Test-Selected` / `is_selected` печатают
   `CHECK skip` для всего, чего нет в `HM_SELECTED` (`verify.ps1:34-37`, `verify.sh:13-19`).
4. **Пропущенное в ходе прогона тоже даёт прочерк.** `HM_SELECTED` для verify чистится от
   `runtimeSkipped` (`src/renderer/app.js:1620-1624`), набор кумулятивен между прогонами
   (`src/renderer/app.js:1550-1552`, сброс только в `startInstall`, 1860-1861).
5. **Проверка расширения не запускает бинари редактора.** verify.ps1 смотрит каталоги
   расширений и матчит `^<extId>-\d` только по каталогам (`scripts/windows/verify.ps1:230-240`);
   ни `--list-extensions`, ни `& $cli` в файле нет — это elevated-процесс, и запуск
   user-writable `code.cmd`/`cursor.cmd` был бы повышением привилегий.
6. **PATH проверки не берётся из пользовательского реестра.** `Update-Path` собирает PATH только
   из `Machine`-ветки и фиксированных админских каталогов (`scripts/windows/verify.ps1:5-25`);
   HKCU не читается вовсе. Оговорка про claude: `Find-ClaudeBinary` (70-96) абсолютным путём
   ищет только в третьей ветке (`$env:USERPROFILE\.local\bin`, 89-93). Первая ветка — обычный
   PATH-lookup `Get-Command claude` (71-72), вторая берёт каталог из `npm config get prefix`
   (75-85), а это значение npm читает из user-writable `~/.npmrc`. Практических последствий
   нет: найденный путь только печатается (строка 115) и на вердикт не влияет (§5, инвариант 7).
7. **Один факт — один стандарт доказательства (Claude CLI, Windows).** `CHECK ok Claude CLI`
   печатается ровно при `verdict -eq 'works'` из `checks.json`; наличие файла-обёртки даёт
   только строку с путём (`scripts/windows/verify.ps1:106-126`).
8. **«Конфиг» зеленеет только при трёх свидетелях.** `settings.json` И `skills` И запись
   `components.config` в `installed.json` (`scripts/windows/verify.ps1:145-167`,
   `scripts/macos/verify.sh:78-94`); при частичном совпадении печатается список отсутствующего
   и `CHECK fail`.
9. **Строки чек-листа не попадают в общий лог и распознаются одной регуляркой.**
   `/^CHECK (ok|fail|skip)\s+(.*)$/` (`src/renderer/app.js:1531-1534`); нераспознанная строка
   с префиксом `CHECK ` уходит в лог как обычная.
10. **Крест чек-листа ломает «Готово!».** `okAll` включает `!checkFailed`
    (`src/renderer/app.js:1927-1931`).
11. **Служебный компонент не удаляется и не числится установленным.** hidden отсекается в
    `detect-state` (`src/main.js:2765`), в записи маркера (`src/main.js:1335`) и в
    `uninstall-component` (`src/main.js:3257-3259`).

## Что ломается, если инвариант нарушить

1. **Не последний** — проверка отчитается о том, чего ещё нет: человек увидит крест на Конфиге,
   который поставится через минуту, и пойдёт «чинить» рабочую установку.
2. **Не `exit 0`** — компонент `verify` попадёт в `failed`, финиш скажет «Установка завершена с
   предупреждениями» и предложит «Повторить» там, где всё установлено. Диагностика начнёт
   изображать поломку вместо того, чтобы её находить.
3. **Крест вместо прочерка на невыбранном** — человек, снявший Python-пакеты, увидит красный
   экран за собственный осознанный выбор и потеряет доверие к остальным галочкам. Пример
   работает только для шести реально проверяемых id (`git`, `node`, `claude`, `config`,
   `pydeps`, `extension`): снятый Cursor не даёт на чек-листе ничего — ни креста, ни прочерка,
   потому что `cursor` в списке проверяемых отсутствует (`verify.ps1` 42/56/97/130/178/218,
   `verify.sh` 24/45/57/72/100/125). Каталог `.cursor\extensions` в verify.ps1 используется
   только как одно из мест поиска расширения Claude (строка 225), а не как проверка Cursor.
4. **Не чистится `runtimeSkipped`** — после «Повторить» вернутся кресты по компонентам, которые
   в этом прогоне корректно не ставили. Крестов по VS Code, Nomad и курсу быть не может: verify
   не печатает по ним ни одной строки `CHECK` (проверяются ровно шесть id, см. «Границы»).
   Реальное следствие — «✕ Расширение»: `extension` объявляет `requires: ["vscode"]`
   (`components.json:88-90`), поэтому при `exit 120` у `vscode` он уходит в dep-skip
   (`src/renderer/app.js:1571-1577`), оставаясь в `HM_SELECTED`; именно этот случай назван в
   комментарии кода (`src/renderer/app.js:1548`, «vscode/extension/nomad exit-120»). Тот же
   механизм даёт кресты «Конфиг» (`requires: ["git","node","claude"]`, `components.json:120-124`)
   и «Python-пакеты» (`pydeps`, `requires: ["config"]`, `components.json:138-140`). Экран будет
   спорить сам с собой — «пропущено, нечего ставить» в логе и «✕» в чек-листе.
5. **Запуск `code.cmd`/`cursor.cmd` из verify** — админский процесс исполнит файл, который может
   переписать обычный пользователь: локальное повышение привилегий на машине новичка, который
   как раз и запускает установщик «от администратора».
6. **PATH из HKCU** — тот же класс: подложенный `git.exe`/`node.exe` из пользовательского
   каталога исполнится под админским токеном, а человеку это будет показано как успешная
   проверка.
7. **`ok` по наличию файла claude** — вернётся ровно та ошибка, ради которой писали `checks.json`:
   зелёная галочка при неработающем `claude`. Человек уйдёт учиться и упрётся в «команда не
   найдена» уже без установщика под рукой.
8. **Дизъюнкция в проверке конфига** — «✓ Конфиг» при половине разложенного дерева: скиллы есть,
   `settings.json` нет. Claude запустится и будет вести себя не так, как обещано, а причина
   останется невидимой.
9. **Сломанная регулярка** — либо чек-лист исчезнет (все строки уйдут в лог как текст), либо в
   лог хлынут служебные строки; на финальном экране блока проверки не будет вовсе.
10. **`okAll` без `checkFailed`** — «Готово! Всё установлено» при красном кресте прямо под этой
    надписью. Это худший из исходов: человек уносит уверенность, что установка удалась.
11. **hidden без отсечек** — на экране выбора появится карточка «Проверка установки» с кнопкой
    «Удалить», а в `installed.json` — запись о версии служебного шага.

## Границы

* Проверка **диагностическая**: она ничего не чинит, не доустанавливает и не откатывает. Кнопки
  «Повторить» относятся к компонентам, а не к пунктам чек-листа.
* Проверяются **шесть** пунктов: Git, Node, Claude CLI, Конфиг, Python-пакеты, Расширение.
  Компоненты `vscode`, `cursor`, `course`, `nomad`, `uv`, `bridge`, `mascot`, `handy`,
  `claude-desktop`, `chatgpt-desktop` в verify не проверяются вовсе — их исход виден только по
  статусу шага.
* Проверка «Расширение» отвечает на вопрос «есть ли каталог расширения», а не «работает ли
  панель»: на Windows это имя каталога вида `<extId>-<версия>`, на macOS — вывод
  `--list-extensions`. Расширение Codex (`openai.chatgpt`) verify не смотрит ни на одной
  платформе.
* Вердикт запуском (`checks.json`) существует только на Windows — в `scripts/macos/` строки
  `checks.json` нет вовсе; macOS-проверка claude довольствуется наличием исполняемого файла.
* Проверка Python-пакетов смотрит ровно два признака: импортируется ли `playwright` и лежит ли
  распакованный Chromium в кэше. Остальные библиотеки из `requirements.txt` не проверяются.
* `verify` не имеет артефакта и не докачивается из облака — в lite-издании он остаётся локальным
  скриптом (в реестре докачки записи для него нет, что и закреплено тестом про lite).
* Уступка по умолчанию: если `HM_SELECTED` не передана (старый вызов установщика), проверяется
  всё подряд — тогда невыбранные компоненты дадут кресты.

## Риски и открытые вопросы

1. **`CHECK_LABEL_TO_ID` не знает «Python-пакеты», а для Claude CLI ошибается иначе.** Карта в
   `src/renderer/app.js:2140-2146` содержит пять ярлыков, комментарий рядом прямо говорит
   «проверок пять», а verify печатает шесть. Следствие: `pydeps`, снятый из-за провала зависимости
   `config`, покажется на финале как «Python-пакеты (не выбрано)» — ровно то расхождение экрана с
   реальностью, которое для остальных пяти пунктов чинили специально. Второй случай того же
   дефекта — установленный, но не подтверждённый запуском Claude CLI: `verify.ps1:122` печатает
   `CHECK skip Claude CLI (установлен, запуск не проверен)`, `src/renderer/app.js:2154` срезает
   ярлык до `Claude CLI`, 2155 находит `cid = 'claude'`, а поскольку `claude` не в `depSkipped`,
   строки 2156-2158 дают `why = 'не выбрано'`, и 2159 рисует «– Claude CLI (установлен, запуск не
   проверен) (не выбрано)». Экран подписывает установленный компонент как невыбранный.
2. **Windows: python 3.11 не ищется.** `pydeps.ps1:39-41` принимает Python313/312/**311** в
   `%LOCALAPPDATA%`, а `verify.ps1:182-184` — только 313 и 312. Найти 3.11 через PATH verify
   тоже не может: `Update-Path` намеренно выбрасывает пользовательский PATH, куда python кладёт
   себя при `PrependPath=1`. Итог — «Python не найден» и красный крест на рабочей установке.
3. **macOS: списки интерпретаторов у установщика и у проверки разные.** `pydeps.sh:14`
   предпочитает `/Library/Frameworks/Python.framework/Versions/3.12/bin/python3` и **сознательно
   отказывается** от `/usr/bin/python3` (комментарий 26-28: шим CLT дёргает GUI-диалог). А
   `verify.sh:104` не содержит путь фреймворка вовсе, зато содержит `/usr/bin/python3` последним
   кандидатом и запускает его `-c "import playwright"`. Если раньше в списке найдётся чужой
   python3 (например, Homebrew) — будет ложный крест; если дойдёт до `/usr/bin/python3` — возможен
   тот самый диалог CLT, которого установщик избегает. Проверено чтением обоих файлов; поведение
   на живой машине не проверялось.
4. **macOS: квитанция конфига проверяется текстовым `grep '"config"'`** (`verify.sh:82`) вместо
   разбора JSON, как на Windows (`verify.ps1:152-153`). Совпадение подстроки где угодно в файле
   считается свидетельством установки — свидетель слабее, чем заявлено в комментарии «зеркало
   verify.ps1».
5. **macOS-скрипт не покрыт ни одним тестом.** В `test/run-tests.js` нет ни одной ссылки на
   `scripts/macos/verify.sh` (единственное упоминание — комментарий на строке 1519); `bash -n`
   прогоняется по списку из девяти скриптов (vscode.sh, claude-desktop.sh, chatgpt-desktop.sh,
   uv.sh, _lib.sh, cursor.sh, node.sh, pydeps.sh, mascot.sh), verify.sh в него не входит
   (`test/run-tests.js:898`). Из шести процитированных в шапке тестов Windows-специфичны три
   (`test/run-tests.js:1452`, `1480`, `7669`); остальные три Windows-ветку не трогают вовсе:
   1543 читает `src/renderer/app.js` через `EG_APP()`, 281 сверяет данные
   `remote-components.json` и `components.json`, 470 вызывает `installEnv.filterRendererEnv`.
6. **Тесты проверяют текст скрипта, а не поведение.** Найденные тесты verify.ps1 — grep-инварианты
   по исходнику (`EG_VERIFY()`); ни один не запускает verify и не сверяет напечатанный чек-лист с
   состоянием файловой системы. Синтаксический прогон verify.ps1 существует, но его заголовок
   собирается динамически (`name + ': PowerShell парсер без ошибок (синтаксис + BOM)'`,
   `test/run-tests.js:884-885`), поэтому дословно процитировать его в шапке нельзя.
7. **Пункт «Расширение» на Windows не различает VS Code и Cursor.** Каталог `.cursor/extensions`
   принимается наравне с `.vscode` (`verify.ps1:222-226`), поэтому расширение, установленное
   только в Cursor, зеленит проверку и для пользователя VS Code.
8. **Любой компонент может подделать чек-лист.** Перехват строк живёт на общем логовом канале
   (`src/renderer/app.js:1528`), а не на выводе конкретно verify; строка `CHECK ok …`, напечатанная
   любым install-скриптом, попадёт в чек-лист. Сброс `STATE.checks` перед запуском verify
   (строка 1588) снимает практическую часть риска, но инвариантом это нигде не закреплено.

   работы.** Совпадений два, оба вне процитированных диапазонов строк:
   `src/renderer/app.js:687` («интерактивный (детект в main.js; на Windows пока пусто — см. TODO
   там)») и `src/main.js:1532` («Известное ограничение (как у всей установки, см. TODO про
