- **Тесты:** `test/audit-pack-regex.test.js`, `test/audit-pack-run.test.js` — тесты этой фичи лежат ОТДЕЛЬНЫМИ файлами, а не в `test/run-tests.js`: второй гоняет сам audit-pack на заведомо зелёном и заведомо битом паке.

  Оговорка, потому что «НЕТ» здесь означает не «покрытия нет вовсе». Тесты у фичи
  есть — `test/audit-pack-regex.test.js` (50 строк) и `test/audit-pack-run.test.js`
  (106 строк), оба прогнаны 29.08.2026 и оба зелёные. Но в `test/run-tests.js` их нет:
  искал по подстрокам `audit-pack`, `audit`, `mcpServers`, `enabledPlugins`,
  `marketplace`, `ВЕРДИКТ`, `связность`, `HARDCODED`, `preflight` — ни одного
  совпадения по этой фиче. Оба файла — самостоятельные скрипты с шебангом, запускаются
  только руками (`node test/audit-pack-regex.test.js`), а `npm test` = `node
  test/run-tests.js` (`package.json`) их не подключает: во всём `run-tests.js` нет ни
  одного `require` соседнего теста и ни одного обхода `test/*.test.js`. Заголовков в
  формате `ok('...')` у них тоже нет — они печатают `console.log('  OK  …')`. Поэтому
  процитировать в шапке нечего, а инвентарь помечает фичу как покрытую («есть»,
  `docs/INVENTORY.md:118`). Расхождение вынесено в «Риски».

## Что обещает человеку

Прямого экрана у фичи нет: её получатель — тот, кто собирает установщик, а через него
ученик. Обещание такое: до выкладки кто-то проверил не «файлы разложились по папкам», а
«конфиг, который поедет человеку, действительно заработает». Разница не теоретическая —
аудит на реальной машине показал картину, ради которой скрипт и написан
(`tools/audit-pack.js:4-8`): 33 плагина включены при пустом каталоге маркетплейсов, MCP
объявлены, но ни один не поднялся, правила ссылаются на скрипты, которых на диске нет.
Установка при этом отчиталась успехом, потому что раскладка файлов и работоспособность —
разные вещи, а проверялось только первое.

Второе обещание — про тихие поломки. Битый `PreToolUse`-хук срабатывает на КАЖДОМ вызове
Bash, битый `statusLine` — на каждой отрисовке строки (`tools/audit-pack.js:162-168`).
Исчезновение одного файла ломает человеку не одну функцию, а всю работу, и до этой
проверки ломало молча. Теперь такой случай — СТОП с ненулевым кодом выхода, а не строка
в логе.

## Как работает

Один самостоятельный скрипт на Node без зависимостей: `require` только `fs` и `path`
(`tools/audit-pack.js:20-21`). Запуск — `node tools/audit-pack.js [путь к паку]`; без
аргумента берётся `vendor/config-pack` относительно каталога `tools/` (строка 23), то
есть ровно то, что вшивается в установщик. Дальше всё читается из `<пак>/.claude`
(строка 24).

Результаты копятся в три списка — `problems`, `notes`, `ok` (строки 26-28) — и печатаются
в конце тремя префиксами: `  OK  `, `  ~    `, `  СТОП ` (строки 244-247). Итог:
`problems` непусты → `ВЕРДИКТ: N проблем(ы), M замечани(й).` и `process.exit(1)`
(249-252); иначе `ВЕРДИКТ: связность в порядке. Замечаний: M.` и обычный выход нулём
(253). Заметки на код выхода не влияют никогда.

Весь разбор JSON идёт через `readJson` (30-32), который на любой ошибке возвращает `null`
без единого слова; вызов в строке 36 подставляет `{}`. Это и есть точка, из-за которой
отсутствующий или синтаксически битый `settings.json` даёт зелёный вердикт — проверено
прогоном на временном каталоге, см. «Риски».

**1. MCP: чем запускаются (36-55).** `settings.mcpServers`, активные — те, где конфиг
истинный и нет `disabled` (38). Счётчик npx (`isNpx`, 45-48) распознаёт команду по ИМЕНИ
файла: строка обрезается от кавычек, режется по `[\\/]`, и хвост сверяется с
`^npx(\.(cmd|exe|bat|ps1))?$`. То есть считаются `npx`, `npx.cmd`, `npx.exe` и абсолютный
путь `C:\Program Files\nodejs\npx.exe`, но не `npx-foo`. Комментарий 40-44 объясняет
цену ошибки: голое `/^npx/` занижало бы ровно ту метрику, ради которой аудит писался, —
npx без каталога Node в СИСТЕМНОМ PATH не поднимается, и человек видит «MCP просто нет».
Результат — заметка (`~`), не СТОП.

**2. MCP: пути (57-95).** Для КАЖДОГО сервера, включая отключённые, собираются
`[command, ...args]` (77), из них выбрасываются значения флагов, которые программа
создаёт сама: `user-data-dir|output|out|profile|storage|cache|data-dir`, в обеих формах —
`--флаг=значение` одним токеном и `--флаг значение` двумя (72-79). Потом три проверки в
порядке приоритета (87-91), и на сервер выводится максимум ОДНА строка:

- `HARDCODED` (65) — путь конкретной машины: `диск:\Users|Vibecode\…`, тот же со слешами
  вперёд, `/Users/…`, `/home/…`. Комментарий 61-64 фиксирует, откуда взялась форма:
  проверка сверяется со строками, пришедшими из `JSON.stringify`, где каждый бэкслеш
  удвоен, и наивный паттерн `C:\\Vibecode` не совпал бы никогда;
- `missing` — аргумент вида `${HOME}/.claude/<путь>`, которого нет в паке (81-84);
- `outside` — `${HOME}/` НЕ в `.claude` (85): у ученика этого не будет.

Ветвление по концу: если сервер помечен `disabled`, строка уходит в заметки с пометкой
`[отключён]` (93), иначе — в проблемы (94).

**3. Плагины (97-120).** Две разные поломки. Первая (101-103): включён хоть один плагин,
а `extraKnownMarketplaces` пуст — СТОП, ставить неоткуда. Вторая (108-120): у плагина
вида `имя@маркет` маркет не объявлен. В допустимые имена складываются ключи
`extraKnownMarketplaces`, встроенные `claude-plugins-official` и `anthropics` (111) и имя
из `<пак>/.claude-plugin/marketplace.json`, если файл читается (113-114). Плагины без
`@` в ключе в эту проверку не попадают вовсе (117).

**4. Правила (122-146).** Обходится `<пак>/.claude/rules`, только верхний уровень, только
`*.md` (128). В тексте ищется `python3?\s+(…\.py)` (130). Ссылка с `${…}` считается
неразрешимой сразу (134): `${WORKSPACE}` нигде не задаётся. Остальные проверяются по трём
кандидатам — от `.claude`, от корня пака и с отрезанным `~/.claude/` (135-136); не нашлось
ни по одному — в `broken`. Есть битые → СТОП со списком до четырёх; нет, но ссылки были →
строка OK со счётчиком.

**5. Хуки — два зеркальных прохода.** Первый (148-160): `rules/hooks.md` упоминает файл
`*.js|py|ps1|sh`, а в `JSON.stringify(settings.hooks)` его нет — заметка. Второй
(162-209), обратный: команда подключена в `settings.json`, а файла нет. Сюда же попадает
`settings.statusLine.command` (177-179). Команда — строка шелла, поэтому режется на токены
самим скриптом с приоритетом кавычек, чтобы путь с пробелами не развалился (186). Каждый
токен: `HARDCODED` → СТОП; `${HOME}/.claude/<путь>` → счётчик и проверка существования,
нет файла → СТОП; `${HOME}/` вне `.claude` → СТОП (188-206). Если файлы считались и ни
одного СТОПа — строка OK с их числом (209).

**6. Счётчики CLAUDE.md (211-240).** Читается `<пак>/CLAUDE.md`, считается реальность:
`skills` — количество ПОДКАТАЛОГОВ (219), `agents` и `commands` — рекурсивно `*.md` кроме
`readme.md` (221-228). Дальше по каждому слову строится `(\d{2,4})\s*` + первые пять букв
слова (`скилл`, `агент`, `коман`, 234) и сравнивается с фактом. Расхождение — заметка, не
СТОП (237).

**Где это вызывается.** Единственный вызов из продакшн-кода — `tools/preflight-build.js`,
блок 443-460, и только в ветке CLI-прогона без `--json` (439-441). Успех: из вывода
выцепляется одна строка с `ВЕРДИКТ` и печатается как `[preflight] связность пака: …`
(451-452). Ненулевой код: `execFileSync` бросает, из перехваченного вывода печатаются
строки, подходящие под `/СТОП|ВЕРДИКТ/` (456-459). Сборку это не роняет ни в одном из двух
случаев — комментарий 443-447 говорит об этом прямо. Второй путь запуска предполётных
гейтов, хук `beforePack` (`tools/before-pack.js`), зовёт `preflight.runPreflight` +
`printPreflight`, а не `main()`, — значит через electron-builder аудит не запускается
вовсе. В `package.json` своего скрипта у него нет, в `.github/workflows/` он не
упоминается (проверено grep по `*.yml`).

## Инварианты

1. **Любая проблема даёт код выхода 1, любая заметка — не даёт.** Держится
   `tools/audit-pack.js:249-252` (`if (problems.length) … process.exit(1)`); заметки
   попадают только в печать (246). Закреплено `test/audit-pack-run.test.js:73` (зелёный
   пак — код 0 при одной заметке) и `:96` (битый пак — код 1).
2. **Подключённый в `settings.json` хук или `statusLine`, чьего файла нет в паке, — это
   СТОП, а не заметка.** Держится `tools/audit-pack.js:197-200` и `177-179`; закреплено
   `test/audit-pack-run.test.js:97-98` (`missing-guard.js`, `no-statusline.js`).
3. **Распознавание «пути конкретной машины» видит обе формы слешей и оба класса корней и
   не трогает `${HOME}`.** Держится единственным литералом `HARDCODED`
   (`tools/audit-pack.js:65`); закреплено `test/audit-pack-regex.test.js:26-48` — 6 строк
   обязан поймать, 6 обязан пропустить, причём тест разбирает литерал прямо из исходника
   (`:16-24`), а не копирует его.
4. **Счётчик npx считает по имени файла команды, а не по началу строки.** Держится
   `isNpx` (`tools/audit-pack.js:45-48`); закреплено `test/audit-pack-run.test.js:76-77`:
   на паке из семи серверов ожидается ровно «5 из 7» — `npx`, `npx.cmd`,
   `C:\Program Files\nodejs\npx.exe`, `/usr/local/bin/npx`, `npx` в двухтокенной форме;
   `node` и `npx-foo` не считаются.
5. **Каталог, который программа создаёт сама, не проверяется на существование ни в одной
   из двух форм записи флага.** Держится `CREATED_PAIR`/`CREATED_INLINE`
   (`tools/audit-pack.js:72-79`); закреплено `test/audit-pack-run.test.js:80-81` — в
   выводе зелёного пака не должно быть ни одной строки «файла нет в паке».
6. **Включённые плагины при полностью пустом списке маркетплейсов — СТОП.** Держится
   `tools/audit-pack.js:101-103`.
7. **Плагин `имя@маркет`, чей маркет не объявлен и не входит в два встроенных, — СТОП.**
   Держится `tools/audit-pack.js:111-120`.
8. **Ссылка на `.py` в `rules/*.md`, не разрешимая ни по одному из трёх кандидатов, —
   СТОП; ссылка с `${…}` неразрешима по определению.** Держится
   `tools/audit-pack.js:130-143`.
9. **Отключённый сервер (`disabled`) не может уронить аудит.** Держится
   `tools/audit-pack.js:93-94`: его строка всегда уходит в заметки с пометкой
   `[отключён]`. Проверено прогоном на синтетическом паке.
10. **В выводе всегда есть строка со словом `ВЕРДИКТ`.** Держится
    `tools/audit-pack.js:250` и `253` — обе ветки печатают её. На этом стоит разбор
    вывода в `tools/preflight-build.js:451` и `457`.
11. **Аудит не блокирует сборку.** Держится тем, что его вызов
    (`tools/preflight-build.js:448-460`) стоит ПОСЛЕ вычисления уровня отчёта, обёрнут в
    `try/catch` и в возвращаемое значение `main()` не входит (462: `rep.level === 'fail'`).

## Что ломается, если инвариант нарушить

1. Аудит превращается в справку: сборщик видит строку «СТОП», глазами её пропускает, и
   узнаёт о поломке из скриншота ученика через неделю. Обратная ошибка не легче — заметка
   про npx роняла бы каждую сборку, и аудит отключили бы целиком.
2. Пак уезжает с хуком, чьего файла нет. У человека `PreToolUse` бьёт на КАЖДОМ вызове
   Bash: Claude Code отвечает ошибкой на любую команду, и выглядит это как «установщик
   сломал мне всё», а не как «нет одного файла».
3. Проверка мертва, а вид у неё зелёный — это уже случалось: паттерн был написан как
   `C:\\Vibecode` и не срабатывал НИКОГДА (`test/audit-pack-regex.test.js:3-9`). Пак с
   путём машины автора проходит аудит, а у ученика сервер молча не поднимается, потому
   что каталога `C:\Users\<автор>\…` у него нет.
4. Счётчик занижается: под Windows команда почти всегда `npx.cmd`, и «12 из 21 через npx»
   превращается в «0 через npx». Ровно та связь, ради которой аудит писался — Node не в
   системном PATH, значит MCP не поднимутся, — исчезает из вывода.
5. Честный конфиг получает ложный СТОП за каталог профиля браузера, которого до первого
   запуска и не должно быть. Сборщик привыкает, что «СТОП тут нормальный», и перестаёт
   читать настоящие.
6. У ученика в списке 29 плагинов, а команд от них нет ни одной: ставить их неоткуда.
   Самая тихая поломка из всех — «плагин есть» и «плагин работает» выглядят одинаково.
7. То же самое, но точечно: один плагин из списка мёртв, остальные живы. Человек винит
   себя или установщик, а причина в одной необъявленной строке маркетплейса.
8. Правило советует человеку команду `python ~/.claude/scripts/что-то.py`, которой на
   диске нет. Ошибка вылезет не при установке, а через месяц, когда он этой командой
   попробует воспользоваться.
9. Сборка падает из-за сервера, который сознательно выключен и никому не мешает; чтобы
   собрать релиз, аудит начинают запускать с обходом.
10. `preflight` печатает пустую строку вместо вердикта — по логу нельзя доказать, что
    аудит вообще отработал.
11. Ошибка запуска самого аудита (нет Node, опечатка в пути) роняла бы релизную сборку
    на этапе, где ни один артефакт ещё не проверен.

## Границы

- Проверяется **пак на диске сборщика**, а не машина ученика. Установленный конфиг,
  реально стартующие MCP, реальный `PATH` — вне охвата: скрипт не запускает ни одного
  сервера и ни одного хука, он читает JSON и проверяет существование файлов.
- MCP берутся ТОЛЬКО из `<пак>/.claude/settings.json` (`tools/audit-pack.js:36-37`).
  Файл `<пак>/.claude/mcp.json` в паке есть, но аудит его не открывает — сервер,
  объявленный только там, для аудита не существует.
- Скан правил узкий: верхний уровень `rules/` (не подкаталоги), только `*.md`, только
  команды вида `python`/`python3` и только с расширением `.py`
  (`tools/audit-pack.js:128-130`). Ссылка на `node …js`, `powershell …ps1` или на скрипт
  внутри подкаталога правил не проверяется.
- Формы `~/.claude/…` и `$HOME/.claude/…` (без фигурных скобок) в аргументах MCP не
  проверяются ни на существование, ни на выход за пак: обе проверки ждут именно
  `${HOME}` (`tools/audit-pack.js:82`, `85`). Проверено прогоном — такие серверы не дают
  ни строки. Уступка сознательная только частично: в комментариях она не оговорена.
- Счётчики `CLAUDE.md` — всегда заметка, никогда СТОП (`:237`), и сравнение грубое:
  «скиллы» считаются подкаталогами, а совпадение ищется по первым пяти буквам слова
  рядом с числом из 2-4 цифр.
- Своего npm-скрипта у аудита нет, в CI он не запускается. Единственная автоматическая
  точка — `npm run preflight` в ручном CLI-прогоне; через `beforePack` (то есть при
  `npx electron-builder`) он не вызывается.
- В `preflight` теряются заметки: успешная ветка печатает только строку с `ВЕРДИКТ`
  (`tools/preflight-build.js:451-452`), ветка ошибки — только `СТОП`/`ВЕРДИКТ`
  (`:457-458`). Строки `~` (в том числе про npx) в лог сборки не попадают вовсе.

## Риски и открытые вопросы

- **Тестов этой фичи нет в `test/run-tests.js`, а `npm test` не запускает те, что есть.**
  Оба файла (`test/audit-pack-regex.test.js`, `test/audit-pack-run.test.js`) — отдельные
  скрипты; `npm test` = `node test/run-tests.js`, и оттуда они не подключаются. Значит
  юнит-гейт CI их не гоняет: правку в `tools/audit-pack.js`, ломающую любой из
  инвариантов 2-5, ни один автоматический прогон не заметит, хотя сами тесты написаны
  именно против этих регрессий и сегодня зелёные. Отдельное следствие для документов:
  `tools/check-specs.js:157-161` на строке «Тесты: НЕТ» при `"tested": "yes"` в
  инвентаре выдаст «скрытое покрытие» — гейт требует либо процитировать тест из
  `run-tests.js`, либо поправить `docs/INVENTORY.md:118`. Честного третьего варианта у
  шапки сейчас нет; правильный выход — подключить оба файла к `run-tests.js`.
- **Пустой или битый пак проходит аудит зелёным.** Проверено прогоном: каталог с одним
  пустым `.claude` даёт `ВЕРДИКТ: связность в порядке. Замечаний: 0.` и код 0; тот же
  каталог с `settings.json`, содержащим строку `not json`, — ровно то же самое. Причина
  в `readJson` (`tools/audit-pack.js:30-32`): `catch` возвращает `null`, а строка 36
  подставляет `{}`. То есть самый громкий сбой сборки конфига (пак не собрался,
  `settings.json` испорчен генератором) неотличим от идеального пака. Ни `ok`, ни `notes`
  об этом не сообщают.
- **Исключение «созданных» каталогов прячет путь конкретной машины.** Фильтр 78-79
  выбрасывает токен ДО того, как по нему пройдёт `HARDCODED` (88). Проверено прогоном на
  синтетическом паке: `--user-data-dir=C:\Users\author\profile` и
  `--output C:\Vibecode\out` не дали ни одной строки, а `--config C:\Users\author\x.json`
  дал СТОП. То есть достаточно назвать флаг одним из семи имён — и жёсткий путь автора
  уезжает ученику мимо проверки. В хуках этой дыры нет: там `HARDCODED` проверяется по
  каждому токену (188).
- **Код выхода 1 сейчас никто не потребляет.** `tools/preflight-build.js:453-459` ловит
  исключение и печатает строки; уровень отчёта не меняется, сборка идёт дальше. Это
  сознательно (комментарий 443-447, 454-455), но означает, что «СТОП» аудита держится
  исключительно на внимании человека, читающего лог. Тот же разрыв уже зафиксирован в
  `docs/RISKS.md:250-252`.
- **Первый проход по хукам сверяет имена подстрокой.** `realHooks.includes(n)`
  (`tools/audit-pack.js:155`) ищет имя файла в JSON целиком — файл, упомянутый в
  `rules/hooks.md`, зачтётся как подключённый, даже если он фигурирует в чужом событии
  или внутри другого пути. Ошибка в безопасную сторону (лишняя заметка не появится), но
  и пропуск возможен.
- **Порядок проверок пути MCP скрывает вторую поломку.** На сервер печатается ровно одна
  строка (87-92): найден жёсткий путь — про отсутствующий файл и выход за пак уже не
  скажут. После починки первой причины аудит придётся прогонять заново.
