# Публикация артефактов в S3

<!-- spec-id: publikaciya-artefaktov-v-s3 -->

- **Раздел:** Публикация и издания
- **Код:** `tools/publish-dist.py:49-205`, `tools/publish-vendor.py:48-257`, `tools/push-component.py:74-471`, `tools/release-check.js`, `remote-components.json`, `.github/workflows/build-mac-lite.yml:92-190`, `.github/workflows/build-mac.yml:219-257`
- **Тесты:** «каждая запись реестра докачки корректна (sha256/size/mirrors)», «реестр: неплейсхолдерные mirror-URL содержат sha256 (content-addressed)», «реестр: нет дублей (remoteId, platform)», «реестр: platform только из enum win32|darwin|linux (опечатка "wind32" — провал)», «BUG #11: remote-компонент имеет сборку в реестре для КАЖДОЙ показанной платформы». Все пять проверяют remote-components.json — артефакт публикации; ни один не запускает сами tools/publish-dist.py, tools/publish-vendor.py, tools/push-component.py (grep по test/run-tests.js этих имён не находит).

## Что обещает человеку

Человек скачивает установщик по ссылке с лендинга и, если у него лёгкая версия,
докачивает тяжёлые компоненты (Git, Node, VS Code, Cursor, Python с колёсами) из
облака прямо во время установки. Обещание такое: ссылка, по которой он пришёл,
отдаёт ту редакцию, которая на ней написана, а докачанный компонент — ровно те
байты, которых ждёт его установщик. Перезалив новой версии не ломает установщики,
скачанные вчера: старый объект остаётся на своём адресе, потому что адрес объекта
образован его собственным sha256 (`tools/push-component.py:381-382`).

Отдельное обещание — про подмену редакций. Windows-сборок две: полная офлайн
(~1,2 ГБ, ставит всё без сети) и лёгкая (~84 МБ, докачивает). Локальные имена и
имена на S3 у них перекрещены (`tools/publish-dist.py:10-18`), и ошибка руками
означала бы, что человек, выбравший «полную офлайн-версию», получил бы лёгкую и
всё равно полез в сеть за гигабайтом. Публикация дистрибутивов не даёт этого
сделать: у каждой цели заявлен диапазон размера, и файл вне диапазона не уезжает.

## Как работает

Три инструмента, две разные вещи публикуются.

**1. Компонент докачки — `tools/push-component.py`.** Пять шагов, печатаются как
`[1/5]…[5/5]`.

- Ещё до кредов: по `platform_to_script` (строки 67-71) вычисляется путь
  install-скрипта — `scripts/macos/<remoteId>.sh` для `--platform darwin`, иначе
  `scripts/windows/<remoteId>.ps1`. Скрипта нет на диске — выход 1 ещё до заливки
  (348-353). Затем проверяются `REGRU_S3_*` креды из
  `~/.claude/.credentials.master.env`; нет — выход 2 (355-361).
- `make_zip` (148-227) приводит вход к zip: готовый `.zip` без `--zip-prefix`
  пропускается как есть; папка пакуется содержимым; `.tar.gz`/`.tgz`
  распаковывается и перепаковывается (с отказом на traversal, symlink/hardlink и
  спец-файлах, 190-216); одиночный файл заворачивается в архив. `--zip-prefix`
  задаёт путь внутри архива, чтобы объект повторял раскладку `vendor/`. Каждый
  член пишется через `_zip_add` (136-146) с фиксированным mtime 1980-01-01 и
  правами 0644 — архив воспроизводим.
- `snapshot_bytes` (127-133) читает архив в память ОДИН раз и считает sha256 и
  размер по этим самым байтам. Дальше в оба зеркала и в реестр уходят они же.
- `gated_files_map` (74-124) сверяет содержимое архива с `vendor/checksums.json`:
  собирает `{базовое имя файла: sha256}` для тех членов, которые на машине
  пользователя проверит вшитый гейт. Деревья `config-pack/`, `npm-cache/`,
  `pywheels/` исключены (99-105). Два разных файла с одинаковым базовым именем —
  отказ (116-122). Ветвление по платформе: без `vendor/checksums.json` публикация
  для `win32` и для вызова без `--platform` останавливается, а для `darwin`
  возвращается пустая карта и публикация продолжается (84-90).
- Ключ объекта: `vibecoding-installer/<remoteId>[-<platform>]-<sha256>.zip`
  (47, 381-382). Заливка `s3_upload` (230-285) идёт path-style + SigV4, с
  `ACL=public-read` и откатом на put без ACL, если провайдер его отверг (278-283).
  Регион и endpoint чистятся и, если непригодны для boto3, чинятся с `[warn]`, а
  не роняют публикацию (258-267). Reg.ru — обязательное зеркало (провал → выход 3);
  Yandex Cloud заливается при наличии `YCLOUD_S3_ACCESS_KEY`+`YCLOUD_S3_BUCKET`, и
  любое исключение на нём приравнивается к «зеркало пропущено» (405-424).
- `verify_public_get` (288-308) качает объект анонимным GET — так же, как это
  сделает установщик, — и сверяет размер и sha. Reg.ru не прошёл → выход 4 и
  реестр НЕ трогается (428-434). Yandex не прошёл → зеркало вычёркивается из
  `mirrors`, публикация продолжается (440-447).
- `upsert` (321-328) кладёт в `remote-components.json` запись
  `{remoteId, name, sizeBytes, sha256, mirrors, installRelPath, gatedFiles[, platform]}`
  (452-466), совпадение ищется по паре `remoteId`+`platform`.

**2. Массовая публикация компонентов — `tools/publish-vendor.py`.** Держит две
карты: `COMPONENTS` для win32 (48-97) и `COMPONENTS_DARWIN` (109-151), выбор —
`--platform` через `PLATFORM_MAPS` (153). Для каждого id вызывает
`push-component.py` подпроцессом (163-170). Два вида спецификаций: `single`
(источник в `vendor/` + `prefix` внутри архива) и `staged` — временный staging из
частей, где `dest_rel` с завершающим `/` означает каталог, а обязательность части
определяется так: литерал обязателен, glob — только если помечен третьим элементом
`True` (`stage_composite`, 173-201). Отсутствие обязательной части даёт
`SystemExit`, и весь прогон останавливается (188-189) — проверка стоит ВНУТРИ
цикла по частям, условия «а другие части есть» в коде нет (`staged_any` смотрится
только на выходе, 201). Поэтому для составного компонента, у которого хоть одна
часть обязательна, полное отсутствие источника даёт не SKIP, а остановку прогона:
проверено запуском `python tools/publish-vendor.py --platform darwin --only handy
--dry-run` → `[fail] Handy … обязательная часть отсутствует в vendor/:
apps/handy-macos-*.dmg`, при том что в `vendor/` нет ни одной его части. В SKIP
уходят только `single` без файла (232-237) и staged-компоненты со сплошь
необязательными частями (например darwin `git`, 114) — тогда прогон живёт
(240-244). `--skip-existing` сверяется с уже существующими
парами `(remoteId, platform)` из реестра (156-160, 227-230). Итог печатается
четырьмя корзинами и даёт код возврата 1, если есть провалы (252-257).

**3. Дистрибутивы — `tools/publish-dist.py`.** Цели описаны в `TARGETS` (49-66):
`win-offline` = `release/Hamidun-Setup-Windows.exe` → ключ
`vibecoding/downloads/Hamidun-Setup-Windows-Offline.exe`, рамки 600-2500 МиБ,
зеркало одно (`REGRU_S3`); `win-lite` = `release/Hamidun-Setup-Windows-Lite.exe` →
ключ `vibecoding/downloads/Hamidun-Setup-Windows.exe`, рамки 20-250 МиБ, зеркала
`REGRU_S3` и `YCLOUD_S3`. Имена локальных файлов совпадают с тем, что реально
собирается: `artifactName` полной сборки — `Hamidun-Setup-Windows.${ext}`
(`package.json:114`), лёгкой — `Hamidun-Setup-Windows-Lite.exe`
(`tools/build-lite.js:68-69`). Порядок: план и отсев по рамкам (127-138) → печать
плана → на `--dry-run` выход → релиз-гейт `node tools/release-check.js --platform
win32`, при ненулевом коде публикация останавливается (161-174) → по каждому
зеркалу снимаются осиротевшие multipart ТОГО ЖЕ ключа (186-189) → `upload_file`
поверх старого объекта, ACL `public-read`, ContentType
`application/vnd.microsoft.portable-executable`, multipart с порога 64 МиБ
(124, 194-195) → анонимный HEAD, размер обязан совпасть (100-108, 197-201) → при
любом несовпадении ненулевой выход (203-204).

**Ветка macOS.** Этим инструментом дистрибутив для мака не публикуется, но
публикуется ДВУМЯ самостоятельными inline-скриптами в workflow'ах, каждый под
своим ключом.

- `.github/workflows/build-mac.yml:219-257` — активный workflow
  (`workflow_dispatch`, 12-13), собирающий ПОЛНОЕ офлайн-издание (3-4). Заливает
  боевой ключ `vibecoding/downloads/Hamidun-Setup-Mac.dmg` (239) через boto3
  прямо в шаге (255-256). Боевая ссылка перезаписывается АВТОМАТИЧЕСКИ на каждом
  прогоне, без участия человека и без каких-либо размерных рамок.
- `.github/workflows/build-mac-lite.yml:363-401` — лёгкое издание под
  staging-ключ `vibecoding/downloads/Hamidun-Setup-Mac-Lite.dmg` (381). Именно
  здесь стабильную ссылку владелец меняет вручную после теста (комментарий
  361-362) — это частный случай ЛЁГКОГО издания, а не общее правило для mac.

Тот же mac-lite workflow готовит файл кредов из секретов (92-134) и вызывает
`python3 tools/publish-vendor.py --platform darwin` (147-150), после чего
прогоняет `node tools/release-check.js --platform darwin` и коммитит обновлённый
реестр с `if: always()`, потому что объекты в S3 к тому моменту уже залиты
(179-190).

**Кто это потом читает.** `remote-components.json` — вход для `src/remote-fetch.js`
(`pickEntry`, `isFetchableUrl`) на машине пользователя и для
`tools/build-lite.js:159-239`, где `gatedFiles` из записи сверяются с вшитым
`checksums.json` до сборки лёгкого издания. Сейчас в реестре 23 записи, у каждой
два зеркала (regru + yandex) и заполненный `installRelPath`.

## Инварианты

1. **Ключ объекта компонента содержит sha256 его собственных байтов.**
   `tools/push-component.py:381-382`, sha берётся из `snapshot_bytes` (127-133).
   Подтверждается на данных тестом «реестр: неплейсхолдерные mirror-URL содержат
   sha256 (content-addressed)».
2. **В оба зеркала и в реестр уходят ОДНИ И ТЕ ЖЕ байты.** Файл читается один раз
   (127-133), `data` передаётся в `s3_upload` для Reg.ru (391) и для Yandex (413);
   повторного чтения с диска нет.
3. **Zip воспроизводим.** `_zip_add` (136-146) фиксирует mtime и права, поэтому
   идентичное содержимое даёт тот же sha и тот же ключ — перезалив идемпотентен.
4. **Запись в реестр появляется только после успешной анонимной загрузки с
   совпавшими размером и sha.** `verify_public_get` (288-308) + выход 4 до
   `upsert` (428-434).
5. **Реестр не содержит битой ссылки на второе зеркало.** Yandex, не прошедший
   анонимную проверку, вычёркивается из `mirrors` (440-447).
6. **Компонент без install-скрипта не публикуется.** Проверка `platform_to_script`
   до заливки, выход 1 (348-353).
7. **Для win32 и для вызова без `--platform` публикация невозможна без
   `vendor/checksums.json`.** `gated_files_map` (84-90) — `SystemExit`.
8. **В одном архиве нет двух разных файлов с одинаковым базовым именем среди тех,
   что проверяет вшитый гейт.** `gated_files_map` (116-122) — `SystemExit`.
9. **Дистрибутив вне размерных рамок своей редакции не публикуется.**
   `TARGETS[*].min_mib/max_mib` (49-66) и отсев (133-137) — цель уходит в
   «ПРОПУСК», заливки не происходит.
10. **Публикация дистрибутива идёт только после GO от release-check.**
    `tools/publish-dist.py:161-174`; единственный обход — `HM_SKIP_RELEASE_CHECK=1`,
    и он печатается в лог отдельной строкой ВНИМАНИЕ.
11. **Старый объект не удаляется — заливка идёт поверх; снимаются только
    осиротевшие multipart с тем же ключом.** 186-189 и 194-195; то же решение в
    `.github/workflows/build-mac-lite.yml:385-399`.
12. **Публикация составного компонента с отсутствующей обязательной частью не
    доводится до конца.** `stage_composite` (188-189) — `SystemExit`, прогон
    останавливается.

## Что ломается, если инвариант нарушить

1. Ключ без sha (mutable-имя) — перезалив перетирает объект, и все ранее скачанные
   установщики получают вечное «файл подменён» на докачке: компонент не ставится
   ни с какой попытки, переустановка не помогает.
2. Разъезд байтов и sha — установщик честно скачивает файл и отвергает его на
   проверке; человек видит бесконечный отказ после нескольких сотен мегабайт
   трафика.
3. Невоспроизводимый zip — при каждой перепубликации того же содержимого рождается
   новый ключ; в бакете копятся объекты-сироты, счёт за хранение растёт, а какой
   объект «живой» — определить можно только по реестру.
4. Запись без анонимной проверки — в реестр попадает ссылка, которая для установщика
   отдаёт 403 (объект приватный). Человек с лёгким изданием не может поставить
   компонент вообще, причём ошибка выглядит как проблема его интернета.
5. Битое второе зеркало в реестре — установщик тратит время и трафик на мёртвый
   URL, прежде чем перейти к живому; на медленном канале это выглядит как зависшая
   установка.
6. Запись без install-скрипта — человек качает сотни мегабайт, после чего установка
   падает на «нечего запускать»: трафик потрачен впустую.
7. Публикация без `vendor/checksums.json` — сверять содержимое архива не с чем, и
   рассинхрон «архив опубликован, vendor пересобран» всплывёт не на сборке, а у
   человека: докачка проходит, установка падает «файл подменён».
8. Два одноимённых файла с разным sha — вшитый гейт ключуется базовым именем, и
   проверка на машине пользователя становится недетерминированной: один и тот же
   архив то ставится, то отвергается.
9. Дистрибутив вне рамок — самое дорогое: человек, выбравший полную офлайн-версию,
   скачивает лёгкую, а она на его компьютере без интернета (ради чего он её и
   выбирал) не поставит ничего. Ссылка при этом рабочая, и подмена всплывает
   только у него.
10. Заливка без релиз-гейта — наружу уезжает сборка с уже известными дефектами:
    протухшим vendor, разъехавшимися цифрами размеров, компонентом без записи в
    реестре.
11. Удаление старого объекта перед заливкой — гарантированные 404 для всех, кто
    зашёл на ссылку во время многоминутной заливки, а при обрыве заливки — до
    следующего ручного прогона.
12. Опубликованный неполный составной компонент — например, `extension` без
    `claude-code.vsix`: докачка проходит с кодом 0, а панель Claude в VS Code
    просто не появляется, без единого сообщения об ошибке.

## Границы

- **Только Windows-дистрибутивы.** `publish-dist.py` знает две цели, обе win32
  (49-66). Публикация `.dmg` живёт вне него — и не в одном месте, а в ДВУХ:
  `.github/workflows/build-mac.yml:219-257` (боевой ключ, полное издание) и
  `.github/workflows/build-mac-lite.yml:363-401` (staging-ключ, лёгкое издание).
  Обе — самостоятельные inline-скрипты, правил из `TARGETS` не знает ни одна.
- **Вручную человек меняет ссылку только у ЛЁГКОГО mac-издания.** mac-lite
  заливает под staging-ключ `Hamidun-Setup-Mac-Lite.dmg`, свап на боевую ссылку —
  ручной (комментарий 361-362). Боевой ключ `Hamidun-Setup-Mac.dmg` при этом
  перезаписывается сам, каждым прогоном `build-mac.yml` (239, 255-256).
- **Проверка после заливки дистрибутива — только размер.** `head_size` (100-108)
  читает `Content-Length`; sha опубликованного `.exe` не сверяется. У компонентов
  сверяется и sha, и размер.
- **Никакой инвалидации кэша CDN и никакой чистки старых объектов.** Инструменты
  ничего не удаляют, кроме своих осиротевших multipart.
- **Креды берутся ровно из одного места** — `~/.claude/.credentials.master.env`
  (`push-component.py:48`, `publish-dist.py:70`); переменные окружения не читаются,
  поэтому CI сначала пишет этот файл (`build-mac-lite.yml:92-134`).
- **Ни одна публикация не запускается из npm-скриптов.** В `package.json` нет
  цели, которая бы вызывала эти три файла; всё запускается руками или из
  mac-workflow.
- **`--dry-run` есть у всех трёх инструментов**, и на нём ничего не заливается и
  реестр не трогается (`publish-dist.py:147-149`, `push-component.py:384-387`).

## Риски и открытые вопросы

- **Тестов на сами инструменты нет.** В `test/run-tests.js` не встречаются ни
  `publish-dist`, ни `publish-vendor`, ни `push-component`; в `_features.json` у
  фичи `tested: "unknown"`. Процитированные тесты проверяют СЛЕДСТВИЕ — схему
  `remote-components.json` (sha 64-hex, `sizeBytes>0`, непустые `mirrors`,
  отсутствие дублей, enum платформ, sha внутри URL). Регресс в логике самих
  публикаторов — например, случайно снятая проверка размера в `publish-dist.py`
  или потерянный `verify_public_get` — не будет пойман ничем, кроме глаз, и
  проявится уже на боевой публикации.
- **Тихий успех `publish-dist.py` без единой заливки.** Если кредов нет ни у
  одного зеркала цели, цикл печатает «кредов нет — зеркало пропущено» (180-183),
  список `failures` остаётся пустым, и скрипт печатает «Готово.» с кодом 0
  (203-205) — при том, что наружу не ушло ничего. Человек, ориентирующийся на
  вывод, будет считать релиз выложенным.
- **`win-offline` публикуется в одно зеркало.** `mirrors: ['REGRU_S3']` (55) — у
  полной офлайн-версии, самой тяжёлой для скачивания, резервного зеркала нет, в
  отличие от лёгкой.
- **Дублирование логики заливки дистрибутива — ТРИ копии.** Ритуал (abort orphan
  multipart своего ключа → upload поверх → multipart с порога 64 МиБ) написан
  трижды: `publish-dist.py:186-195`, `.github/workflows/build-mac-lite.yml:385-399`
  и `.github/workflows/build-mac.yml:250-256`. У второй копии размерный
