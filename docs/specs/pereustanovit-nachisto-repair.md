## Что обещает человеку

У компонента, который установщик нашёл на диске, под карточкой есть кнопка «Переустановить начисто». Обычный повторный запуск установщика только доносит недостающее и ничего существующего не трогает; эта кнопка — способ сказать «поставь базовые файлы заново, свежей версией», когда конфиг сломался или устарел, а обычная доустановка его уже не чинит (доустановка намеренно не перезаписывает то, что лежит).

Для общей базы `~/.claude` (компонент `config`) кнопка не срабатывает молча: сначала появляется отдельный вопрос «Переустановить конфиг начисто?», и без ответа «да» перезаписи не будет. Даже после согласия перезаписываются только файлы, привезённые установщиком: ключи (`.credentials.master.env`, `.credentials.json`), память (`MEMORY.md`, каталог `memory/`), история сессий (`projects/`, `todos/`, `chats.db*`), локальные настройки (`settings.local.json`) и сессия Telegram (`tg_session.session*`) исключены из перезаписи в обоих режимах preserve-list-ом (`scripts/windows/config.ps1:53-55`, `scripts/macos/config.sh:105-106`). `~/CLAUDE.md` в preserve-list НЕ значится (комментарий рядом это и говорит: `config.ps1:52`, `config.sh:103` — «обрабатывается отдельно (только-если-нет)») и в дерево merge вообще не попадает, поскольку лежит в корне профиля (`$env:USERPROFILE` / `$HOME`), а не внутри `~/.claude`; не перезаписывается он по другому механизму — копируется только при отсутствии (`scripts/windows/config.ps1:243-247`, `scripts/macos/config.sh:272-274`, инвариант 8). Перед раскладкой делается копия-бэкап `~/.claude.backup.<дата-время>`.

## Как работает

1. **Кнопка существует только у обнаруженного установленным компонента.** `renderCard` подставляет блок действий условием `installed ? renderInstalledActions(c) : ''` (`src/renderer/app.js:456`), а `installed` берётся из результата детекции `STATE.detected[c.id].installed` (`src/renderer/app.js:416-417`). Сама кнопка рисуется в `renderInstalledActions` (`src/renderer/app.js:508-524`) и меняет подпись с «Переустановить начисто» на «✓ переустановить начисто», когда `STATE.repair[c.id]` включён.

2. **Клик — в `wireInstalledActions` (`src/renderer/app.js:526-553`).** Вычисляется `turningOn = !STATE.repair[c.id]`. Ветвление: **если включаем И `c.id === 'config'`** — показывается `window.confirm(...)` с текстом «Переустановить конфиг начисто?…». Ответ «нет» → `return` до всякой записи состояния, то есть режим не включается вовсе. Ответ «да» → `STATE.repairConfirmed[c.id] = true`. Для всех остальных компонентов диалога нет.

3. **Запись состояния.** `STATE.repair[c.id] = turningOn`; при выключении `STATE.repairConfirmed[c.id] = false` (`src/renderer/app.js:547-548`). Затем, если режим включён, компонент и его зависимости принудительно выбираются на установку: `enableWithDeps(c.id)` (`src/renderer/app.js:550`). Флаг `STATE.repair[id]` дополнительно защищает компонент от авто-снятия галки после повторной детекции (`src/renderer/app.js:232`: установленное снимается, только если `!STATE.repair[id]`).

4. **Оба флага уезжают в env отдельными ключами.** `envForRun` (`src/renderer/app.js:1299-1302`) собирает `HM_REPAIR` — список id, где `STATE.repair[id]` истинен, и `HM_REPAIR_CONFIRMED` — id, где истинны **оба** (`STATE.repairConfirmed[id] && STATE.repair[id]`). Там же эмитится `HM_ADDITIVE`, но это только подсказка: в комментарии (`src/renderer/app.js:1292-1294`) прямо сказано, что решение принимает main.

5. **Фильтр renderer-env.** Значение renderer-ключа копируется в env элевейтед-скрипта, только если ключ есть в allowlist `RENDERER_ENV_ALLOW` (`src/install-env.js:20-28`): там перечислены `hm_repair` и `hm_repair_confirmed`. Фильтр режет ТОЛЬКО прямой проброс значения — «ключа нет в списке» не означает «скрипт его не увидит вовсе»: main вправе перечитать ключ из сырого `rendererEnv` и поставить в `childEnv` сам. Ровно это происходит с `HM_DRY_RUN`: в `RENDERER_ENV_ALLOW` его нет, поэтому `filterRendererEnv` его выбрасывает (`src/main.js:824` — Windows, `:859` — POSIX), но main читает его из сырого payload (`src/main.js:933`: `process.env.HM_DRY_RUN || rendererEnv.HM_DRY_RUN`) и сам кладёт в env дочернего процесса (`src/main.js:1164`), а скрипты его читают (`scripts/windows/config.ps1:24`, `scripts/macos/config.sh:41`).

6. **Авторитетное решение — в main, и только для `config`** (блок `src/main.js:1172-1195`). Выполняется живая детекция ФС `installMode.detectAdditive(os.homedir())` (`:1173`), читаются `listHas(rendererEnv.HM_REPAIR, 'config')` и `listHas(rendererEnv.HM_REPAIR_CONFIRMED, 'config')` (`:1174-1175`), решение принимает `installMode.decideConfigMode(det, repairRequested, repairConfirmed)` (`:1176`). Режим `additive` → `childEnv.HM_ADDITIVE = '1'`; режим `clean` → `delete childEnv.HM_ADDITIVE` (`:1177-1181`). Итог печатается человеку и в лог (`:1182-1184`) строкой `[режим конфига] АДДИТИВНЫЙ (только недостающее)` либо `[режим конфига] чистая установка` с причиной из детекции.

7. **Правило решения** (`src/install-mode.js:75-79`): `additive = !detection || detection.additive !== false`. Если `additive === false` (детекция **доказала**, что кастомизаций нет) → `clean` без всяких флагов и без диалога. Иначе `clean` возвращается только при `repairRequested === true && repairConfirmed === true`; всё прочее → `additive`.

8. **Детекция кастомизаций** (`src/install-mode.js:16-61`). Пробы: `~/.claude/skills`, `agents`, `commands`, `rules`, `settings.json`, `.credentials.master.env` и `~/CLAUDE.md`. `probePath` считает «нет» **только** genuine `ENOENT`; `EACCES`, `EIO`, `ELOOP`, `ENOTDIR` возвращаются как `error`, и `detectAdditive` превращает их в `additive: true` с причиной `probe-error: …(fail-safe)`. Отсутствие `homedir` и любое исключение — тоже `additive`.

9. **Скрипт видит режим через один флаг.** Windows: `$ADDITIVE = ($env:HM_ADDITIVE -eq '1')` (`scripts/windows/config.ps1:42`); ветвление раскладки — `scripts/windows/config.ps1:224-230`: additive = `robocopy … /E /XC /XN /XO /XJ /XF $excludeNames /XD $mergeXD`, repair = тот же вызов **без** `/XC /XN /XO`, то есть существующие наши базовые файлы перезаписываются. macOS: `ADDITIVE=0; [ "${HM_ADDITIVE:-}" = "1" ] && ADDITIVE=1` (`scripts/macos/config.sh:28-29`); ветвление — `scripts/macos/config.sh:247-265`: `rsync -a --ignore-existing …` против `rsync -a …`, а при отсутствии `rsync` — свой `hm_copy` в режимах `missing` / `overwrite` (`scripts/macos/config.sh:167-193`).

10. **Общее для обоих режимов, до раскладки.** Если `~/.claude` существует, первой операцией снимается копия-бэкап `~/.claude.backup.<yyyyMMdd-HHmmss>` (`scripts/windows/config.ps1:110-139`, `scripts/macos/config.sh:119-159`), хранятся 3 последние, старые удаляются. Бэкап — **копия, не перенос**; его неполнота печатает предупреждение и не прерывает установку. Из бэкапа намеренно исключены секреты: `.credentials.master.env`, `.credentials.json`, `tg_session.session*` (`scripts/windows/config.ps1:121`, `scripts/macos/config.sh:118`).

11. **Прунинг наборов скиллов не зависит от режима.** Удаляются только скиллы, входящие в невыбранный пак И доложенные нами: `$weAdded = (-not $preExisting.ContainsKey($_.Name)) -or $ourPrev.ContainsKey($_.Name)` (`scripts/windows/config.ps1:323-327`). Сбой перечисления или раскладки (`$pruneDisabled` / `$installFailed`) выключает прунинг целиком (`scripts/windows/config.ps1:292-294`).

12. **Последействие в манифесте** (`src/main.js:1339-1348`): если прогон был аддитивным и записанная версия строго старше текущей, версия в манифесте **не** продвигается — `updateAvailable` не гаснет, и UI продолжает предлагать «Переустановить начисто» как единственный способ реально применить обновление.

13. **Для НЕ-config компонентов** repair остаётся чисто клиентским форсом: `HM_REPAIR` эмитится, но ни один install-скрипт его не читает (поиск по `scripts/` даёт только упоминание в комментарии `scripts/windows/config.ps1:41`), а `src/main.js` читает список исключительно внутри `if (id === 'config')`. Эффект — компонент не снимается детекцией и ставится заново своим обычным путём.

## Инварианты

1. **Чистая перезапись `~/.claude` при обнаруженных кастомизациях требует ОБОИХ флагов сразу.** `decideConfigMode` возвращает `'clean'` только при `repairRequested === true && repairConfirmed === true` (`src/install-mode.js:78`).
2. **Renderer не может подменить только подсказку `HM_ADDITIVE`.** Решение и запись `HM_ADDITIVE` в env дочернего процесса делает main (`src/main.js:1176-1181`): он либо ставит `'1'`, либо удаляет ключ, независимо от того, что прислал renderer. Ровно эту узкую формулировку заявляет и сам код (`src/install-mode.js:4-5`: «renderer-подсказка HM_ADDITIVE не может перевести установку в перезапись»). **Дальше независимости нет:** `repairRequested` и `repairConfirmed` main берёт ИЗ renderer-а — `listHas(rendererEnv.HM_REPAIR, 'config')` и `listHas(rendererEnv.HM_REPAIR_CONFIRMED, 'config')` (`src/main.js:1174-1175`), где `rendererEnv` — сырой IPC-payload (`src/main.js:928`: `Object.assign({}, (payload && payload.env) || {})`, вычёркивается только `HM_REMOTE_CACHE`), а `src/preload.js:8` отдаёт env насквозь без санитизации. Единственный гейт-диалог живёт в renderer-е (`src/renderer/app.js:538`); в `main.js` нет ни одного `showMessageBox`/`dialog`. Renderer, приславший `HM_REPAIR=config` и `HM_REPAIR_CONFIRMED=config`, получает `mode = 'clean'` (`src/install-mode.js:78`) и перезапись базовых файлов без всякого подтверждения: эти два renderer-управляемых поля и есть ключ от clean.
3. **Любая неопределённость детекции = additive.** Только genuine `ENOENT` считается «нет»; ошибка пробы, отсутствие `homedir` и исключение дают `additive: true` (`src/install-mode.js:34-61`).
4. **Диалог подтверждения предшествует включению режима.** При отказе `wireInstalledActions` выходит `return` до присвоения `STATE.repair` и `STATE.repairConfirmed` (`src/renderer/app.js:537-546`).
5. **Выключение repair аннулирует подтверждение.** `if (!turningOn) STATE.repairConfirmed[c.id] = false` (`src/renderer/app.js:548`); плюс `envForRun` отправляет id в `HM_REPAIR_CONFIRMED`, только если он одновременно есть в `STATE.repair` (`src/renderer/app.js:1301-1302`).
6. **Оба ключа объявлены в allowlist renderer-env.** `'hm_repair', 'hm_repair_confirmed'` в `RENDERER_ENV_ALLOW` (`src/install-env.js:23`) — без строки в списке значение ключа молча не будет скопировано фильтром в env скрипта (`src/install-env.js:39-46`). Абсолютной формулировки «скрипт не увидит ключ вовсе» инвариант не даёт: main может перечитать ключ из сырого `rendererEnv` и поставить его сам, как это сделано с `HM_DRY_RUN` (`src/main.js:933`, `:1164`), которого в allowlist нет.
7. **Preserve-list не перезаписывается даже в repair.** Windows: `/XF $excludeNames /XD $mergeXD` присутствуют в обеих ветках (`scripts/windows/config.ps1:226,229`, список — `:53-55`). macOS: те же `$PRESERVE_FILE_GLOBS $PRESERVE_DIR_GLOBS` в обеих ветках (`scripts/macos/config.sh:250,259`, список — `:105-106`), а fallback `hm_copy` фильтрует те же имена через `case` (`scripts/macos/config.sh:176-180`).
8. **`~/CLAUDE.md` и шаблон credentials кладутся только при отсутствии — в обоих режимах.** `scripts/windows/config.ps1:244-253`, `scripts/macos/config.sh:272-274`.
9. **`~/.claude` никогда не переносится и не стирается ни в одном режиме.** Раскладка — merge-копия поверх; механизм snapshot/restore/wipe удалён (`scripts/windows/config.ps1:26-38`, `scripts/macos/config.sh:16-27`).
10. **Копия-бэкап делается до раскладки, её провал не отменяет установку.** `scripts/windows/config.ps1:110-129` (`$backupOk = $false` → предупреждение и продолжение), `scripts/macos/config.sh:139-149`.
11. **Скиллы, существовавшие до раскладки, прунинг не удаляет даже в repair — безусловно ТОЛЬКО на macOS.** `scripts/macos/config.sh:319-330`: `we_added=0` при любом попадании имени в `PRE_EXISTING_SKILLS`, аналога `$ourPrev` там нет. На Windows условие сохранности сильнее: `$weAdded = (-not $preExisting.ContainsKey($_.Name)) -or $ourPrev.ContainsKey($_.Name)` (`scripts/windows/config.ps1:323`) — второй дизъюнкт **перебивает** `$preExisting`, поэтому имя, попавшее в `~/.claude/.hamidun-skills.txt` прошлым прогоном (читается `:176-181`, пишется `:273-285`), даёт `$weAdded = true` даже для пред-существующего каталога, и на `:325` идёт `Remove-Item -Recurse -Force`. Сценарий достижим: прогон 1 доложил скилл X (X записан в список), дальше пользователь держит в этом каталоге свою работу, прогон 2 со снятым паком сносит каталог целиком. То есть на Windows условие — «существовал до раскладки **И** не числится в `.hamidun-skills.txt`». Сбой перечисления → `$pruneDisabled` → прунинг не выполняется вовсе (`scripts/windows/config.ps1:293-294`).
12. **Merge не пишет сквозь reparse-point/symlink — полностью только на Windows.** Там из раскладки исключаются ВСЕ immediate-дети `~/.claude` с атрибутом ReparsePoint, а сбой самой проверки → fail-closed (`$installFailed = $true`) (`scripts/windows/config.ps1:197-223`); причина названа прямо в коде — пакет везёт `agents`, `commands`, `rules`, `hooks`, `tools`, `config`, `templates`… (`:192-194`). На macOS проверка симлинка есть ТОЛЬКО для `skills`: `[ -L "$CLAUDE_HOME/skills" ]` (`scripts/macos/config.sh:225`), дети `skills` (`:232-233`), `SKILLS_EXCLUDE="--exclude=/skills"` (`:238`) и тот же единственный guard в fallback `hm_copy` (`:183-185`). Полный список `-L`-проверок в файле — `:204, :210, :225, :233, :301, :314`, ни одной по остальным детям `~/.claude`; `rsync` (`:250`, `:259`) получает только `$PRESERVE_*_GLOBS` и `$SKILLS_EXCLUDE`. Аналога `$kidScanOk`/fail-closed в `config.sh` тоже нет. Значит слинкованные пользователем `~/.claude/agents`, `rules`, `commands`, `hooks`, `tools` и т.д. на macOS из раскладки НЕ исключаются.
13. **Выбранный режим виден человеку.** Строка `[режим конфига] …` уходит и в UI (`send`), и в файл лога (`logLine`) вместе с причиной детекции: сборка `msg` — `src/main.js:1182-1183`, `send(msg); logLine(msg);` — `:1184`.

## Что ломается, если инвариант нарушить

1. **Нарушен №1** — общая база перезаписывается по одному клику, без вопроса. Человек, который нажал «Переустановить начисто», думая, что это доустановка, теряет свои правки в базовых файлах `~/.claude`.
2. **Нарушен №2** — скомпрометированный или просто рассинхронизированный renderer (medium integrity, тот же пользователь) диктует элевейтед-скрипту режим перезаписи; UI показывает «доустановка», а на диске идёт clean. Оговорка: инвариант закрывает только подсказку `HM_ADDITIVE`; через пару `HM_REPAIR` + `HM_REPAIR_CONFIRMED` этот же исход достижим уже сейчас, без всякого нарушения (см. инвариант 2).
3. **Нарушен №3** — при заблокированном EDR-ом или недоступном `~/.claude` детекция читает «кастомизаций нет» и уходит в clean на машине, где кастомизации есть. Это ровно тот сценарий, где данные теряются молча: человек ничего не подтверждал.
4. **Нарушен №4** — нажатие «Отмена» в диалоге всё равно включает режим; следующий запуск установки перезаписывает базу, хотя человек явно отказался.
5. **Нарушен №5** — человек передумал и выключил режим, но подтверждение осталось; при повторном включении (или при рассинхроне флагов) перезапись пройдёт без нового вопроса.
6. **Нарушен №6** — последствий нет вообще, инвариант держится вхолостую. Allowlist применяется ТОЛЬКО при сборке `childEnv` для скрипта (`src/main.js:824` и `:859` внутри `buildInstallEnv`, вызов — `:1090`), а решение о режиме main читает из НЕфильтрованного `rendererEnv` (`src/main.js:1174-1175`). Удаление `'hm_repair'` / `'hm_repair_confirmed'` из `RENDERER_ENV_ALLOW` (`src/install-env.js:23`) на эти строки не влияет, а до скрипта `HM_REPAIR` и не должен доезжать — его там никто не читает (см. п.13). Формулировка инварианта («без строки в списке значение ключа не скопируется фильтром в env скрипта») верна, но описанный сценарий потери фичи недостижим.
7. **Нарушен №7** — из `~/.claude` исчезают ключи API, память и история сессий; восстановить их можно только вручную из `~/.claude.backup.*`, а ключи и tg-сессия в бэкап не кладутся (см. Границы) — то есть ключи теряются безвозвратно.
8. **Нарушен №8** — личный `~/CLAUDE.md` (собственные инструкции пользователя) затирается шаблоном пакета; работа, накопленная в этом файле, пропадает.
9. **Нарушен №9** — возвращается инцидентный сценарий wipe: реальный `~/.claude` уезжает в сторону, и при неполном бэкапе часть данных не возвращается никогда.
10. **Нарушен №10** — либо установка падает на залоченном файле (открыт Cursor/Claude) и человек не может переустановить конфиг вовсе, либо бэкапа нет и откатиться после неудачной перезаписи некуда.
11. **Нарушен №11** — сносится каталог скилла, который написал сам человек, потому что его имя совпало с именем скилла из невыбранного пака. На Windows этот исход достижим и без нарушения — для имени, попавшего в `.hamidun-skills.txt` прошлым прогоном (см. инвариант 11).
12. **Нарушен №12** — запись уходит по junction/симлинку во внешнюю папку (например, в git-репозиторий пользователя, слинкованный в `~/.claude/skills`) и перезаписывает там файлы, о которых установщик ничего не знает. На macOS этот исход достижим и без нарушения — для всего, кроме `skills` (`agents`, `rules`, `commands`, `hooks`, `tools`…), см. инвариант 12.
13. **Нарушен №13** — человек не может понять, что именно произошло с его базой: в логе нет ни режима, ни причины, и разбор инцидента упирается в догадки.

## Границы

- **Кнопка не появляется, пока компонент не найден установленным.** Для не установленного компонента блок действий не рендерится вовсе (`src/renderer/app.js:456`).
- **Диалог подтверждения — только для `config`.** Для остальных компонентов «Переустановить начисто» включается сразу, без вопроса (`src/renderer/app.js:537`).
- **Для НЕ-config компонентов repair не меняет логику установки.** `HM_REPAIR` не читает ни один install-скрипт, а main смотрит на него только внутри `if (id === 'config')`; эффект ограничен принудительным выбором компонента и его зависимостей.
- **«Начисто» не означает «с нуля».** Ни в одном режиме `~/.claude` не удаляется и не переносится: перезаписываются только файлы, привезённые пакетом. Файлы пользователя, которых в пакете нет, остаются на месте (кроме прунинга скиллов невыбранных паков — и то лишь тех, что доложил сам установщик).
- **Отката из интерфейса нет.** Бэкап `~/.claude.backup.<stamp>` кладётся рядом, но кнопки «вернуть как было» в UI не существует; восстановление — ручное копирование.
- **Бэкап не полный намеренно.** `.credentials.master.env`, `.credentials.json`, `tg_session.session*` в него не попадают, чтобы секреты не размножались в трёх ротируемых копиях (`scripts/windows/config.ps1:121`, `scripts/macos/config.sh:112-118`). Оригиналы при этом не трогаются ни в одном режиме.
- **Хранятся 3 последние копии**, более старые удаляются автоматически (`scripts/windows/config.ps1:130-138`, `scripts/macos/config.sh:150-158`).
- **Состояние repair живёт только в памяти renderer** (`STATE.repair`, `STATE.repairConfirmed` — `src/renderer/app.js:24-25`). Перезапуск приложения его сбрасывает; снятие галки с карточки (`toggle`, `src/renderer/app.js:331-336`) — нет.
- **Clean возможен и вовсе без этой кнопки** — когда детекция доказала отсутствие кастомизаций (`decideConfigMode` при `detection.additive === false`, `src/install-mode.js:77`). То есть repair нужен только там, где данные пользователя уже есть.
- **В dry-run ничего не перезаписывается**: скрипт печатает строки `WOULD …` и выходит с кодом 0 до клонирования и бэкапа (`scripts/windows/config.ps1:61-68`, выход — `:67`; `scripts/macos/config.sh:41-55`, выход — `:53-54`; клонирование — `config.ps1:70-95` / `config.sh:57-91`, бэкап — `config.ps1:110` / `config.sh:119`). Строка `WOULD (repair): …` печатается ТОЛЬКО в repair-ветке (`config.ps1:66`, `config.sh:51`); аддитивная ветка печатает `WOULD (add-missing): …` (`config.ps1:65`, `config.sh:49`).

## Риски и открытые вопросы

- **Текст диалога расходится с поведением скриптов в двух местах из трёх, оба — в сторону «страшнее/точнее, чем есть».** Диалог (`src/renderer/app.js:539-543`) обещает: (а) «полная резервная копия ~/.claude» — но бэкап намеренно без ключей и tg-сессии (`scripts/windows/config.ps1:121`, `scripts/macos/config.sh:118`); (б) «ключи, память и история сессий будут сохранены и возвращены» — механизм сохранения-и-возврата (snapshot/restore) удалён, эти данные просто никогда не перезаписываются (`scripts/windows/config.ps1:36-38`); (в) «твои собственные скиллы… будут заменены свежей базой» — а здесь диалог **точен**, расхождения нет. В repair merge идёт БЕЗ `/XC /XN /XO` (`scripts/windows/config.ps1:229`) и без `--ignore-existing` (`scripts/macos/config.sh:259`), а `skills` в preserve-list не входит (`config.ps1:53-55`, `config.sh:105-106`) и исключается только при reparse-point. Значит любой файл в `~/.claude/skills/<имя>`, совпавший по относительному пути с файлом пакета, перезаписывается — ровно тот сценарий, что назван в самом коде (`scripts/windows/config.ps1:264-267`: «пред-существующий каталог ЮЗЕРА, чьё имя совпало с нашим паком (git-workflow, security-audit, database-design…)»). Лишние файлы внутри каталога уцелеют — `/PURGE` и `--delete` не используются. Тесты `config.ps1/config.sh REPAIR: пред-существующий скилл юзера…` этого НЕ покрывают: там `user-skill` есть в снятом паке, но его НЕТ в clone (`test/run-tests.js:2460` — «user-skill в снятом паке (в ALL, НЕ в KEEP), но НЕ в clone»), перезаписывать нечем, и ассерт `:2465` тривиален; закреплено ими только НЕудаление прунингом. Ни один тест не сверяет текст диалога с фактическим поведением: проверка `P0-1 app.js: …` смотрит только на наличие `window.confirm('Переустановить конфиг начисто?` в исходнике.
- **Поведение самого обработчика кнопки тестами не покрыто.** Ни один тест не выполняет `wireInstalledActions`: нет проверки, что отказ в диалоге НЕ включает режим, что выключение сбрасывает `repairConfirmed`, что включение форс-выбирает компонент через `enableWithDeps`. Покрытие здесь — только регексп по тексту `src/renderer/app.js`. GUI-тест `test/e2e-gui.js` слова `repair` не содержит вовсе (поиск пуст).
- **Функциональные прогоны `config.ps1` и `config.sh` условны.** Они обёрнуты в `if (bashAvailable())` (`test/run-tests.js:2266` — блок `config.sh`, else-ветка с печатью на `:2421-2423`) и `if (powershellAvailable())` (`:2425` — блок `config.ps1`); на машине без одного из интерпретаторов половина покрытия repair пропускается с печатью «⚠️ bash недоступен — функциональные прогоны config.sh пропущены», и прогон при этом остаётся зелёным.
- **Снятие карточки не сбрасывает repair.** `toggle` (`src/renderer/app.js:331-336`) меняет только `STATE.selected`; `STATE.repair` и `STATE.repairConfirmed` переживают деселект. Поведение согласовано с UI (кнопка продолжает показывать «✓ переустановить начисто»), но повторного вопроса при возврате компонента в установку не будет.
- **`HM_REPAIR` — ключ без потребителя, кроме проверки на `'config'`.** Он проходит allowlist и доезжает до каждого элевейтед-скрипта, но читает его только `src/main.js:1174` (`:1171` — строка комментария). Если завтра какой-то скрипт начнёт на него опираться, отдельного подтверждения (в отличие от config) у него не будет — а `HM_REPAIR` включается без диалога.
- **Диалог рисуется через `window.confirm` в renderer.** Если в сборке блокируются нативные диалоги, включение режима для `config` станет невозможным (функция вернёт `false` → `return`); проверки этого пути в тестах нет. Поведение в такой сборке кодом не подтверждено — не проверял.
