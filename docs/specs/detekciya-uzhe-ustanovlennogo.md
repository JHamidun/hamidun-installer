## Что обещает человеку

Установщик перед первым кликом сам смотрит, что на машине уже стоит, и помечает такие компоненты бейджем «✓ уже установлено» — снимая с них галку. По умолчанию будет доустановлено только недостающее: то, что уже работает, не переставляется поверх. Кто хочет — включает компонент обратно руками или жмёт «Переустановить начисто».

Второе обещание — про честность отрицательного ответа. На Windows список того, что установлено, строится в том числе по системному PATH, а прочитать его иногда не удаётся (антивирус или политика блокируют системные команды). В этом случае человек видит не молчаливое «ничего не установлено», а красный баннер: список ниже может ошибаться, проверь по факту, прежде чем ставить заново.

## Как работает

**1. Запуск.** Renderer после первичного рендера зовёт `detectAndApply()` (`src/renderer/app.js:159`, тело — 215-243), та через `window.installer.detectState()` (`src/preload.js:10`) вызывает IPC-обработчик `detect-state` (`src/main.js:2758`). Пере-детекция повторяется после удаления компонента (`src/renderer/app.js:574`).

**2. Свежие кэши на проход.** `detectComponents()` начинается с `detResetCaches()` (`src/main.js:2549`), который очищает только кэш владельцев файлов `_detOwnerCache`. Кэш системного PATH (`_detPathCache`) проход детекции НЕ трогает — он сбрасывается точечно, через `invalidatePathCache()` после завершения компонентного скрипта (`src/main.js:1323`) и после правки PATH при удалении (`src/main.js:3057`).

**3. Чтение PATH (только Windows).** `freshWindowsPath()` (`src/main.js:2087`) читает машинный `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment\Path` и пользовательский `HKCU\Environment\Path` ОДНИМ вызовом `regQueryManyDotNet`; при сбое делается ровно один ретрай (2098). К результату дописываются `~/.local/bin`, `~/AppData/Roaming/npm` и кастомный npm-префикс из `~/.npmrc` (`npmPrefixFromRc`, 2058-2077). Возвращается `{ path, partial }`, где `partial = true`, если хоть один из двух запросов не удался (2105, 2130). `freshWindowsPathCached()` (2153-2162) пишет `_lastPathReadOk = !r.partial` и кэширует ТОЛЬКО полный результат.

**4. Детекторы по компонентам** (`src/main.js:2554-2752`), каждый даёт `{ installed, detectedVersion }`:

- `git` — `resolveExecutable(['git.exe'] / ['git'])` + Program Files\Git; версия через `probeVersion(bin, ['--version'])`. Ветвление macOS: если найден `/usr/bin/git` и Xcode Command Line Tools отсутствуют (`xcodeCltPresent()`, 2537), это Apple-шим — его НЕ пробим и считаем git не установленным (2563-2565), потому что его запуск сам открывает системный диалог установки инструментов разработчика.
- `node` — `resolveExecutable` + `Program Files\nodejs`, версия по `-v`.
- `cursor` — существование `Cursor.exe` в `%LOCALAPPDATA%\Programs\cursor` или `Program Files\cursor`; на macOS — `Cursor.app` в `/Applications` или `~/Applications`.
- `vscode` — «установлен» только если есть И приложение (`Code.exe` / `Visual Studio Code.app`), И ОБА расширения именно в каталогах VS Code: `vsCodeHasExt(home, claudeExtId) && vsCodeHasExt(home, 'openai.chatgpt')` (2588-2594). `claudeExtId` берётся из `config.json` → `claudeCodeExtensionId`, дефолт `anthropic.claude-code`.
- `claude` — `findClaudeBinary()` (2513-2530): фиксированный список путей, PATH не смотрится вовсе (в отличие от `git`/`node`/`pydeps`/`nomad`/`uv`, идущих через `resolveExecutable`), поэтому детекция `claude` от чтения реестра не зависит. На Windows пять кандидатов: `<prefix>/claude.cmd`, `<prefix>/claude.exe`, `<prefix>/claude` в npm-префиксе плюс `~/.local/bin/claude.exe` и `~/.local/bin/claude.cmd` — голого `claude` в `~/.local/bin` НЕ ищется (2517-2520). На POSIX — `~/.local/bin/claude`, `<prefix>/bin/claude`, `/usr/local/bin/claude`, `/opt/homebrew/bin/claude`. Версия не пробится, `detectedVersion` всегда `''`.
- `extension` — подкаталог расширения в `~/.cursor/extensions`, `~/.vscode/extensions`, `~/.vscode-oss/extensions`.
- `config` — маркер завершённости `~/.claude/.hamidun-config-complete` ИЛИ легаси-пара `~/.claude/skills` + `~/.claude/settings.json` (2619-2622).
- `pydeps` — `python(3)` + успешный `import PIL, requests`. Гейты до запуска: macOS-шим `/usr/bin/python3` без CLT не запускается (2637) и `winSafeToExec(py)` (2641) — но второй гейт работает ТОЛЬКО на Windows: `winSafeToExec` возвращает `true` первой же строкой при `!IS_WIN` (2420). Усиление самого вызова тоже Windows-only: базовый `opts` (2651) не содержит ни `env`, ни `cwd`, аргумент `-E` подставляется по `IS_WIN` (2652), а `opts.env = detectSpawnEnv()` и `opts.cwd` в System32 — внутри `if (IS_WIN)` (2653-2656). На macOS проба идёт как `python3 -c "import PIL, requests"` с унаследованными `process.env` и рабочим каталогом.
- `course` — `CLAUDE.md` или `.claude/skills/course-driver/SKILL.md` внутри `<HM_COURSE_TARGET|~/HamidunCourse>/vibecoding-course`.
- `nomad` — шимы `nmd` / `nomad-agent` / `nomad-acp`, ИЛИ каталог uv-тула `nomad-agent`, ИЛИ клон исходников с `pyproject.toml`. Голое имя `nomad` намеренно не ищется (2673-2676). Шимы ищутся НЕ только в `~/.local/bin`: этот каталог передан лишь как `extraDirs` (`shimDir`, 2678-2682), а `resolveExecutable` кладёт `extraDirs` первыми и дописывает к ним весь системный PATH (2434-2448) — на Windows прочитанный из реестра `freshWindowsPathCached()`, на POSIX фиксированные `/usr/local/bin`, `/opt/homebrew/bin`, `/usr/bin`, `/bin`, `~/.local/bin`, `~/.cargo/bin` плюс `process.env.PATH`. Отсюда два следствия: любой `nmd`/`nomad-agent`/`nomad-acp` где угодно на PATH засчитывается как «установлено», и детекция `nomad` на Windows зависит от успешного чтения PATH из реестра, то есть попадает под тот же баннер `pathReadOk`.
- `uv` — известный путь ТОЛЬКО первой проверкой, при промахе идёт поиск по PATH: `firstExisting([…uv.exe]) || resolveExecutable(['uv.exe'], [])` на Windows и `firstExisting([~/.local/bin/uv]) || resolveExecutable(['uv'], [])` на macOS (2697-2699). Версия дополнительно пробится `--version` (2700).
- `bridge` — по существованию одного известного пути: `%LOCALAPPDATA%\HamidunBridge\bridge_agent.py` на Windows, `~/Library/Application Support/HamidunBridge/bridge_agent.py` на macOS (2705-2707).
- `claude-desktop` — известные пути тоже лишь ПЕРВАЯ из трёх проверок Windows-ветки (2729-2735): `firstExisting([<LocalAppData>\AnthropicClaude\claude.exe, <LocalAppData>\Microsoft\WindowsApps\claude.exe])`, затем префикс-скан `dirHasChildStarting(<LocalAppData>\AnthropicClaude, 'app-')`, затем префикс-скан `dirHasChildStarting(<LocalAppData>\Packages, 'Claude')`. На macOS — два известных пути: `/Applications/Claude.app`, `~/Applications/Claude.app` (2737).
- `chatgpt-desktop` — на Windows НЕ проверяется НИ ОДНОГО известного пути. Вся детекция — префикс-скан по `%LOCALAPPDATA%\Packages`: `(dirHasChildStarting(pkgs, 'ChatGPT') || dirHasChildStarting(pkgs, 'OpenAI')) ? pkgs : ''` (2744-2747), а `dirHasChildStarting` требует подкаталог, подходящий под `^ChatGPT-<цифра>` / `^OpenAI-<цифра>` (2496-2502). Это тот же конструкт, что в macOS-ветке `mascot` ниже. Штатное имя каталога MSIX/Store-пакета устроено как `<Name>_<хэш издателя>` — через подчёркивание, без дефиса и цифры; по коду это не проверить (внешнее знание о Windows, не подтверждено кодом), но под требуемый шаблон такое имя не подходит, то есть детектор структурно рискует всегда отдавать «не установлено». На macOS — два известных пути: `/Applications/ChatGPT.app`, `~/Applications/ChatGPT.app` (2749).
- `mascot` — на Windows по существованию двух известных путей (`%LOCALAPPDATA%\Programs\ClaudeMascot`, `~/.claude-mascot/.installed`). На macOS это НЕ проверка известного пути, а составная эвристика по `~/Applications` (2717-2722): требуется одновременно подкаталог, проходящий `^Claude-<цифра>` (`dirHasChildStarting(appsDir, 'Claude')`), И любое имя в том же каталоге, подходящее под `/mascot|claude/i` и оканчивающееся на `.app`. Штатное имя приложения скрепки (`Claude Mascot.app`, `ClaudeMascot.app`) под `^Claude-<цифра>` не подходит — дефис и цифра обязательны, — поэтому на macOS `mascot` практически всегда показывается «не установлено».
- `handy` — детектора НЕТ вовсе: в `detectComponents()` нет ни одного присваивания `out.handy`, хотя компонент есть в `components.json` (группа `desktop-apps`, `platforms: ["win32","darwin"]`, не `hidden`) и оба фильтра `detect-state` проходит. Срабатывает фолбэк `det[id] || { installed: false, detectedVersion: '' }` (2767), поэтому `handy` ВСЕГДА отдаётся как «не установлено»: бейдж «✓ уже установлено» не появляется и галка автоматически не снимается.

**5. Сборка ответа** (`src/main.js:2763-2788`). Обходятся `COMPONENT_META`; скрытые (`comp.hidden`) и не показанные на этой платформе (`componentShownOnPlatform`) пропускаются. На каждый id отдаётся `installed` (живая детекция), `detectedVersion`, `installedVersion` (из манифеста `~/.hamidun-setup/installed.json`), `currentVersion` (из `components.json`), `updateAvailable = installed && manifest.isOutdated(installedVersion, currentVersion)` и `receipted = receipts.hasReceipt(home, id)`. Отдельным полем едет `pathReadOk`: на не-win32 всегда `true`, на Windows — `lastPathReadOk()`.

**6. Показ.** `detectAndApply()` кладёт состояние в `STATE.detected`, ставит `STATE.pathReadFailed = (r.pathReadOk === false)` и для каждого установленного не-скрытого компонента без активного repair выставляет `STATE.selected[id] = false` (`src/renderer/app.js:230-235`). Затем рисуются: карточка с бейджами «✓ уже установлено · <версия>» и «обновление доступно» (`renderCard`, 423-426), жёлтый баннер `#installed-banner` про аддитивную доустановку (246-262) и красный `#pathread-warn` — только если `STATE.pathReadFailed` (267-279). Весь блок обёрнут в `try` с `finally { STATE.detectDone = true; refreshDerived(); }` — кнопка установки разблокируется даже при сбое детекции.

## Инварианты

1. **Ответ на «установлен ли X?» даёт живая проверка, а не манифест.** `detectComponents` строит `out.*` только из `fs.existsSync` / `fs.readdirSync` / запуска бинаря (`src/main.js:2554-2752`); из манифеста в `detect-state` берётся ТОЛЬКО `installedVersion` для показа и сравнения (2768-2769). Модель доверия зафиксирована в шапке `src/install-manifest.js:7-13`.
2. **«Не смогли прочитать PATH» не выдаётся за «не установлено».** Признак живёт отдельным полем: `freshWindowsPath` возвращает `partial` (`src/main.js:2130`), `freshWindowsPathCached` пишет `_lastPathReadOk = !r.partial` (2156), `detect-state` отдаёт `pathReadOk` (2787), renderer поднимает `#pathread-warn` (`src/renderer/app.js:229`, 267-279).
3. **Неполный PATH не кэшируется.** `if (!r.partial) _detPathCache = r.path;` (`src/main.js:2160`) — один сбой чтения реестра не замораживает огрызок на весь сеанс.
4. **Под elevated-токеном не запускается бинарь, который мог подменить medium-юзер.** `probeVersion` выходит с пустой версией, если `winSafeToExec(bin)` false (`src/main.js:2471`); тот же гейт стоит перед запуском python (2641). `winSafeToExec` (2419-2430) сначала канонизирует путь через `fs.realpathSync.native` (не смог — `false`), затем требует admin-owned корень (`winPathAdminOwned`) ИЛИ admin-owned файл с отсутствием write-прав у не-admin принципалов на файл и его родителя (`winFileAdminOwned`, 2368-2414).
5. **Детекционные спавны на Windows идут с доверенным окружением, а не с `process.env`.** `detectSpawnEnv()` (`src/main.js:2171-2186`) собирает `SystemRoot`/`PATH`/`PSModulePath` из валидированного системного корня и пропускает только профильные переменные; используется в `probeVersion` (2478), в проверке владельца (2407-2409) и в pydeps-пробе (2654).
6. **Расширение засчитывается только по подкаталогу `^<extId>-<цифра>` и только если это каталог.** `dirHasChildStarting` (`src/main.js:2496-2502`) — `withFileTypes: true` + `d.isDirectory()` + regex с экранированным id и обязательной цифрой.
7. **`vscode` считается установленным только при приложении И обоих расширениях в VS Code.** `installed: !!appPresent && bothExts` (`src/main.js:2594`), где `bothExts` требует Claude И `openai.chatgpt` именно в `.vscode`/`.vscode-oss` (`vsCodeHasExt`, 2506-2510).
8. **`config` считается установленным по маркеру завершённости, а не по наличию файлов.** `~/.claude/.hamidun-config-complete` (пишется скриптами только в конце успешной раскладки) либо легаси-пара `skills`+`settings.json` (`src/main.js:2619-2622`).
9. **Apple-шимы на macOS без Command Line Tools не запускаются.** `git`: `macShim` (`src/main.js:2563`); `python`: `pyShim` (2637); оба опираются на `xcodeCltPresent()`, который зовёт `xcode-select -p` — команду, которая, в отличие от `git` и `xcode-select --install`, диалог установки не открывает (2533-2545).
10. **Обнаруженное установленным по умолчанию снимается с галки, а не переустанавливается.** `STATE.selected[id] = false` для `installed && !hidden && !STATE.repair[id]` (`src/renderer/app.js:230-235`).
11. **Бейдж «обновление доступно» требует и подтверждённой установки, и строго меньшей записанной версии.** `!!d.installed && manifest.isOutdated(...)` (`src/main.js:2778`); `isOutdated` даёт `true` только при `compareVersions < 0` и пустых значениях возвращает `false` (`src/install-manifest.js:199-202`), а непарсимые версии (`1.0.1-rc`) дают `parseVersion → null → compareVersions → 0` (177-196).
12. **Кнопка «Удалить» предлагается только для того, что ставил установщик.** `receipted: receipts.hasReceipt(home, id)` (`src/main.js:2781`), карточка гейтит `removable = REMOVABLE.has(c.id) && det.receipted` (`src/renderer/app.js:513`).
13. **Сбой детекции не блокирует установку.** `detectAndApply` завершается блоком `finally { STATE.detectDone = true; refreshDerived(); }` (`src/renderer/app.js:239-242`), а `detect-state` при исключении возвращает `{ ok:false, error, state:{} }`, а не бросает (`src/main.js:2789-2791`).
14. **Скрытые и чужие по платформе компоненты в ответ детекции не попадают.** Пропуск по `comp.hidden` и `componentShownOnPlatform` (`src/main.js:2765-2766`).

## Что ломается, если инвариант нарушить

1. Отставший или повреждённый `installed.json` начинает решать за реальность: человек с рабочим Claude Code видит «не установлено» (или наоборот) и получает установку поверх живого — при этом манифест лежит в user-writable `~/.hamidun-setup` и его может подделать любой процесс того же пользователя.
2. На машине с корпоративным антивирусом весь список показывается «не установлено» без единого предупреждения — человек ставит заново уже работающие git/node/Claude и в лучшем случае теряет полчаса, в худшем ломает свою рабочую конфигурацию.
3. Один случайный таймаут чтения реестра ослепляет детекцию до конца сеанса: в кэше навсегда огрызок PATH, а перезапустить детекцию человеку нечем. Кнопки «перепроверить» в интерфейсе НЕТ: `detectAndApply()` зовётся ровно из двух мест — один раз на старте (`src/renderer/app.js:159`) и после удаления компонента (574); единственная кнопка с похожей надписью, «Проверить снова» в жёлтом баннере лёгкой версии (201, обработчик 205-209), зовёт `runNetProbe()` — пробу сервера докачки — и на PATH-кэш не влияет вовсе. Остаётся перезапуск установщика.
4. Малварь того же пользователя кладёт `git.exe` в `~/AppData/Roaming/npm`, установщик запускает его на `--version` под правами администратора — и получает выполнение произвольного кода ещё до первого клика человека.
5. То же самое, но через переменные окружения: подложенный `PYTHONPATH`/`PYTHONSTARTUP` (или `PSModulePath` для powershell) заставляет интерпретатор импортировать чужой модуль под администратором прямо в фазе детекции.
6. Каталог `anthropic.claude-code-helper-1.0` или одноимённый ФАЙЛ засчитываются как установленное расширение: галка снимается, расширение не ставится, Claude Code в редакторе не появляется, и человек не понимает, почему «всё установлено», а работать нечем.
7. Сценарий «VS Code уже стоит, Codex нет» снова становится молчаливым: галка снимается, единственный доставщик Codex (`vscode.ps1`/`vscode.sh`) не запускается, человек остаётся без второго ассистента без всякого сообщения.
8. Оборванная на середине раскладка `~/.claude` (сон, перезагрузка, антивирус) выглядит завершённой: галка `config` снимается, повторный запуск ничего не доразворачивает, и человек живёт с половиной скиллов и без настроек.
9. Первое же открытие установщика на чистом маке выкидывает системный диалог «установить инструменты разработчика» — до единого клика, поверх окна, с непонятной человеку формулировкой; тестер уже упирался в это.
10. Установка перестаёт быть аддитивной: по умолчанию переставляется всё найденное, включая конфиг с личными скиллами и настройками, — обещание «твои скиллы и настройки в ~/.claude в безопасности» из жёлтого баннера становится ложью.
11. Ложный бейдж «обновление доступно» на всём подряд (в том числе при пустой записи или версии вида `1.0.1-rc`) — человек запускает переустановку без причины.
12. Кнопка «Удалить» появляется у чужого `course`, `uv`, `mascot` или `bridge`, который человек ставил сам задолго до установщика: удаление чужого софта чужим инсталлятором. Радиус ограничен вторым гейтом: `removable = REMOVABLE.has(c.id) && !!(det && det.receipted)` (`src/renderer/app.js:513`), а `REMOVABLE` — жёстко зашитое множество из четырёх id `['course','uv','mascot','bridge']` (43). У `git`, `node` и Cursor кнопка не появится даже при полностью сломанном инварианте — первый конъюнкт для них ложен независимо от `receipted`.
13. При любом исключении в детекции кнопка «Установить» остаётся выключенной навсегда — установщик мёртв, а причина на экране не названа.
14. Видимого отказа сегодня НЕ наступает — это слой защиты, а не единственный барьер, и честнее сказать так, чем придумать последствие. В ответ детекции протекли бы служебный `verify` (`hidden: true`) и компоненты чужой платформы, но до экрана они не доходят: список выбора строится из ДРУГОГО источника (`components: componentsForPlatform()`, `src/main.js:527`), карточки фильтруются `!c.hidden` (`src/renderer/app.js:371`), авто-снятие галки — тем же `!c.hidden` (232), жёлтый баннер — тоже (248). Платформенная половина гейта вдобавок латентна: одноплатформенных компонентов в `components.json` НЕТ вовсе — поле `platforms` стоит только у `uv`, `claude-desktop`, `chatgpt-desktop` и `handy`, и у всех четырёх это `["win32","darwin"]`, то есть `componentShownOnPlatform` пропускает их на обеих ОС. Цена нарушения проявится, когда появится первый одноплатформенный компонент или когда renderer лишится своего фильтра. (Комментарий в коде на `src/main.js:606-607` приводит как пример «uv=win32-only» — он устарел: у `uv` есть и darwin-сборка, и своя macOS-ветка детекции на 2699.)

## Границы

- Детекция отвечает на вопрос «присутствует ли», а НЕ «работает ли» и НЕ «подходит ли версия». Ни для одного компонента нет проверки минимальной версии: `out.git.installed = !!(bin && v)` — годится любой распознанный `git --version`.
- Версия показывается только там, где её удалось пробить: `git`, `node`, `uv`. У остальных, включая `claude`, `detectedVersion` — пустая строка по коду, поэтому бейдж «✓ уже установлено» у них без версии.
- Поиск идёт по известным путям и PATH; реестр Windows Uninstall, Homebrew-манифесты, winget-каталог и прочие реестры установленного не опрашиваются. Установка в нестандартный каталог, которого нет в PATH, не будет замечена.
- Program Files выводится из валидированного системного корня, а не из переменных окружения (`src/main.js:2318-2329`). Осознанная уступка, названная прямо в комментарии: у администратора, перенёсшего Program Files на другой диск, компонент может не задетектиться — предпочли безопасный ложно-отрицательный.
- `pydeps` заведомо допускает ложный негатив (комментарии 2624-2625, 2634-2636): при недоступном для запуска python пакеты не проверяются вовсе, а сама проверка сведена к двум представителям — `PIL` и `requests`.
- UNC-пути (`\\server\share`) в PATH при детекции пропускаются целиком (`src/main.js:2454`) — компонент, установленный на сетевой диск, невидим.
- Один показываемый человеку компонент — `handy` — детектора не имеет вовсе и всегда отдаётся как «не установлено» (см. §4). Обещание из шапки «установщик сам смотрит, что на машине уже стоит» для него не выполняется: бейджа не будет даже у того, кто уже поставил Handy сам.
- `pathReadOk` — исключительно про Windows и исключительно про чтение PATH из реестра: на macOS он всегда `true` (2787), и никакой аналогичной честной пометки для других видов сбоя детекции нет.
- Признак «уже установлено» не различает, кто поставил компонент; для этого есть отдельный `receipted` (квитанции установщика), и именно он, а не `installed`, гейтит удаление.

## Риски и открытые вопросы

- **Ключевая часть фичи не покрыта тестом.** По `test/run-tests.js` нет ни одного совпадения на `pathReadOk`, `pathReadFailed`, `renderPathReadWarning`, `pathread-warn`, `renderInstalledBanner`, `installed-banner`. Обещанный «честный баннер» и авто-снятие галки не проверяются вовсе. Покрыт только источник флага — тест «freshWindowsPath: сбой чтения реестра → partial, огрызок не кэшируется» (`test/run-tests.js:7580`), и он обёрнут в `if (process.platform === 'win32')` (`test/run-tests.js:7579`), то есть на macOS-раннере молча не выполняется. Инвентарь при этом помечает фичу `tested: yes`.
- **Сбой детекции целиком остаётся немым.** `detect-state` при исключении отдаёт `{ ok:false, state:{} }` (`src/main.js:2789-2791`), а `detectAndApply` на `!r.ok` просто делает `return` (`src/renderer/app.js:223`) — до `renderPathReadWarning` дело не доходит. Человек видит всё как «не установлено» без единого предупреждения: ровно тот сценарий, ради которого сделан баннер, но по другой ветке.
- **Цена честности при сбое чтения реестра.** Неполный PATH намеренно не кэшируется (2160), но `freshWindowsPathCached` всё равно возвращает огрызок, и каждый следующий `resolveExecutable` в проходе (`git`, `node`, `python`, `nomad`, `uv`) заново платит запуск интерпретатора с ретраем. То есть именно тот проход, в котором PATH не читается, оказывается самым медленным — при выключенной кнопке «Установить».
- **`_cltPresent` кэшируется на весь процесс** (`src/main.js:2536`) и НЕ сбрасывается `detResetCaches` (2150). Если человек на macOS поставит Command Line Tools, не закрывая установщик, повторная детекция продолжит считать `/usr/bin/git` и `/usr/bin/python3` шимами и показывать git/pydeps ненайденными.
- **Комментарий разошёлся с кодом.** На строке 2631 в `src/main.js` написано «(ТОТ ЖЕ класс, что git-шим выше, стр. 1379)», но на строке 1379 находится ветка отказа докачки (`resolve({ …, stage: 'fetch' })`), разбор причины падения скрипта (`failureExplain.explainScriptFailure`) — на 1385, а git-шим — на 2563. Ссылка устарела.
- **Существующие тесты детекции — грепы по исходнику, а не прогон.** «main.js: detectComponents детектит vscode…», «…знает claude-desktop и chatgpt-desktop…», «P1 (main.js): detectComponents.vscode = приложение И оба расширения…» читают `src/main.js` регулярками и проверяют наличие строк. Функционально прогоняется только regex из `dirHasChildStarting` (воспроизведён в теле теста) и `freshWindowsPath` (через `new Function` с заглушкой реестра). Сам `detectComponents` ни разу не вызывается тестами — переименование поля или инверсия условия внутри детектора грепом не ловятся.
- **Открытый вопрос: почему `_lastPathReadOk` живёт вне проходов детекции.** Флаг инициализирован `true` и обновляется только внутри `freshWindowsPathCached` при холодном кэше (2153-2162). Пока кэш заполняется только успехом, значение честное; но связь «pathReadOk относится к ТЕКУЩЕМУ проходу» держится на этом совпадении, а не на явном сбросе в `detResetCaches`.
