## Что обещает человеку

Установщик несёт внутри себя чужие исполняемые файлы: инсталляторы VS Code, Cursor,
Git, Node, Python, Handy, бинарь скрепки, архив курса, исходники Nomad. Обещание
такое: перед тем как запустить любой из них — а часть запускается с правами
администратора — установщик сверяет байты файла с эталоном, снятым в момент сборки.
Не сошлось, эталона нет, записи об этом файле нет — файл не запускается вовсе, и
установка останавливается. Человек не получит «наполовину установленную» систему, в
которую под админом заехал подменённый инсталлятор.

Второе обещание — про язык отказа. Когда гейт срабатывает, человеку не показывают
«код 1». Показывают: сверка не сошлась, твой компьютер и интернет тут ни при чём,
повтор даст тот же результат, пришли журнал в поддержку — почти наверняка нужна
свежая сборка (`src/failure-explain.js:51-66`, kind `artifact-integrity`).

## Как работает

**Эталон (build-time).** Манифест `vendor/checksums.json` генерится последним шагом
выкачки vendor. На Windows это `tools/fetch-vendor.ps1:516-547`, на macOS —
`tools/fetch-vendor-mac.sh:510-541`. Формат один: `{ generatedAt, algorithm:"sha256",
files: { "<базовое имя файла>": { "sha256": "<64 hex>", "bytes": N } } }`, одна запись
на строку, CRLF на Windows. **Ключ — базовое имя файла, путь не хранится**: поэтому
`apps/claude-mascot/claude-mascot.exe` и `apps/uv/uv.exe` попадают в манифест наравне с
файлами верхнего уровня. Наборы файлов у платформ разные: Windows берёт всё непустое в
`vendor/apps` рекурсивно плюс `course/vibecoding-course.zip`, `nomad-src.sha256` и
`nomad-src/pyproject.toml`; macOS — `vendor/apps` только первого уровня, плюс
`claude-mascot/**/Contents/MacOS/*`, плюс те же курс и два файла nomad.

`tools/regen-checksums.js` пересчитывает тот же манифест **без перекачки vendor** —
поводом была правка артефакта на месте (пересобрали курс рядом), после которой
`release-check` честно вставал с «манифест разошёлся с диском по размеру». Его набор
файлов повторяет **Windows-генератор** (`vendor/apps` рекурсивно + курс + два файла
nomad), формат воспроизводится байт-в-байт (CRLF, те же отступы, сортировка по
базовому имени). Флаг `--check` не пишет, а только сообщает о расхождении и выходит с
кодом 1; сравнивается только объект `files`, `generatedAt` игнорируется намеренно. В
`package.json` скрипта под него нет — запускается руками: `node tools/regen-checksums.js`.

**Проверка (install-time), Windows.** `scripts/windows/_verify.ps1` дот-сорсится
компонент-скриптами (`. (Join-Path $PSScriptRoot '_verify.ps1')`). Главный вентиль —
`Confirm-HmArtifact $path`, порядок отказов такой:

1. файла нет → «БЕЗОПАСНОСТЬ: файл для проверки не найден» → `exit 1`;
2. не задан `$env:HM_VENDOR` → `exit 1`;
3. нет `$HM_VENDOR\checksums.json` → «Отказываюсь запускать вшитый '<имя>'» → `exit 1`;
4. в манифесте нет записи для базового имени → «возможна подмена» → `exit 1`;
5. SHA-256 не совпал → печатает ожидалось/получено → `exit 1`;
6. поле `bytes` есть и размер не совпал → `exit 1`;
7. иначе печатает «Целостность подтверждена (SHA-256): <имя>» и возвращает управление.

Хеш считается своим кодом на .NET (`Get-HmFileSha256`), а не `Get-FileHash`: модуль
Utility в powershell из electron-builder-сборки не подхватывается. Запись из манифеста
достаётся регуляркой (`Get-HmChecksumEntry`), а не `ConvertFrom-Json`, — по той же
причине; регулярка требует 64 hex-символа и опционально ловит `bytes`.

Вызовы: `uv.ps1:39,46` (uv.exe и uvx.exe до первого запуска), `vscode.ps1:69` (setup) и
`vscode.ps1:135` (каждый .vsix до копирования в пользовательский temp),
`course.ps1:59` (архив курса до распаковки), `cursor.ps1:83` (только ветка
`$instBundled` — у онлайн-скачанного другой гейт, Authenticode через
`Test-HmTrustedSigner`), `git.ps1:63`, `node.ps1:106`, `handy.ps1:137`,
`mascot.ps1:19`, `pydeps.ps1:55`, `extension.ps1:38` (vsix, при `-not $DRY`),
`nomad.ps1:205-206`.

**Мягкий вариант.** `Test-HmArtifact` (Windows) и `verify_artifact_soft` (macOS)
возвращают ложь вместо остановки. Единственный потребитель — шрифт JetBrains Mono
(`extension.ps1:173`, `extension.sh:78`): не сошлось — шрифт просто не ставится
(«не критично»), установка продолжается.

**Проверка (install-time), macOS.** `scripts/macos/_lib.sh:219-246`, функция
`verify_artifact`, зеркало Windows-вентиля с двумя отличиями: она **дополнительно**
падает, если посчитать хеш нечем (`hm_sha256` перебирает `shasum` → `sha256sum` →
`openssl`, пустой ответ → `exit 1`), и она **не сверяет `bytes`** — только sha.
Ожидаемое значение достаётся `grep -F "\"<имя>\":" | head -n1 | sed …` — то есть
формат «одна запись = одна строка» является требованием, а не косметикой. Вызовы:
`uv.sh:41` (строго до `tar -xzf`), `vscode.sh:34` и `vscode.sh:110`, `course.sh:44`,
`cursor.sh:27` и `node.sh:27` (обе — только при `BUNDLED=1`), `git.sh:46`,
`handy.sh:76`, `pydeps.sh:17`, `mascot.sh:94`, `extension.sh:13`, `nomad.sh:54-55`.

**Отдельная ветка: nomad-src (дерево, а не файл).** Исходники агента лежат в vendor
распакованными, и `uv tool install` исполняет их build-hook под администратором.
Поэтому здесь три проверки подряд (`nomad.ps1:197-215`, `nomad.sh:42-65`): (а) нет
`$HM_VENDOR/nomad-src.sha256` → своё сообщение и `exit 1`; (б) сам файл-манифест дерева
и `pyproject.toml` проверяются обычным `Confirm-HmArtifact`/`verify_artifact` против
`checksums.json`; (в) пересчитывается детерминированный хеш **всего дерева** и
сверяется с содержимым `nomad-src.sha256`, при расхождении — «НЕ СОВПАЛ SHA-256 дерева
nomad-src» и `exit 1`. Рецепты дерева у платформ **разные и не взаимозаменяемые**:
Windows (`Get-HmTreeSha256`) строит строки `<относительный путь>:<sha файла>`,
сортирует ORDINAL, склеивает через `\n` и хеширует UTF-8-байты; macOS
(`hm_tree_sha256`) делает `find . -type f -print0 | LC_ALL=C sort -z | xargs -0 shasum
-a 256 | shasum -a 256`. Каждый рецепт парный своему генератору: Windows-копия
продублирована в `tools/fetch-vendor.ps1:443-462`, macOS-генератор
`tools/fetch-vendor-mac.sh` сорсит тот же `_lib.sh`.

Сборка Nomad идёт **из временной копии** (`hm-nomad-build-<guid>` на Windows,
`BUILD_SRC` на macOS): uv/setuptools кладут `build/` и `*.egg-info/` рядом с
исходником, дерево vendor меняется, и при повторной установке гейт честно сказал бы
«vendor подменён» — компонент не поставился бы больше никогда.

**Ветка докачки (lite-издание).** Компонент приезжает архивом, распаковывается в
проверенный по sha staging, и этот staging становится `HM_VENDOR`. Чтобы второй гейт
не остался без манифеста, `src/main.js:1070-1075` кладёт в staging **копию вшитого**
`checksums.json`; не удалось скопировать — компонент не запускается вовсе (`stage:
'fetch'` с текстом «второй гейт целостности не сработает»). Там же, `main.js:1116-1125`,
в staging компонента `nomad` доносится вшитый uv — иначе `nomad.ps1` не нашёл бы
`apps\uv\uv.exe` и ушёл бы ставить uv из сети под админом.

**Сверка двух гейтов до релиза.** У lite есть первый гейт (sha архива в
`remote-components.json`) и второй (вшитый `checksums.json`). Они могут разъехаться
при пересборке vendor без перепубликации компонента — и тогда у **каждого**
lite-пользователя докачка проходит, а установка падает с «файл подменён».
`tools/build-lite.js:159-239` (`assertRegistryMatchesChecksums`) сверяет их до сборки и
бросает исключение с готовой командой починки; запись без поля `gatedFiles` считается
непроверяемой и тоже роняет сборку. `tools/release-check.js:51-101` сверяет манифест с
диском: отсутствие файла — предупреждение (норма для чужой платформы), расхождение
размера или sha (`--deep`) — провал. `tools/push-component.py:105-124` при публикации
запрещает архив, где два разных файла имеют одно базовое имя.

## Инварианты

1. **Ни один вшитый артефакт не исполняется и не распаковывается без совпадения
   sha256 с манифестом.** Держится в `Confirm-HmArtifact`
   (`scripts/windows/_verify.ps1:89-95`) и `verify_artifact`
   (`scripts/macos/_lib.sh:239-244`) — оба при несовпадении делают `exit 1`.
2. **Отсутствие манифеста запрещает запуск, а не разрешает его.** `_verify.ps1:73-81`
   и `_lib.sh:225-230`: нет `HM_VENDOR` или нет `checksums.json` → `exit 1`. Это
   fail-closed: гейт нельзя обойти, удалив эталон.
3. **Отсутствие записи для конкретного имени равносильно несовпадению.**
   `_verify.ps1:84-87`, `_lib.sh:232-234` — «в checksums.json нет записи … возможна
   подмена», `exit 1`. Дописать в vendor новый файл и «проскочить» нельзя.
4. **Ключ манифеста — базовое имя файла, и оно уникально в пределах vendor.**
   Верификаторы ищут по basename (`[IO.Path]::GetFileName`, `basename`), генераторы
   пишут basename (`fetch-vendor.ps1:540`, `fetch-vendor-mac.sh:524`), публикация
   запрещает дубли имён в архиве (`tools/push-component.py:116-122`).
5. **Проверка предшествует использованию, а не сопровождает его.** `uv.sh:41` стоит до
   `tar -xzf` (проверяется тестом «P1-A uv.sh: …» через сравнение индексов),
   `course.ps1:59` — до `Expand-Archive`, `vscode.ps1:135` — до копирования vsix,
   `nomad.ps1:205-208` — до `uv tool install` (проверяется тестом «Nomad собирается из
   КОПИИ …» через `assertOrder`).
6. **Для nomad-src проверяется всё дерево, а не только один файл.** `nomad.ps1:207-214`
   и `nomad.sh:56-63` сверяют пересчитанный хеш дерева с `nomad-src.sha256`, который
   сам закреплён в `checksums.json`.
7. **Рецепт хеша дерева одинаков у генератора и верификатора внутри одной
   платформы.** Windows: `tools/fetch-vendor.ps1:443-462` и
   `scripts/windows/_verify.ps1:24-43`. macOS: `tools/fetch-vendor-mac.sh` сорсит
   `scripts/macos/_lib.sh:268-271`.
8. **Nomad ставится из копии, а не из vendor напрямую** (`nomad.ps1:226-229`,
   `nomad.sh` — `BUILD_SRC`), иначе инвариант 6 ломает сам себя после первой установки.
9. **Мягкая проверка применяется только к неисполняемому артефакту.** Единственные
   вызовы `Test-HmArtifact` / `verify_artifact_soft` — шрифт (`extension.ps1:173`,
   `extension.sh:78`).
10. **В lite-издании staging не становится `HM_VENDOR` без манифеста.**
    `src/main.js:1070-1075`: копирование `checksums.json` в staging обязательно, при
    неудаче компонент отклоняется.
11. **Опубликованный архив и вшитый манифест сходятся по sha до выпуска сборки.**
    `tools/build-lite.js:186-198` и `tools/release-check.js:214-229`.
12. **Срабатывание гейта опознаётся как отдельная причина отказа, а не как «код 1».**
    `src/failure-explain.js:51-66`, `kind: 'artifact-integrity'`; тест «девять причин
    не путаются между собой» держит его отличимость от восьми других, а «WebView2:
    правило ловит СВОЙ случай и не крадёт чужие падения скрепки» проверяет, что
    соседнее правило не забирает падение гейта себе.

## Что ломается, если инвариант нарушить

1. Подменённый `cursor-setup.exe` или `python-setup.exe` запускается с правами
   администратора — на машине ученика исполняется чужой код, и человек об этом не
   узнаёт: внешне установка «прошла».
2. Достаточно удалить `checksums.json` рядом с vendor, чтобы установщик перестал
   что-либо проверять. Атака упрощается до «сотри один файл».
3. Файл, которого нет в манифесте, проходит как доверенный: злоумышленнику хватает
   положить свой `.exe` в `vendor/apps` — никто не спросит, откуда он.
4. Два разных файла с одним именем делают проверку недетерминированной: `head -n1` на
   macOS возьмёт первую запись, и один из двух файлов будет сверяться с чужим хешем —
   то есть либо ложный отказ, либо ложное «подтверждено».
5. Сверка после запуска бесполезна: код уже исполнился. Для курса — архив уже
   распакован в рабочую папку ученика, и «остановка» ничего не откатывает.
6. Пин одного `pyproject.toml` не спасает: подменить можно любой из тысяч `.py` в
   дереве, а исполняются они все при `uv tool install` под администратором.
7. Разъехавшийся рецепт хеша дерева даёт постоянный ложный отказ: Nomad не ставится
   ни у кого, и текст сообщения («vendor подменён») уводит поддержку в расследование
   атаки вместо релизной ошибки.
8. Без сборки из копии Nomad ставится ровно один раз: после первой установки дерево
   vendor обрастает `build/`, и любая повторная попытка — включая нажатие «Повторить
   неустановленное» — упирается в «vendor подменён» навсегда.
9. Жёсткая проверка шрифта уронила бы всю установку панели редактора из-за
   косметического файла: человек остался бы без Claude Code ради шрифта.
10. В lite-издании staging заслоняет вшитый vendor. Без копии манифеста второй гейт
    находит «нет checksums.json» → `exit 1`, и **все** докачиваемые компоненты падают
    на ровном месте; либо, если сделать гейт мягким, докачка вообще перестанет
    проверяться вторым рубежом.
11. Пересобрали vendor, не перепубликовав компонент — и у каждого lite-пользователя
    компонент падает «файл подменён» после честной загрузки. Ошибка релиза выглядит
    как атака, и чинится не там, где сломано.
12. Без отдельной причины человек видит «код 1» и жмёт «Повторить» — бесполезно,
    результат тот же. Поддержка получает «не работает» вместо «сборка выпущена с
    рассогласованным манифестом».

## Границы

- Гейт стережёт **только вшитые** артефакты. Онлайн-скачанное сюда не попадает
  намеренно: у него другая версия и хеш законно не совпадёт. Для скачанного действуют
  другие рубежи — sha архива в `remote-components.json`, Authenticode на Windows
  (`cursor.ps1:90`, `Test-HmTrustedSigner`), codesign + Team ID + нотаризация на macOS
  (`_lib.sh:302-352`, `mascot.sh:96-100`).
- Это проверка **целостности, а не подлинности**. `checksums.json` лежит рядом с
  артефактами и записывается тем же пользователем: атакующий с теми же правами может
  подменить и файл, и манифест. Так и написано в `_lib.sh:333-335` — против same-UID
  подмены работает крипто-подпись издателя, а не sha. sha закрывает порчу, ошибку
  сборки и подмену тем, у кого нет доступа к манифесту.
- `bytes` проверяется только на Windows. macOS-вентиль сверяет исключительно sha
  (`_lib.sh:231-244`), поля `bytes` он не читает вовсе.
- В dry-run гейт не выполняется: `course.ps1` выходит до `Confirm-HmArtifact`,
  `extension.ps1:38` проверяет `-not $DRY`, `vscode.ps1:134` возвращает путь без
  проверки, `nomad.sh:48` весь блок целостности обёрнут в `[ -z "$DRY" ]`. Превью
  дисковых проверок не делает.
- `Get-HmTreeSha256`/`hm_tree_sha256` считают хеш **содержимого файлов и их путей**.
  Права, атрибуты, симлинки, пустые каталоги в хеш не входят.
- `tools/regen-checksums.js` воспроизводит **Windows-набор** файлов. На vendor
  macOS-раскладки он пройдёт `vendor/apps` рекурсивно и захеширует всё содержимое
  `.app`-бандлов, чего `fetch-vendor-mac.sh` не делает; это не заявленный сценарий
  использования.
- Скрипт `regen-checksums.js` не подключён к `package.json` — его нет ни в `dist`, ни в
  `release:check`, ни в `preflight`. Автоматически манифест не чинится.
- Манифест ничего не говорит о **возрасте** артефактов. `release-check.js:62` умеет
  лишь предупредить, что снимок старше 30 дней.

## Риски и открытые вопросы

- **Дубль рецепта хеша дерева на Windows.** `Get-HmTreeSha256` существует в двух
  копиях — `tools/fetch-vendor.ps1:443-462` и `scripts/windows/_verify.ps1:24-43`, — и
  обе снабжены комментарием «ОБЯЗАН совпадать». Теста, который сверял бы копии между
  собой, в `test/run-tests.js` не нашлось: поиск по `Get-HmTreeSha256` даёт
  единственное упоминание (`assertOrder` в тесте «Nomad собирается из КОПИИ …»).
  Расхождение проявится не падением сборки, а тем, что Nomad перестанет ставиться у
  всех, с сообщением про подмену.
- **Прямых юнит-тестов самого вентиля нет.** Все процитированные тесты — либо
  статические (регулярка по тексту скрипта: «вызов присутствует», «стоит раньше
  распаковки»), либо функциональные, но проходящие гейт **успешно** (`sealNomadVendor`
  честно запечатывает фикстуру теми же функциями `_lib.sh`). Ни одного теста, который
  испортил бы байт и убедился, что `Confirm-HmArtifact`/`verify_artifact` действительно
  дают `exit 1`, найти не удалось. Более того, функциональные прогоны PS 5.1 в
  песочнице (`test/run-tests.js:5959`, `5999`) подкладывают **заглушку**
  `_verify.ps1`, где `Confirm-HmArtifact` — пустая функция, а `Test-HmArtifact` всегда
  `$true`. То есть в этих прогонах гейт отключён по построению.
- **Ветка `catch` при генерации манифеста на Windows молчит в лог, но не роняет
  сборку.** `tools/fetch-vendor.ps1:547`: `catch { Write-Host "  ! checksums.json не
  сгенерирован - …" }` — выкачка vendor продолжается и завершается «успешно» с
  устаревшим или отсутствующим манифестом. Ловится это позже,
  `tools/release-check.js:54-61`, но только если release-check запускали.
- **Уникальность базовых имён обеспечена не везде.** Публикация компонента её проверяет
  (`push-component.py:116-122`), генераторы манифеста — нет: `fetch-vendor.ps1:524`
  обходит `vendor/apps` рекурсивно и при совпадении имён выпишет два ключа с одним
  именем в один JSON-объект. Поведение читателей в этом случае разное (Windows —
  первое совпадение регулярки, macOS — `head -n1`), и оно не покрыто тестом.
- **`Confirm-HmArtifact` завершает весь процесс.** Это `exit 1` внутри функции, а не
  исключение: вызывающий скрипт не может ни залогировать своё, ни прибрать за собой.
  Для `vscode.ps1` это означает, что временные копии vsix (`Remove-HmVsixTemps`) при
  срабатывании гейта не удаляются — уборка стоит на других путях выхода.
- **Порядок сортировки в `regen-checksums.js` и в `fetch-vendor.ps1` реализован
  по-разному**: `localeCompare(a, b, 'en')` против `Sort-Object Name`. Совпадают ли они
  на всех именах из vendor — **не подтверждено кодом**; при расхождении `--check` дал бы
  ложное «манифест разошёлся» (сравнивается `JSON.stringify` объекта `files`, а он
  чувствителен к порядку ключей).
- **Один относящийся к делу тест процитировать нельзя.** Заголовок
  `test/run-tests.js:9417` содержит вложенные «ёлочки», а `tools/check-specs.js`
  выцепляет заголовки регуляркой `/«([^»]+)»/g` и обрывает такой заголовок на первой
  внутренней закрывающей кавычке. Именно этот тест проверяет самое ценное для человека
  — что гейту сопоставлен `kind: 'artifact-integrity'` и что в тексте есть «повтор
  даст тот же результат». Здесь он не процитирован осознанно, чтобы шапка не содержала
  усечённого заголовка.
- **`vendor/checksums.json` в репозитории датирован `2026-08-23T22:44:52Z` и описывает
  15 файлов Windows-раскладки.** Это снимок конкретной машины, а не часть исходников;
  спека опирается на его формат, не на содержимое.
