# CI: обязательный юнит-гейт

- **Код:** `.github/workflows/unit-tests.yml`, `.github/workflows/e2e-win.yml`, `.github/workflows/build-mac.yml`, `.github/workflows/staging-primitive.yml`, `test/run-tests.js:50-68`, `tools/check-specs.js`, `tools/extract-features.js`, `tools/sync-sizes.js`, `package.json`
- **Тесты:** «CI: build-mac-lite больше НЕ удаляет опубликованный dmg перед заливкой (404-окно)»

  Оговорка: это ЕДИНСТВЕННЫЙ тест в `test/run-tests.js`, который вообще читает файлы
  из `.github/workflows/` (строки 8144-8152), и проверяет он `build-mac-lite.yml` и
  `build-mac.yml` на отсутствие `s3.delete_object` — то есть соседний по каталогу
  сюжет, а не сам юнит-гейт. Тестов, которые проверяли бы `unit-tests.yml` (триггеры,
  наличие джобы `gate`, отсутствие `continue-on-error`), в наборе НЕТ — искал по
  подстрокам `workflows`, `.yml`, `unit-tests`, `continue-on-error`, `PIPESTATUS`,
  `e2e-win`, `staging-primitive`. Инвентарь помечает фичу как покрытую («есть»),
  и это расхождение вынесено в «Риски».

## Что обещает человеку

Прямого экрана у этой фичи нет: её получатель — тот, кто скачивает установщик. Обещание
такое: код, который приезжает в `main`, прогоняется всем юнит-набором на настоящей Windows
и настоящем macOS, и ни один прогон не сделан «мягким». При PR прогон идёт ДО слияния;
при прямом push в `main` — уже ПОСЛЕ того, как коммит в ветке: `push` — триггер
постфактум, он отчитывается, а не запрещает приём. Если тесты упали, джоба красная,
а не «красная, но пропустим».

Второе обещание — документам. Джоба `specs` идёт при каждом push и PR в `main`, даже когда
правились только `.md`-файлы: спека, разошедшаяся с кодом, роняет тот же гейт, что и
упавший тест.

## Как работает

Пять точек, из которых автоматически при каждом коммите в `main` работает только первая.

**1. `.github/workflows/unit-tests.yml` — автоматический гейт.** Триггеры (строки 20-24):
`push` в `main` и `pull_request` в `main`. `concurrency` (28-30) с
`cancel-in-progress: true` гасит устаревший прогон при новом push в ту же ветку.
Пять джоб — `changes` (40), `unit-tests-windows` (82), `unit-tests-macos` (134),
`specs` (190), `gate` (206); ниже они сведены в четыре пункта, обе тестовые в одном:

- `changes` (40-81, `ubuntu-latest`, timeout 5 мин). Собирает список затронутых файлов:
  для PR — `git diff --name-only origin/<base>...HEAD`, для push — `git diff` от
  `github.event.before`. Ветвление в 62-66: если `BEFORE` пустой, нулевой
  (`0000…0000`) или объекта нет в репозитории (первый push в ветку, force-push),
  берётся `git ls-files`, то есть «затронуто всё». Классификатор — БЕЛЫЙ список
  не-кода (75-78): `*.md`, `docs/*`, `.beads/*`, `LICENSE`, `*.webp`, `*.png`,
  `*.jpg`, `*.svg`; любое другое расширение считается кодом. Результат уходит в
  `outputs.code`.
- `unit-tests-windows` (82-133, `windows-latest`, timeout 15 мин) и `unit-tests-macos`
  (134-177, `macos-latest`, timeout 15 мин) — обе под условием
  `if: needs.changes.outputs.code == 'true'`. Шаги одинаковы: `actions/checkout@v4`,
  `actions/setup-node@v4` (node 20, кеш npm), `npm ci --no-audit --no-fund`, затем
  сам гейт (107-114 / 152-159):

  ```
  set +e
  npm test 2>&1 | tee test-output.log
  code=${PIPESTATUS[0]}
  echo "=== npm test exit=$code ===" | tee -a test-output.log
  exit $code
  ```

  `PIPESTATUS[0]` берётся намеренно: `$?` в этом конвейере вернул бы код `tee`, и
  красное стало бы зелёным (комментарий 105-106). Предпоследняя строка (113 / 158)
  не декоративна: она дописывает код возврата В САМ `test-output.log`, поэтому
  улика содержит не только вывод тестов, но и итог прогона. Дальше `actions/upload-artifact@v4`
  с `if: always()` (116-123 / 161-168) увозит `test-output.log` на 14 дней —
  это ответ на прогон, чьи логи пришли пустыми и причину восстановить было нечем
  (комментарий 99-103). Завершает джобу `npm run sizes:check` (132 / 177) =
  `node tools/sync-sizes.js --check`; на раннере `vendor` не развёрнут, поэтому шаг
  ловит не расхождение чисел, а сломанный генератор.
- `specs` (190-199, `ubuntu-latest`, timeout 5 мин) — БЕЗ условия на `changes`, идёт
  всегда. Ставит node 20 и запускает `npm run specs:check` =
  `node tools/extract-features.js --check && node tools/check-specs.js`. `npm ci`
  здесь нет сознательно: оба скрипта требуют только `fs` и `path` (проверено —
  `tools/check-specs.js:26-27`, `tools/extract-features.js:17-18`). Комментарий
  179-189 объясняет, почему джоба отдельная: `changes` относит `docs/*` и `*.md` к
  не-коду, и правка одной только спеки тестовые джобы не поднимает — стой эта
  проверка шагом внутри windows-джобы, она молча пропускала бы ровно тот случай,
  ради которого написана.
- `gate` (206-239, `ubuntu-latest`, `if: always()`, `needs: [changes,
  unit-tests-windows, unit-tests-macos, specs]`). Читает `.result` четырёх джоб.
  `changes != success` → `exit 1` («не могу утверждать, что тесты не нужны»). Для
  тестовых джоб законны `success` и `skipped` (правились только документы), всё
  остальное → `exit 1`. Для `specs` поблажки на `skipped` НЕТ (комментарий 232-234):
  джоба идёт всегда и условий не имеет, поэтому её пропуск означал бы поломку самого
  воркфлоу.

**2. `test/run-tests.js` — то, что гейт запускает.** `npm test` = `node test/run-tests.js`
(`package.json`). Раннер `ok(name, fn)` (50-61) считает `pass`/`fail`; `SKIP()` (49)
даёт третью категорию `skipped` со значком ⏭, которая НЕ красит прогон красным.
Асинхронная функция, переданная в синхронный `ok()`, засчитывается провалом (51-56).
Код возврата — строка 6173: `process.exit(fail ? 1 : 0)`. Без этой строки шаг гейта
был бы зелёным всегда.

**3-5. Тяжёлые прогоны — вручную.** Автоматики на `main` у них нет:

- `.github/workflows/e2e-win.yml` — `workflow_dispatch` (входы `component`, `run_full`)
  плюс `push` на ветки `e2e/**` (строки 22-35). Джобы: `e2e` (Windows lite, 90 мин),
  `e2e-full` (150 мин, условие `github.event_name == 'workflow_dispatch' &&
  github.event.inputs.run_full == 'true'` — строка 197, ~1,4 ГБ докачки),
  `e2e-mac` (офлайн-издание, 75 мин),
  `e2e-mac-lite` (реальная докачка с S3, 75 мин).
- `.github/workflows/build-mac.yml` — только `workflow_dispatch` (12-23) со входом
  `config_ref`. `concurrency` без `ref` и с `cancel-in-progress: false` (25-30):
  релизную сборку нельзя рвать на середине, она заливает объекты в S3. Третьим шагом
  джобы (64-65), сразу после `actions/checkout@v4` (46) и `actions/setup-node@v4`
  (48), — `npm run assert:clean`. Комментарий 55-63 называет его «первым» про
  цепочку внутри `npm run dist`, а не про порядок шагов джобы.
- `.github/workflows/staging-primitive.yml` — `workflow_dispatch` плюс `push` на
  `probe/**` и `e2e/**` с фильтром путей (`scripts/windows/_deelev.ps1`,
  `test/staging-primitive.ps1`, сам файл воркфлоу). Гоняет один примитив
  `New-HmSecureStagingDir` ДВАЖДЫ — в Windows PowerShell 5.1 (боевая оболочка, где
  перегрузка `CreateDirectory(path, SD)` существует) и в pwsh 7, где её нет (48-54).
  Диагностика ACL — только `if: failure()` (58-66).

## Инварианты

1. **Каждый push в `main` и каждый PR в `main` ЗАПУСКАЕТ прогон юнит-набора на
   обеих ОС, если затронут хоть один не-документарный файл; результат виден в
   джобе `gate`.** Держится триггерами `unit-tests.yml:20-24` (push+PR в `main`)
   и условием `if: needs.changes.outputs.code == 'true'` на джобах 84 и 136.
   Приём кода в `main` этим НЕ запрещается: `push` срабатывает уже после того,
   как коммит в ветке, а процитированное `if`-условие — механизм ПРОПУСКА (правки
   только `*.md`/`docs/*`), и такой `skipped` `gate` считает успехом (225-230).
   Запретить приём может только защита ветки — её в репозитории нет (см. «Границы»).
2. **Падение хоть одного теста роняет джобу.** Держится связкой
   `process.exit(fail ? 1 : 0)` (`test/run-tests.js:6173`) и `exit $code` с
   `PIPESTATUS[0]` (`unit-tests.yml:112-114`, `157-159`). `continue-on-error` в
   `unit-tests.yml` НЕ ЗАДАН ни на одном шаге как настройка: строка встречается
   там только в комментарии (12) и в именах шагов (107, 152). Как ключ YAML он
   есть лишь в `e2e-win.yml` (95, 129, 266, 337, 343) — проверено grep по всему
   `.github/`.
3. **Незнакомое расширение считается кодом.** Держится белым списком
   `unit-tests.yml:76`: под `case` попадают только перечисленные не-кодовые
   шаблоны, всё прочее выставляет `CODE=true`.
4. **Неопределимая база сравнения означает «затронуто всё», а не «ничего».**
   Держится веткой `unit-tests.yml:62-66`: пустой/нулевой/несуществующий `BEFORE`
   → `git ls-files`.
5. **Каждый прогон оставляет улику.** Держится шагами
   `upload-artifact` с `if: always()` (`unit-tests.yml:116-123`, `161-168`),
   артефакты `test-output-windows` / `test-output-macos`, 14 дней.
6. **Спеки сверяются при КАЖДОМ push в `main` и КАЖДОМ PR в `main`, включая
   правки одних только документов.** Держится тем, что джоба `specs` (190-199)
   не имеет условия на `changes`. За пределами `main` воркфлоу не поднимается
   вовсе: триггеры ограничены ветками (20-24), поэтому push в `e2e/**`,
   `probe/**`, `mac-lite/**` и рабочие ветки джобу `specs` не запускает.
7. **`skipped` у `specs` не считается успехом.** Держится проверкой
   `if [ "$S" != "success" ]` (`unit-tests.yml:235-238`) — в отличие от тестовых
   джоб, где `skipped` законен (225-230).
8. **Сбой самого определения затронутого не пропускается.** Держится проверкой
   `if [ "$C" != "success" ]` (`unit-tests.yml:220-223`).
9. **`gate` идёт всегда и потому пригоден как обязательная проверка защиты ветки.**
   Держится `if: always()` (208) — пропущенная джоба не превращается в «ожидает» и
   не запирает PR навсегда (комментарий 37-39, 201-205).
10. **В `e2e-win.yml` ни один шаг СЦЕНАРИЯ не помечен `continue-on-error`.**
    Держится по факту: `continue-on-error: true` стоит на пяти шагах — строки 95,
    129, 266, 337, 343, и все пять это «Юнит-тесты (информативно)» и «Диагностика
    зеркал», а не `node test/e2e-gui.js <mode>`.
11. **Тяжёлые прогоны не запускаются автоматически на `main`.** Держится триггерами:
    `e2e-win.yml:22-35` (dispatch + `e2e/**`), `build-mac.yml:12-13` (только
    dispatch), `staging-primitive.yml:8-15` (dispatch + `probe/**`, `e2e/**`).
12. **Релизная сборка macOS не отменяется на середине.** Держится
    `cancel-in-progress: false` в `build-mac.yml:28-30`.

## Что ломается, если инвариант нарушить

1. В `main` уезжает непроверенный коммит; регрессию находит ученик на своей машине,
   а не CI. Ровно это и было до появления файла: комментарий 3-8 фиксирует, что
   раньше ни один воркфлоу не запускался на push/PR.
2. Тесты идут, отчёт красный внутри лога, а джоба зелёная — гейт превращается в
   декорацию. Подмена кода возврата через `tee` уже случалась дважды в ручных
   прогонах (комментарий 105-106).
3. Появляется новый тип файла (например `.psm1`), правки в нём едут без тестов, и
   поломка вскрывается на сборке релиза.
4. Первый push в ветку и force-push проходили бы вообще без тестов — то есть ровно
   те случаи, где кода приезжает больше всего.
5. Плавающее падение нечем разобрать: логи упавшей джобы приходят пустыми,
   перезапуск даёт зелёное, и на такой гейт перестают смотреть.
6. PR, правящий только спеку, разъезжается с кодом молча — а именно расхождение
   документов с кодом дало 12 из 48 находок аудита (`tools/check-specs.js:5-7`).
7. Сломанный воркфлоу (джоба `specs` не стартовала) читался бы как «проверять было
   нечего», и проверка тихо перестала бы проверять.
8. Провал шага определения затронутого выглядел бы как «кода не трогали» — тесты не
   поднялись бы вовсе, а `gate` отчитался бы зелёным.
9. Пропущенная джоба в статусе «ожидает» запирает PR навсегда, и защиту ветки
   отключают целиком — вместе с гейтом.
10. Упавший E2E-сценарий (обрыв сети выдан за успех, затёртый профиль пользователя)
    не окрасил бы джобу, и лёгкое издание уехало бы, не скачав ни одного компонента.
11. Каждый коммит поднимал бы macOS-раннеры по десятикратному тарифу и часовые GUI-
    прогоны; на практике это заканчивается отключением CI, а не терпением.
12. Прерванная релизная сборка оставляет половину объектов в S3 — dmg по ссылке
    битый, а Release уже опубликован.

## Границы

- Гейт проверяет ТОЛЬКО юнит-набор, `sizes:check` и `specs:check`. Он не запускает
  GUI, не качает ничего с S3, не собирает установщик и не проверяет подпись.
- `npm run sizes:check` на раннере ничего не сверяет по существу: `vendor` не
  развёрнут, и `tools/sync-sizes.js:413-417` печатает «ПРОПУЩЕНО: vendor не
  развёрнут — НИ ОДНО число не сверено.», после чего возвращает 0 — шаг на
  раннере зелёный и по существу не проверяет ничего. Короткая формулировка
  «ПРОПУЩЕНО: НИ ОДНО число не сверено» — из комментария `unit-tests.yml:125-130`,
  а не из вывода скрипта. Ценность шага — поймать сломанный генератор.
- Пропуск тестовых джоб при чисто документарных правках — сознательная уступка
  (`gate`, 225-230): за экономию раннеров платим тем, что правка `.md`, которая на
  самом деле что-то ломает, гейтом не поймается.
- `skipped`-тесты внутри `npm test` (`SKIP()`, не та ОС, занятый Cursor) не роняют
  прогон. Сколько именно тестов пропущено, из статуса джобы не видно — только из
  артефакта `test-output.log`.
- Реальная эффективность инварианта 9 зависит от настроек защиты ветки на стороне
  GitHub. В репозитории этих настроек нет, кодом они не подтверждаются: файл лишь
  спроектирован под роль обязательной проверки.
- `probe-handy-teamid.yml` и `build-mac-lite.yml` в инвентаре у этой фичи не
  значатся; первый — только `workflow_dispatch`, второй имеет ещё и `push` на
  `mac-lite/**` (проверено grep по триггерам).

## Риски и открытые вопросы

- **Инвентарь считает фичу покрытой тестами, а покрытия нет.** `docs/INVENTORY.md:98`
  ставит «есть», `_features.json` — `"tested": "yes"`. Фактически ни один тест не
  читает `unit-tests.yml` и не проверяет ни отсутствие `continue-on-error`, ни
  наличие джобы `gate`, ни триггеры на `main`. Единственный тест, трогающий
  `.github/workflows/`, — про `delete_object` в mac-сборках. Последствие конкретное:
  гейт можно ослабить одной строкой (`continue-on-error: true` на шаге 107) и ни
  один прогон этого не заметит — сам себя воркфлоу не сторожит.
- **Формулировка инвентаря «`continue-on-error` не ставится нигде» неточна.**
  В `e2e-win.yml` он стоит пять раз (95, 129, 266, 337, 343). Все пять — на
  информативных шагах, но утверждение «нигде» проверку grep не переживает; верное
  утверждение: «не ставится ни в `unit-tests.yml`, ни на шагах E2E-сценариев».
  То же слово в слово повторено в `docs/PRD.md:139`.
- **Число тестов в документах не сходится.** Комментарий `unit-tests.yml:6` говорит
  «350+ тестов», `docs/PRD.md:138` — «436 юнит-тестов». Я насчитал 408 вызовов
  `ok(...)` и 1 `okAsync(...)` в начале строки; сколько тестов РЕАЛЬНО выполняется,
  не подтверждено — часть вызовов может стоять внутри циклов, и `npm test` я не
  запускал.
- **`if-no-files-found: warn` у артефакта.** Если `test-output.log` не создался
  (падение до `tee`), шаг только предупредит. Улики в этом сценарии не будет —
  ровно в том случае, ради которого артефакт заведён.
- **Джоба `specs` работает без `npm ci`.** Сейчас это верно (`check-specs.js` и
  `extract-features.js` тянут только `fs`/`path`), но ничем не закреплено: первая же
  внешняя зависимость в этих скриптах уронит `specs`, а `gate` не прощает ей ничего,
  кроме `success`.
- Не обнаружено: TODO, веток без обработки ошибки внутри `unit-tests.yml`,
  расхождений комментариев с кодом в самом файле воркфлоу.
