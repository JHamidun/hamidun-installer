## Что обещает человеку

После установки на компьютере есть рабочий Node.js LTS: в новом окне терминала команды `node` и `npm` находятся и отвечают версией. Это движок, на котором запускается сам Claude Code (компонент `claude` в `components.json:71-73` объявлен `requires: ["node"]`, `config` — `requires: ["git","node","claude"]`, строки 120-124) и на котором собирается всё, что человек напишет на JavaScript.

Отдельно обещано то, что при обычной установке Node не гарантируется: запись каталога Node в **системный** PATH. Комментарий в `scripts/windows/node.ps1:26-32` описывает случившийся отказ — шаг рапортовал «OK: node v22», но в системном PATH записи не было, поэтому у человека в новом терминале `node` не находился, `npx` не работал, а вместе с ним молча не поднимался ни один MCP-сервер. Именно из-за этого в скрипте появился `Add-HmMachinePath`.

## Как работает

### Общий вход

Оба скрипта получают от главного процесса переменную `HM_VENDOR` — корень каталога с вшитыми артефактами (`src/main.js:1127`, `childEnv.HM_VENDOR = vroot`). В обычном (офлайн) издании это вшитый `vendor/`, в lite-издании — staging-каталог, в который пак был докачан и проверен по sha256 (`src/main.js:1067-1076`). Карта `COMPONENT_VENDOR_ARTIFACT` (`src/main.js:701-723`, ключ `node` — строка 703) объявляет для `node` основной артефакт `apps/node-lts.msi`: если он есть в bundled vendor, докачка не запускается вовсе. `node` входит в `SCRIPT_ONLINE_FALLBACK` (`src/main.js:742`) — то есть при неудачной докачке из облака главный процесс не роняет компонент жёстко, а даёт скрипту попробовать свой собственный онлайн-путь.

Сами артефакты кладутся в vendor на сборке: Windows — `tools/fetch-vendor.ps1:22-24` берёт первую запись с непустым `lts` из `https://nodejs.org/dist/index.json` и качает `node-<ver>-x64.msi` в `apps/node-lts.msi`; macOS — `tools/fetch-vendor-mac.sh:36-37` тем же приёмом качает `node-<ver>.pkg` в `apps/node.pkg` (universal2). Конкретная версия LTS нигде не пришпилена — берётся та, что была LTS на момент сборки.

### Windows (`scripts/windows/node.ps1`)

Скрипт первыми строками дот-сорсит `_verify.ps1` (даёт `Confirm-HmArtifact`) и `_deelev.ps1` (даёт `New-HmSecureStagingDir`, `Remove-HmSecureStagingDir`, `Test-HmTrustedSigner`) — строки 3-4. Весь установщик на Windows идёт с правами администратора (`package.json:113`, `"requestedExecutionLevel": "requireAdministrator"`), поэтому node.ps1 всегда исполняется elevated.

Ветвление (строки 92-156), сверху вниз, первая сработавшая ветка выигрывает:

1. **Node уже есть** (`Get-Command node`, строка 93). Печатает версию. В dry-run выходит сразу (строка 95). Иначе — молча чинит системный PATH через `Add-HmMachinePath` и `exit 0` (строки 98-99).
2. **Вшитый MSI** — если задан `HM_VENDOR` и существует `$HM_VENDOR\apps\node-lts.msi` (строки 102-103). Перед запуском вызывается `Confirm-HmArtifact` (fail-closed sha256 против `vendor/checksums.json`), затем `msiexec /i "<msi>" /qn /norestart` под `-Wait` (строка 106).
3. **winget** — если MSI нет, но `Get-Command winget` находит winget (строка 107): `winget install -e --id OpenJS.NodeJS.LTS --silent --accept-package-agreements --accept-source-agreements` (строка 109).
4. **Онлайн-загрузка** (строки 110-156). Создаётся Admins-only каталог `New-HmSecureStagingDir -Elevated $true` в `%ProgramData%` (строка 124); не удалось создать — ветка обрывается с `exit 1` (строки 126-129), в user-writable `%TEMP%` не качаем. Дальше `Invoke-RestMethod` на `index.json` с `-TimeoutSec 60`, выбор первой LTS-записи, `Invoke-WebRequest` на `node-<ver>-x64.msi` с `-TimeoutSec 600` и `$ProgressPreference='SilentlyContinue'` (строки 132-136). Сбой сети — чистка кэша и `exit 1` (строки 137-141). Перед запуском — `Test-HmTrustedSigner` (строка 147): недостаточно `Status='Valid'`, требуется корень цепочки в `LocalMachine\Root` и EKU Code Signing (`_deelev.ps1:375-435`). Подпись не подтвердилась — `msiexec` **не** запускается, печатается «БЕЗОПАСНОСТЬ: … НЕ запускаю (fail-closed)» (строки 150-152). Кэш убирается в любом случае (строка 154).

Финал (строки 158-173): в dry-run выход 0; иначе `Update-Path` правит PATH **только внутри процесса** (строки 5-24; HKCU PATH не читается намеренно — комментарий на строках 6-10 объясняет, что medium-процесс того же пользователя мог бы дописать туда каталог с подложенным node), затем повторный `Get-Command node`. Если node найден — вызывается `Add-HmMachinePath` на `%ProgramFiles%\nodejs`, потом читается реальный `Machine`-PATH и ищется запись, оканчивающаяся на `\nodejs` (строки 163-165). Не нашлась — печатается предупреждение про неработающие `npx` и MCP (строки 166-169), но шаг всё равно завершается `exit 0` со строкой `OK: node <ver>, npm <ver>`. Node не найден — `exit 1`.

`Add-HmMachinePath` (строки 39-89) работает с реестром напрямую, а не через `[Environment]::SetEnvironmentVariable`: комментарий 33-38 объясняет почему — .NET-путь разворачивает `%VAR%` в литералы и пишет `REG_SZ`, что тихо портит системный PATH навсегда. Порядок действий: каталог должен существовать (строка 40); открывается `SYSTEM\CurrentControlSet\Control\Session Manager\Environment`; сырое значение читается с `DoNotExpandEnvironmentNames`, но сверка на дубль идёт по **развёрнутой** копии (строки 48-53); если новая строка выходит ≥ 4095 символов — не пишем, а печатаем инструкцию человеку (строки 59-63); запись типом `ExpandString` (строка 64); затем broadcast `WM_SETTINGCHANGE` через `SendMessageTimeout` с таймаутом 5000 мс (строки 73-85), иначе уже открытые окна не увидели бы новый PATH.

### macOS (`scripts/macos/node.sh`)

`set -uo pipefail` — без `-e` намеренно (комментарий на строке 24: без явной проверки провал скачивания молча дошёл бы до `admin_run`). Первым делом PATH расширяется на `/usr/local/bin:/opt/homebrew/bin:$HOME/.local/bin` (строка 5) — под GUI/Electron PATH урезан, и только что установленный node иначе не виден.

1. **Node уже есть** — `have node`, печать версии, `exit 0` (строки 7-8).
2. **Вшитый pkg** — если `$HM_VENDOR/apps/node.pkg` существует, берём его и ставим `BUNDLED=1` (строки 11-12).
3. **Онлайн** (строки 13-26): версия LTS достаётся из `index.json` **без python3** (комментарий 15: голый `/usr/bin/python3` без Command Line Tools дёргает GUI-диалог установки) — `curl ... | grep -o '{[^{}]*}' | grep '"lts":"' | head -n1 | sed`. Таймауты жёсткие: `--connect-timeout 20 --max-time 900 --retry 3 --retry-connrefused`. Версия не определилась — `exit 1` с текстом про сеть или изменившийся формат `index.json`. Файл качается в `/tmp/node-${VER}.pkg` функцией `dl` из `_lib.sh:8-14` (та же обвязка таймаутов, при провале частичный файл удаляется); провал `dl` — `exit 1`.

`verify_artifact "$PKG"` (sha256 против `$HM_VENDOR/checksums.json`, fail-closed) вызывается **только для вшитого** артефакта — `[ "$BUNDLED" = 1 ] && verify_artifact "$PKG"` (строка 27). Для онлайн-загрузки это невозможно: версия другая, хэш законно не совпал бы.

Установка (строки 36-40): `NODE_TEAM_ID='HX7739G8FX'`, затем `admin_run /bin/sh -c "$HM_PKG_INSTALL_SH" hm_pkg_install "$PKG" "$NODE_TEAM_ID"`. `admin_run` (`_lib.sh:38-68`) квотирует каждый argv-элемент, экранирует строку для AppleScript и запускает osascript под `env -i` с фиксированным PATH — весь класс env-hijack закрыт в одной точке. Сам `HM_PKG_INSTALL_SH` (`_lib.sh:302-312`) под root: создаёт `mktemp -d /var/root/hm_pkg.XXXXXX`, копирует туда pkg, проверяет `pkgutil --check-signature` **на staged копии** (требуется строка `Status: signed by a developer certificate issued by Apple` и leaf `1. Developer ID Installer: … (HX7739G8FX)` с Team ID, заякоренным в конце строки), и только потом `installer -pkg <staged> -target /`. Любой шаг не прошёл — `exit 1`, и node.sh печатает «подпись .pkg не подтверждена или установка не удалась (fail-closed)» и выходит 1 (строки 38-40).

Финал (строки 42-43): успех объявляется, если `have node` **или** существует исполняемый `/usr/local/bin/node`; иначе `exit 1`.

### Проверка после установки

Шаг `verify` (отдельный компонент, `components.json:97-106`) печатает `CHECK ok Node` / `CHECK fail Node`, если компонент был выбран: Windows — `Get-Command node` + `node -v` (`scripts/windows/verify.ps1:55-67`), macOS — `have node && node -v` (`scripts/macos/verify.sh:45-52`).

## Инварианты

1. **Вшитый MSI/pkg не запускается без совпадения sha256 с манифестом `vendor/checksums.json`.** Windows — `Confirm-HmArtifact $local` перед `msiexec` (`node.ps1:106`; сама проверка — `_verify.ps1:64-104`, при несовпадении `exit 1`). macOS — `verify_artifact "$PKG"` при `BUNDLED=1` (`node.sh:27`, реализация `_lib.sh:219-246`, при несовпадении `exit 1`).
2. **Онлайн-скачанный MSI на Windows запускается только после `Test-HmTrustedSigner` с пустым результатом.** `node.ps1:147-152`; функция требует Authenticode `Status=Valid`, корень цепочки именно в `LocalMachine\Root` и EKU Code Signing (`_deelev.ps1:375-435`). Причина не подтвердилась — `msiexec` не вызывается.
3. **Онлайн-загрузка на Windows идёт только в Admins-only каталог.** `New-HmSecureStagingDir -Elevated $true` (`node.ps1:124`); каталог не создался — `exit 1` без скачивания (`node.ps1:126-129`). Права ставятся атомарно в момент создания, владелец — Administrators (`_deelev.ps1:147-171`).
4. **macOS: проверка подписи и установка идут над одной и той же root-owned копией.** `HM_PKG_INSTALL_SH` (`_lib.sh:302-312`) копирует pkg в `/var/root/hm_pkg.*` и проверяет/ставит именно её — окна подмены между verify и install нет.
5. **macOS: Team ID установщика равен `HX7739G8FX`.** `node.sh:36` + grep на `\($2\)$` в `_lib.sh:311` — Team ID заякорен в конце CN, подстрока в середине имени не проходит.
6. **PATH для elevated-скрипта на Windows не собирается из HKCU.** `Update-Path` берёт только `Machine`-PATH и фиксированные admin-owned каталоги (`node.ps1:11-23`).
7. **Системный PATH не дописывается вслепую.** Дубль отсекается сверкой по развёрнутой строке (`node.ps1:51-53`), при длине ≥ 4095 символов запись не делается, а человеку печатается ручная инструкция (`node.ps1:59-63`), тип значения сохраняется `ExpandString` (`node.ps1:64`).
8. **`Add-HmMachinePath` вызывается во всех ветках, где node в итоге есть.** Ветка «уже установлен» — `node.ps1:98`; ветка после свежей установки — `node.ps1:163`.
9. **Сетевые вызовы имеют конечный таймаут.** Windows — `-TimeoutSec 60` и `-TimeoutSec 600` (`node.ps1:132,136`), это же стережёт тест «Windows: НИ ОДИН сетевой вызов без -TimeoutSec (дефолт = бесконечность)». macOS — `--connect-timeout 20 --max-time 900` в самом скрипте (`node.sh:18`) и в `dl` (`_lib.sh:9`).
10. **`-Wait` у `msiexec` допустим только с тихим флагом.** `node.ps1:106,149` содержат `/qn`; это же проверяет тест «Windows: установщики, САМИ запускающие приложение, идут БЕЗ -Wait», перебирающий `node.ps1` в списке.
11. **Успех Windows-ветки объявляется только после реального `Get-Command node`.** `node.ps1:160,170-173`: строка `OK: node …, npm …` печатается внутри ветки «node найден», иначе `exit 1`.
12. **Размер, показанный в окне выбора, взят из реального артефакта.** `components.json:30-33` (`win32: 32874496`, `darwin: 92775015`) сверяется с `apps/node-lts.msi` / `apps/node.pkg` через `tools/sync-sizes.js:84,115` — тест «размеры: файловые компоненты (setup.exe/msi/vsix/zip) сходятся с vendor».

## Что ломается, если инвариант нарушить

1. Человек запускает под администратором подменённый MSI/pkg — это выполнение произвольного кода с правами администратора на его машине под видом установки Node.
2. То же самое, но вектор другой: same-UID малварь без всякого UAC кладёт свой корневой сертификат в `HKCU\...\SystemCertificates\Root`, и подложенный установщик выглядит подписанным. Без пункта 2 он был бы запущен elevated.
3. MSI скачан в `%TEMP%`, куда пишет любой процесс того же пользователя: между скачиванием и `msiexec` файл подменяется, и вместо Node ставится чужое — снова RCE под админом.
4. На macOS проверка подписи была бы над `/tmp`-файлом, а установка — над ним же позже: пока открыт диалог пароля, файл подменяется, и root ставит другие байты.
5. Установится .pkg, подписанный любым владельцем Developer ID, а не Node.js Foundation. Человек не увидит разницы: диалог пароля и «Готово» те же.
6. Малварь дописывает в пользовательский PATH каталог с подложенным `node.exe` — и наш elevated-процесс запускает его вместо настоящего.
7. Дубль в системном PATH или, хуже, порча `%JAVA_HOME%\bin` и подобных записей: часть уже установленных на машине программ перестаёт находить свои каталоги. При переполнении PATH старые программы, читающие его в фиксированный буфер, начинают падать — и виноват будет «установщик Жемала».
8. Ровно тот отказ, ради которого написан `Add-HmMachinePath`: шаг зелёный, «OK: node v22», а в новом терминале `node` не найден. `npx` не работает, MCP-серверы не поднимаются — человек видит Claude Code без инструментов и не понимает, почему.
9. Шаг висит бесконечно на плохом канале или при перехвате трафика: спиннер крутится, watchdog процессы не убивает намеренно, человек ждёт и закрывает установщик.
10. `msiexec` без `/qn` открыл бы своё окно и держал шаг до ручного клика — на чужой машине это выглядит как зависание.
11. Ложное «Готово»: установка отчиталась успехом, а Node на диске нет. Дальше падают `claude` и `config`, которые от него зависят, и причина уже не видна.
12. В окне выбора компонентов написано одно число, скачается другое. На медленном канале это разница между «10 минут» и «час», а доверие к остальным числам теряется целиком.

## Границы

- **Версия Node не выбирается и не пришпилена.** Ставится тот LTS, что был актуален на момент сборки vendor (`tools/fetch-vendor.ps1:22-23`) или, в онлайн-ветке, на момент установки (`node.ps1:133`, `node.sh:18`). Ни `components.json`, ни скрипты не содержат номера версии; `"version": "1.0.0"` в `components.json:24` — версия описания компонента, не Node.
- **Менеджеры версий не ставятся и не настраиваются.** Ни nvm, ни fnm, ни volta в коде не упоминаются.
- **Уже установленный Node не обновляется.** Первая же ветка обоих скриптов выходит по факту наличия `node` в PATH (`node.ps1:93`, `node.sh:8`), версия не сравнивается ни с чем.
- **Компонент не удаляется деинсталлятором.** `uninstallTargets('node', …)` возвращает `null` — тест «targets: неизвестный/не-removable id → null (деинсталляция отклоняется fail-closed)» перечисляет `node` среди неудаляемых.
- **Windows-ветка ставит только x64.** И вшитый артефакт (`node-<ver>-x64.msi`), и онлайн-фолбэк (`node.ps1:134`) жёстко x64; ARM64-ветки нет.
- **macOS не правит файлы шелла.** `persist_local_bin_path` из `_lib.sh:177-194` в node.sh не вызывается — расчёт на то, что `.pkg` кладёт бинарь в `/usr/local/bin`, который в PATH по умолчанию. Симметричной Windows-починки PATH здесь нет.
- **Уступка: системный PATH чинится best-effort.** Если запись не удалась (нет доступа к ключу, переполнение), шаг всё равно завершается успехом с предупреждением (`node.ps1:166-169`), а не ошибкой.

## Риски и открытые вопросы

- **У `Add-HmMachinePath` нет ни одного теста.** Поиск по `test/run-tests.js` по `Add-HmMachinePath`, `MachinePath`, `nodejs`, `WM_SETTINGCHANGE`, `ExpandString` не даёт совпадений. Это самая содержательная часть скрипта (51 строка), написанная по следам реального отказа, и она не защищена ничем: регрессия вернёт ровно тот баг — зелёный шаг при неработающем `npx`.
- **Не покрыты тестами и сами ветки выбора источника.** По `msiexec`, `OpenJS.NodeJS`, `node-lts` в тестах совпадений нет; проверка `Confirm-HmArtifact` перед запуском вшитого MSI, порядок «vendor → winget → онлайн» и fail-closed по подписи в онлайн-ветке держатся только чтением кода. `tested: "yes"` в инвентаре относится к macOS-половине (`node.sh`) — Windows-половина по существу не проверена.
- **`Get-Command winget` в `node.ps1:107` — тот самый приём, который в соседнем скрипте признан небезопасным и убран.** Тест «chatgpt-desktop.ps1: winget PublisherId 8wekyb3d8bbwe + БЕЗ Get-Command fallback…» (`test/run-tests.js:962-973`) прямо утверждает: `Get-Command winget` fallback убран, потому что это user-writable alias, и подпись `winget.exe` обязана проверяться до запуска. В `node.ps1` ни того, ни другого нет: winget резолвится через `Get-Command` и запускается elevated без проверки подписи. Является ли это принятым риском или недоделкой — по коду не установить.
- **`node.sh` не понимает `HM_DRY_RUN`.** Переменная в файле не встречается вовсе, тогда как её обрабатывают 10 из 17 macOS-скриптов и `node.ps1`. Что это значит на практике — зависит от того, запускается ли компонент в dry-run вообще; `src/main.js:1156` (`if (isDryRun) childEnv.HM_DRY_RUN = '1';`) переменную до скрипта доводит, а скрипт её игнорирует. Поведение сухого прогона на macOS **не подтверждено кодом** — я не проследил, отсекается ли запуск раньше.
- **Сообщение dry-run на Windows врёт про ветку.** `node.ps1:158` печатает «[dry-run] Node.js: офлайн-ветка выбрана, без изменений» безусловно — в том числе после того, как выше был выбран winget или онлайн-путь и напечатано соответствующее `WOULD`.
- **`needsAdmin: false` у компонента (`components.json:29`) расходится с поведением macOS.** Флаг рисует бейдж «админ» в списке (`src/renderer/app.js:447`), а `node.sh:38` вызывает `admin_run`, то есть спрашивает пароль администратора. Расхождение системное, не только у node: `vscode.sh:64` и `cursor.sh:65` делают то же при `needsAdmin: false`. На Windows вопрос не стоит — установщик целиком elevated.
- **Стухшая ссылка в комментарии.** `tools/sync-sizes.js:83` указывает `scripts/windows/node.ps1:30` как место, где берётся `apps/node-lts.msi`; на строке 30 в node.ps1 сейчас комментарий про MCP-серверы, а путь к MSI — на строке 102.
- **Онлайн-ветка Windows при неподтверждённой подписи не выходит на месте.** После сообщения «НЕ запускаю (fail-closed)» (`node.ps1:151`) управление идёт дальше, к финальной проверке, и шаг падает уже с общим текстом «Node.js не обнаружен после установки» (`node.ps1:173`). Итоговый код 1 верный, но человек в логе увидит две разные причины подряд.
- **Устойчивость парсинга `index.json` на macOS.** Версия достаётся связкой `grep -o '{[^{}]*}'` + `grep '"lts":"'` (`node.sh:19`): формат обещает, что записи идут от новых к старым и что у LTS поле `lts` — строка. Изменение формата на стороне nodejs.org даст пустую версию и честный `exit 1` (строка 21) — это обработано, но онлайн-путь молча перестанет работать до правки скрипта.
