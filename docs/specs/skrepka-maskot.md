## Что обещает человеку

На рабочем столе появляется отдельное приложение-помощник, которое живёт поверх окон и запускается само при каждом входе в систему. По текстам, которые печатают сами скрипты (`scripts/windows/mascot.ps1:132`, `scripts/macos/mascot.sh:391`), обещание звучит так: «Скрепка установлена и запущена — она уже на экране. Ctrl+Shift+D откроет твои сессии Claude». Описание компонента в `components.json:250-251` добавляет: скрепка показывает, что делает Claude, и даёт кнопки «Разрешить/Отклонить» прямо на экране, чтобы не искать нужную вкладку.

Второе, более узкое обещание — про чужой конфиг. Установка трогает `~/.claude/settings.json`, то есть весь личный конфиг Claude Code, и обязуется сделать это безопасно: заменить ровно одну подстроку, проверить JSON до и после, положить рядом резервную копию `settings.json.hm-bak` и подменить файл атомарно, а при любом сбое оставить оригинал нетронутым (`mascot.ps1:50-92`, `mascot.sh:174-325`). Компонент выключен по умолчанию (`components.json:252`, `"default": false`) и требует установленного Claude Code (`components.json:253-255`, `requires: ["claude"]`).

Важно, чего в обещании нет: сама скрепка — внешнее приложение, в этот репозиторий попадает только готовый бинарь. Всё, что она рисует и умеет после запуска, кодом этого репозитория не подтверждается.

## Как работает

### Откуда берётся бинарь

Windows: `tools/fetch-vendor.ps1:320-331` копирует `claude-mascot.exe` из локальной сборки (`$env:HM_MASCOT_SRC`, по умолчанию `%USERPROFILE%\claude-mascot\src-tauri\target\release\claude-mascot.exe`) в `vendor/apps/claude-mascot/`. Если компонент `mascot` объявлен в `components.json`, а exe нет — сборка валится с FATAL (`tools/fetch-vendor.ps1:605-616`: условие на строке 609, сообщение «Скрепка: нет vendor\apps\claude-mascot\claude-mascot.exe» на 612, `exit 1` на 613).

macOS: `tools/fetch-vendor-mac.sh:326-366` тянет подписанную и нотаризованную `*.app` из релизов публичного репозитория `JHamidun/claude-mascot-macos-ci` (переопределяется `HM_MASCOT_MAC_URL`). Сборочный гейт (`tools/fetch-vendor-mac.sh:618-698`) безусловно проверяет `Info.plist`, `CFBundleExecutable`, Mach-O, `codesign --verify --deep --strict` (строка 678, вызывается без guard), точное совпадение `TeamIdentifier` с `3VN93XA9DY` (683-686) и наличие записи в `checksums.json` (695-697) — иначе FATAL. Нотаризация тоже fail-closed по построению: `MASCOT_NOTAR_OK` инициализируется нулём (688), поднять его может только `xcrun stapler validate` (689) или `spctl --assess` (690), и при отсутствии обоих инструментов остаётся `0` → FATAL (691-693). А вот проверка обоих слайсов (arm64 + x86_64) **условная**: она целиком обёрнута в `if command -v lipo >/dev/null 2>&1` (672-676), и оба `mascot_fatal` (674, 675) лежат ВНУТРИ этого `if`. Нет `lipo` в PATH — arch-контроль молча пропускается, FATAL не наступает, и не-universal `.app` (только arm64) проходит гейт. Комментарий 670-671 («lipo -archs на раннере есть») — допущение о среде сборки, а не вентиль. Отсюда же и запись `mac-arch-support.json` → `mascot`: `"kind": "universal"`.

В lite-издании артефакт докачивается: `remote-components.json` содержит две записи с `remoteId: "mascot"` (win32 — 283 593 812 байт, darwin — 202 286 822 байта), у каждой два зеркала (regru, yandex), `installRelPath` и `gatedFiles` с sha256 главного бинаря. Гейт «vendor-first» — `COMPONENT_VENDOR_ARTIFACT.mascot = 'apps/claude-mascot'` (`src/main.js:708`): есть артефакт во вшитом vendor — докачка не запускается вовсе. `mascot` **не** входит в `SCRIPT_ONLINE_FALLBACK` (`src/main.js:742`), то есть своего онлайн-пути у скрипта нет.

### Обнаружение и удаление

Детект «уже установлено» — `src/main.js:2710-2725`. Windows: существование `%LOCALAPPDATA%\Programs\ClaudeMascot` либо `~/.claude-mascot/.installed`. macOS: `dirHasChildStarting(appsDir, 'Claude')` (строка 2718) И наличие в `~/Applications` имени, подходящего под `/mascot|claude/i` и `/\.app$/i` (строка 2720).

Удаление доступно из UI: `mascot` входит в `REMOVABLE` (`src/renderer/app.js:43`). План целей — `src/uninstall-targets.js:185-238`. Общая для обеих платформ цель `hookurl`: файл `~/.claude/settings.json`, `from: '127.0.0.1:45832/hook'`, `to: '127.0.0.1:VSCODE_PORT/hook'`. Windows добавляет `killproc claude-mascot.exe`, `dirtree` на каталог приложения, `file` на `.installed`, `emptydir` на `~/.claude-mascot` и `reg` на значение `ClaudeMascot` в `HKCU\...\Run`. macOS добавляет `launchagent com.hamidun.claude-mascot`, а `appbundle` — **только** если `ctx.mascotMac` пришёл из доверенного vendor (`resolveMascotVendorApp`, `src/main.js:3087-3098`), с точным путём, эталонным `expectBundleId` и `teamId = '3VN93XA9DY'`; иначе в `notes` уходит честное «Vendor недоступен — .app скрепки не удаляю».

Исполнение цели `hookurl` — `uninstallExec.restoreHookUrl` (`src/uninstall-exec.js:507-562`), подключённая и к описанию плана (`case 'hookurl'` в `describeTarget` — `src/main.js:3134`, сама функция объявлена на 3126), и к его исполнению (`case 'hookurl'` в `executeUninstallTarget` — `src/main.js:3165`, функция объявлена на 3144). Там свой узкий допуск: разрешён ровно один путь `~/.claude/settings.json`, symlink и не-обычный файл отбиваются, JSON валидируется до и после, запись атомарная. Комментарий 514-518 так объясняет цену бездействия: обращение на закрытый локальный порт под Windows отбивается за ~2,2 с, а хук-записей в паке, по его словам, четырнадцать — около полуминуты мёртвого ожидания в каждой сессии Claude Code у того, кто скрепку снял. Число «четырнадцать» содержимым пака не подтверждается (см. «Риски»).

## Инварианты

1. **Вшитый бинарь не запускается без совпадения sha256 с манифестом.** Windows — `Confirm-HmArtifact $src` (`mascot.ps1:19`; реализация `_verify.ps1:64-104`, при несовпадении `exit 1`). macOS — `verify_artifact "$APP_BIN_PATH"` (`mascot.sh:94`, реализация в `scripts/macos/_lib.sh`).
2. **macOS: .app ставится только с нашей подписью Developer ID и подтверждённой нотаризацией.** `mascot.sh:102-118`: инструменты по абсолютным путям и с `require -x`, `codesign … -R "=anchor apple generic and certificate leaf[subject.OU] = \"3VN93XA9DY\""`, `spctl --assess --type execute` без обходных путей.
3. **macOS: карантин снимается только после проверки РЕЗУЛЬТАТА установки.** `mascot.sh:165-172` — сначала `verify_app_bundle "$DEST"`, и лишь потом `xattr -dr com.apple.quarantine`.
4. **macOS: старая рабочая скрепка не теряется из-за битой новой.** `mascot.sh:139-169` — ditto в staging, проверка staging до касания `$DEST`, откладывание старого бандла в `$DEST.old` и возврат его при любом отказе.
5. **Windows: свежескопированный exe запускается де-элевированно.** `mascot.ps1:118` — только `Start-Process explorer.exe "$dest"`; прямого `Start-Process $dest` в файле нет.
6. **`settings.json` правится только если он валидный JSON и содержит точную подстроку `127.0.0.1:VSCODE_PORT/hook`.** `mascot.ps1:69-71`; `mascot.sh:227-233` (выход `11` — не JSON, выход `3` — плейсхолдера нет).
7. **Запись `settings.json` атомарная и с резервной копией `.hm-bak`.** Windows — `mascot.ps1:79-82` (bak → tmp → повторный разбор с диска → `Move-Item -Force`). macOS — `mascot.sh:246-311` (`0600` + `fsync`, ре-валидация с диска, атомарный бэкап через `os.replace`).
8. **Любой сбой правки конфига оставляет маркер `.installed` на месте — держится ТОЛЬКО на macOS.** `mascot.sh:314-324`: `KEEP_MARKER=1` ставят все ветки `case`, кроме `0` и `3`, включая `*)` на строке 323 — туда попадает `sys.exit(10)` (строка 224, «не прочитался»); при `KEEP_MARKER=1` маркер не удаляется (`mascot.sh:326-331`). **На Windows инвариант нарушен в двух сбойных ветках из четырёх.** `$keepMarker = $true` выставляется ровно на `mascot.ps1:75` (JSON сломался после замены) и `mascot.ps1:87` (не удались бэкап или запись) — обе внутри ветки замены. ## Что ломается, если инвариант нарушить

1. Вместо скрепки в автозагрузку пользователя прописывается подменённый или битый бинарь — и стартует при каждом входе в систему, поверх всех окон, с видом штатного помощника.
2. На Mac в `~/Applications` встаёт приложение, подписанное чужим Developer ID (или не нотаризованное), а Gatekeeper потом молчит, потому что карантин с него мы же и сняли.
3. Тот же исход другим путём: проверили исходник в vendor, а карантин сняли с того, что реально легло в `~/Applications`, — если между этим что-то подменилось, мы своими руками выдали ему зелёный свет.
4. Человек обновляет скрепку и остаётся вообще без неё: новая копия не встала, а старая уже удалена. Либо, если бы `ditto` домержил новое в выживший старый бандл, — микс двух версий со сломанной подписью, который не запускается и не объясняет почему.
5. Малварь того же пользователя подменяет `claude-mascot.exe` между копированием и запуском — и её код исполняется с правами администратора, потому что установщик целиком elevated.
6. Порча личного конфига Claude Code: подстановка в чужие поля, где случайно встретилось слово `VSCODE_PORT`, или запись поверх файла, который и до нас не парсился. У человека перестаёт запускаться Claude Code, а причина выглядит как «после установщика всё сломалось».
7. Обрыв питания или кончившееся место в момент записи оставляют `settings.json` усечённым — и восстановить его неоткуда, потому что резервной копии не сделали. Это потеря всех личных настроек, а не одной строки.
8. Маркер `.installed` снят, хотя правка хуков не сделана. На Windows это не гипотеза, а текущее поведение двух веток из четырёх (`mascot.ps1:66` и `:70` → удаление маркера на строке 95). Чем это оборачивается для человека, кодом этого репозитория **не подтверждается**: самой скрепки здесь нет, а комментарии скрипта противоречат друг другу — строка 94 обещает, что снятый маркер заставит приложение перепрописать хуки заново (то есть само себя вылечить), строка 97 — что как раз ОСТАВЛЕННЫЙ маркер даст ей «докрутить правку самой». Одно из двух описаний неверно, и какое именно — из этого репозитория не установить.
9. Правка, которую в этот же момент делает сам Claude Code, молча затирается нашей — пользователь теряет только что сохранённые настройки и не связывает это с установщиком.
10. В сборке без скрепки шаг покраснел бы ошибкой, которую нечем починить, а в списке установленного появился бы маркер несуществующего компонента — и кнопка «Удалить», которая пошла бы сносить чужое.
11. Ровно тот отказ, ради которого написана ветка: зелёная галочка на финальном экране и пустой рабочий стол. Человек решает, что не понял, как скрепку вызвать, и ищет ошибку в себе.
12. Честный красный у косметического компонента начал бы валить зависимые шаги — установка Claude Code или курса падала бы из-за необязательной картинки на экране.
13. Деинсталлятор сносит из `~/Applications` чужое приложение, чьё имя просто похоже на наше. Это удаление данных, которых мы не ставили.
14. Хуки остаются указывать на порт 45832, где после удаления никто не слушает: каждое такое обращение под Windows отбивается не мгновенно, а за ~2,2 с (замер в комментарии `src/uninstall-exec.js:514-518`), и человек видит просто «Claude стал тормозить». Масштаб потери **на текущем содержимом репозитория не подтверждается**: тот же комментарий (строка 516) считает полминуты из четырнадцати хук-записей в паке, а в `vendor/config-pack` хук-групп ровно две (`PreToolUse`, `SessionStart`), обе `"type": "command"`, и строки `VSCODE_PORT` нет ни в одном из 9 765 файлов — то есть подставлять порт сейчас некуда и мёртвых hook-url взяться неоткуда (см. «Риски»).
15. В окне выбора написано одно число, скачивается другое. Для 280-мегабайтного компонента на слабом канале это разница между «пара минут» и «полчаса», и доверие теряется ко всем остальным числам.

## Границы

- **Самой скрепки в этом репозитории нет.** Сюда попадает готовый артефакт из внешней сборки: Windows — из локального каталога сборщика (`tools/fetch-vendor.ps1:321`), macOS — из релизов `JHamidun/claude-mascot-macos-ci` (`tools/fetch-vendor-mac.sh:338`). Всё поведение приложения после запуска — окно поверх окон, кнопки «Разрешить/Отклонить», `Ctrl+Shift+D`, HTTP-эндпоинт `/health` на 45832 — **кодом этого репозитория не подтверждается**: здесь есть только тексты сообщений и обращение к `http://127.0.0.1:45832/health`.
- **Установщик не создаёт `settings.json`.** Файла нет — печатается сообщение и правка пропускается (`mascot.ps1:60-62`, `mascot.sh:191-192`); хуки в этом случае пропишет само приложение при первом запуске.
- **Установщик не пишет хук-записи, а только подставляет порт в уже существующий плейсхолдер.** Ни одного места, где добавлялась бы новая запись в `hooks`, в обоих скриптах нет.
- **Windows: подпись Authenticode у `claude-mascot.exe` не проверяется.** В `mascot.ps1` нет ни `Test-HmTrustedSigner`, ни `_deelev.ps1`, ни слова `Authenticode` — доверие держится только на sha256 из манифеста. На macOS проверка подписи и нотаризации есть.
- **WebView2 Runtime не устанавливается.** Скрипт только диагностирует его отсутствие и даёт ссылку (`mascot.ps1:147-151`).
- **macOS: `KeepAlive` в LaunchAgent намеренно не ставится** (`mascot.sh:334-335`) — закрытая пользователем скрепка не перезапускается до следующего входа.
- **Деинсталляция не чистит хуки целиком**, а только возвращает hook-url к плейсхолдеру; в `notes` об этом сказано прямо: «Хуки в ~/.claude/settings.json НЕ трогаю (там могут быть твои правки)» (`src/uninstall-targets.js:237`).
- **Компонент выключен по умолчанию и требует Claude Code** (`components.json:252-255`); `needsAdmin: false` (строка 256) — это только бейдж в списке (`src/renderer/app.js:447`), реальное разграничение прав им не управляется.
- **Dry-run выходит до всех проверок целостности — на ОБЕИХ платформах, это не Windows-специфика.** Windows: `mascot.ps1:13-16` против `Confirm-HmArtifact` на строке 19. macOS: `mascot.sh:78-81` против `verify_artifact "$APP_BIN_PATH"` на строке 94 И `verify_app_bundle "$APP"` на строке 121. То есть сухой прогон молчит про sha256 на обеих платформах, а на macOS — ещё и про Developer ID с нотаризацией.
- **«Маскот» в `src/renderer/app.js:283-295` — это другое.** Там Омлетон, картинка внутри окна установщика (`src/renderer/index.html:27`, `mascot/*.webp`); к компоненту `mascot` он отношения не имеет, и путать их нельзя.

## Риски и открытые вопросы

- **Плейсхолдера `127.0.0.1:VSCODE_PORT/hook` нет в поставляемом конфиг-паке.** Поиск по всем 9 765 файлам `vendor/config-pack` даёт ноль совпадений со строкой `VSCODE_PORT`; в `vendor/config-pack/.claude/settings.json` всего два поля `url` (`extraKnownMarketplaces…source.url` и `mcpServers.miro.url`), и оба — не хуки. В самом репозитории строка встречается в обоих install-скриптах (`mascot.ps1:14,50,52,57`, `mascot.sh:79,174,177,188`), в коде удаления (`src/uninstall-exec.js:510`, `src/uninstall-targets.js:187,205`), в тесте (`test/run-tests.js:3632`, `const HOOK_TO = '127.0.0.1:VSCODE_PORT/hook';` — единственное вхождение во всём файле) и в собранной копии скриптов под `release/win-unpacked/resources/scripts/` — но нигде в самом паке. Значит, на текущем содержимом пака §4 обоих скриптов — no-op, и хуки в любом случае прописывает само приложение. Пак тянется из внешнего репозитория `JHamidun/claude-code-config-pack` (`scripts/windows/config.ps1:76`), поэтому утверждение «конфиг-пак несёт hook-записи с плейсхолдером» (комментарий `mascot.ps1:50-51`) **на коде этого репозитория не подтверждается** — как и число «четырнадцать хук-записей» из `src/uninstall-exec.js:516`: хук-групп в паке ровно две (`PreToolUse`, `SessionStart`), и обе — `"type": "command"`, то есть на порт вообще не ходят.
- **Детект «скрепка уже стоит» на macOS, судя по коду, недостижим.** `src/main.js:2718` начинается с `dirHasChildStarting(appsDir, 'Claude')`, а эта функция (`src/main.js:2496-2502`) строит регулярку `^Claude-\d` (строка 2498) и требует `d.isDirectory()` (строка 2500), то есть каталог с таким именем. Реальное имя бандла произвольное (`find … -name '*.app'`), в тесте фигурирует `Claude Mascot.app` — под `^Claude-\d` оно не подходит. Второй конъюнкт с `/mascot|claude/i` при этом никогда не оценивается. Следствие: `out.mascot.installed` на macOS почти всегда `false`, и UI не покажет, что компонент уже установлен. Живьём это не проверялось — вывод сделан чтением кода.
- **Windows-проверка живости не подтверждает, что ответил НАШ процесс.** `mascot.ps1:127` считает успехом любой HTTP-200 с `127.0.0.1:45832/health`. На macOS этот риск закрыт отдельным `pgrep` (`mascot.sh:388-390`) с явным комментарием «на :45832 мог ответить чужой процесс»; на Windows аналога нет — чужой слушатель на этом порту даст ложное «OK: Скрепка установлена и запущена».
- **Комментарий в сборочном скрипте расходится с поведением.** `tools/fetch-vendor-mac.sh:621-622` утверждает: «mascot.sh у пользователя всё равно делает hard exit 1 без валидной .app — „пропуска компонента“ при установке НЕ существует». Фактически `mascot.sh:48` выходит с кодом `120`, то есть штатным graceful skip. Сам сборочный FATAL при этом обоснован независимо, но обоснование в комментарии неверное.
- **Де-элевация запуска на Windows ничем не закреплена.** Поиск по `test/run-tests.js` даёт совпадения на `explorer.exe` только в контексте `src/main.js` (`winLaunchDeElevated`); ни одного теста, который проверял бы, что `mascot.ps1` запускает скрепку через `explorer.exe`, а не напрямую, нет. Это самый серьёзный из инвариантов скрипта (пункт 5) — и он держится только комментарием на строках 113-116.
- **Windows-правка `settings.json` тоже без теста.** Проверены только зеркальные операции при удалении (`restoreHookUrl`). Атомарность, наличие `.hm-bak`, поведение при битом JSON и логика `$keepMarker` в `mascot.ps1:56-98` не покрыты ничем; macOS-половина покрыта частично (тест на `mascot.sh` проверяет подпись и нотаризацию, но не python-блок правки).
- **`Test-Path` перед `Confirm-HmArtifact` — не гонка, но и не защита.** Между проверкой существования `$src` (строка 8), сверкой sha256 (строка 19) и `Copy-Item` (строка 45) файл лежит в vendor, доступном на запись тому же пользователю в lite-издании (staging-каталог докачки). Насколько это закрыто правами staging-каталога, по коду `mascot.ps1` не установить — проверка прав живёт в `src/main.js` и в рамках этой фичи не прослеживалась.
- **`$ErrorActionPreference = 'Continue'`** (`mascot.ps1:2`) означает, что необработанные ошибки не прерывают скрипт; корректность зависит от явных проверок в каждой ветке. Ветки, где результат не проверяется явно, — `New-Item` каталога (строка 42) и `Remove-Item` маркера (строка 95); последствия обеих не критичны, но диагностики по ним нет.
