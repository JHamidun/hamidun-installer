## Что обещает человеку

На финишном экране установщика человек видит три поля и кнопку «Сохранить ключи». Он вставляет
туда ключи Google (Gemini), OpenAI и ElevenLabs — те, что нужны генерации картинок, видео и
озвучки, — жмёт кнопку и получает надпись «Сохранено (N) в .credentials.master.env ✓». Больше
ничего делать не надо: искать домашнюю папку, находить скрытый файл, править его блокнотом и не
ошибиться в синтаксисе `КЛЮЧ=значение` — не требуется. Поля подписаны placeholder'ами прямо в
интерфейсе (`src/renderer/app.js:2175-2177`), заголовок блока честно говорит «необязательно —
можно добавить позже» (`src/renderer/app.js:2173`).

Второе обещание, и оно важнее первого: **уже записанные ключи не пострадают**. Человек мог
заполнить файл раньше — руками или прошлым запуском установщика. Визард дописывает и заменяет
строки точечно, а если существующий файл прочитать не удалось, он отказывается писать вовсе и
говорит об этом прямо, вместо того чтобы затереть чужие ключи тремя новыми строками.

## Как работает

**Отрисовка.** Блок ключей — константа `keysHtml` внутри `renderNextSteps()`
(`src/renderer/app.js:2171-2183`): три `<input type="text">` с id `key-GOOGLE_API_KEY`,
`key-OPENAI_API_KEY`, `key-ELEVENLABS_API_KEY`, кнопка `#ns-save-keys` и статус-строка
`#ns-keys-status`. Блок подставляется в разметку финиша безусловно (`src/renderer/app.js:2305`) —
ветвления «показывать/не показывать» нет: он есть и при полностью успешной установке, и при
провалах. Обработчик вешается при наличии кнопки (`src/renderer/app.js:2458-2459`).

**Сбор значений.** `saveCredentialKeys()` (`src/renderer/app.js:2467-2486`) идёт по списку
`CRED_KEY_NAMES = ['GOOGLE_API_KEY', 'OPENAI_API_KEY', 'ELEVENLABS_API_KEY']`
(`src/renderer/app.js:2465`), читает `el.value.trim()` и кладёт в объект только непустые. Если
непустых нет — в статус пишется «Заполни хотя бы одно поле.» и IPC не вызывается. Иначе статус
становится «Сохраняю…», и вызывается `window.installer.saveCredentials(keys)` — мост
`contextBridge` в `src/preload.js:40`, канал `save-credentials`.

**Запись.** Обработчик `ipcMain.handle('save-credentials', …)` (`src/main.js:2261-2311`) работает
так:

1. Считает пути: `dir = ~/.claude`, `file = ~/.claude/.credentials.master.env`
   (`src/main.js:2263-2264`). Путь **захардкожен** — `finish.credentialsRelPath` из `config.json`
   здесь не читается.
2. `fs.mkdirSync(dir, { recursive: true })` — каталог создаётся, если его нет.
3. Читает существующий файл. **Развилка на ошибке чтения** (`src/main.js:2267-2280`): коды
   `ENOENT` и `ENOTDIR` считаются «файла ещё нет» → продолжаем с пустым `text`. **Любой другой
   код** (EBUSY/EACCES/EIO/ELOOP/EMFILE, cloud-placeholder OneDrive) → немедленный возврат
   `{ ok: false, error: … }` с текстом «Ключи НЕ сохранены, чтобы не потерять уже записанные»; на
   диск не пишется ничего. Комментарий в коде прямо называет это fail-closed по образцу `probePath`
   из `src/install-mode.js:34-42`.
4. Для каждого ключа входного объекта (`src/main.js:2282-2297`): имя должно совпасть с
   `/^[A-Z][A-Z0-9_]*$/`, иначе `continue`; значение должно быть строкой, иначе `continue`;
   значение `.trim()` и из него удаляются все `\r` и `\n`; пустое после этого — `continue`.
   Дальше вторая развилка: если в тексте уже есть строка `^KEY=.*$` (regexp с флагом `m`), она
   заменяется через **функцию-замену** `() => line`; если нет — строка дописывается в конец, с
   добором `\n`, когда текст не заканчивался переводом строки. Имя ключа попадает в `saved`.
5. Запись — только если `saved.length` (`src/main.js:2298-2306`): текст пишется во временный файл
   `<file>.tmp-<pid>`, затем `fs.renameSync(tmp, file)`. Если `rename` упал — временный файл
   удаляется и ошибка пробрасывается наружу.
6. Возврат `{ ok: true, saved, path: file }`. Любое неперехваченное исключение выше даёт
   `{ ok: false, error: String(e) }` (`src/main.js:2308-2310`).

**Показ результата.** Renderer пишет в `#ns-keys-status` либо
``Сохранено (${(res.saved || []).length}) в .credentials.master.env ✓``, либо «Не удалось
сохранить: » + `res.error` (`src/renderer/app.js:2481-2485`).

**Соседняя кнопка «Показать файл ключей»** (`#ns-keys`, `src/renderer/app.js:2300`, обработчик
`src/renderer/app.js:2440`) зовёт `revealPath(credPath)`. Аргумент из renderer'а main **игнорирует**:
`ipcMain.handle('reveal-path', …)` (`src/main.js:1578-1589`) сам собирает цель из
`config.json` → `finish.credentialsRelPath` (сейчас `.claude/.credentials.master.env`,
подтверждено чтением `config.json`), проверяет, что она внутри домашнего каталога, что файл
существует, и вызывает `shell.showItemInFolder`. Путь, который renderer показывает человеку
(`credPath`), собирается отдельно — из того же `finish.credentialsRelPath` с платформенным
разделителем (`src/renderer/app.js:2035-2038`).

**Платформенных ветвлений у самой фичи нет:** `path.join(os.homedir(), '.claude')` и `renameSync`
одинаковы на Windows и macOS; отличается только отрисовка пути на экране (`sep` = `\` или `/`) и
поведение системного «показать файл» на уровне Electron.

## Инварианты

1. **Ошибка чтения существующего файла (кроме ENOENT/ENOTDIR) НИКОГДА не приводит к записи.**
   Держится в `src/main.js:2275-2278`: проверка `if (!(e && (e.code === 'ENOENT' || e.code ===
   'ENOTDIR')))` → `return { ok: false, error: … }` до любого `writeFileSync`.
2. **Ни одна строка файла, кроме строк сохраняемых ключей, не меняется, не удаляется и не
   переставляется.** Держится на том, что весь остальной текст переносится из `text` как есть:
   единственные мутации — `text.replace(re, …)` по `^KEY=.*$` и конкатенация в конец
   (`src/main.js:2289-2295`).
3. **В файл попадают только имена вида `^[A-Z][A-Z0-9_]*$`.** Гейт `src/main.js:2283`. Он же
   гарантирует, что имя ключа не содержит метасимволов регулярного выражения, которое строится
   из него на следующем шаге (`new RegExp('^' + key + '=.*$', 'm')`, `src/main.js:2289`).
4. **Значение ключа не может внести лишние строки в файл.** `raw.trim().replace(/[\r\n]+/g, '')`
   (`src/main.js:2286`) убирает все переводы строк, так что одна пара ключ-значение — ровно одна
   строка.
5. **Спецсимволы замены (`$&`, `$1`, `$'`) внутри значения не интерпретируются.** Замена сделана
   функцией `() => line`, а не строкой (`src/main.js:2291`); в коде это отмечено комментарием
   «fn-replacement: `$` в значении не трогаем».
6. **Файл ключей никогда не остаётся обрезанным из-за сбоя посреди записи.** Запись идёт в
   `<file>.tmp-<pid>` и завершается `renameSync` в пределах того же каталога
   (`src/main.js:2302-2304`).
7. **Пустые поля не создают пустых присваиваний.** Двойная фильтрация: renderer не кладёт в объект
   пустое после `trim()` (`src/renderer/app.js:2472-2473`), main отбрасывает пустое повторно
   (`src/main.js:2287`).
8. **Если сохранять нечего — файл не трогается вообще.** Блок записи обёрнут в
   `if (saved.length)` (`src/main.js:2298`).
9. **Renderer не может заставить main показать произвольный путь.** `reveal-path` игнорирует
   аргумент, собирает цель из вшитого `config.json`, требует, чтобы она начиналась с
   `home + path.sep`, и чтобы файл существовал (`src/main.js:1584-1585`).

## Что ломается, если инвариант нарушить

1. Файл ключей заблокирован антивирусом или лежит в OneDrive как cloud-placeholder, чтение падает
   с EBUSY — и вместо «не сохранил» установщик пишет поверх три новые строки. Человек теряет все
   ранее накопленные ключи (ANTHROPIC, TELEGRAM_BOT_TOKEN, всё) без бэкапа, причём под надписью
   «Сохранено (N) в .credentials.master.env ✓» — то есть даже не узнает, что потерял. Цветом
   статус исход не различает вовсе: `.ns-keys-status` объявлен единственным правилом
   `font-size: 12px; color: var(--text-muted)` (`src/renderer/styles.css:522`), а `className` и
   `classList` у `#ns-keys-status` не трогаются ни в одной ветке — меняется только `textContent`
   (`src/renderer/app.js:2481-2485`). Успех и провал выглядят одинаково приглушённо; у соседнего
   Nomad для этого есть `setMsg(text, kind)` с классами `good`/`bad`
   (`src/renderer/app.js:2354-2357`), у мини-визарда такого механизма нет.
2. Слетает всё, чего мини-визард не знает: токены ботов, комментарии, ключи других сервисов.
   Человек приходит к тому, что вчера работавшие скиллы вдруг «просят ключ», и связать это с
   нажатием «Сохранить ключи» не может.
3. В `.env` уезжает строка вида `rm -rf=…` или имя с кириллицей — файл перестаёт быть валидным
   для потребителей, и ключи, включая ранее рабочие, перестают читаться целиком.
4. Значение с `\r`/`\n`, пришедшее по каналу `save-credentials`, разрывается на две строки: первая
   становится обрезанным ключом, вторая — мусорной строкой. Сервис отвечает 401, а на глаз файл
   выглядит нормально. Пользовательский сценарий «скопировал из кабинета вместе с переводом
   строки» сюда НЕ ведёт: поля визарда — однострочные `<input type="text">`
   (`src/renderer/app.js:2175-2177`), а из них `el.value` (`src/renderer/app.js:2472`) переводов
   строки не отдаёт, плюс там же `.trim()`. Инвариант 4 страхует произвольного вызывающего по IPC,
   а не вставку в поле.
5. Ключ, в котором встретилось `$&` (для API-ключей символ `$` реален), записывается искажённым:
   вместо самого ключа подставляется найденный фрагмент. Человек видит «ключ сохранён», а сервис
   его не принимает — и отладить это по внешнему виду файла почти невозможно.
6. Диск заполнился или процесс убили посреди записи — файл ключей остаётся обрезанным на середине.
   Ломается не только новый ключ, а весь набор: следующая строка после обрыва перестаёт
   существовать.
7. В файл попадают строки `GOOGLE_API_KEY=` без значения. Потребитель ключа получает пустую
   строку вместо «ключа нет» и падает не с понятным «не настроено», а произвольной ошибкой
   аутентификации.
8. Вызов обработчика с объектом, из которого все ключи отсеялись гейтами main
   (`src/main.js:2283-2287`), переписывал бы файл вхолостую — лишний шанс потерять его при сбое
   там, где сохранять было нечего. Через интерфейс этот сценарий недостижим: при всех пустых
   полях renderer выходит ранним `return` до IPC (`src/renderer/app.js:2475-2478`), и
   `save-credentials` не запускается вовсе. Инвариант 8 страхует только не-UI вызывающего.
9. Скомпрометированный renderer передал бы `\\attacker\share\…`, и `shell.showItemInFolder` под
   elevated-процессом смонтировал бы чужой UNC/WebDAV-ресурс — вектор из комментария в
   `src/main.js:1574-1577`.

## Границы

- **Ключи не проверяются.** Ни формата, ни длины, ни живости: любая непустая строка сохранится как
  есть. Сравнение по контрасту: поле ключа Nomad на том же экране валидирует ввод и возвращает
  причины `malformed`/`empty` (`src/renderer/app.js:2371-2374`) — у мини-визарда такой проверки нет.
- **Ровно три ключа**, зашитых в `CRED_KEY_NAMES` (`src/renderer/app.js:2465`). Четвёртый сервис
  через этот экран не добавить — только руками в файл.
- **Только добавление и замена.** Удалить ключ или очистить значение через визард нельзя: пустое
  поле означает «не трогай», а не «сотри».
- **Значения не маскируются и не стираются после сохранения.** Поля — `type="text"`
  (`src/renderer/app.js:2175-2177`), и после успешного сохранения они не очищаются
  (`src/renderer/app.js:2481-2485`). Ключи остаются видимыми на экране до закрытия установщика.
  Соседний сценарий Nomad поступает иначе — там поле чистится намеренно, с комментарием «Ключ на
  экран не возвращаем и в поле не оставляем» (`src/renderer/app.js:2367-2368`).
- **Права на файл не выставляются.** `fs.mkdirSync` и `fs.writeFileSync` вызываются без опции
  `mode`, `chmod` в обработчике нет (`src/main.js:2265`, `src/main.js:2303`) — файл получает права
  по умолчанию процесса.
- **Профиль назначения — домашний каталог того аккаунта, под которым идёт процесс.**
  `os.homedir()` берётся как есть, без переадресации на интерактивного пользователя. При
  «over-the-shoulder UAC» (админ ввёл свой пароль на чужой машине) ключи уедут в профиль админа.
  Установщик предупреждает об этом отдельным баннером до установки
  (`detectForeignUserWarning`, `src/main.js:439-511`), но сам мини-визард никакой компенсации не
  делает.
- **Ничего не перезапускается.** Записанный ключ подхватят только те процессы, которые прочитают
  файл после сохранения; уже открытый терминал или редактор об изменении не узнают.
- **Два источника пути живут раздельно.** Запись — по захардкоженному
  `~/.claude/.credentials.master.env` (`src/main.js:2264`), показ файла и подпись пути — по
  `finish.credentialsRelPath` из `config.json` (`src/main.js:1581`, `src/renderer/app.js:2035`).
  Сейчас значения совпадают (проверено чтением `config.json`).

## Риски и открытые вопросы

- **Тестов нет.** По всему каталогу `test/` нет ни одного вхождения `save-credentials`,
  `saveCredentials`, `ns-save-keys`, `key-GOOGLE_API_KEY`, `key-OPENAI_API_KEY`, `CRED_KEY_NAMES`,
  `reveal-path`, `revealPath`. Упоминания `.credentials.master.env` в `test/run-tests.js`
  относятся к другим фичам, и их больше двух: сохранность ключей при разворачивании конфига
  (`config.ps1`/`config.sh` — строки 2042, 2107, 2203, 2247), исключение ключей из бэкапа
  `config.sh` (6550, 6563, 6568), план деинсталляции курса (`utMod.uninstallTargets('course', …)` —
  2995, 3015), квитанции установки (`install-receipts.js`, тест «crafted-квитанция с artifacts на
  ~/.claude НЕ влияет на план» — 3975) и детекция режима additive
  (`modeMod.detectAdditive` — 4510). Чем это грозит: главный
  инвариант фичи (п. 1, fail-closed на чтении) — тонкая проверка кода ошибки, которую тривиально
  сломать рефакторингом, упростив `catch` до `text = ''`. Такая правка молча превращает визард из
  «не сохранил и сказал» в «затёр все ключи и отрапортовал успех», и ни один прогон тестов этого
  не заметит. Столь же не покрыты: замена существующей строки вместо дублирования, функция-замена
  против `$&` в значении, tmp+rename.
- **`await` без `try/catch` в renderer.** `const res = await window.installer.saveCredentials(keys);`
  (`src/renderer/app.js:2480`) не обёрнут в `try`. Если IPC-вызов отклонится (канал недоступен,
  исключение при сериализации), обещание отвергнется, обработчик прервётся, и статус навсегда
  останется «Сохраняю…» — человек не узнает ни об успехе, ни о провале. Соседний вызов
  `nomadSetKey` в том же файле обёрнут (`src/renderer/app.js:2364`). Само по себе это не
  критично — main перехватывает всё внутри себя и всегда возвращает объект, — но защита в
  renderer'е отсутствует, а асимметрия с Nomad выглядит недосмотром.
- **Временный файл с ключами может остаться на диске.** `fs.writeFileSync(tmp, …)` вызывается вне
  `try` (`src/main.js:2303`): удаление `tmp` (`fs.rmSync`, `src/main.js:2305`) предусмотрено только
  для провала `renameSync`. Если упадёт сама запись (диск полон, антивирус), исключение уходит во
  внешний `catch` (`src/main.js:2308-2310`) и превращается в `{ ok: false, error: String(e) }` —
  ни дозаписи, ни удаления `tmp` по этой ветке нет. В `~/.claude` останется
  `.credentials.master.env.tmp-<pid>`, и никто его не подчищает. **Насколько он полон — кодом не
  гарантируется:** для первого же названного сценария (диск полон, ENOSPC) `writeFileSync` бросает
  исключение из середины записи, оставив на диске лишь успевший сброситься префикс. То есть в
  остатке может оказаться как всё содержимое будущего файла со всеми ранее сохранёнными ключами,
  так и его обрезанная часть; кодом установщика подтверждается только факт остаточного файла.
- **Заменяется только ПЕРВОЕ вхождение ключа.** Регулярка `new RegExp('^' + key + '=.*$', 'm')`
  (`src/main.js:2289`) идёт без флага `g`. Если в файле почему-то две строки `GOOGLE_API_KEY=…`,
  обновится верхняя, нижняя останется прежней. Какое из двух значений увидит потребитель ключа,
  кодом установщика не определяется — это зависит от парсера на стороне читателя и здесь не
  подтверждено.
- **`{ ok: true, saved: [] }` возможен на уровне IPC.** Если бы обработчик позвали с объектом, где
  все ключи отсеялись гейтами (`src/main.js:2283-2287`), он вернул бы успех с пустым `saved`, и
  renderer показал бы «Сохранено (0) … ✓» (`src/renderer/app.js:2482-2483`) — успех при нулевом
  результате. Через интерфейс это недостижимо: имена приходят из константы `CRED_KEY_NAMES`, а
  пустые значения renderer отсеивает раньше. Записи при этом всё равно не происходит (п. 8
  инвариантов), так что данные не страдают — портится только формулировка.
- **`ENOTDIR` трактуется как «файла нет».** Комментарий в `src/install-mode.js:32-33` для
  аналогичной проверки утверждает обратное — там `ENOTDIR` намеренно НЕ считается «нет», как
  аномалия. Здесь он в списке «продолжаем с пустым текстом» (`src/main.js:2275`). Потери данных
  это не даёт: при `ENOTDIR` на пути последующие `mkdirSync`/`writeFileSync` тоже упадут и уйдут в
  общий `catch` с `{ ok: false }`. Но два одинаковых по смыслу гейта в одном проекте описывают
  один и тот же код ошибки по-разному — расхождение стоит либо объяснить в коде, либо свести.
- Не подтверждено кодом: что происходит с ключами дальше — какой процесс и когда читает
  `.credentials.master.env`. В рассмотренных файлах установщика чтения этого файла для
  использования ключей нет; он только создаётся из шаблона, исключается из бэкапов и открывается в
  проводнике.
