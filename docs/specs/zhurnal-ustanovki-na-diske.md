## Что обещает человеку

Вывод установочных скриптов и служебные отметки главного процесса дописываются в один
текстовый файл `~/.hamidun-setup/install.log`. Когда что-то пошло не так, человеку не
нужно ничего выделять мышкой, скроллить назад и собирать по кусочкам: на финишном экране
есть кнопка «Показать лог для поддержки» (`src/renderer/app.js:2121`), она открывает этот
файл, и файл целиком отправляется в поддержку.

Обещание «что на экране, то и в файле» кодом НЕ подтверждается и держит только часть
экрана. В файл попадает лишь то, что породил main. Одиннадцать сообщений renderer рисует
сам, вызывая свою `appendLog()` напрямую (`src/renderer/app.js:1569`, `:1582`, `:1611`,
`:1636`, `:1657`, `:1705`, `:1709`, `:1714`, `:1724`, `:1733`, `:1906`) — они идут в ту же
панель `#log`, но мимо main, а `logToFile` вызывается только из main
(`src/main.js:937`, `:3278`), поэтому renderer физически не может ничего записать.
Теряются при этом ФОРМУЛИРОВКИ, но не всегда сама причина. Сообщения о провале докачки
(«докачка не удалась … Проверь интернет и нажми «Повторить».», `:1709`) и о провале
проверки подлинности («файл не прошёл проверку подлинности … Повтор не поможет», `:1714`)
строятся из `res.error`, а это тот же `errMsg` (`src/main.js:1056`, возвращается на
`:1070`), который main строкой раньше уже записал в файл:
`=== fetch-remote result: … FAIL <error> ===` (`:1050`), а для брошенного исключения —
`[ERROR] fetch-remote: …` (`:1047`). Полностью теряется другое — отказ среды
(«не удалось подготовить защищённый каталог для загрузки», `:1705`): соответствующий
`return` (`src/main.js:1024-1029`) срабатывает ДО `logLine('=== fetch-remote start …')`
(`:1033`), поэтому в файл не попадает ни текст, ни даже след того, что этап докачки
начинался. Тем же свойством обладают `return` на `:997` (нет сборки для платформы) и на
`:1082` (не удалось положить checksums.json в staging). Единственный проброс из main в эту
панель — `appendLog(line)` внутри `onLog` (`src/renderer/app.js:1535`).

Второе обещание — журнал не теряет то, что уже не помещается на экран. В интерфейсе
держится кольцо из последних 800 строк (`LOG_MAX_LINES`, `src/renderer/app.js:1322`),
потому что pip, uv и npm выдают десятки тысяч строк; полный вывод при этом живёт в
файле (комментарий там же, строки 1320-1321). Строка попадает на диск синхронно, в
момент появления, — то есть журнал остаётся читаемым и после падения установщика.

## Как работает

1. **Пути.** `LOG_DIR = ~/.hamidun-setup`, `LOG_PATH = <LOG_DIR>/install.log` — считаются
   один раз при загрузке модуля из `os.homedir()` (`src/main.js:174-175`). Платформенного
   ветвления нет: на Windows и macOS путь строится одинаково через `path.join`.
2. **Запись.** `logToFile(id, line)` (`src/main.js:183-193`):
   при первой строке создаёт каталог (`fs.mkdirSync(..., {recursive:true})`, флаг
   `logDirReady`), при первой строке открывает файл `fs.openSync(LOG_PATH, 'a')` и держит
   дескриптор в `logFd`, дальше на каждую строку делает только `fs.writeSync`. Формат
   строки: `[<ISO-время>] [<id компонента>] <строка>\n`.
3. **Почему дескриптор удерживается.** Комментарий в коде (`src/main.js:177-181`) прямо
   называет причину: `fs.appendFileSync` открывал и закрывал файл на КАЖДОЙ строке, а
   строк за установку десятки тысяч, и всё это синхронные вызовы в главном процессе,
   который одновременно качает насос сообщений окна.
4. **Ветка ошибки.** Любое исключение внутри `logToFile` ловится (`src/main.js:188-192`):
   если дескриптор был открыт, он закрывается и `logFd` сбрасывается в `null`, поэтому
   следующая строка откроет файл заново. Наружу ошибка не выходит — журналирование не
   может уронить установку.
5. **Кто зовёт.** Два IPC-обработчика, и только они:
   - `run-component` (`src/main.js:877`) объявляет `logLine` (`:935`);
   - `uninstall-component` (`src/main.js:3163`) объявляет такой же `logLine` (`:3278`) и
     поверх него `say = (line) => { send(line); logLine(line); }` (`:3285`).
6. **Что именно пишется при установке.** Обёртка `emitLine` (`src/main.js:1268-1276`)
   разбирает поток stdout/stderr дочернего процесса построчно (`mkLineReader`,
   StringDecoder — чтобы не рвать кириллицу на границе чанка) и:
   - строку-квитанцию `HM-RECEIPT …` пишет ТОЛЬКО в файл и в интерфейс не отдаёт
     (`:1268-1269`);
   - остальные строки отдаёт и в интерфейс (`send`), и в файл (`logLine`) — `:1272-1273`.
   Помимо вывода скрипта в файл идут служебные отметки: `=== start ===` (`:1232`),
   `[ERROR] spawn failed: …` (`:1249`), `[ERROR] <message>` от `child.on('error')`
   (`:1319`), предупреждение сторожа молчащего шага раз в 10 минут (`:1308-1313`),
   `=== exit code: N ===` (`:1326`), строки этапа докачки
   `=== fetch-remote start/result ===` (`:1033`, `:1050`) и объяснение неуспеха — двумя
   блоками: `[почему]` (`:1395-1396`) и `[что именно упало]` (`:1404-1405`).
7. **Ветвление dry-run.** `isDryRun` считается авторитетно: `process.env.HM_DRY_RUN` ИЛИ
   подсказка из renderer (`src/main.js:935`, аналогично `:3276`). При dry-run `logLine`
   не вызывает `logToFile` вовсе — на диске не остаётся следов (`:934-935`, `:3277-3278`).
8. **Как файл попадает к человеку.** `bootstrap` возвращает в renderer поле
   `logPath: LOG_PATH` (`src/main.js:541`); renderer кладёт его в `STATE.logPath`
   (`src/renderer/app.js:69`), рисует кнопку только если путь непустой (`:2121`) и по
   клику зовёт `window.installer.openPath(STATE.logPath)` (`:2442`), то есть IPC
   `open-path` из `src/preload.js:28`. Обработчик `open-path` (`src/main.js:1510-1527`)
   не доверяет renderer'у и пропускает только три цели: ровно `LOG_PATH`, памятку
   «Что дальше — Hamidun.html» на рабочем столе и файлы внутри ресурсов установщика;
   всё прочее — `{ok:false, error:'bad-path'}`.
9. **Соседи по каталогу.** В том же `~/.hamidun-setup` живут манифест `installed.json`
   (`src/install-manifest.js:21`) и квитанции `receipts/<id>.json`
   (`src/install-receipts.js:26`). Весь каталог входит в защищённые корни
   деинсталлятора (`src/uninstall-exec.js:72-79`), поэтому удаление компонента не может
   стереть журнал.

## Инварианты

1. **Строка вывода скрипта, показанная в интерфейсе, есть и в файле — но ТОЛЬКО внутри
   `emitLine`.** Там `send(l)` и `logLine(l)` идут подряд, без условий между ними
   (`src/main.js:1274-1275`). Обратное неверно намеренно: строки-квитанции идут только в
   файл (`:1268-1269`). Шире `emitLine` инвариант не держится, и фактически работающий
   разрыв один — renderer-side:
   - **renderer пишет на экран мимо файла.** Одиннадцать сообщений он рисует своей
     `appendLog()` (`src/renderer/app.js:1569`, `:1582`, `:1611`, `:1636`, `:1657`,
     `:1705`, `:1709`, `:1714`, `:1724`, `:1733`, `:1906`), а `logToFile` вызывается
     только из main (`src/main.js:937`, `:3278`) — в файле этих строк нет вовсе;
   - **vendor-first в самом main пишет РАЗНЫЕ тексты, но ветка мёртвая.** В ветке
     `} else if (declared && useBundled) {` (`src/main.js:992-995`) на экран уходит
     `[локально] «git» уже вшит в установщик — докачка не нужна.` (`:992`), а в файл —
     `vendor-first: git (уже вшит в установщик) — download пропущен.` (`:993`).
     Расхождение текстов в коде реально, но как разрыв инварианта оно не проявляется:
     ветка требует ОБА условия — `declared = compRemote.get(id)` (`:969`) и
     `useBundled = vendorHasArtifact || isOfflineEdition()` (`:987`), — а ни в одной из
     трёх конфигураций, существующих в репозитории, они вместе не выполняются.
     `loadRemoteMaps()` (`src/main.js:630-653`) кладёт в `compRemote` только два класса:
     явный `c.remote && c.remoteId` из `components.json` (`:643-644`) либо lite-авто-remote
     `lite && ids.has(c.id) && !BUNDLED_ONLY.has(c.id)` (`:645-646`). В `components.json`
     17 компонентов, и ни у одного нет ни `remote`, ни `remoteId` → в офлайн-издании
     `declared` всегда `undefined` (это же говорит комментарий `src/main.js:657-658`).
     В lite-издании `declared` есть, но `tools/build-lite.js` вшивает только
     `checksums.json`, `apps/uv`, `course/vibecoding-course.zip` (`LITE_KEEP_WIN`
     `:45-49`) — на macOS вместо `apps/uv` идут `apps/uv-macos-*.tar.gz`, плюс
     `licenses` (`LITE_KEEP_MAC` `:55-60`); артефакты ровно тех компонентов, что стали авто-remote,
     из vendor вырезаны, поэтому `vendorHasArtifact` (`src/main.js:976`) там false, а
     `offlineEdition` lite-сборка выставляет в false (`tools/build-lite.js:320`).
     В самом репозитории `config.json` не содержит ни `offlineEdition`, ни `edition`,
     значит и dev-прогон даёт пустой `compRemote`.
2. **Файл открывается один раз на процесс.** `fs.openSync` вызывается только под
   `if (logFd === null)` (`src/main.js:186`); дальше — только `fs.writeSync` (`:185`).
   Тест «журнал на диске: дескриптор открыт один раз, а не на каждую строку» гоняет саму
   функцию в `vm`-песочнице с подменённым `fs` и считает вызовы: 4000 строк → 4000
   `writeSync` и ровно 1 `openSync`.
3. **Сбой записи не глушит журнал навсегда и не роняет установку.** В `catch` дескриптор
   закрывается и обнуляется (`src/main.js:188-192`), исключение не пробрасывается. Тот же
   тест проверяет поведенчески: после подложенного `EBADF` — один `closeSync`, следующая
   строка даёт второй `openSync` и записывается.
4. **Каждая строка датирована и подписана компонентом.** Префикс
   `'[' + new Date().toISOString() + '] [' + id + '] '` (`src/main.js:187`).
5. **Журнал дописывается, а не перезаписывается.** Флаг открытия — `'a'`
   (`src/main.js:186`); кода усечения, ротации или удаления файла в репозитории нет.
6. **В dry-run на диск не пишется ничего.** `logLine` гейтится `isDryRun` в обоих
   обработчиках (`src/main.js:937`, `:3278`). Держит тест «P1-8 main.js: dry-run — БЕЗ
   докачки и БЕЗ записи install.log», сверяющий обе строки дословно регуляркой.
7. **`~/.hamidun-setup` не может стать целью удаления.** Каталог в `protectedRoots`
   (`src/uninstall-exec.js:72-79`); `checkTarget` отказывает и на сам каталог, и на всё
   внутри него. Держит тест «guard: сам ~/.claude, всё внутри него, дом, предок дома,
   ~/CLAUDE.md, ~/.hamidun-setup → отказ».
8. **Кнопка «Показать лог» открывает ровно журнал, а не то, что попросил renderer.**
   `open-path` сравнивает `path.resolve(p)` с `path.resolve(LOG_PATH)` и двумя другими
   разрешёнными целями (`src/main.js:1520-1521`); несовпадение → `bad-path`.
9. **Путь к журналу renderer не конструирует.** Он приходит из main через `bootstrap`
   (`src/main.js:541` → `src/renderer/app.js:69`), а кнопка рисуется только при непустом
   `STATE.logPath` (`:2121`).

## Что ломается, если инвариант нарушить

1. Человек присылает в поддержку файл, в котором нет той самой строки с ошибкой,
   которую он видел на экране. Для провалов докачки и проверки подлинности теряется
   только человеческая формулировка — причина в файле есть (`src/main.js:1052`, `:1047`).
   А отказ среды (`src/renderer/app.js:1705`; `return` в `src/main.js:1024-1029`
   срабатывает до `logLine` на `:1033`) не оставляет в файле ничего: по нему выходит, что
   этап докачки даже не начинался. Разбор идёт по неполным данным и заканчивается «у нас
   всё зелёно».
2. Возврат к `appendFileSync` — это открытие/запись/закрытие файла на каждой из десятков
   тысяч строк pip и npm в главном процессе. Окно перестаёт откликаться на кликах и
   перерисовке; со стороны человека это «установщик завис», и он закрывает окно посреди
   установки.
3. Без сброса дескриптора одна случайная ошибка записи (файл переименовали, антивирус
   подержал хендл) убивает журналирование до конца сессии — молча. Человек нажимает
   «Показать лог» и видит файл, обрывающийся на середине, без всякого признака, что
   дальше запись просто не велась. Без `try/catch` было бы хуже: исключение из
   журналирования уронило бы саму установку.
4. Без времени нельзя понять, что шаг стоял 40 минут, а не упал мгновенно; без id
   компонента вывод трёх параллельных шагов сливается в неразделимую кашу — поддержка
   не отличит ошибку `pydeps` от ошибки `vscode`.
5. Открытие с усечением стёрло бы журнал предыдущего запуска. Ровно тот случай, когда он
   и нужен: человек уже перезапустил установщик «на всякий случай», и первопричина
   осталась только в старом файле.
6. В dry-run (проверочный прогон) на машине человека появляется файл и каталог, которых
   он не просил, — обещание «ничего не трогаем» нарушено, а следы прогона путаются с
   реальной установкой.
7. Удаление компонента унесло бы вместе с собой журнал и квитанции — и разбирать
   неудачное удаление стало бы нечем ровно в тот момент, когда это нужнее всего.
8. `open-path` работает в elevated-процессе: пропущенный чужой путь означает запуск
   произвольного файла (например, подложенного в user-writable каталог `.exe`) с правами
   администратора. Кнопка поддержки превращается в вектор эскалации.
9. Если renderer сам собирает путь, он рано или поздно разойдётся с тем, куда реально
   пишет main (другой домашний каталог при запуске под другой учёткой) — кнопка откроет
   пустоту или чужой файл.

## Границы

- Журнал покрывает только два обработчика: `run-component` и `uninstall-component`.
  Старт приложения, `bootstrap`, `detect-user-warning`, `detect-state`, `probe-remote`
  (`src/main.js:678`), `send-telemetry`, `nomad-set-key`, `save-credentials`,
  `mac-selfheal` в файл не пишут ничего. Если человек не дошёл до нажатия «Установить»,
  файла может не быть вовсе.
- Ротации, верхней границы размера и удаления старых записей нет: файл растёт от запуска
  к запуску. Кода, который бы его чистил, в репозитории нет.
- Сообщения, которые renderer сочиняет сам, в файл не попадают: `logToFile` вызывается
  только из main (`src/main.js:937`, `:3278`), а одиннадцать вызовов `appendLog()` в
  `src/renderer/app.js` (`:1569`, `:1582`, `:1611`, `:1636`, `:1657`, `:1705`, `:1709`,
  `:1714`, `:1724`, `:1733`, `:1906`) рисуют строку только на экране. Человек видит их,
  поддержка в присланном файле — нет.
- Содержимое НЕ обезличивается. `scrubText` из `src/uid-telemetry.js` применяется только
  к телеметрии, уходящей на сервер (`src/main.js:1486`); в `logToFile` он не вызывается
  (`src/main.js:183-193`).
  В файл попадает сырой вывод скриптов — с домашним каталогом, именем пользователя и
  всем, что печатают pip/npm/git. Это осознанно: файл локальный и отправляет его человек
  сам, — но перед отправкой он не вычищен.
- Отправка файла в поддержку не автоматизирована: установщик его только открывает
  (`shell.openPath`), приложить к письму человек должен сам.
- Дескриптор не закрывается явно при выходе: в `window-all-closed` и `before-quit`
  (`src/main.js:381-387`) вызываются `killChildren` и `cleanupAllSecureDirs`, закрытия
  `logFd` там нет. Практически это безопасно, потому что `fs.writeSync` пишет
  синхронно и буфера в пользовательском пространстве не держит, но «закрыть за собой»
  код не делает.
- Одновременная запись двух экземпляров установщика в один файл не рассматривается:
  единственность процесса держит отдельный механизм single-instance (`app.on('second-instance')`,
  `src/main.js:353`).

## Риски и открытые вопросы

- **Ссылка инвентаря `src/main.js:1937` не относится к этой фиче.** По этому адресу —
  строка комментария `// в Finder. Пустой клик — худший из возможных исходов.` внутри
  macOS-ветки функции `launchVsCodeOn` (открытие папки курса в редакторе); сама функция
  кончается `return false;` на `:1943` и закрывающей скобкой на `:1944`. Ни `logToFile`,
  ни `logFd`, ни `LOG_PATH` там не упоминаются; поиск по всему файлу даёт `logFd` только
  в строках 180, 184 и 189. Ссылку в `docs/specs/_features.json`
  (`codeRefs.raw = "src/main.js:171-193,1937"`) следует исправить.
- **Деградация на полном диске не отличается от протухшего дескриптора.** Ветка `catch`
  одна на все ошибки (`src/main.js:188-192`). При `ENOSPC` каждая строка будет закрывать
  и переоткрывать файл — то есть поведение вернётся ровно к тому дорогому режиму
  «открытие на строку», ради ухода от которого дескриптор и удерживается. Отдельной
  обработки этого случая в коде нет.
- **Неограниченный рост файла.** Не подтверждено кодом никакого предела: ни счётчика
  байт, ни `statSync(LOG_PATH)`, ни усечения. При многократных перезапусках установки с
  обильным выводом pip/npm файл станет тяжёлым для отправки в поддержку.
- **У `open-path` нет теста.** Поиск по `test/run-tests.js` не находит ни `open-path`,
  ни `openPath`, ни `bad-path`. Аллоулист (`src/main.js:1520-1521`) — граница доверия
  elevated-процесса, и сейчас её удерживает только код, без проверки.
- **Нет теста на связку `bootstrap.logPath` → кнопка.** Что renderer получает путь и
  открывает именно его, тестами не подтверждено; проверены только сама запись в файл и
  гейт dry-run.
- **Сырые возвраты каретки попадают в файл.** Разбиение потока идёт по `/\r?\n/`
  (`src/main.js:1287`, и то же в `flush` — `:1289`), поэтому полоска прогресса,
  перерисовывающая строку одиночным `\r`, уходит в файл одной длинной строкой с
  внутренними CR: `logToFile` (`src/main.js:183-193`) с `\r` ничего не делает. Для
  интерфейса это отдельно вычищено (`src/renderer/app.js:1347-1355`, тест «журнал: строка
  с возвратом каретки не стирает предыдущую» — `test/run-tests.js:7460`); для файла — нет.
  На читаемость в блокноте это влияет, данные не теряются.
