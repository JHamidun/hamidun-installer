# Журнал установки на диске

- **Раздел:** Сопутствующее
- **Код:** `src/main.js:169-191`, `src/main.js:513-560`, `src/main.js:875-935`, `src/main.js:1248-1318`, `src/main.js:1500-1517`, `src/main.js:3243-3277`, `src/preload.js:28`, `src/renderer/app.js:1311-1322`, `src/renderer/app.js:2121`, `src/renderer/app.js:2442`, `src/uninstall-exec.js:72-79`
- **Тесты:** «журнал на диске: дескриптор открыт один раз, а не на каждую строку», «P1-8 main.js: dry-run — БЕЗ докачки и БЕЗ записи install.log», «guard: сам ~/.claude, всё внутри него, дом, предок дома, ~/CLAUDE.md, ~/.hamidun-setup → отказ»

## Что обещает человеку

Всё, что установщик написал на экране во время установки или удаления компонента,
одновременно дописывается в один текстовый файл `~/.hamidun-setup/install.log`. Когда
что-то пошло не так, человеку не нужно ничего выделять мышкой, скроллить назад и
собирать по кусочкам: на финишном экране есть кнопка «Показать лог для поддержки»
(`src/renderer/app.js:2121`), она открывает этот файл, и файл целиком отправляется в
поддержку.

Второе обещание — журнал не теряет то, что уже не помещается на экран. В интерфейсе
держится кольцо из последних 800 строк (`LOG_MAX_LINES`, `src/renderer/app.js:1322`),
потому что pip, uv и npm выдают десятки тысяч строк; полный вывод при этом живёт в
файле (комментарий там же, строки 1320-1321). Строка попадает на диск синхронно, в
момент появления, — то есть журнал остаётся читаемым и после падения установщика.

## Как работает

1. **Пути.** `LOG_DIR = ~/.hamidun-setup`, `LOG_PATH = <LOG_DIR>/install.log` — считаются
   один раз при загрузке модуля из `os.homedir()` (`src/main.js:172-173`). Платформенного
   ветвления нет: на Windows и macOS путь строится одинаково через `path.join`.
2. **Запись.** `logToFile(id, line)` (`src/main.js:181-191`):
   при первой строке создаёт каталог (`fs.mkdirSync(..., {recursive:true})`, флаг
   `logDirReady`), при первой строке открывает файл `fs.openSync(LOG_PATH, 'a')` и держит
   дескриптор в `logFd`, дальше на каждую строку делает только `fs.writeSync`. Формат
   строки: `[<ISO-время>] [<id компонента>] <строка>\n`.
3. **Почему дескриптор удерживается.** Комментарий в коде (`src/main.js:175-179`) прямо
   называет причину: `fs.appendFileSync` открывал и закрывал файл на КАЖДОЙ строке, а
   строк за установку десятки тысяч, и всё это синхронные вызовы в главном процессе,
   который одновременно качает насос сообщений окна.
4. **Ветка ошибки.** Любое исключение внутри `logToFile` ловится (`src/main.js:186-190`):
   если дескриптор был открыт, он закрывается и `logFd` сбрасывается в `null`, поэтому
   следующая строка откроет файл заново. Наружу ошибка не выходит — журналирование не
   может уронить установку.
5. **Кто зовёт.** Два IPC-обработчика, и только они:
   - `run-component` (`src/main.js:875`) объявляет `logLine` (`:935`);
   - `uninstall-component` (`src/main.js:3243`) объявляет такой же `logLine` (`:3270`) и
     поверх него `say = (line) => { send(line); logLine(line); }` (`:3277`).
6. **Что именно пишется при установке.** Обёртка `emitLine` (`src/main.js:1258-1266`)
   разбирает поток stdout/stderr дочернего процесса построчно (`mkLineReader`,
   StringDecoder — чтобы не рвать кириллицу на границе чанка) и:
   - строку-квитанцию `HM-RECEIPT …` пишет ТОЛЬКО в файл и в интерфейс не отдаёт
     (`:1260-1261`);
   - остальные строки отдаёт и в интерфейс (`send`), и в файл (`logLine`).
   Помимо вывода скрипта в файл идут служебные отметки: `=== start ===` (`:1224`),
   `[ERROR] spawn failed: …` (`:1241`), `[ERROR] <message>` от `child.on('error')`
   (`:1311`), предупреждение сторожа молчащего шага раз в 10 минут (`:1300-1305`),
   `=== exit code: N ===` (`:1318`), строки этапа докачки
   `=== fetch-remote start/result ===` (`:1025`, `:1042`) и объяснение неуспеха
   (`:1387-1397`).
7. **Ветвление dry-run.** `isDryRun` считается авторитетно: `process.env.HM_DRY_RUN` ИЛИ
   подсказка из renderer (`src/main.js:933`, аналогично `:3268`). При dry-run `logLine`
   не вызывает `logToFile` вовсе — на диске не остаётся следов (`:934-935`, `:3269-3270`).
8. **Как файл попадает к человеку.** `bootstrap` возвращает в renderer поле
   `logPath: LOG_PATH` (`src/main.js:539`); renderer кладёт его в `STATE.logPath`
   (`src/renderer/app.js:69`), рисует кнопку только если путь непустой (`:2121`) и по
   клику зовёт `window.installer.openPath(STATE.logPath)` (`:2442`), то есть IPC
   `open-path` из `src/preload.js:28`. Обработчик `open-path` (`src/main.js:1500-1517`)
   не доверяет renderer'у и пропускает только три цели: ровно `LOG_PATH`, памятку
   «Что дальше — Hamidun.html» на рабочем столе и файлы внутри ресурсов установщика;
   всё прочее — `{ok:false, error:'bad-path'}`.
9. **Соседи по каталогу.** В том же `~/.hamidun-setup` живут манифест `installed.json`
   (`src/install-manifest.js:21`) и квитанции `receipts/<id>.json`
   (`src/install-receipts.js:26`). Весь каталог входит в защищённые корни
   деинсталлятора (`src/uninstall-exec.js:72-79`), поэтому удаление компонента не может
   стереть журнал.

## Инварианты

1. **Строка, показанная в интерфейсе, есть и в файле.** `emitLine` вызывает `send(l)` и
   `logLine(l)` подряд, без условий между ними (`src/main.js:1262-1265`). Обратное неверно
   намеренно: строки-квитанции идут только в файл (`:1260-1261`).
2. **Файл открывается один раз на процесс.** `fs.openSync` вызывается только под
   `if (logFd === null)` (`src/main.js:184`); дальше — только `fs.writeSync` (`:185`).
   Тест «журнал на диске: дескриптор открыт один раз, а не на каждую строку» гоняет саму
   функцию в `vm`-песочнице с подменённым `fs` и считает вызовы: 4000 строк → 4000
   `writeSync` и ровно 1 `openSync`.
3. **Сбой записи не глушит журнал навсегда и не роняет установку.** В `catch` дескриптор
   закрывается и обнуляется (`src/main.js:186-190`), исключение не пробрасывается. Тот же
   тест проверяет поведенчески: после подложенного `EBADF` — один `closeSync`, следующая
   строка даёт второй `openSync` и записывается.
4. **Каждая строка датирована и подписана компонентом.** Префикс
   `'[' + new Date().toISOString() + '] [' + id + '] '` (`src/main.js:185`).
5. **Журнал дописывается, а не перезаписывается.** Флаг открытия — `'a'`
   (`src/main.js:184`); кода усечения, ротации или удаления файла в репозитории нет.
6. **В dry-run на диск не пишется ничего.** `logLine` гейтится `isDryRun` в обоих
   обработчиках (`src/main.js:935`, `:3270`). Держит тест «P1-8 main.js: dry-run — БЕЗ
   докачки и БЕЗ записи install.log», сверяющий обе строки дословно регуляркой.
7. **`~/.hamidun-setup` не может стать целью удаления.** Каталог в `protectedRoots`
   (`src/uninstall-exec.js:72-79`); `checkTarget` отказывает и на сам каталог, и на всё
   внутри него. Держит тест «guard: сам ~/.claude, всё внутри него, дом, предок дома,
   ~/CLAUDE.md, ~/.hamidun-setup → отказ».
8. **Кнопка «Показать лог» открывает ровно журнал, а не то, что попросил renderer.**
   `open-path` сравнивает `path.resolve(p)` с `path.resolve(LOG_PATH)` и двумя другими
   разрешёнными целями (`src/main.js:1507-1511`); несовпадение → `bad-path`.
9. **Путь к журналу renderer не конструирует.** Он приходит из main через `bootstrap`
   (`src/main.js:539` → `src/renderer/app.js:69`), а кнопка рисуется только при непустом
   `STATE.logPath` (`:2121`).

## Что ломается, если инвариант нарушить

1. Человек присылает в поддержку файл, в котором нет той самой строки с ошибкой,
   которую он видел на экране. Разбор идёт по неполным данным и заканчивается «у нас всё
   зелёно».
2. Возврат к `appendFileSync` — это открытие/запись/закрытие файла на каждой из десятков
   тысяч строк pip и npm в главном процессе. Окно перестаёт откликаться на кликах и
   перерисовке; со стороны человека это «установщик завис», и он закрывает окно посреди
   установки.
3. Без сброса дескриптора одна случайная ошибка записи (файл переименовали, антивирус
   подержал хендл) убивает журналирование до конца сессии — молча. Человек нажимает
   «Показать лог» и видит файл, обрывающийся на середине, без всякого признака, что
   дальше запись просто не велась. Без `try/catch` было бы хуже: исключение из
   журналирования уронило бы саму установку.
4. Без времени нельзя понять, что шаг стоял 40 минут, а не упал мгновенно; без id
   компонента вывод трёх параллельных шагов сливается в неразделимую кашу — поддержка
   не отличит ошибку `pydeps` от ошибки `vscode`.
5. Открытие с усечением стёрло бы журнал предыдущего запуска. Ровно тот случай, когда он
   и нужен: человек уже перезапустил установщик «на всякий случай», и первопричина
   осталась только в старом файле.
6. В dry-run (проверочный прогон) на машине человека появляется файл и каталог, которых
   он не просил, — обещание «ничего не трогаем» нарушено, а следы прогона путаются с
   реальной установкой.
7. Удаление компонента унесло бы вместе с собой журнал и квитанции — и разбирать
   неудачное удаление стало бы нечем ровно в тот момент, когда это нужнее всего.
8. `open-path` работает в elevated-процессе: пропущенный чужой путь означает запуск
   произвольного файла (например, подложенного в user-writable каталог `.exe`) с правами
   администратора. Кнопка поддержки превращается в вектор эскалации.
9. Если renderer сам собирает путь, он рано или поздно разойдётся с тем, куда реально
   пишет main (другой домашний каталог при запуске под другой учёткой) — кнопка откроет
   пустоту или чужой файл.

## Границы

- Журнал покрывает только два обработчика: `run-component` и `uninstall-component`.
  Старт приложения, `bootstrap`, `detect-user-warning`, `detect-state`, `probe-remote`
  (`src/main.js:676`), `send-telemetry`, `nomad-set-key`, `save-credentials`,
  `mac-selfheal` в файл не пишут ничего. Если человек не дошёл до нажатия «Установить»,
  файла может не быть вовсе.
- Ротации, верхней границы размера и удаления старых записей нет: файл растёт от запуска
  к запуску. Кода, который бы его чистил, в репозитории нет.
- Содержимое НЕ обезличивается. `scrubText` из `src/uid-telemetry.js` применяется только
  к телеметрии, уходящей на сервер (`src/main.js:1476`); в `logToFile` он не вызывается.
  В файл попадает сырой вывод скриптов — с домашним каталогом, именем пользователя и
  всем, что печатают pip/npm/git. Это осознанно: файл локальный и отправляет его человек
  сам, — но перед отправкой он не вычищен.
- Отправка файла в поддержку не автоматизирована: установщик его только открывает
  (`shell.openPath`), приложить к письму человек должен сам.
- Дескриптор не закрывается явно при выходе: в `window-all-closed` и `before-quit`
  (`src/main.js:379-385`) вызываются `killChildren` и `cleanupAllSecureDirs`, закрытия
  `logFd` там нет. Практически это безопасно, потому что `fs.writeSync` пишет
  синхронно и буфера в пользовательском пространстве не держит, но «закрыть за собой»
  код не делает.
- Одновременная запись двух экземпляров установщика в один файл не рассматривается:
  единственность процесса держит отдельный механизм single-instance (`app.on('second-instance')`,
  `src/main.js:351`).

## Риски и открытые вопросы

- **Ссылка инвентаря `src/main.js:1935` не относится к этой фиче.** По этому адресу
  находится `return false;` — последняя строка функции `launchVsCodeOn` (открытие папки
  курса в редакторе). Ни `logToFile`, ни `logFd`, ни `LOG_PATH` там не упоминаются;
  поиск по всему файлу даёт `logFd` только в строках 180, 184 и 189. Ссылку в
  `docs/specs/_features.json` следует исправить.
- **Деградация на полном диске не отличается от протухшего дескриптора.** Ветка `catch`
  одна на все ошибки (`src/main.js:186-190`). При `ENOSPC` каждая строка будет закрывать
  и переоткрывать файл — то есть поведение вернётся ровно к тому дорогому режиму
  «открытие на строку», ради ухода от которого дескриптор и удерживается. Отдельной
  обработки этого случая в коде нет.
- **Неограниченный рост файла.** Не подтверждено кодом никакого предела: ни счётчика
  байт, ни `statSync(LOG_PATH)`, ни усечения. При многократных перезапусках установки с
  обильным выводом pip/npm файл станет тяжёлым для отправки в поддержку.
- **У `open-path` нет теста.** Поиск по `test/run-tests.js` не находит ни `open-path`,
  ни `openPath`, ни `bad-path`. Аллоулист (`src/main.js:1506-1511`) — граница доверия
  elevated-процесса, и сейчас её удерживает только код, без проверки.
- **Нет теста на связку `bootstrap.logPath` → кнопка.** Что renderer получает путь и
  открывает именно его, тестами не подтверждено; проверены только сама запись в файл и
  гейт dry-run.
- **Сырые возвраты каретки попадают в файл.** Разбиение потока идёт по `/\r?\n/`
  (`src/main.js:1277`), поэтому полоска прогресса, перерисовывающая строку одиночным
  `\r`, уходит в файл одной длинной строкой с внутренними CR. Для интерфейса это
  отдельно вычищено (`src/renderer/app.js`, тест «журнал: строка с возвратом каретки не
  стирает предыдущую»); для файла — нет. На читаемость в блокноте это влияет, данные не
  теряются.
