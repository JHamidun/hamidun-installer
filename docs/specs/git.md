## Что обещает человеку

После установки на компьютере есть рабочая команда `git`, и она уже настроена так, чтобы
не задавать вопросов. Пользователю не нужно ни выбирать компоненты в чужом установщике, ни
понимать, что такое ветка: в `components.json:11-12` обещание сформулировано словами
«хранит историю проекта и позволяет откатывать изменения. Claude пользуется ей сам — тебе
учить её не нужно». Компонент включён по умолчанию (`"default": true`) и не требует прав
администратора отдельно (`"needsAdmin": false`).

Второе обещание — что установка не превратится в диалог. На Windows Git ставится тихо
(`/VERYSILENT /NORESTART /SP- /SUPPRESSMSGBOXES`), на macOS основной путь вообще не открывает
системных окон Apple. Сразу после установки скрипт задаёт дружелюбные умолчания: длинные пути,
ветка `main`, перевод строк и заглушка имени/почты — чтобы первый же `git commit`, который
сделает Claude, не упал с вопросом «кто ты».

## Как работает

Оркестрация одинакова для всех компонентов. `scriptFor(id)` (`src/main.js:569-573`) собирает
путь `scripts/windows/git.ps1` на win32 и `scripts/macos/git.sh` на остальных платформах;
скрипту передаются `HM_VENDOR` (`src/main.js:1127`) и, в холостом прогоне, `HM_DRY_RUN='1'`
(`src/main.js:1156`). На Windows установщик запущен от администратора —
`package.json:113` задаёт `"requestedExecutionLevel": "requireAdministrator"`, и весь разбор
безопасности в `git.ps1` исходит именно из этого.

**Откуда берутся байты.** `COMPONENT_VENDOR_ARTIFACT.git = 'apps/git-setup.exe'`
(`src/main.js:702`). Если этот файл лежит во вшитом vendor или издание помечено офлайновым, то
`useBundled` истинно (`src/main.js:979`) и докачка не запускается вовсе. В lite-издании
`loadRemoteMaps` (`src/main.js:638-647`) автоматически считает git remote-компонентом по записи
в реестре, и main скачивает архив из `remote-components.json`: для win32 — запись `"remoteId":
"git"` с `installRelPath: scripts/windows/git.ps1` и `gatedFiles: { "git-setup.exe": "af12577d…" }`,
для darwin — `"Git for macOS (dugite, arm64+x64)"` с двумя gated-файлами
`git-macos-arm64.tar.gz` и `git-macos-x64.tar.gz` и `installRelPath: scripts/macos/git.sh`.
Скачанный staging становится `HM_VENDOR`, и туда же копируется вшитый `checksums.json`
(`src/main.js:1070-1076`) — иначе второй гейт целостности внутри скрипта не сработал бы.
Git входит в `SCRIPT_ONLINE_FALLBACK` (`src/main.js:742`): провал докачки не роняет компонент
сразу, а пускает скрипт с пустым vendor, чтобы тот ушёл в winget/прямую загрузку; при этом
`fetchFellBack` помнит причину, и «нечего ставить» уже не будет засчитано как успех.

**Windows, `scripts/windows/git.ps1`.** Скрипт дот-сорсит `_verify.ps1` (`Confirm-HmArtifact`)
и `_deelev.ps1` (`New-HmSecureStagingDir`, `Remove-HmSecureStagingDir`, `Test-HmTrustedSigner`),
затем читает `$DRY = [bool]$env:HM_DRY_RUN` (строка 26).

1. Строка 57 — `Get-Command git`. Git уже есть: в dry-run печатается «[dry-run] Git уже
   установлен — без изменений» и `exit 0`; в боевом прогоне вызывается `Set-HmGitDefaults`
   и `exit 0`. Комментарий строк 55-56 объясняет, почему выход в dry-run обязателен: иначе
   холостой прогон проваливался бы в install-ветку и winget переустанавливал бы Git.
2. Ветка 1, офлайн (строки 59-63). `$env:HM_VENDOR\apps\git-setup.exe` существует →
   `Confirm-HmArtifact $local` сверяет SHA-256 и размер с `$HM_VENDOR/checksums.json` и при
   любом расхождении делает `exit 1`; только после этого
   `Start-Process … '/VERYSILENT','/NORESTART','/SP-','/SUPPRESSMSGBOXES' -Wait`.
3. Ветка 2, winget (строки 64-66). Вшитого файла нет, но `winget` в PATH →
   `winget install -e --id Git.Git --silent --accept-package-agreements --accept-source-agreements`.
   Код возврата winget не проверяется — результат оценивается общей проверкой на строке 116.
4. Ветка 3, прямая загрузка (строки 67-111). Ни файла, ни winget. Скрипт создаёт
   Admins-only кэш `New-HmSecureStagingDir -ProgramData … -Icacls … -Elevated $true`; если
   кэш создать не удалось — печатает «Не удалось создать защищённый кэш…» и `exit 1`.
   Дальше `Invoke-RestMethod https://api.github.com/repos/git-for-windows/git/releases/latest`
   (`User-Agent: hamidun-setup`, `-TimeoutSec 60`), выбор ассета по маске `64-bit\.exe$`,
   `Invoke-WebRequest … -TimeoutSec 600`. Любая ошибка сети → снос кэша + `exit 1`.
   Перед запуском — `Test-HmTrustedSigner` (`_deelev.ps1:375`): пустая строка означает
   «доверен», иначе печатается «БЕЗОПАСНОСТЬ: подпись установщика Git не подтвердилась» и
   установщик НЕ запускается. В конце ветки кэш сносится `Remove-HmSecureStagingDir`.
5. Строка 114 — в dry-run скрипт выходит здесь, ничего не изменив.
6. `Update-Path` (строки 5-24) пересобирает `$env:Path` из **машинного** PATH плюс
   `System32`, `%SystemRoot%`, `WindowsPowerShell\v1.0`, `OpenSSH`, `%ProgramFiles%\Git\cmd`,
   `%ProgramFiles%\Git\bin`, `%ProgramFiles%\nodejs`, `%ProgramFiles(x86)%\Git\cmd`.
   Пользовательский (HKCU) PATH не читается никогда — комментарий строк 6-10 называет причину:
   medium-процесс того же пользователя мог бы дописать туда каталог с подложенным `git`.
7. Строка 116 — финальная проверка `Get-Command git`: успех → `Set-HmGitDefaults` и `exit 0`,
   иначе «Git не обнаружен после установки» и `exit 1`.

`Set-HmGitDefaults` (строки 29-52) работает с `$ErrorActionPreference = 'Continue'` и обёрнута
в try/catch: сбой конфигурации печатает предупреждение, но установку не валит. Каждое значение
ставится только если пусто: `core.longpaths true`, `init.defaultBranch main`,
`core.autocrlf true`. Если пусто `user.name` — задаются сразу и `user.name` (из `$env:USERNAME`,
иначе `user`), и `user.email` (`<имя>@example.com`), с подсказкой поменять почту.

**macOS, `scripts/macos/git.sh`.** Файл начинается с `set -uo pipefail` (без `-e`) и подключает
`_lib.sh`.

1. Строка 34 — детект. Условие намеренно сложное: `have git` И (`command -v git` не равен
   `/usr/bin/git` ИЛИ `xcode-select -p` уже отвечает) И `git --version` отработал. Комментарий
   строк 32-33 объясняет: голый `/usr/bin/git`-шим на чистом маке сам открывает диалог установки
   Command Line Tools, поэтому его нельзя дёргать вслепую. Git уже есть → `set_git_defaults`, `exit 0`.
2. Ветка 1, вшитый портативный Git (строки 43-72). Берётся
   `${HM_VENDOR}/apps/git-macos-$(arch_tag).tar.gz`, где `arch_tag` (`_lib.sh:69`) даёт `arm64`
   для `uname -m = arm64` и `x64` иначе. `verify_artifact` (`_lib.sh:219`) — fail-closed SHA-256
   против `$HM_VENDOR/checksums.json`. Дальше: `rm -rf ~/.local/hamidun-git`, распаковка туда,
   требование исполняемого `$GROOT/bin/git`, снятие карантина `xattr -dr com.apple.quarantine`,
   и запись обёртки `~/.local/bin/git`, которая экспортирует `GIT_EXEC_PATH`,
   `GIT_TEMPLATE_DIR` и (если не задан) `GIT_CONFIG_SYSTEM` — комментарий строки 52 объясняет,
   что dugite собран без `RUNTIME_PREFIX`. Обёртка проверяется запуском `--version`; успех →
   `persist_local_bin_path` (`_lib.sh:177` — дописывает `export PATH="$HOME/.local/bin:$PATH"` в
   `~/.zshrc` и `~/.bash_profile` под маркером `HAMIDUN_LOCAL_BIN`), `set_git_defaults`, `exit 0`.
   Не распаковалось или обёртка не запустилась — обёртка удаляется, и управление уходит в ветку 2.
3. Ветка 2, Apple Command Line Tools (строки 79-118). Перед ней, если архива под нашу
   архитектуру нет, а под чужую есть, `hm_arch_note_missing` (`_lib.sh:97`) печатает честное
   объяснение, и скрипт добавляет «Поэтому Git поставлю через системные Command Line Tools от
   Apple — это дольше». Дальше `xcode-select --install`, подробная инструкция про известный баг
   macOS с оценкой «осталось 130 часов» и ссылку `https://developer.apple.com/download/all/`,
   затем поллинг `git_ready` (проверяет `/Library/Developer/CommandLineTools/usr/bin/git` либо
   `xcode-select -p` + `git --version`): 90 итераций по `sleep 10`, то есть примерно 15 минут.
   Успех → `set_git_defaults`, `exit 0`; истёк лимит → «ОШИБКА: Git пока не установлен…», `exit 1`.

`set_git_defaults` (строки 6-29) ставит те же `core.longpaths true` и `init.defaultBranch main`,
но `core.autocrlf` здесь `input`, а не `true`. `user.name` и `user.email` проверяются и ставятся
**независимо друг от друга** — комментарий строк 17-18 прямо говорит, что у пользователя может
быть настроено только одно из двух.

**Сборка.** Вшитые артефакты кладут `tools/fetch-vendor.ps1` (строка 19 — скачивание
`git-setup.exe`; строка 551 — включение имени в контрольный список) и `tools/fetch-vendor-mac.sh`
(строки 555-556 — `chk_file` на оба архива, `arm64` и `x64`). Декларация архитектур —
`mac-arch-support.json`, где git объявлен `"kind": "perArch"` с шаблоном
`apps/git-macos-{arch}.tar.gz` и пометкой, что это «единственный тяжёлый компонент с честной
парой архивов — и единственный, который встал у ученика на Intel».

## Инварианты

1. **Вшитый `git-setup.exe` не запускается без совпадения SHA-256 и размера.**
   `scripts/windows/git.ps1:63` вызывает `Confirm-HmArtifact` до `Start-Process`;
   сама проверка — `scripts/windows/_verify.ps1:64-104`, при расхождении `exit 1`.
2. **Вшитый `git-macos-<arch>.tar.gz` не распаковывается без совпадения SHA-256.**
   `scripts/macos/git.sh:46` вызывает `verify_artifact` до `tar -xzf`; реализация —
   `scripts/macos/_lib.sh:219-246`, при расхождении `exit 1`.
3. **Отсутствие манифеста целостности — тоже отказ, а не пропуск проверки.**
   `_verify.ps1:73-82` и `_lib.sh:225-230`: нет `HM_VENDOR` или нет `checksums.json` → `exit 1`.
4. **Скачанный из интернета установщик Git запускается только с подтверждённой подписью,
   чья цепочка ведёт к корню в `LocalMachine\Root` и у чьего leaf есть EKU Code Signing.**
   `git.ps1:103-108` + `_deelev.ps1:375-434`. Не подтвердилась — `Start-Process` не выполняется.
5. **Скачивание идёт только в Admins-only каталог, а не в `%TEMP%`.**
   `git.ps1:80-86`: `New-HmSecureStagingDir … -Elevated $true`; каталог не создался — `exit 1`
   (`git.ps1:83-86`). DACL и владелец назначаются атомарно при создании (`_deelev.ps1:131-171`).
6. **Elevated-скрипт никогда не берёт PATH пользователя.** `Update-Path` (`git.ps1:5-24`)
   читает `[Environment]::GetEnvironmentVariable('Path','Machine')` и фиксированные
   админ-каталоги; обращения к `'User'` в файле нет.
7. **Все сетевые вызовы ограничены по времени.** `git.ps1:89` — `-TimeoutSec 60`,
   `git.ps1:92` — `-TimeoutSec 600`. Комментарий строк 71-72 называет причину:
   дефолтный `TimeoutSec=0` означает «ждать бесконечно».
8. **Ни один установочный вызов не может открыть окно.** Windows —
   `/VERYSILENT /NORESTART /SP- /SUPPRESSMSGBOXES` (`git.ps1:62,63,68,105`) и `--silent
   --accept-package-agreements --accept-source-agreements` (`git.ps1:66`); тест
   «Windows: установщики, САМИ запускающие приложение, идут БЕЗ -Wait» отдельно требует, чтобы
   в `git.ps1` каждая строка со `Start-Process … -Wait` несла тихий флаг.
9. **Dry-run не меняет систему.** `git.ps1` в каждой ветке печатает `WOULD:` вместо действия
   (строки 62, 65, 68) и выходит на строке 114 до `Update-Path`; `main.js:980-981` в dry-run
   не запускает и докачку.
10. **Умолчания git не затирают уже настроенное пользователем.** Каждое значение ставится
    только при пустом чтении: `git.ps1:33-49`, `git.sh:8-26`.
11. **Ошибка при выставлении умолчаний не валит установку компонента.**
    `git.ps1:30` (`$ErrorActionPreference = 'Continue'`) + try/catch на строках 31-51;
    в `git.sh` каждый вызов заканчивается `|| true` (строки 9, 12, 15, 22, 25).
12. **На macOS `/usr/bin/git`-шим не дёргается вслепую.** `git.sh:34` и `git.sh:98-102`
    проверяют `xcode-select -p` либо прямой путь бинаря CLT прежде, чем звать `git`.
13. **Ожидание Command Line Tools ограничено.** `git.sh:106` — цикл `while [ "$i" -lt 90 ]`
    с `sleep 10`; по исчерпании `exit 1` с текстом, объясняющим, что делать.
14. **Артефакт под каждую архитектуру Mac объявлен и гейтится на сборке.**
    `mac-arch-support.json` (секция `components.git`, `kind: perArch`) плюс
    `tools/fetch-vendor-mac.sh:555-556`; держат тесты
    «scripts/macos/*.sh: каждый $(arch_tag)-артефакт ОБЪЯВЛЕН в mac-arch-support.json» и
    «tools/fetch-vendor-mac.sh: у каждого perArch-артефакта гейт на ОБЕ арх».
15. **У git есть запись в реестре докачки для обеих платформ.** `remote-components.json` —
    win32-запись с `installRelPath: scripts/windows/git.ps1` и darwin-запись с
    `installRelPath: scripts/macos/git.sh`; win32-часть держит тест
    «lite: тяжёлые компоненты авто-remote по реестру; uv bundled-only».
16. **`gatedFiles` реестра и `vendor/checksums.json` согласованы по git-setup.exe.**
    Обе записи несут `af12577d0fdff74243a5988197aa49b957d5044edc17004f6ddf0768996f1dca`;
    `bytes: 65388144` в `checksums.json` совпадает с `components.json` `sizeBytes.win32`.
    Машинной сверки именно этой пары в тестах не нашёл — см. «Риски».
17. **Git — корень зависимостей конфига.** `components.json`: `config` требует
    `["git","node","claude"]`, `pydeps` требует `config`; поведение держат тесты
    «enableWithDeps: selecting "config" pulls in git+node» и
    «disableDependents: turning off git turns off config+pydeps».
18. **Провал докачки git не превращается в тихий «пропущено».** `SCRIPT_ONLINE_FALLBACK`
    содержит `git` (`src/main.js:742`), и `fetchFellBack` (`src/main.js:1053`) не даёт
    засчитать graceful-skip за успех.

## Что ломается, если инвариант нарушить

1. Человек молча получает под администратором чужой `.exe`, подсунутый вместо Git: установщик
   запущен elevated, и подменённый инсталлятор делает на машине что угодно.
2. То же на Mac: вместо портативного Git в `~/.local/bin/git` встаёт чужой бинарь, и дальше
   его выполняет каждая команда Claude — включая те, что ходят в репозитории пользователя.
3. Установка «проходит» на сборке без манифеста, и вся защита целостности становится
   декоративной: никто не заметит, что проверок фактически нет.
4. Классический privesc: медиум-малварь того же пользователя кладёт свой корень в
   `CurrentUser\Root`, получает `Status=Valid` и исполнение под админом — ровно сценарий,
   описанный в `_deelev.ps1:362-369`.
5. Скачивание в user-writable `%TEMP%` даёт окно подмены между загрузкой и запуском: файл
   проверен, а запущен уже другой.
6. Elevated-процесс исполняет `git.exe` из каталога, дописанного в пользовательский PATH без
   UAC. Пользователь этого не увидит: команда называется так же.
7. На плохом канале (а целевая аудитория — люди на домашнем интернете) установка виснет
   навсегда. Внешне это «установщик завис», и человек убивает его на середине.
8. Всплывает окно стороннего установщика, часто ЗА окном Hamidun Setup. Шаг стоит, пользователь
   видит зависший прогресс и не понимает, что от него хотят.
9. Холостой прогон (в том числе на чужой машине при отладке) переставляет Git и меняет
   пользовательский `~/.gitconfig` — то есть «проверка» становится изменением.
10. Пользователь с настроенной подписью коммитов и своей почтой получает коммиты от
    `user@example.com`; в командном репозитории это ломает авторство и правила ветвления.
11. Git встал, но одна неудачная строка `git config` красит весь компонент в ошибку —
    пользователь жмёт «Повторить» и переустанавливает то, что уже работает.
12. На чистом Mac всплывает диалог Apple «Установка ПО» там, где офлайн-путь его не требовал:
    ученик получает те самые «осталось 130 часов» вместо тихой установки за минуту.
13. Скрипт висит бесконечно, если установка CLT не идёт (человек закрыл окно Apple, нет сети):
    установщик выглядит намертво зависшим и не даёт поставить остальные компоненты.
14. Сборка уезжает с архивом только под Apple Silicon, и на Intel-маке git молча уходит в
    длинный путь через CLT — тот самый случай 07.08.2026, «Готово 1 · Ошибок 4 · Пропущено 2».
15. В lite-издании компонент нечем скачать: `pickEntry` вернёт `null`, и main отдаст
    «Нет сборки „git“ для платформы …» (`src/main.js:989`) — конфиг и pydeps не поставятся вслед.
16. Скачанный по реестру архив пройдёт первый гейт (sha всего zip), но второй
    (`Confirm-HmArtifact` по `checksums.json`) отвергнет содержимое, и компонент упадёт на
    ровном месте с текстом про подмену.
17. Пользователь снимает галку с Git и получает выбор, в котором конфиг «включён», но ставиться
    ему не на чем: `config.ps1` клонирует конфиг именно гитом.
18. Сеть отвалилась, докачка не удалась, скрипт честно сказал «нечего ставить» — и это
    засчиталось успехом. Человек уходит с зелёным экраном и без Git.

## Границы

- Компонент не выбирает версию Git и не обновляет уже установленный: любой найденный в PATH
  `git` считается достаточным (`git.ps1:57`, `git.sh:34`) — даже очень старый.
- Умолчания применяются только к `--global`. Настройки уровня system и репозитория не трогаются.
- `user.email` заполняется заглушкой `<имя>@example.com`. Это сознательная уступка ради того,
  чтобы первый коммит не упал; пользователю печатается подсказка поменять почту.
- Ничего не делается с ключами SSH, GPG-подписью, кредами и `credential.helper`. Защита от
  интерактивного запроса кредов живёт в другой фиче — в `config.ps1`/`config.sh` и
  `NONINTERACTIVE_ENV` в `src/main.js` (её покрывает тест «git НИКОГДА не спрашивает креды —
  иначе окно помощника вешает установку», который к `git.ps1`/`git.sh` не обращается).
- На macOS ветка CLT ставит не только Git, а весь набор Command Line Tools — это цена отказа
  от вшитого архива, а не желаемое поведение.
- Обёртка `~/.local/bin/git` перезаписывается безусловно (`git.sh:53-60`), как и каталог
  `~/.local/hamidun-git` (`git.sh:48` — `rm -rf`). Чужого содержимого по этим путям скрипт
  не ожидает.
- `persist_local_bin_path` правит только `~/.zshrc` и `~/.bash_profile`. Пользователи fish и
  прочих оболочек PATH не получат.
- Windows-ветка не проверяет код возврата winget и не различает «winget отказал» и «winget
  поставил» — вывод делается по факту наличия `git` после `Update-Path`.
- Компонент не удаляется: сценария отката установки Git в скриптах нет.

## Риски и открытые вопросы

- **Ни `git.ps1`, ни `git.sh` не покрыты проверкой синтаксиса.** Списки в `test/run-tests.js`
  (строки 884 и 898) перечисляют файлы поимённо, и git там нет — ни в PowerShell-`ParseFile`,
  ни в `bash -n`. BOM у `git.ps1` фактически на месте (проверил первые байты), но требование
  BOM для него тоже никем не проверяется, а без BOM Windows PowerShell 5.1 испортит всю
  кириллицу в выводе.
- **Функциональных тестов нет ни у одной из трёх Windows-веток и ни у одной из двух macOS.**
  Всё найденное покрытие — статическое: одна строчная проверка внутри теста
  «Windows: установщики, САМИ запускающие приложение, идут БЕЗ -Wait» плюс инварианты про
  архитектуры и реестр. Ни `Set-HmGitDefaults`, ни `set_git_defaults`, ни ветка winget, ни
  ветка прямой загрузки, ни путь dugite тестами не затронуты — сравните с `config.sh` и
  `nomad.sh`, у которых функциональные прогоны есть.
- **Сообщение dry-run противоречит поведению.** `git.ps1:114` печатает «[dry-run] Git:
  офлайн-ветка выбрана, без изменений» независимо от того, какая ветка сработала: та же строка
  выводится и после winget-ветки, и после ветки прямой загрузки. Диагностика dry-run в этих
  случаях вводит в заблуждение.
- **Расхождение Windows и macOS в `user.email`.** В `git.ps1:43-49` почта ставится только
  внутри проверки `user.name`: у пользователя с заданным именем и пустой почтой она останется
  пустой, и первый коммит упадёт. В `git.sh:21-26` это исправлено явно, с комментарием
  «каждый независимо». Похоже на неперенесённый на Windows фикс, но подтверждения (коммит,
  issue) в коде нет.
- **`core.autocrlf` различается по платформам:** `true` на Windows (`git.ps1:41`), `input` на
  macOS (`git.sh:15`). Для самого Git это норма, но в спеке фиксирую явно: одинаковыми их
  считать нельзя.
- **`core.longpaths` на macOS бессмысленен** — это Windows-настройка (`git.sh:8-10`).
  Вреда нет, но строка «Git-дефолты применены (longpaths, main, autocrlf=input)» обещает
  человеку то, чего на его системе не происходит.
- **Провал гейта подписи не даёт своего кода возврата.** `git.ps1:106-108` печатает причину и
  проваливается дальше к общей проверке, которая скажет обобщённое «Git не обнаружен после
  установки» и вернёт `exit 1`. Отличить «не скачалось», «подпись не подтвердилась» и
  «установилось, но не в PATH» по коду возврата снаружи нельзя.
- **Согласованность `remote-components.json` ↔ `vendor/checksums.json` по git-setup.exe я
  сверил руками** (обе стороны несут `af12577d…`), но теста, который держал бы эту пару, я не
  нашёл — искал по `gatedFiles`, `installRelPath` и `COMPONENT_VENDOR_ARTIFACT`. Разъедутся —
  lite-издание будет качать архив, чей внутренний файл не пройдёт второй гейт.
- **`components.json` `sizeBytes.darwin` = 63387151 не подтверждён кодом.** Для win32 число
  совпадает с `bytes` в `checksums.json`; для darwin вшитого манифеста в этом дереве нет
  (в `vendor/checksums.json` записей `git-macos-*` нет вовсе — это Windows-vendor), а в
  реестре у darwin-архива указан размер всего zip (123139118), то есть другая величина.
  Откуда взято 63387151 — не подтверждено.
- **Порядок веток на Windows жёстко зашит.** Если вшитый `git-setup.exe` есть, но повреждён,
  `Confirm-HmArtifact` делает `exit 1`, и до winget дело не доходит вообще. Задумано ли это
  как fail-closed или как недосмотр — по коду не определить: комментария на этот счёт нет.
