## Что обещает человеку

После установки в новом окне терминала работает команда `claude` — сам ИИ-агент, которому пишешь задачу словами. Компонент включён по умолчанию и требует Node.js (`components.json:70-73`), поэтому Node подтянется вместе с ним автоматически.

Главное обещание — не «файл положен», а «команда отвечает». Зелёная галочка в финальном чек-листе на Windows ставится по вердикту `works`, а вердикт выносит реальный запуск `claude --version` с нулевым кодом (финальная проба в `scripts/windows/claude.ps1`, перенос вердикта в чек-лист — в `scripts/windows/verify.ps1`) — с оговоркой, что вердикт читается из файла, пережившего прошлые прогоны (см. риск 8). Красная строка с объяснением, что делать, появляется только при ДОКАЗАННОМ отказе запуска (`broken`): `claude.ps1:397-403` и `311-313`. Если запустить не получилось (исход `unverified` — де-элевация не отчиталась), красной строки нет ни в одном месте: шаг печатает «OK: Claude Code CLI установлен (… проверить запуском де-элевированно не удалось)» и выходит с кодом 0 (`claude.ps1:435-439`), а чек-лист даёт `CHECK skip Claude CLI (установлен, запуск не проверен)` (`verify.ps1:118-122`). Это сознательный fail-open, он же описан в инварианте 1 и в «Границах». Обратная сторона обещания: если у тебя уже стоит рабочий `claude`, установщик его не тронет и не перетрёт (`scripts/windows/claude.ps1`, снимок `$preExisting`). И отвечает она не только в cmd: в PowerShell — терминале VS Code по умолчанию — `claude` упирался в политику выполнения скриптов (на клиентской Windows по умолчанию `Restricted`), и установщик теперь разрешает свои локальные скрипты для учётки (`CurrentUser = RemoteSigned`). Где политику задаёт компания или стоит `AllSigned`, он её не трогает, а в чек-листе появляется отдельная красная строка «Запуск claude в PowerShell» с советом набирать `claude.cmd`. Эти починки пользовательской среды (PATH пользователя и политика) делает одна общая функция `Repair-HmClaudeUserEnv` (`scripts/windows/_claudeenv.ps1`): её зовёт `claude.ps1` сразу после установки и скрытый шаг проверки `verify.ps1` — на КАЖДОМ запуске установщика. Это не лишнее: повторный запуск снимает галочку с уже найденного `claude`, и `claude.ps1` для таких людей не выполняется вовсе; без второго вызова починки до поставивших claude раньше не доходили бы.

## Как работает

Главный процесс подбирает скрипт по id компонента: `scripts/<windows|macos>/claude.<ps1|sh>` (`src/main.js:571-575`) и передаёт ему `HM_VENDOR` — корень вшитого vendor либо sha-проверенный staging докачки в lite-издании (`src/main.js:1103` — вычисление `vroot`, `src/main.js:1137` — сама передача `childEnv.HM_VENDOR = vroot`). Порядок установки топологический, поэтому `node` встаёт раньше `claude` (`src/renderer/deps.js:26-39`).

### Windows (`scripts/windows/claude.ps1`)

1. **Подготовка.** Форсится TLS 1.2 (строка 7), дот-сорсятся примитив де-элевации `_deelev.ps1` (строка 9) и общие помощники: `_userpath.ps1` (PATH пользователя) и `_claudeenv.ps1` (вердикты `checks.json`, политика PowerShell, `Repair-HmClaudeUserEnv`). `Update-Path` собирает PATH **только** из машинной ветки HKLM плюс фиксированные админ-owned каталоги (`System32`, `Program Files\Git\cmd`, `\bin`, `nodejs`); пользовательский HKCU PATH не читается никогда — комментарий называет это SECURITY #4.
2. **Снимок «до».** `Find-ClaudeBinary` (32-58) ищет по трём местам: `Get-Command claude` → `npm config get prefix` (`claude.cmd`/`claude.exe`/`claude`) → `%USERPROFILE%\.local\bin`. Найденный бинарь прогоняется через `Test-HmClaudeRuns`; вердикт `works` означает «уже стоит и отвечает» — офлайн-установка не запускается вовсе (196-205).
3. **Офлайн-ветка** (207-234). Условие входа: снимок не дал `works`, `$env:HM_VENDOR\npm-cache` существует, `npm` доступен. Команда: `npm install -g '@anthropic-ai/claude-code' --offline --cache $cache --no-audit --no-fund`. Код возврата запоминается (`$npmExit = $LASTEXITCODE`, 211) и **гейтит саму проверку запуском**: `Update-Path` → `Find-ClaudeBinary` → `Test-HmClaudeRuns` стоят внутри ветки `if ($npmExit -eq 0)` (212-216). При ненулевом коде проверки запуском не происходит вовсе — `else` (231-233) печатает «Офлайн-установка npm вернула код …» и управление уходит в онлайн-ветку (236). Обратное тоже верно: нулевой код сам по себе успехом не считается — успех даёт только проба (см. инвариант 1 про её единственное исключение).
4. **Проверка запуском** — `Test-HmClaudeRuns` (98-123). Она вызывает `Invoke-HmDeElevated $bin @('--version')`, то есть исполняет `claude` через одноразовую задачу планировщика с `RunLevel LeastPrivilege` и self-check на medium integrity `S-1-16-8192` (`_deelev.ps1:566-624`). Исходы три: `works` (Gate=medium, Code=0), `broken` (Gate=medium, код 1..255), `unverified` — если де-элевация не отчиталась, если пришёл служебный статус планировщика из списка `267008…267045` (112) или код вне диапазона 0..255 (121).
5. **Уборка нерабочей обёртки** (217-227). Только при `broken`, только если до прогона тут не было рабочего claude, и только по аллоулисту `Test-HmOurClaudeDir` (134-158): `%USERPROFILE%\.local\bin`, `%APPDATA%\npm` и фактический `npm config get prefix`. Удаляются шимы `claude`, `claude.cmd`, `claude.ps1`, `claude.exe` и пакет `node_modules\@anthropic-ai\claude-code`. Каталог вне аллоулиста — печатается «чужие файлы не трогаю» и возвращается `$false`.
6. **Онлайн-ветка** (236-252). `Invoke-RestMethod "https://claude.ai/install.ps1" -TimeoutSec 120 | Invoke-Expression`. При исключении — запасной шаг `npm install -g '@anthropic-ai/claude-code' --no-audit --no-fund` из онлайн-реестра (комментарий объясняет: claude.ai отдаёт из РФ 403, а registry.npmjs.org доступен). Если `npm` не найден — `exit 1`.
7. **Финал** (254-324). Повторный `Find-ClaudeBinary`; не нашли — `exit 1` без записи вердикта `claude` (вердикт `claude-ps` прошлого прогона сброшен в `n/a` ещё в самом начале скрипта, поэтому красной строки «Запуск claude в PowerShell» по давним данным не будет). Проба переиспользуется, если бинарь тот же. `broken` вне наших каталогов → отдельный текст «это твои файлы, удали свою установку» + `Write-HmCheck 'claude' 'broken'` + `exit 1`. `broken` в нашем каталоге → `exit 1`. Иначе общая функция `Repair-HmClaudeUserEnv` (`scripts/windows/_claudeenv.ps1`) дописывает каталог бинаря и `~/.local\bin` в PATH пользователя через `Add-HmUserPath` из `scripts/windows/_userpath.ps1` (сырое значение `REG_EXPAND_SZ` с `DoNotExpandEnvironmentNames`, дубль ищется по развёрнутой копии, после записи — рассылка `WM_SETTINGCHANGE`; PATH самого процесса не трогается). `~/.local\bin` пишется с `-AllowMissing`, даже если каталога ещё нет: при офлайн-установке через npm его создают позже шаг Nomad, uv или нативный установщик claude. Затем — PowerShell (п. 7а, та же функция), запись вердиктов `claude-ps` и `works`/`unverified` в `~/.hamidun-setup/checks.json` через temp+move и `exit 0`.
7а. **PowerShell и политика выполнения** (`Set-HmUserExecPolicy`, `Get-HmExecPolicyPlan` и `Test-HmClaudeViaPowerShell` лежат в `scripts/windows/_claudeenv.ps1`, общие с `verify.ps1`) — только если рядом с бинарём лежит `claude.ps1` (его кладёт `npm install -g`; у нативного `claude.exe` политика ни при чём). PowerShell из двух одноимённых шимов берёт `claude.ps1`, а на клиентской Windows политика по умолчанию `Restricted`: «Невозможно загрузить файл claude.ps1 … выполнение сценариев отключено». `Set-HmUserExecPolicy` читает области (`Get-ExecutionPolicy -List`; область `Process` не учитывается — её задал запуск самого скрипта), решение выносит чистая `Get-HmExecPolicyPlan`: групповая политика (`MachinePolicy`/`UserPolicy`) и `AllSigned` — не трогаем, только говорим набирать `claude.cmd`; итоговая `Restricted` (явная или по умолчанию) — `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, результат сверяется чтением области обратно; `LocalMachine` не трогается никогда. Затем `Test-HmClaudeViaPowerShell` прогоняет `claude --version` ТЕМ ЖЕ путём, что человек: де-элевированно `powershell.exe -EncodedCommand` без своей политики, с каталогом установки первым в PATH; код 197 — отказ загрузки `claude.ps1` (`UnauthorizedAccess`). Вердикт пишется отдельным фактом `claude-ps` (`works`/`blocked`/`broken`/`unverified`/`n/a`) и на вердикт `claude` не влияет. Из `verify.ps1` функция зовётся без пробы (де-элевации там нет, а запускать `claude` под администратором нельзя): при разрешённой политике вердикт `unverified`, при запрете — `blocked`.
8. **Чек-лист.** Секция Claude CLI в `verify.ps1` не судит по наличию файла: он читает `checks.json` и печатает `CHECK ok Claude CLI` только при `verdict = works`; `unverified` → `CHECK skip … (установлен, запуск не проверен)`; `broken` или отсутствие вердикта → `CHECK fail`. Вердикт `claude-ps` = `blocked` или `broken` даёт отдельную строку `CHECK fail Запуск claude в PowerShell` с советом набирать `claude.cmd`; `works`, `unverified`, `n/a` лишней строки не добавляют. Перед чек-листом `verify.ps1` выполняет блок починок профиля (границы — строки `# --- every-run repairs (B) ---` и `# --- end ---`): если галочки у `claude` в этом прогоне нет, бинарь найден на диске и прошлый вердикт не `broken`, он зовёт `Repair-HmClaudeUserEnv` (без пробы) и пишет `claude-ps`; красная строка берётся из этого свежего вердикта, а не из файла давнего прогона.
9. **Dry-run.** При `HM_DRY_RUN` обе ветки печатают строку «WOULD» и выходят с кодом 0 (209, 237) — ничего не ставится и вердикт не пишется.

### macOS (`scripts/macos/claude.sh`)

Логика зеркальная, но с тремя отличиями, каждое видно в коде:

- **Пользовательский prefix.** Всё ставится с `--prefix "$HOME/.local"` (66, 93): node из `.pkg` держит глобальный npm-prefix в `/usr/local` (root:wheel), и `npm -g` без sudo упал бы с EACCES.
- **Арх-гейт перед офлайн-путём** (41-51). Настоящий бинарь едет платформенным optional-пакетом `@anthropic-ai/claude-code-darwin-<arch>`; наличие **архива** (а не packument) проверяет `hm_npm_cache_has_tarball` (`_lib.sh:138-142`) по ключу cacache `"/<имя>/-/<имя>-"`. Нет архива под текущую арх — человеку сразу говорят, что этот компонент придётся качать из интернета.
- **Офлайн ставится закреплённая версия, а не latest** (`claude.sh:57-79`). Живой случай 23.09.2026 (Intel): в кеше лежали архивы 2.1.197, а закешированные метаданные называли latest 2.1.278 — `npm install --offline` без версии получал ENOTCACHED. Теперь `hm_claude_offline_version` (`_lib.sh:496-504`) выбирает самую новую версию, для которой в кеше есть ОБА архива — основной пакет и `claude-code-darwin-<arch>` той же версии, — и npm ставит `@anthropic-ai/claude-code@<версия>`. Пары нет — честное сообщение и онлайн.
- **Онлайн-путь не висит молча** (`claude.sh:113-147`). Сначала 20-секундная проба `claude.ai/install.sh`; отвечает — нативный установщик под сторожем `hm_run_with_timeout 600` (`hm_run_with_timeout` в `_lib.sh`: команда остаётся в группе процессов самого скрипта — без `set -m`, иначе SIGKILL группы, которым `main.js` снимает шаг при закрытии окна, её не достаёт, и остаётся сирота без потолка по времени; по таймауту сторож обходит потомков команды и снимает всё дерево — TERM, через 2 с KILL, код 124; TERM/INT/HUP, пришедшие самому скрипту, тоже снимают дерево, код 128+N); не отвечает (из России без VPN) — сразу npm с `registry.npmjs.org` под сторожем 900 с. Провал заканчивается советом включить VPN в режиме «весь компьютер». Раньше `curl --max-time 900 --retry 3` к claude.ai мог молчать около часа.
- **Финальный факт — новое окно Терминала** (`claude.sh:190-236`). Сам `claude` к этому моменту отвечает (`claude_install_ok`), поэтому вердикт `works` пишется ДО проверки окна и от неё не зависит. После `persist_local_bin_path` проверка `claude_new_terminal_gate` запускает `command -v claude && claude --version` в чистом окружении оболочкой входа человека (`hm_fresh_shell_run`, `_lib.sh`: `env -i`, zsh `-i -l`, bash `-l`) и различает «не находит» (код оболочки 41) и «находит, но не запускает» (42). Не находит — дописывает строку PATH в `~/.zprofile` (`persist_local_bin_zprofile`, `_lib.sh`) и проверяет снова. Не помогло — это НЕ провал компонента, а частичный успех: код 121 и одна последняя строка `ЧАСТИЧНО: claude установлен, но новый Терминал его не видит — выполни в Терминале: echo 'export PATH="$HOME/.local/bin:$PATH"' >> <файл> и открой новое окно` (≤ 240 знаков; `<файл>` — по оболочке входа, `hm_login_profile_name`: zsh → `~/.zprofile`, bash → `~/.bash_profile`, прочие → `~/.profile`); «находит, но не запускает» даёт свою строку `ЧАСТИЧНО: … в новом окне Терминала не запускается …`. Код 121, а не 1, нужен потому, что от claude зависят конфиг, курс и скрепка (`components.json`, `requires`), а за конфигом — Python-пакеты: красный шаг ронял бы их все каскадом из-за PATH в оболочке, а сам claude работает; поток засчитывает 121 как успех и рисует шаг жёлтым с этой строкой. Оболочка не zsh/bash или не ответила за 30 с — проверка пропускается с пояснением, установку это не валит. Живой случай 10.09.2026: отчёт ok=True при «zsh: command not found: claude».
- **Копия кеша в temp** (61-67). Vendor на маке лежит на образе только для чтения, а npm пишет в `--cache` даже в режиме `--offline`, поэтому кеш копируется в `mktemp -d` и получает `chmod -R u+w`.
- **Починка PATH на каждом прогоне** (`scripts/macos/touchup-claude-path.sh`). Компонент, уже отмеченный установленным, на повторном запуске снимается с галочки и `claude.sh` не выполняется, так что его собственная починка до тех, у кого claude уже стоит, не дотягивается. Поэтому есть автономный скрипт без сети (≤ 5 с, всегда код 0), который `verify.sh` зовёт на каждом прогоне (подключается отдельной правкой сборки): проверяются наш `~/.local/bin/claude` (если claude не выбран в этом прогоне — иначе его новое окно уже проверил `claude.sh` — и в `~/.hamidun-setup/checks.json` нет прошлого вердикта `broken`: сломанный claude не трогаем) и команда `nmd` Nomad из того же каталога (PATH для неё не пишет никто, кроме этого скрипта); ни того ни другого нет — молчит; новое окно находит всё нужное — молчит; не находит — дописывает PATH в профиль оболочки входа, проверяет снова и печатает ровно одну строку `ОБНОВЛЕНО: …` с названием того, что не находилось (`claude`, `nmd` или оба; если не помогло — с тем, что сделать руками); оболочка не zsh/bash, не ответила, профиль не записать — одна строка `[touchup-claude-path] пропущено: <причина>`. Проверка новым окном — это `command -v` в оболочке входа человека: сами `claude` и `nmd` не исполняются. Сухой прогон (`HM_DRY_RUN`) ничего не пишет и печатает одну строку `[dry-run] WOULD: …`. Общий контракт always-run скриптов (`hm_touchup_begin`/`_end` в `_lib.sh`) — автономность, идемпотентность, молчание при нечем заняться, никогда не ненулевой код.

Единый гейт `claude_install_ok` (21-31) стоит на всех путях — офлайн, `curl … install.sh | bash`, npm-фолбэк и финал (70, 91, 94, 110). При провале он удаляет ровно свои артефакты: `~/.local/bin/claude` и `~/.local/lib/node_modules/@anthropic-ai/claude-code`. На успехе `persist_local_bin_path` (`_lib.sh:177-194`) дописывает `~/.local/bin` в `~/.zshrc` и `~/.bash_profile`.

### Откуда берётся офлайн-кеш

Сборкой: `tools/fetch-vendor.ps1:68-88` делает `npm install '@anthropic-ai/claude-code' --prefix <tmp> --cache vendor\npm-cache` и затем обязательный `tools/prune-npm-cache.js` — без чистки каждый релиз оставлял в кеше предыдущий архив (~80 МиБ), и к 11.08.2026 накопилось 13 версий = 1005 МиБ. На маке (`tools/fetch-vendor-mac.sh:73-128`) дополнительно докладываются платформенные пакеты **обеих** архитектур через `npm cache add`, потому что раннер `macos-latest` — Apple Silicon и `npm install` кеширует .tgz только своей платформы.

В lite-издании кеш не вшит: компонент авто-становится remote по наличию записи в реестре (`src/main.js:636-649`), архив качается с зеркал с обязательной проверкой sha256, а `HM_VENDOR` указывает на проверенный staging: `stagingVendor = fr.path` (`src/main.js:1086`) → `const vroot = stagingVendor || bundledVendorEarly` (`1101`) → `childEnv.HM_VENDOR = vroot` (`1135`).

## Инварианты

1. **Вердикт выносит запуск `claude --version`, а не код установщика.** Нулевой код npm/установщика сам по себе не даёт `works`: за ним всегда идёт проба (`scripts/windows/claude.ps1:193-218, 212-216, 264`; `scripts/macos/claude.sh:21-31, 70, 91, 94, 110`). На macOS инвариант держится в абсолютной форме: `claude_install_ok` — это реальный запуск, и другого исхода, кроме «ответил / не ответил», у него нет. **На Windows есть исключение:** при нулевом коде npm и исходе `unverified` (де-элевация не отчиталась, `claude.ps1:196`) успех засчитывается без доказанного ответа — `$offlineOk = $true` (228-230), онлайн-путь не пробуется, финал пишет вердикт `unverified` и печатает «OK: Claude Code CLI установлен …» с `exit 0` (320-324); это сознательный fail-open, см. «Границы». Безусловно держится только сужённая форма: **`broken` не даёт OK ни на одном пути** (`claude.ps1`, ветки `broken`; `claude.sh:110-117`).
2. **Проверочный запуск на Windows идёт только де-элевированно.** `claude` лежит в user-writable каталоге, а скрипт исполняется elevated, поэтому запуск проходит через `Invoke-HmDeElevated` с `RunLevel LeastPrivilege` и self-check `S-1-16-8192`; не medium — обёртка выходит с 210 и бинарь не запускается (`scripts/windows/claude.ps1:100`; `scripts/windows/_deelev.ps1:566-575, 602-606`).
3. **Удаляем только то, что кладём сами.** `Remove-HmBrokenClaude` гейтится аллоулистом `Test-HmOurClaudeDir`; путь вне аллоулиста не трогается вовсе (`scripts/windows/claude.ps1:166-180`), на маке удаляются строго два пути внутри `~/.local` (`scripts/macos/claude.sh:28-29`).
4. **Работавший до прогона claude не удаляется никогда.** Снимок `$preExisting` берётся до установки, а уборка вызывается только при `$preExisting -ne 'works'` (`scripts/windows/claude.ps1`, снимок `$preExisting` и условие уборки).
5. **В сомнении — `unverified`, а не `broken`.** Служебные статусы планировщика и любые коды вне 0..255 не считаются отказом бинаря (`scripts/windows/claude.ps1:112, 121`).
6. **При `broken` не печатается ни одной строки «OK», выход — код 1.** Красный вердикт выносится раньше квитанции (`scripts/windows/claude.ps1`, ветки `broken` стоят раньше записи `works`/`unverified`).
7. **Один факт — один стандарт доказательства.** Вердикт пишется в `~/.hamidun-setup/checks.json` через `Write-HmFileSafe` (случайный временный файл рядом + `File.Replace`, ссылка проверяется впритык к замене), а чек-лист его переносит, а не выводит заново по наличию файла (`Write-HmCheck` в `scripts/windows/_claudeenv.ps1`; секция Claude CLI в `scripts/windows/verify.ps1`).
8. **PATH elevated-скрипта не содержит пользовательскую ветку реестра.** Собирается только из `Machine` + фиксированных каталогов (`scripts/windows/claude.ps1:11-28`).
9. **Правка User PATH сохраняет тип `REG_EXPAND_SZ`, не задваивает каталог и не трогает PATH процесса.** `Add-HmUserPath` (`scripts/windows/_userpath.ps1`) читает сырое значение с `DoNotExpandEnvironmentNames`, сверяет по развёрнутой копии без учёта регистра и хвостового `\`, после записи рассылает `WM_SETTINGCHANGE` (`Send-HmEnvBroadcast`: средствами .NET, без `Add-Type` — компиляция в `%TEMP%` под администратором давала подмену исходника); каталог из профиля пользователя в PATH elevated-процесса не попадает. С `-Prepend` (так Python встаёт перед заглушкой Магазина) уже стоящий, но не первый каталог переносится в начало, остальные записи и `%VAR%` остаются как были; запись с кавычкой, в которой есть `;`, порядок не меняет.
10. **Node ставится раньше claude.** `requires: ["node"]` + топологический порядок (`components.json:71-73`; `src/renderer/deps.js:26-39`).
11. **На macOS офлайн-ветка запускается только при наличии в кеше ПАРЫ архивов одной версии — основного пакета и платформенного текущей архитектуры — и ставит именно эту версию** (`scripts/macos/claude.sh:57-79`; `scripts/macos/_lib.sh:487-504`). Сборка падает, если такой пары нет хотя бы для одной арх или версии разошлись с основным пакетом (`tools/fetch-vendor-mac.sh:651-665`).
12. **Офлайн-кеш адресуется только через `$HM_VENDOR`, относительных путей нет** (`scripts/windows/claude.ps1:279`; `scripts/macos/claude.sh:43, 62`). Саму переменную главный процесс выставляет одним местом: `const vroot = stagingVendor || bundledVendorEarly` (`src/main.js:1116`) и `childEnv.HM_VENDOR = vroot` (`src/main.js:1150`).
13. **Политику выполнения установщик меняет только в области `CurrentUser` и только с `Restricted` на `RemoteSigned`.** Групповая политика и `AllSigned` не трогаются, более разрешающее значение не «понижается», `LocalMachine` не пишется никогда; успех засчитывается только после чтения области обратно (`Get-HmExecPolicyPlan`, `Set-HmUserExecPolicy` в `scripts/windows/_claudeenv.ps1`).
14. **Проба из PowerShell — второй, отдельный факт, и установку она не сносит никогда.** Её исход живёт только в `claude-ps`: `blocked` (код 197) и `broken` не меняют вердикт `claude` и не вызывают `Remove-HmBrokenClaude`; служебные коды планировщика и коды вне 0..255 — `unverified` (`Test-HmClaudeViaPowerShell`).
15. **Починки пользовательской среды не зависят от галочек и не запускают `claude`.** `Repair-HmClaudeUserEnv` вызывается и после установки (`claude.ps1`), и блоком `every-run repairs (B)` в `verify.ps1`; оба раза она только читает и пишет HKCU (PATH), политику области `CurrentUser` и `~/.hamidun-setup\checks.json`. Сам `claude` оттуда не стартует, claude с вердиктом `broken` не трогается, в dry-run ничего не пишется.
13. **На macOS «новый Терминал не видит claude» — частичный успех, а не провал.** Работающий claude уже отмечен вердиктом `works` и строкой `OK`, а шаг выходит с кодом 121 и ровно одной последней строкой `ЧАСТИЧНО: …` длиной до 240 знаков (`scripts/macos/claude.sh:226-248`); код 1 остаётся только для claude, который не отвечает вовсе.
14. **Сторож времени не уводит команду из группы процессов скрипта.** Никакого `set -m`: группа команды — группа скрипта, дерево снимается обходом потомков, а TERM/INT/HUP самому скрипту снимают это же дерево (`hm_run_with_timeout`, `scripts/macos/_lib.sh`).

## Что ломается, если инвариант нарушить

1. Человек получает зелёную галочку и нерабочую команду: `npm` отчитывается успехом, когда платформенного optional-пакета нет, и оставляет обёртку, которая при запуске печатает «claude native binary not installed». Это уже случилось на живом маке, но не на промахе офлайн-кеша, а на ОНЛАЙН-установке: «npm отчитался успехом ОНЛАЙН, человек получил зелёную галочку и нерабочий claude — худший исход из всех» (`scripts/macos/claude.sh:15-17`). Механизм у офлайн- и онлайн-пути один, и именно из-за этого случая гейт запуском стоит теперь на ВСЕХ путях, а не только в офлайн-ветке, как раньше (`claude.sh:16-17`).
2. Установщик исполнил бы под правами администратора файл, который medium-процесс того же пользователя мог подложить на место `claude` — прямой подъём привилегий на чистой машине.
3. Скрипт с правами администратора снёс бы чужую рабочую установку claude (свой npm-prefix, volta, scoop). Человек теряет то, что у него работало, и ничего не получает взамен, если онлайн-путь упрётся в 403 из России.
4. То же самое, но по другой причине: офлайн-ветка перетёрла бы чужую рабочую установку заведомо неработающей обёрткой, а следом её же и удалила.
5. Служебный статус планировщика («задача завершена», «в очереди») был бы прочитан как «claude сломан», и рабочий CLI удалялся бы на ровном месте — цена ошибки несимметрична: снести рабочее хуже, чем не подтвердить.
6. Финал печатает «OK: Claude Code CLI установлен» при claude, который падает при первом запуске. Человек уходит уверенным, что всё хорошо, и упирается в это позже, уже без установщика под рукой.
7. Чек-лист начинает зеленеть по наличию файла — а файл оставляет и провалившаяся офлайн-установка. Возвращается ровно та ложная галочка, ради которой заведён `checks.json`.
8. Malware того же пользователя дописывает в HKCU PATH каталог с подложным `git`/`node`/`npm`, и elevated-скрипт исполняет его под админским токеном.
9. Тихая порча PATH пользователя: `%USERPROFILE%` и прочие переменные превращаются в литералы, тип значения меняется на `REG_SZ` — ломаются пути, которые человек прописывал сам.
10. `npm` на шаге claude отсутствует, офлайн-ветка не запускается вовсе, установка уходит в интернет там, где всё нужное лежит внутри установщика.
11. На Intel-маке офлайн-издание молча ставит обёртку-пустышку, гейт её ловит и уходит в сеть — то есть «офлайн-издание» офлайн не работает, и человек об этом не знает.
12. В lite-издании скрипт искал бы кеш во вшитом vendor, которого там нет, вместо sha-проверенного staging — компонент падал бы у каждого lite-пользователя.
13. Установщик молча ослабил бы политику, которую выставил администратор или групповая политика компании, — или «понизил» бы человеку уже разрешающее значение до `RemoteSigned`.
14. Человек, у которого claude не пускает только политика, потерял бы рабочую установку: отказ загрузки `claude.ps1` прочитан как «бинарь сломан», и уборка снесла бы шимы и пакет.
15. Люди, поставившие claude раньше, остались бы без починок: повторный запуск снимает у них галочку с `claude`, `claude.ps1` не выполняется, и в терминале VS Code команда `claude` по-прежнему упирается в политику выполнения скриптов, а `nmd` и `python` не находятся в новом окне.
16. Из-за PATH в чужой оболочке человек получает красный claude, который на самом деле работает, а конфиг, курс и скрепка, которым claude нужен лишь как установленный, пропускаются каскадом; за конфигом следом отваливаются Python-пакеты.
17. Закрытие окна установщика снимает шаг SIGKILL'ом группы скрипта; команда в чужой группе (при `set -m`) переживает его и остаётся сиротой: сторож времени погиб вместе с группой скрипта, и у установщика claude.ai или npm больше нет потолка по времени.

## Границы

- **Не авторизует.** Ни в `claude.ps1`, ни в `claude.sh` нет ни строки про вход в аккаунт, API-ключ или подписку — ставится только CLI. Логин человек делает сам при первом запуске.
- **Не ставит панель в редакторе** — это отдельный компонент `extension` (`components.json:82-96`), и не ставит Node — компонент `node`.
- **Не обновляет уже стоящий claude.** Вердикт `works` означает «не трогаю» (`claude.ps1:201-205`): версия не сверяется, апдейт не предлагается.
- **Не чинит чужую сломанную установку.** Сломанный claude вне наших каталогов — честный `exit 1` с инструкцией «удали свою установку и запусти компонент заново» (`claude.ps1:301-309`).
- **`unverified` засчитывается как успех.** Если де-элевация недоступна, офлайн-установка считается удавшейся, онлайн-путь не пробуется, финал печатает OK с оговоркой «проверить запуском не удалось» (`claude.ps1:228-230, 320-322`). Это сознательный fail-open к прежней проверке «бинарь на диске».
- **На Windows нет арх-гейта офлайн-кеша.** В отличие от `claude.sh:41-51`, `claude.ps1` не проверяет, есть ли в кеше платформенный пакет под текущую архитектуру; несовпадение ловится уже пробой запуска, задним числом.
- **Офлайн-кеш не покрыт `vendor/checksums.json`.** Манифест хеширует файлы `vendor/apps`, архив курса и nomad-манифест (`tools/fetch-vendor.ps1:522-553`: заголовок блока — 522, хеширование — 540-547, запись `vendor\checksums.json` — 550-551); каталог `npm-cache` в него не попадает, и `claude.ps1` не подключает `_verify.ps1`. Целостность байтов кеша держится на content-addressed индексе самого npm — **это поведение npm, кодом репозитория оно не подтверждается**.
- **Онлайн-установщик не сверяется по sha256** — сознательная уступка: версия плавающая, доверие строится на TLS и подлинности домена (`claude.ps1:5-7`).
- **Windows-кеш не копируется в temp** перед `npm install --offline`, в отличие от macOS: `--cache` указывает прямо в `$HM_VENDOR\npm-cache` (`claude.ps1:210`). Пишет ли туда npm при установке из read-only каталога — кодом не проверяется.

## Риски и открытые вопросы

1. **`irm | iex` под администратором.** `Invoke-RestMethod "https://claude.ai/install.ps1" | Invoke-Expression` (`claude.ps1:240`) — единственное место фичи, где elevated-процесс исполняет код, не сверенный ни с sha, ни с подписью. Комментарий это признаёт прямо («Своего SHA-256 для него нет»). Для остальных вшитых артефактов проект держит fail-closed sha-гейт, здесь его нет по объективной причине (плавающая версия), но риск остаётся.
2. **Комментарий в `src/main.js:735-744` расходится с кодом скриптов.** Там сказано: «Компоненты БЕЗ такого фолбэка (nomad/pydeps/extension/claude) остаются fail-closed», и `claude` не входит в `SCRIPT_ONLINE_FALLBACK`. Но собственный онлайн-фолбэк у claude есть — `claude.ps1:236-252` и `claude.sh:84-102`. Следствие для lite: если докачка архива не удалась, компонент краснеет со `stage:'fetch'`, а скрипт, который мог бы поставить claude из интернета, не запускается вовсе. Возможно, это осознанное решение (не тратить трафик дважды), но обоснование в комментарии фактически неверно.
3. **Размер опубликованной записи докачки не сходится с текущим кешем.** `remote-components.json` для `claude/win32` объявляет 1 051 595 315 байт, а `vendor/npm-cache` на диске сегодня — 108 433 729 байт (ровно `sizeBytes` из `components.json:77`). Цифра ~1 ГБ совпадает с описанным в `tools/fetch-vendor.ps1:75-83` накоплением 13 версий, а `tools/build-lite.js:172` прямо называет запись «claude (npm-кеш, ~1 ГБ)». Похоже, компонент опубликован до чистки кеша, и lite-пользователь Windows качает в десять раз больше нужного. **Не подтверждено:** содержимое опубликованного архива без скачивания проверить нельзя.
4. **`gatedFiles: {}` у обеих записей claude.** Второй рубеж целостности (`Confirm-HmArtifact` по basename) для этого компонента не проверяет ни одного файла — у компонентов-каталогов представителя в манифесте нет. `tools/build-lite.js:171-178` это фиксирует предупреждением, а не отказом: остаётся только sha архива в реестре, которая ловит порчу, но не устаревшую публикацию.
5. **Асимметрия чек-листа между платформами.** `scripts/macos/verify.sh:56-69` печатает `CHECK ok Claude CLI` по факту наличия исполняемого файла, без вердикта запуска, — тогда как Windows переносит вердикт из `checks.json`. Сломанный claude вне `~/.local` (например, из brew) даст на маке зелёную строку в чек-листе, хотя сам шаг завершился ошибкой. Это ровно тот класс ложной галочки, который на Windows уже закрыт.
6. **Код возврата онлайн-`npm install` не проверяется** (`claude.ps1:247`): выполнение продолжается к финальной пробе. Итог правильный (гейтит проба), но причина отказа npm теряется — человек увидит общий текст «не запускается», а не сообщение пакетного менеджера.
7. **`Test-HmClaudeRuns($null)` возвращает `broken`** (`claude.ps1:99`) — вердикт «сломан» без единой попытки запуска. Достижимо, если `Find-ClaudeBinary` вернёт `$null` сразу после успешного `npm install` (215-216); практических последствий нет (уборка отказывает на `$null`, флоу уходит в онлайн-путь), но исход противоречит правилу «в сомнении — unverified».
8. **Ветка `exit 1` «claude не установился» не пишет вердикт `claude` в `checks.json`** (вердикт `claude-ps` в начале скрипта сбрасывается в `n/a`, а `Write-HmCheck` подключается из `_claudeenv.ps1` до любого выхода, но ключ `claude` на этой ветке по-прежнему не трогается). Последствие хуже, чем «итог верный, но без причины». `checks.json` переживает прогоны: поиск по репозиторию (кроме `release/` и `node_modules`) показывает: пишут `claude.ps1` и блок починок `verify.ps1` (ключ `claude-ps`), читает `verify.ps1`, — то есть ни файл, ни ключ `claude` нигде не очищаются и не сверяются с текущим прогоном; возраст записи `verify.ps1:108-111` тоже не проверяет, а `src/uninstall-exec.js:73-78` держит `~/.hamidun-setup` в `protectedRoots`, так что файл не стирается даже при удалении. Наличия бинаря чек-лист не требует: `$claudeBin` на `verify.ps1:114-115` только печатается строкой, в условие 116 не входит. Поэтому `CHECK fail` эта ветка даёт только на ПЕРВОМ прогоне, когда вердикта в файле ещё нет. На ПОВТОРНОМ (прошлый прогон записал `works` — `claude.ps1:433`; человек снёс claude; теперь офлайн-ветка не дала бинарь, `irm` упал, `npm install` (247) не сработал → 257-260) чек-лист напечатает `CHECK ok Claude CLI` при физически отсутствующем claude — ровно та ложная зелёная галочка, ради которой заведён `checks.json`.
9. **Windows-ветка на ARM.** Кеш собирается на Windows-раннере и содержит платформенный пакет его архитектуры; арх-гейта в `claude.ps1` нет. По коду ожидается: обёртка встанет, проба вернёт `broken`, обёртка будет убрана, установка уйдёт в онлайн. **Не подтверждено испытанием** — это вывод из чтения кода, не наблюдение.
10. **Проба из PowerShell зависит от того же планировщика задач, что и остальная де-элевация.** Если задача не стартует, `claude-ps` = `unverified`, и отдельной строки в чек-листе нет; запрет, который мы не вправе снять (групповая политика, `AllSigned`), определяется и без запуска и сразу даёт `blocked`. Красная строка «Запуск claude в PowerShell», как любой красный пункт чек-листа, меняет заголовок финального экрана на «проверка нашла проблемы».
