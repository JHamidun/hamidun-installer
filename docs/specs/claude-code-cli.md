## Что обещает человеку

После установки в новом окне терминала работает команда `claude` — сам ИИ-агент, которому пишешь задачу словами. Компонент включён по умолчанию и требует Node.js (`components.json:70-73`), поэтому Node подтянется вместе с ним автоматически.

Главное обещание — не «файл положен», а «команда отвечает». Зелёная галочка в финальном чек-листе на Windows ставится по вердикту `works`, а вердикт выносит реальный запуск `claude --version` с нулевым кодом (`scripts/windows/claude.ps1:264-322`, `scripts/windows/verify.ps1:116-117`) — с оговоркой, что вердикт читается из файла, пережившего прошлые прогоны (см. риск 8). Красная строка с объяснением, что делать, появляется только при ДОКАЗАННОМ отказе запуска (`broken`): `claude.ps1:302-308` и `311-313`. Если запустить не получилось (исход `unverified` — де-элевация не отчиталась), красной строки нет ни в одном месте: шаг печатает «OK: Claude Code CLI установлен (… проверить запуском де-элевированно не удалось)» и выходит с кодом 0 (`claude.ps1:320-324`), а чек-лист даёт `CHECK skip Claude CLI (установлен, запуск не проверен)` (`verify.ps1:118-122`). Это сознательный fail-open, он же описан в инварианте 1 и в «Границах». Обратная сторона обещания: если у тебя уже стоит рабочий `claude`, установщик его не тронет и не перетрёт (`scripts/windows/claude.ps1:196-205`).

## Как работает

Главный процесс подбирает скрипт по id компонента: `scripts/<windows|macos>/claude.<ps1|sh>` (`src/main.js:571-575`) и передаёт ему `HM_VENDOR` — корень вшитого vendor либо sha-проверенный staging докачки в lite-издании (`src/main.js:1103` — вычисление `vroot`, `src/main.js:1137` — сама передача `childEnv.HM_VENDOR = vroot`). Порядок установки топологический, поэтому `node` встаёт раньше `claude` (`src/renderer/deps.js:26-39`).

### Windows (`scripts/windows/claude.ps1`)

1. **Подготовка.** Форсится TLS 1.2 (строка 7), дот-сорсится примитив де-элевации `_deelev.ps1` (строка 9). `Update-Path` (10-29) собирает PATH **только** из машинной ветки HKLM плюс фиксированные админ-owned каталоги (`System32`, `Program Files\Git\cmd`, `\bin`, `nodejs`); пользовательский HKCU PATH не читается никогда — комментарий называет это SECURITY #4.
2. **Снимок «до».** `Find-ClaudeBinary` (32-58) ищет по трём местам: `Get-Command claude` → `npm config get prefix` (`claude.cmd`/`claude.exe`/`claude`) → `%USERPROFILE%\.local\bin`. Найденный бинарь прогоняется через `Test-HmClaudeRuns`; вердикт `works` означает «уже стоит и отвечает» — офлайн-установка не запускается вовсе (196-205).
3. **Офлайн-ветка** (207-234). Условие входа: снимок не дал `works`, `$env:HM_VENDOR\npm-cache` существует, `npm` доступен. Команда: `npm install -g '@anthropic-ai/claude-code' --offline --cache $cache --no-audit --no-fund`. Код возврата запоминается (`$npmExit = $LASTEXITCODE`, 211) и **гейтит саму проверку запуском**: `Update-Path` → `Find-ClaudeBinary` → `Test-HmClaudeRuns` стоят внутри ветки `if ($npmExit -eq 0)` (212-216). При ненулевом коде проверки запуском не происходит вовсе — `else` (231-233) печатает «Офлайн-установка npm вернула код …» и управление уходит в онлайн-ветку (236). Обратное тоже верно: нулевой код сам по себе успехом не считается — успех даёт только проба (см. инвариант 1 про её единственное исключение).
4. **Проверка запуском** — `Test-HmClaudeRuns` (98-123). Она вызывает `Invoke-HmDeElevated $bin @('--version')`, то есть исполняет `claude` через одноразовую задачу планировщика с `RunLevel LeastPrivilege` и self-check на medium integrity `S-1-16-8192` (`_deelev.ps1:566-624`). Исходы три: `works` (Gate=medium, Code=0), `broken` (Gate=medium, код 1..255), `unverified` — если де-элевация не отчиталась, если пришёл служебный статус планировщика из списка `267008…267045` (112) или код вне диапазона 0..255 (121).
5. **Уборка нерабочей обёртки** (217-227). Только при `broken`, только если до прогона тут не было рабочего claude, и только по аллоулисту `Test-HmOurClaudeDir` (134-158): `%USERPROFILE%\.local\bin`, `%APPDATA%\npm` и фактический `npm config get prefix`. Удаляются шимы `claude`, `claude.cmd`, `claude.ps1`, `claude.exe` и пакет `node_modules\@anthropic-ai\claude-code`. Каталог вне аллоулиста — печатается «чужие файлы не трогаю» и возвращается `$false`.
6. **Онлайн-ветка** (236-252). `Invoke-RestMethod "https://claude.ai/install.ps1" -TimeoutSec 120 | Invoke-Expression`. При исключении — запасной шаг `npm install -g '@anthropic-ai/claude-code' --no-audit --no-fund` из онлайн-реестра (комментарий объясняет: claude.ai отдаёт из РФ 403, а registry.npmjs.org доступен). Если `npm` не найден — `exit 1`.
7. **Финал** (254-324). Повторный `Find-ClaudeBinary`; не нашли — `exit 1` без записи вердикта. Проба переиспользуется, если бинарь тот же. `broken` вне наших каталогов → отдельный текст «это твои файлы, удали свою установку» + `Write-HmCheck 'claude' 'broken'` + `exit 1`. `broken` в нашем каталоге → `exit 1`. Иначе `Add-ToUserPath` для каталога бинаря и для `~/.local\bin` (62-81: читается сырое `REG_EXPAND_SZ`, чтобы не превратить `%USERPROFILE%` в литерал), запись вердикта `works`/`unverified` в `~/.hamidun-setup/checks.json` через temp+move (269-287) и `exit 0`.
8. **Чек-лист.** `verify.ps1:97-127` не судит по наличию файла: он читает `checks.json` и печатает `CHECK ok Claude CLI` только при `verdict = works`; `unverified` → `CHECK skip … (установлен, запуск не проверен)`; `broken` или отсутствие вердикта → `CHECK fail`.
9. **Dry-run.** При `HM_DRY_RUN` обе ветки печатают строку «WOULD» и выходят с кодом 0 (209, 237) — ничего не ставится и вердикт не пишется.

### macOS (`scripts/macos/claude.sh`)

Логика зеркальная, но с тремя отличиями, каждое видно в коде:

- **Пользовательский prefix.** Всё ставится с `--prefix "$HOME/.local"` (66, 93): node из `.pkg` держит глобальный npm-prefix в `/usr/local` (root:wheel), и `npm -g` без sudo упал бы с EACCES.
- **Арх-гейт перед офлайн-путём** (41-51). Настоящий бинарь едет платформенным optional-пакетом `@anthropic-ai/claude-code-darwin-<arch>`; наличие **архива** (а не packument) проверяет `hm_npm_cache_has_tarball` (`_lib.sh:138-142`) по ключу cacache `"/<имя>/-/<имя>-"`. Нет архива под текущую арх — человеку сразу говорят, что этот компонент придётся качать из интернета.
- **Копия кеша в temp** (61-67). Vendor на маке лежит на образе только для чтения, а npm пишет в `--cache` даже в режиме `--offline`, поэтому кеш копируется в `mktemp -d` и получает `chmod -R u+w`.

Единый гейт `claude_install_ok` (21-31) стоит на всех путях — офлайн, `curl … install.sh | bash`, npm-фолбэк и финал (70, 91, 94, 110). При провале он удаляет ровно свои артефакты: `~/.local/bin/claude` и `~/.local/lib/node_modules/@anthropic-ai/claude-code`. На успехе `persist_local_bin_path` (`_lib.sh:177-194`) дописывает `~/.local/bin` в `~/.zshrc` и `~/.bash_profile`.

### Откуда берётся офлайн-кеш

Сборкой: `tools/fetch-vendor.ps1:68-88` делает `npm install '@anthropic-ai/claude-code' --prefix <tmp> --cache vendor\npm-cache` и затем обязательный `tools/prune-npm-cache.js` — без чистки каждый релиз оставлял в кеше предыдущий архив (~80 МиБ), и к 11.08.2026 накопилось 13 версий = 1005 МиБ. На маке (`tools/fetch-vendor-mac.sh:73-128`) дополнительно докладываются платформенные пакеты **обеих** архитектур через `npm cache add`, потому что раннер `macos-latest` — Apple Silicon и `npm install` кеширует .tgz только своей платформы.

В lite-издании кеш не вшит: компонент авто-становится remote по наличию записи в реестре (`src/main.js:636-649`), архив качается с зеркал с обязательной проверкой sha256, а `HM_VENDOR` указывает на проверенный staging: `stagingVendor = fr.path` (`src/main.js:1086`) → `const vroot = stagingVendor || bundledVendorEarly` (`1101`) → `childEnv.HM_VENDOR = vroot` (`1135`).

## Инварианты

1. **Вердикт выносит запуск `claude --version`, а не код установщика.** Нулевой код npm/установщика сам по себе не даёт `works`: за ним всегда идёт проба (`scripts/windows/claude.ps1:98-123, 212-216, 264`; `scripts/macos/claude.sh:21-31, 70, 91, 94, 110`). На macOS инвариант держится в абсолютной форме: `claude_install_ok` — это реальный запуск, и другого исхода, кроме «ответил / не ответил», у него нет. **На Windows есть исключение:** при нулевом коде npm и исходе `unverified` (де-элевация не отчиталась, `claude.ps1:101`) успех засчитывается без доказанного ответа — `$offlineOk = $true` (228-230), онлайн-путь не пробуется, финал пишет вердикт `unverified` и печатает «OK: Claude Code CLI установлен …» с `exit 0` (320-324); это сознательный fail-open, см. «Границы». Безусловно держится только сужённая форма: **`broken` не даёт OK ни на одном пути** (`claude.ps1:301-314`; `claude.sh:110-117`).
2. **Проверочный запуск на Windows идёт только де-элевированно.** `claude` лежит в user-writable каталоге, а скрипт исполняется elevated, поэтому запуск проходит через `Invoke-HmDeElevated` с `RunLevel LeastPrivilege` и self-check `S-1-16-8192`; не medium — обёртка выходит с 210 и бинарь не запускается (`scripts/windows/claude.ps1:100`; `scripts/windows/_deelev.ps1:566-575, 602-606`).
3. **Удаляем только то, что кладём сами.** `Remove-HmBrokenClaude` гейтится аллоулистом `Test-HmOurClaudeDir`; путь вне аллоулиста не трогается вовсе (`scripts/windows/claude.ps1:166-180`), на маке удаляются строго два пути внутри `~/.local` (`scripts/macos/claude.sh:28-29`).
4. **Работавший до прогона claude не удаляется никогда.** Снимок `$preExisting` берётся до установки, а уборка вызывается только при `$preExisting -ne 'works'` (`scripts/windows/claude.ps1:196-205, 222`).
5. **В сомнении — `unverified`, а не `broken`.** Служебные статусы планировщика и любые коды вне 0..255 не считаются отказом бинаря (`scripts/windows/claude.ps1:112, 121`).
6. **При `broken` не печатается ни одной строки «OK», выход — код 1.** Красный вердикт выносится раньше квитанции (`scripts/windows/claude.ps1:301-314`).
7. **Один факт — один стандарт доказательства.** Вердикт пишется в `~/.hamidun-setup/checks.json` атомарно (temp + `Move-Item`), а чек-лист его переносит, а не выводит заново по наличию файла (`scripts/windows/claude.ps1:269-287`; `scripts/windows/verify.ps1:106-126`).
8. **PATH elevated-скрипта не содержит пользовательскую ветку реестра.** Собирается только из `Machine` + фиксированных каталогов (`scripts/windows/claude.ps1:11-28`).
9. **Правка User PATH сохраняет тип `REG_EXPAND_SZ` и не задваивает каталог.** Читается сырое значение с `DoNotExpandEnvironmentNames`, сверка идёт по развёрнутой копии (`scripts/windows/claude.ps1:62-81`).
10. **Node ставится раньше claude.** `requires: ["node"]` + топологический порядок (`components.json:71-73`; `src/renderer/deps.js:26-39`).
11. **На macOS офлайн-ветка запускается только при наличии .tgz платформенного пакета текущей архитектуры** (`scripts/macos/claude.sh:41-53`; `scripts/macos/_lib.sh:138-142`).
12. **Офлайн-кеш адресуется только через `$HM_VENDOR`, относительных путей нет** (`scripts/windows/claude.ps1:184`; `scripts/macos/claude.sh:43, 62`). Саму переменную главный процесс выставляет одним местом: `const vroot = stagingVendor || bundledVendorEarly` (`src/main.js:1103`) и `childEnv.HM_VENDOR = vroot` (`src/main.js:1137`).

## Что ломается, если инвариант нарушить

1. Человек получает зелёную галочку и нерабочую команду: `npm` отчитывается успехом, когда платформенного optional-пакета нет, и оставляет обёртку, которая при запуске печатает «claude native binary not installed». Это уже случилось на живом маке, но не на промахе офлайн-кеша, а на ОНЛАЙН-установке: «npm отчитался успехом ОНЛАЙН, человек получил зелёную галочку и нерабочий claude — худший исход из всех» (`scripts/macos/claude.sh:15-17`). Механизм у офлайн- и онлайн-пути один, и именно из-за этого случая гейт запуском стоит теперь на ВСЕХ путях, а не только в офлайн-ветке, как раньше (`claude.sh:16-17`).
2. Установщик исполнил бы под правами администратора файл, который medium-процесс того же пользователя мог подложить на место `claude` — прямой подъём привилегий на чистой машине.
3. Скрипт с правами администратора снёс бы чужую рабочую установку claude (свой npm-prefix, volta, scoop). Человек теряет то, что у него работало, и ничего не получает взамен, если онлайн-путь упрётся в 403 из России.
4. То же самое, но по другой причине: офлайн-ветка перетёрла бы чужую рабочую установку заведомо неработающей обёрткой, а следом её же и удалила.
5. Служебный статус планировщика («задача завершена», «в очереди») был бы прочитан как «claude сломан», и рабочий CLI удалялся бы на ровном месте — цена ошибки несимметрична: снести рабочее хуже, чем не подтвердить.
6. Финал печатает «OK: Claude Code CLI установлен» при claude, который падает при первом запуске. Человек уходит уверенным, что всё хорошо, и упирается в это позже, уже без установщика под рукой.
7. Чек-лист начинает зеленеть по наличию файла — а файл оставляет и провалившаяся офлайн-установка. Возвращается ровно та ложная галочка, ради которой заведён `checks.json`.
8. Malware того же пользователя дописывает в HKCU PATH каталог с подложным `git`/`node`/`npm`, и elevated-скрипт исполняет его под админским токеном.
9. Тихая порча PATH пользователя: `%USERPROFILE%` и прочие переменные превращаются в литералы, тип значения меняется на `REG_SZ` — ломаются пути, которые человек прописывал сам.
10. `npm` на шаге claude отсутствует, офлайн-ветка не запускается вовсе, установка уходит в интернет там, где всё нужное лежит внутри установщика.
11. На Intel-маке офлайн-издание молча ставит обёртку-пустышку, гейт её ловит и уходит в сеть — то есть «офлайн-издание» офлайн не работает, и человек об этом не знает.
12. В lite-издании скрипт искал бы кеш во вшитом vendor, которого там нет, вместо sha-проверенного staging — компонент падал бы у каждого lite-пользователя.

## Границы

- **Не авторизует.** Ни в `claude.ps1`, ни в `claude.sh` нет ни строки про вход в аккаунт, API-ключ или подписку — ставится только CLI. Логин человек делает сам при первом запуске.
- **Не ставит панель в редакторе** — это отдельный компонент `extension` (`components.json:82-96`), и не ставит Node — компонент `node`.
- **Не обновляет уже стоящий claude.** Вердикт `works` означает «не трогаю» (`claude.ps1:201-205`): версия не сверяется, апдейт не предлагается.
- **Не чинит чужую сломанную установку.** Сломанный claude вне наших каталогов — честный `exit 1` с инструкцией «удали свою установку и запусти компонент заново» (`claude.ps1:301-309`).
- **`unverified` засчитывается как успех.** Если де-элевация недоступна, офлайн-установка считается удавшейся, онлайн-путь не пробуется, финал печатает OK с оговоркой «проверить запуском не удалось» (`claude.ps1:228-230, 320-322`). Это сознательный fail-open к прежней проверке «бинарь на диске».
- **На Windows нет арх-гейта офлайн-кеша.** В отличие от `claude.sh:41-51`, `claude.ps1` не проверяет, есть ли в кеше платформенный пакет под текущую архитектуру; несовпадение ловится уже пробой запуска, задним числом.
- **Офлайн-кеш не покрыт `vendor/checksums.json`.** Манифест хеширует файлы `vendor/apps`, архив курса и nomad-манифест (`tools/fetch-vendor.ps1:522-553`: заголовок блока — 522, хеширование — 540-547, запись `vendor\checksums.json` — 550-551); каталог `npm-cache` в него не попадает, и `claude.ps1` не подключает `_verify.ps1`. Целостность байтов кеша держится на content-addressed индексе самого npm — **это поведение npm, кодом репозитория оно не подтверждается**.
- **Онлайн-установщик не сверяется по sha256** — сознательная уступка: версия плавающая, доверие строится на TLS и подлинности домена (`claude.ps1:5-7`).
- **Windows-кеш не копируется в temp** перед `npm install --offline`, в отличие от macOS: `--cache` указывает прямо в `$HM_VENDOR\npm-cache` (`claude.ps1:210`). Пишет ли туда npm при установке из read-only каталога — кодом не проверяется.

## Риски и открытые вопросы

1. **`irm | iex` под администратором.** `Invoke-RestMethod "https://claude.ai/install.ps1" | Invoke-Expression` (`claude.ps1:240`) — единственное место фичи, где elevated-процесс исполняет код, не сверенный ни с sha, ни с подписью. Комментарий это признаёт прямо («Своего SHA-256 для него нет»). Для остальных вшитых артефактов проект держит fail-closed sha-гейт, здесь его нет по объективной причине (плавающая версия), но риск остаётся.
2. **Комментарий в `src/main.js:735-744` расходится с кодом скриптов.** Там сказано: «Компоненты БЕЗ такого фолбэка (nomad/pydeps/extension/claude) остаются fail-closed», и `claude` не входит в `SCRIPT_ONLINE_FALLBACK`. Но собственный онлайн-фолбэк у claude есть — `claude.ps1:236-252` и `claude.sh:84-102`. Следствие для lite: если докачка архива не удалась, компонент краснеет со `stage:'fetch'`, а скрипт, который мог бы поставить claude из интернета, не запускается вовсе. Возможно, это осознанное решение (не тратить трафик дважды), но обоснование в комментарии фактически неверно.
3. **Размер опубликованной записи докачки не сходится с текущим кешем.** `remote-components.json` для `claude/win32` объявляет 1 051 595 315 байт, а `vendor/npm-cache` на диске сегодня — 108 433 729 байт (ровно `sizeBytes` из `components.json:77`). Цифра ~1 ГБ совпадает с описанным в `tools/fetch-vendor.ps1:75-83` накоплением 13 версий, а `tools/build-lite.js:172` прямо называет запись «claude (npm-кеш, ~1 ГБ)». Похоже, компонент опубликован до чистки кеша, и lite-пользователь Windows качает в десять раз больше нужного. **Не подтверждено:** содержимое опубликованного архива без скачивания проверить нельзя.
4. **`gatedFiles: {}` у обеих записей claude.** Второй рубеж целостности (`Confirm-HmArtifact` по basename) для этого компонента не проверяет ни одного файла — у компонентов-каталогов представителя в манифесте нет. `tools/build-lite.js:171-178` это фиксирует предупреждением, а не отказом: остаётся только sha архива в реестре, которая ловит порчу, но не устаревшую публикацию.
5. **Асимметрия чек-листа между платформами.** `scripts/macos/verify.sh:56-69` печатает `CHECK ok Claude CLI` по факту наличия исполняемого файла, без вердикта запуска, — тогда как Windows переносит вердикт из `checks.json`. Сломанный claude вне `~/.local` (например, из brew) даст на маке зелёную строку в чек-листе, хотя сам шаг завершился ошибкой. Это ровно тот класс ложной галочки, который на Windows уже закрыт.
6. **Код возврата онлайн-`npm install` не проверяется** (`claude.ps1:247`): выполнение продолжается к финальной пробе. Итог правильный (гейтит проба), но причина отказа npm теряется — человек увидит общий текст «не запускается», а не сообщение пакетного менеджера.
7. **`Test-HmClaudeRuns($null)` возвращает `broken`** (`claude.ps1:99`) — вердикт «сломан» без единой попытки запуска. Достижимо, если `Find-ClaudeBinary` вернёт `$null` сразу после успешного `npm install` (215-216); практических последствий нет (уборка отказывает на `$null`, флоу уходит в онлайн-путь), но исход противоречит правилу «в сомнении — unverified».
8. **Ветка `exit 1` на строке 257-260 не пишет вердикт в `checks.json`** — `Write-HmCheck` объявлена ниже, на 269. Последствие хуже, чем «итог верный, но без причины». `checks.json` переживает прогоны: полный grep по репозиторию (кроме `release/` и `node_modules`) даёт ровно четыре места — запись `claude.ps1:266,273` и чтение `verify.ps1:101,108`, — то есть ни файл, ни ключ `claude` нигде не очищаются и не сверяются с текущим прогоном; возраст записи `verify.ps1:108-111` тоже не проверяет, а `src/uninstall-exec.js:73-78` держит `~/.hamidun-setup` в `protectedRoots`, так что файл не стирается даже при удалении. Наличия бинаря чек-лист не требует: `$claudeBin` на `verify.ps1:114-115` только печатается строкой, в условие 116 не входит. Поэтому `CHECK fail` эта ветка даёт только на ПЕРВОМ прогоне, когда вердикта в файле ещё нет. На ПОВТОРНОМ (прошлый прогон записал `works` — `claude.ps1:318`; человек снёс claude; теперь офлайн-ветка не дала бинарь, `irm` упал, `npm install` (247) не сработал → 257-260) чек-лист напечатает `CHECK ok Claude CLI` при физически отсутствующем claude — ровно та ложная зелёная галочка, ради которой заведён `checks.json`.
9. **Windows-ветка на ARM.** Кеш собирается на Windows-раннере и содержит платформенный пакет его архитектуры; арх-гейта в `claude.ps1` нет. По коду ожидается: обёртка встанет, проба вернёт `broken`, обёртка будет убрана, установка уйдёт в онлайн. **Не подтверждено испытанием** — это вывод из чтения кода, не наблюдение.
