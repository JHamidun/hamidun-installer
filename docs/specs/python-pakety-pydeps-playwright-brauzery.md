## Что обещает человеку

После этого шага на машине есть интерпретатор Python и набор библиотек, на которых
работают «продвинутые» навыки конфига: картинки (`pillow`), документы (`python-docx`,
`openpyxl`, `python-pptx`, `pypdf`, `pdfplumber`), Telegram (`telethon`), клиенты
AI-провайдеров (`anthropic`, `openai`, `google-genai`) и браузерная автоматизация
(`playwright`). Список — не выдумка спеки: он лежит в `config-pack/requirements.txt`
внутри установщика и ставится целиком, как есть.

Обещание сформулировано в `components.json` двумя разными строками для двух ОС, и
разница честная: на macOS браузер для автоматизации «уже внутри» (`sizeNote.darwin`),
на Windows «браузер Chromium докачивается из интернета при установке»
(`sizeNote.win32`). То есть на Windows этот шаг в общем случае **требует сети** ради
браузера, даже когда все библиотеки встали офлайн из вшитых колёс.

## Как работает

Компонент объявлен в `components.json:140-160`: `id: "pydeps"`, `default: true`,
`requires: ["config"]`, `needsAdmin: false`. Числа `sizeBytes` (win32 203 922 495,
darwin 797 395 819) не пишутся руками — их генерирует `tools/sync-sizes.js` из карты
`VENDOR_PARTS`, и наборы у платформ РАЗНЫЕ: win32 — `['apps/python-setup.exe', 'pywheels']`
(`tools/sync-sizes.js:101`), darwin — `['apps/python.pkg', 'pywheels', { glob:
'playwright-browsers-*', pick: 'max' }]` (`:123`). Отличий два: на macOS Python приезжает
не установщиком `.exe`, а пакетом `.pkg` (`scripts/macos/pydeps.sh:15`), и туда же входят
браузеры Playwright.

Перед запуском скрипта `src/main.js` собирает окружение: `HM_VENDOR` указывает либо на
докачанный staging (lite-издание), либо на вшитый vendor (`vroot`, `src/main.js:1267`;
присвоение — `:1135`), а `HM_BUNDLED_CONFIG` резолвится через `vendorPick('config-pack')` —
«есть в staging → оттуда, иначе из вшитого vendor» (`vendorPick` объявлен в
`src/main.js:1275-1282`, присвоение — `:1136`). Именно из-за lite-издания там и появился
`vendorPick`: staging компонента `pydeps` не содержит config-pack, и без этого шаг падал.

### Windows — `scripts/windows/pydeps.ps1`

1. `$ErrorActionPreference = 'Continue'` (строка 3) — под `Stop` нативные `python`/`pip`
   валили бы шаг своим stderr.
2. Дот-сорсятся `_verify.ps1` (`Confirm-HmArtifact`) и `_deelev.ps1`
   (`New-HmSecureStagingDir`, `Test-HmTrustedSigner`).
3. `Update-Path` (6-26) пересобирает `$env:Path` **только** из `Machine`-ветки реестра и
   фиксированных системных каталогов. Пользовательский PATH (HKCU) не читается вовсе.
4. `Get-Py` (29-47) ищет интерпретатор: сперва `python`/`python3` из PATH, отбрасывая
   Store-заглушку из `WindowsApps` и требуя, чтобы `--version` дал `Python \d`; затем
   абсолютные пути `%LOCALAPPDATA%\Programs\Python\Python313|312|311\python.exe`; затем `py`.
5. **Ветвление «Python не найден»** (50-109), три пути:
   - вшитый установщик `$HM_VENDOR\apps\python-setup.exe` — `Confirm-HmArtifact` (SHA-256,
     fail-closed), затем `/quiet InstallAllUsers=0 PrependPath=1 Include_test=0` с `-Wait`;
   - winget — ветка присутствует, но комментарий 60-62 прямо говорит, что она
     **недостижима по построению**: `winget` живёт в `%LOCALAPPDATA%\Microsoft\WindowsApps`,
     а `Update-Path` такой каталог в PATH не кладёт;
   - онлайн-фолбэк python.org (67-108): `$pyVer = '3.12.10'`, каталог загрузки создаётся
     `New-HmSecureStagingDir` в `ProgramData` (Admins-only DACL), скачивание —
     `Invoke-WebRequest -TimeoutSec 600`, затем гейт подписи
     `Test-HmTrustedSigner -ExpectedSubjectMatch 'Python Software Foundation'`. Функция
     возвращает **пустую строку при успехе** и строку-причину при провале
     (`_deelev.ps1:467-548`); непустая причина → установщик не запускается вовсе.
     Кэш убирается `Remove-HmSecureStagingDir` в любом исходе. Не удалось создать
     защищённый каталог — онлайн-фолбэк пропускается целиком (104-106).
6. Нет Python: в dry-run — `exit 0` (110), иначе `exit 1` (111).
7. **Поиск `requirements.txt`** (117-132) — пять кандидатов по порядку:
   `$HM_BUNDLED_CONFIG`, `$HM_VENDOR\config-pack`, `$HM_VENDOR_BUNDLED\config-pack`,
   вшитый vendor рядом со скриптами (`<resources>\scripts\windows` → `<resources>\vendor`),
   и последним — легаси-клон `%USERPROFILE%\.hamidun-setup\config-repo`. Порядок
   намеренный: admin-owned источники раньше user-writable.
8. Ни один кандидат не найден → печатается список проверенных путей и `exit 120` (133-141) —
   graceful skip, а не ошибка.
9. Dry-run (145-151) печатает выбранную ветку строками `[dry-run] WOULD: …` и выходит 0.
10. **Установка библиотек** (152-168): есть `$HM_VENDOR\pywheels` →
    `pip install --user --no-index --find-links $wheels -r $req`; при ненулевом коде — не
    падение, а онлайн-докачка `pip install --user --find-links $wheels -r $req`
    (вшитые колёса остаются в игре, сеть закрывает дыры). Нет `pywheels` → обычный
    онлайн `pip install --user -r $req`. Итоговый ненулевой код → `exit 1`.
11. **Браузеры Playwright** (170-199): есть `$HM_VENDOR\playwright-browsers` → рекурсивное
    копирование в `%LOCALAPPDATA%\ms-playwright`, затем **всегда**
    `python -m playwright install chromium` — сверка ревизий (вшитый набор мог не совпасть
    с версией пакета, плюс `fetch-vendor` срезает `chromium_headless_shell`). Нет папки →
    сразу онлайн-докачка. Провал в обоих случаях выставляет `$pwWarn = $true` и печатает
    предупреждение, но **шаг не валит**.
12. **Доводка рантайма** (201-221): если есть `%USERPROFILE%\.claude\scripts\setup_runtime.py`
    — запуск. Комментарий объясняет причину: `config` идёт раньше (`pydeps` требует `config`),
    Python там ещё не установлен, и доводка не выполнялась ни разу. Провал — только предупреждение.
12а. **Команда `python` в новом терминале** (перед финалом). Скрипт сам зовёт Python по абсолютному
    пути, а человек набирает `python` — и если каталога Python нет в PATH (Python стоял раньше без
    галочки «Add python.exe to PATH»), Windows отдаёт заглушку Магазина из `WindowsApps`: «Python was
    not found…». `Find-HmOnPath` (`scripts/windows/_userpath.ps1`) ищет `python` по машинному и
    пользовательскому PATH из реестра так же, как cmd (путь собирается `[IO.Path]::Combine` внутри `try`: записи PATH на несуществующих дисках не пишут в журнал ошибок `DriveNotFound`); чистая `Get-HmPythonPathPlan` решает: первым
    находится настоящий python или стоит Python из Магазина (`WindowsApps\PythonSoftwareFoundation.Python.*`) —
    не трогаем; заглушка или ничего — каталог Python и его `Scripts` дописываются В НАЧАЛО PATH
    пользователя (`Add-HmUserPath -Prepend`), как сделала бы та галочка; если каталог Python уже стоит в PATH, но ПОЗЖЕ заглушки Магазина, он переносится в начало, остальные записи и `%VAR%` остаются как были. Всё это — одна функция `Repair-HmPythonPath` в `scripts/windows/_userpath.ps1`: её зовёт `pydeps.ps1` и блок починок `verify.ps1` на каждом прогоне (Python ищется в привычных каталогах функцией `Find-HmKnownPython` и сам не запускается). Повторный запуск снимает галочку `pydeps`, и без второго вызова человек, поставивший библиотеки раньше, остался бы со ссылкой на Магазин. Если и после этого первой
    остаётся заглушка, печатается, где выключить псевдонимы приложений; сами псевдонимы установщик
    не трогает.
13. Финал (223-225): при `$pwWarn` — «библиотеки установлены, но браузеры Playwright — нет»,
    иначе «OK». В обоих случаях `exit 0`.

### macOS — `scripts/macos/pydeps.sh`

Тот же порядок, четыре существенных отличия:

- Python ставится из `.pkg` под root через общий скрипт `HM_PKG_INSTALL_SH` с **пином
  Team ID PSF `BMM5U3QVKW`** (строки 11, 20, 37); verify и install идут атомарно на
  staged-копии, окна TOCTOU нет. Вшитый pkg дополнительно проходит `verify_artifact` (SHA-256).
- Кандидатов `requirements.txt` всего два (45-49), и отсутствие файла — **`exit 1`**
  с текстом «сначала установите конфиг», а не graceful skip.
- `pip` вызывается с `--break-system-packages`, и при провале `pydeps_fail` сначала
  пробует объяснить причину через `hm_explain_build_failure` (живой случай: Intel Mac, нет
  колеса `cryptography`, pip полез собирать Rust) и только если причина не опознана —
  говорит про сеть. В `$PIPLOG` дублируется вывод **не всех** вызовов pip, а только тех,
  что идут через обёртку `pip_run` с `tee -a "$PIPLOG"` (`pydeps.sh:62-65`): это `:83`,
  `:86`, `:91`. Два оставшихся вызова — апгрейды самого pip (`:85`, `:89`) — обёртку не
  зовут и вывод выбрасывают в `/dev/null`, так что их провал `hm_explain_build_failure`
  (`:70`) объяснить не сможет: в логе его нет.
- Браузеры лежат в арх-специфичной папке `playwright-browsers-$(arch_tag)`; после `cp -R`
  снимается `com.apple.quarantine` (иначе Gatekeeper не даёт стартовать ненотаризованному
  Chromium). Компонент объявлен в `mac-arch-support.json` как `resolvedAtInstall` с явным
  описанием риска Intel.
- **Компиляция только там, где она возможна** (`pydeps.sh:66-86`, решение —
  `hm_build_policy` в `_lib.sh:492-498`). На Intel, под Rosetta и без Xcode Command Line
  Tools pip получает `--only-binary=:all:`: сам берёт самую новую версию с готовой сборкой
  под этот Mac (для `cryptography` на Intel это 48.x) и не запускает ни Rust, ни системный
  `cc` с окном «требуются инструменты разработчика». Исключение `--no-binary=<имена>` —
  только для чистого Python без компилятора (`hm_pip_exempt_sdists`): `pyaes` из списка
  заведомо чистых (на PyPI у него ТОЛЬКО исходники, это зависимость Telethon — он нужен и
  без вшитого набора колёс) плюс вшитые архивы, прошедшие проверку `hm_sdist_is_pure_python`
  (в архиве нет C/C++/Rust/Cython-исходников и расширений в сборочных файлах; нечитаемый
  архив считается «не чистым»). Проверка нужна, потому что `pip download` кладёт во вшитый
  набор исходники и для скомпилированной библиотеки, у которой новейший выпуск без колеса
  под раннер, а пустить такой архив в обход запрета значило бы собирать его на Mac
  человека. На Apple Silicon с инструментами — прежнее поведение плюс `--prefer-binary`.
- **Не «всё или ничего»** (`pydeps_per_library`). Нет готовой сборки (`hm_pip_failure_kind`
  = `no-wheel`, без признаков сети) у части библиотек раньше проваливало ВСЕ: pip решает
  `requirements.txt` целиком. Теперь после такого отказа каждая строка ставится отдельно
  (те же правила: только готовые сборки плюс проверенный чистый Python). Что встало —
  стоит; не встала часть — последней строкой `ЧАСТИЧНО: не поставились: a, b, c — нет
  готовой сборки под этот Mac; навыки с ними не заработают, остальное на месте` и
  `exit 121` (список имён укорачивает `hm_names_summary`: строка укладывается в 240 знаков
  и при десятках имён); не встала ни одна — осознанный пропуск `exit 120` с понятной
  последней строкой (`pydeps_skip_no_prebuilt`); провал другого рода (сеть, место, сборка)
  посреди поштучной установки — красный `exit 1` по логу последней попытки, а не
  «пропуск». Доводка рантайма (на чистом Python, от этих библиотек не зависит) выполняется и
  при пропуске 120; при частичном успехе 121 дальше идут и браузеры Playwright. Причина
  провала судится по онлайн-попытке: лог офлайн-попытки обнуляется перед ней
  (`pydeps.sh:155`).

### Почему на Windows браузер всегда из сети

`package.json:115-126` — фильтр `win.extraResources`: `"!playwright-browsers/**"` и
`"!playwright-browsers-*/**"`. В Windows-сборку папка не едет (потолок 32-битного
makensis), поэтому офлайн-ветка `pydeps.ps1:174` в упакованном установщике не выбирается
и Chromium докачивается. На macOS весь `vendor` копируется на том dmg целиком, поэтому
браузер там действительно вшит.

### Как результат виден в интерфейсе

`exit 0` → маркер установки пишется (`shouldRecordInstall`, `src/install-receipts.js:57-59`).
`exit 120` → `isSkipExit` (`:33-34`), маркер и манифест **не** пишутся: `skipped =
receipts.isSkipExit(code)` (`src/main.js:1549`), гейт записи `shouldRecordInstall(code,
isDryRun, hidden)` (`:1335`) на коде 120 ложен, и в лог уходит «пропущен (код 120, нечего
ставить) — маркер/манифест НЕ записаны» (`:1365`). Renderer ставит шагу статус `skipped`,
добавляет его в `bad` (чтобы зависимые не стартовали) и печатает «Пропущено: нечего устанавливать»
(`src/renderer/app.js:1740-1751`).

## Инварианты

1. **Вшитый `python-setup.exe` не запускается без совпадения SHA-256.**
   `Confirm-HmArtifact $pyInst` (`pydeps.ps1:57`) → `_verify.ps1:66-106`: нет файла, нет
   `HM_VENDOR`, нет `checksums.json`, нет записи, не совпал хеш или размер → `exit 1`.
2. **Скачанный с python.org установщик не запускается без подтверждённой подписи.**
   `Test-HmTrustedSigner -ExpectedSubjectMatch 'Python Software Foundation'`
   (`pydeps.ps1:96-102`) требует Authenticode `Status=Valid`, цепочку с корнем **в
   `LocalMachine\Root`** (а не `CurrentUser\Root`), EKU Code Signing и совпадение Subject.
   Любая непустая причина → «НЕ запускаю (fail-closed)».
3. **Загрузка идёт не в `%TEMP%`, а в Admins-only каталог.** `New-HmSecureStagingDir`
   (`pydeps.ps1:81`); если каталог создать не удалось — онлайн-фолбэк не выполняется
   вовсе (`:104-106`), а после установки каталог удаляется (`:103`).
4. **Elevated-PATH не содержит пользовательских каталогов.** `Update-Path`
   (`pydeps.ps1:8-28`) читает только `Machine`-PATH и фиксированные системные пути;
   `WindowsApps`-заглушка отбрасывается отдельно (`:33`, `:45`).
5. **Ни один вызов `Invoke-WebRequest`/`Invoke-RestMethod` не остаётся без таймаута.**
   `Invoke-WebRequest … -TimeoutSec 600` (`pydeps.ps1:87`). Держится тестом «Windows: НИ
   ОДИН сетевой вызов без -TimeoutSec…» (`test/run-tests.js:5889`): он обходит все `.ps1`

## Что ломается, если инвариант нарушить

1. **(SHA-256 вшитого установщика.)** Подменённый `python-setup.exe` внутри установщика
   запустится с правами администратора: человек получает не Python, а чужой код на своей
   машине, и узнать об этом ему неоткуда.
2. **(Подпись онлайн-установщика.)** Файл, подсунутый по дороге или через отравленный
   пользовательский корень сертификатов, исполнится под админом. Это тот самый сценарий,
   ради которого корень требуется именно в `LocalMachine\Root`: `CurrentUser\Root`
   пишется без UAC, и подделка выглядела бы «валидной».
3. **(Admins-only кэш.)** Загрузка в `%TEMP%` даёт окно подмены между скачиванием и
   запуском: процесс того же пользователя (без прав администратора) заменяет файл, а
   запускает его установщик уже elevated.
4. **(PATH.)** В elevated-процесс попадёт `python.exe`/`pip.exe` из каталога, который
   пользовательский процесс дописал в свой PATH — и все дальнейшие `pip install`
   выполнятся чужим интерпретатором.
5. **(Таймаут.)** На плохом канале или при перехвате трафика шаг висит бесконечно:
   человек видит вечный спиннер, watchdog его намеренно не убивает.
6. **(`-Wait` с тихим флагом.)** Установщик Python откроет интерактивное окно и будет
   ждать нажатия — установка встанет намертво посреди автоматического прогона.
7. **(Код 120.)** Если сборка без `requirements.txt` вернёт 1 — человек увидит красный
   крест на шаге, хотя Python установлен и работает; если вернёт 0 — будет записан маркер
   «pydeps установлен», и при следующем запуске установщик не предложит доставить
   библиотеки, которых нет.
8. **(Онлайн-докачка после офлайн-провала.)** Одно колесо, не вшитое под текущий ABI или
   архитектуру, обнулит весь шаг: библиотеки не встанут вовсе, хотя 129 колёс из 130 были
   в коробке.
9. **(Сверка ревизий.)** Скопированный Chromium может не подойти установленной версии
   `playwright`, и вместо ошибки на установке человек получит падение в бою:
   «Executable doesn't exist … chrome-headless-shell.exe» — при следующем запуске навыка,
   без связи с установщиком.
10. **(Честный финал.)** Строка «OK: Python-зависимости установлены» после неудачной
    докачки браузеров — прямая ложь: браузерные навыки уже сломаны, а человек уверен, что
    всё встало. Ровно это и чинили в `pydeps.sh` (комментарий 147-150).
11. **(Фильтр сборки.)** Возврат `playwright-browsers` в Windows-сборку раздувает
    portable-exe. Класс причины задокументирован (`package.json:39`: 32-битный makensis
    падает на mmap при >2 ГБ — «та же причина, что у `!playwright-browsers`»), но
    количественного исхода для этой папки в репозитории нет, и собственные цифры его не
    подтверждают: база 1195 МиБ при потолке ≈2048 МиБ (`package.json:43`, `:48`) плюс
    замер рабочего `vendor/playwright-browsers` на этой машине — 390 МиБ несжатых при
    `"compression": "maximum"` (`package.json:59`) — дают ≈1585 МиБ, то есть ≈77 %
    потолка, а не выход за него. Не подтверждено кодом, что Windows-издание перестанет
    собираться; подтверждено только то, что фильтр эту папку исключает (`:118-123`).
12. **(Team ID на macOS.)** `installer` под root поставит любой подписанный кем угодно
    пакет — то есть отдаст root машине, которую человек просто попросил настроить.
13. **(Порядок кандидатов.)** Список пакетов будет прочитан из каталога в профиле
    пользователя, куда мог дописать не-admin процесс: под админом установится то, что там
    написано.

## Границы

- Компонент **не ставит Node.js и npm** — они приходят из `node`, а `playwright` как
  npm-пакет здесь не устанавливается вовсе (`python -m playwright` — это python-пакет из
  `requirements.txt`).
- **Виртуального окружения нет**: всё ставится в пользователя (`pip install --user`;
  на macOS дополнительно `--break-system-packages`). Изоляции от чужих пакетов
  пользователя компонент не обещает.
- **Скачанные с PyPI колёса не проверяются по SHA-256** — гарантия распространяется на
  вшитые артефакты (`Confirm-HmArtifact`) и на подпись установщика Python; доверие к PyPI
  здесь такое же, как у обычного `pip`.
- **Версия Python не фиксирована одна на все пути.** Вшитый установщик собирается под
  версию сборочной машины (`tools/fetch-vendor.ps1:351-353`), онлайн-фолбэк жёстко берёт
  3.12.10 (`pydeps.ps1:70`), а `Get-Py` уже установленный интерпретатор по версии почти не
  фильтрует: первая ветка (`pydeps.ps1:33-39`) отдаёт любой `python`/`python3` из
  Machine-PATH, чей `--version` матчится регуляркой `Python \d` (то есть и 3.9, и 3.14),
  последняя (`:44-45`) отдаёт `py`, версию которого не проверяет вовсе, и только средняя
  (`:39-41`) ограничена абсолютными путями `Python313|312|311`. Это ровно ABI-вопрос из
  риска 2.
- **Отката нет**: установленные пакеты и браузеры при повторном/неудачном прогоне не
  удаляются; повтор шага идемпотентен только в том смысле, что `pip` и
  `playwright install` сами по себе идемпотентны.
- **Winget-ветка мертва по построению** — это осознанная уступка, задокументированная в
  самом коде (`pydeps.ps1:62-64`), а не забытый код.
- **Успех шага не означает работающих браузерных навыков**: при `$pwWarn` шаг всё равно
  завершается `exit 0`.
- Доводка рантайма (`setup_runtime.py`) — не часть обещания этого компонента: её провал
  печатает предупреждение и не влияет на код возврата.

## Риски и открытые вопросы

1. **Мёртвый третий кандидат `requirements.txt`.** `pydeps.ps1:122` читает
   `$env:HM_VENDOR_BUNDLED`, но эту переменную никто не устанавливает. Во всём
   `src/main.js` присвоений `childEnv.*` двенадцать, и это полный список ключей:
   `HM_VENDOR` (`:1135`), `HM_BUNDLED_CONFIG` (`:1136`), `HM_AGENT_DIR` (`:1137`),
   `HM_NOMAD_SRC` (`:1138`), `HM_ASSETS` (`:1139`), `HM_COURSE_BEACON_URL` и
   `HM_COURSE_BEACON_SECRET` (`:1158-1159`), `HM_REMOTE_CACHE` (`:1161`), `HM_DRY_RUN`
   (`:1164`), `HM_ADDITIVE` (`:1178`), `HM_CONFIG_REPO_URL` (`:1192`),
   `HM_CONFIG_REPO_BRANCH` (`:1194`); плюс два снятия через `delete` — `HM_REMOTE_CACHE`
   (`:1095`) и `HM_ADDITIVE` (`:1180`). `HM_VENDOR_BUNDLED` среди них нет: поиск по
   репозиторию даёт этому имени только ЧТЕНИЯ (здесь же `:120` и
   `scripts/windows/nomad.ps1:202`) и ни одной записи. Allowlist `src/install-env.js:20-28`
   такой ключ из renderer не пропускает. В `scripts/windows/nomad.ps1:198-202` то же чтение снабжено
   оговоркой «если main его пробросил» — то есть ветка писалась под ещё не сделанный
   проброс. Сейчас кандидат просто пропускается.
2. **Комментарий про ABI колёс расходится с кодом сборки.** `pydeps.ps1:67-68` утверждает:
   «pywheels = cp312 / win_amd64; tools/fetch-vendor.ps1 -> 3.12.10». Фактически
   `tools/fetch-vendor.ps1:351-353` берёт версию **локального** Python сборочной машины, а
   `3.12.10` — только фолбэк, если `python` на машине не нашёлся; колёса качаются тем же
   локальным Python «без кросс-флагов» (`:276-286`). В рабочем `vendor/pywheels` на этой
   машине 130 файлов: 128 `.whl` и два sdist (`docopt-0.6.2.tar.gz`, `pyaes-1.6.1.tar.gz`).
   Из колёс **24** несут тег `cp313` и **ни одного** — `cp312`. Практическое следствие:
   онлайн-фолбэк ставит 3.12.10, вшитые колёса под него не подойдут, офлайн-ветка
   провалится и уйдёт в онлайн — то есть «офлайн» обещание в этой комбинации не держится.
   Дыру закрывает фолбэк из инварианта 8, но комментарий читается как гарантия, которой нет.
3. **Тестов на саму `pydeps.ps1` по существу нет.** Файл участвует ровно в двух общих
   проверках (`-Wait` с тихим флагом и `-TimeoutSec`) — ни `exit 120`, ни цепочка
   кандидатов `requirements.txt`, ни гейт подписи, ни фолбэк pip, ни ветка браузеров не
   покрыты. Асимметрия видна рядом: `pydeps.sh` проверяется и `bash -n`, и тестом на
   Team ID; в списке файлов, которым тест требует BOM и прогон PowerShell-парсера
   (`vscode.ps1`, `_deelev.ps1`, `extension.ps1`, `verify.ps1`, `claude-desktop.ps1`,
   `chatgpt-desktop.ps1`, `uv.ps1`), `pydeps.ps1` отсутствует — BOM у файла есть, но
   держится он ничем.
4. **Платформы расходятся на одном и том же случае.** Нет `requirements.txt`: Windows —
   graceful skip 120 с объяснением (`pydeps.ps1:135-143`), macOS — `exit 1` «сначала
   установите конфиг» (`pydeps.sh:50`). Комментарий 113-116 в Windows-скрипте описывает,
   почему смягчили (в lite-издании `HM_BUNDLED_CONFIG` указывает на staging самого
   pydeps, где config-pack нет); на macOS правку не перенесли, хотя `HM_BUNDLED_CONFIG`
   там задаётся тем же `vendorPick`.
5. **Провал копирования браузеров на Windows проглатывается.**
   `Copy-Item -Recurse -Force … -ErrorAction SilentlyContinue` (`pydeps.ps1:178`) — код
   возврата не проверяется. На macOS ровно этот случай ловится (`if cp -R …`, `:101`) и
   ведёт к честному онлайн-фолбэку с отдельным сообщением. На Windows последующий
   `playwright install` обычно закроет дыру, но если и он упадёт, различить «не
   скопировалось» и «не скачалось» по логу нельзя.
6. **`exit 0` при `$pwWarn` даёт маркер установки.** `shouldRecordInstall` смотрит только
   на код 0 (`src/install-receipts.js:57-59`), поэтому компонент считается установленным
   и в UI зелёный, хотя финальная строка говорит обратное. Предупреждение живёт только в
   тексте лога — открытый вопрос, не должен ли этот случай иметь свой код возврата.
7. **Устаревшие ссылки на строки в комментариях `tools/sync-sizes.js`.** Там указаны
   `pydeps.ps1:197` для онлайн-докачки Chromium (фактически 184 и 194) и `pydeps.sh:53`
   для колёс, `:72` для браузеров (фактически 83 и 95). На поведение не влияет, но это
   тот же класс дрейфа, против которого написан `tools/check-specs.js`.
8. **У Windows-ветки нет собственного лога pip и объяснителя.** На macOS вывод pip из
   вызовов через `pip_run` дублируется в `$PIPLOG` и разбирается
   `hm_explain_build_failure`; на Windows человек
   получает «Часть библиотек не установилась — смотри лог» (`pydeps.ps1:170`).
   Общий разбор хвоста — `failureExplain.explainScriptFailure(outTail)` в
   `src/main.js:1627` (словарь `src/failure-explain.js:27` знает про
   `cargo`/`rustc`/`PyO3`) — частично это компенсирует, но специализированного объяснения,
   как на macOS, здесь нет.
