## Что обещает человеку

Человек ставит галочку «Nomad — приватный AI-агент» (она стоит по умолчанию: `components.json:197` — `"default": true`) и получает на машине автономного агента с командами `nmd`, `nomad-agent`, `nomad-acp`. Обещание из карточки (`components.json:194-195`): доступ к нейросети двумя способами — своим API-ключом к любой модели или ключом из кабинета Nomad, и во втором случае «без VPN и без зарубежной карты», потому что запросы идут через облако владельца `https://cp.nomadnet.ai/v1` (`config.json:10`). Плюс локальная панель управления на `127.0.0.1`.

Честная часть обещания, которую видно в самой карточке: компонент «докачивает Python и библиотеки из интернета (~300 МБ) — нужен доступ к сети» (`components.json:194`, `sizeNote` в 188). Без сети он не поставится, и установщик скажет это словами, а не упадёт (см. «Как работает», шаг 3). После установки на финишном экране есть поле «Ключ из кабинета (начинается с `nmd_`)» — вставленный туда ключ записывается в конфиг агента без единой команды в терминале (`src/renderer/app.js:2435-2443`, `src/nomad-key.js:126-192`).

## Как работает

Обе платформы идут одним и тем же каркасом: `scripts/windows/nomad.ps1` и `scripts/macos/nomad.sh`. Ниже — по шагам, с местами, где пути расходятся.

**0. Что запускает скрипт.** `src/main.js:1304` кладёт в окружение дочернего процесса `HM_NOMAD_SRC = vendorPick('nomad-src')`; `vendorPick` (`src/main.js:1275-1281`) берёт путь из staging докачки, если он там есть, иначе из вшитого vendor. `HM_VENDOR` ставится туда же (`src/main.js:1301`). Renderer подставить эти переменные не может: `src/install-env.js:20-28` — явный allowlist, и в комментарии (`src/install-env.js:12-15`) прямо сказано, что `HM_NOMAD_CLOUD_BASEURL/KEY` в него не входят намеренно. На Windows весь установщик работает с правами администратора (`package.json:116` — `"requestedExecutionLevel": "requireAdministrator"`), и `nomad.ps1` де-элевацию не делает: он подключает только `_verify.ps1` (`scripts/windows/nomad.ps1:9`), в отличие от соседей вроде `bridge.ps1`, которые дот-сорсят `_deelev.ps1`.

**1. Guard на чужое.** До всего остального скрипт смотрит, не занято ли имя: каталог uv-тула `nomad-agent` (в `%APPDATA%\uv\tools` и `~/.local/share/uv/tools`) и шимы `nmd`/`nomad-agent`/`nomad-acp` в `~/.local/bin` (`nomad.ps1:73-141`, `nomad.sh:12-21`). Нашлось хоть что-то — `exit 120`, без перезаписи и без `--force`. Перед этим выходом, если в `~/.local\bin` лежит `nmd.exe`, скрипт дописывает этот каталог в PATH пользователя (`Add-HmUserPath`, шим при этом не запускается): у людей с давно поставленным Nomad этого каталога в PATH как раз и нет («Имя nmd не распознано»), а до записи PATH в конце скрипта дело у них уже не доходит.

**2. Источник — только вшитый vendor.** `$src = $env:HM_NOMAD_SRC`; источник считается доверенным, только если в нём лежит `pyproject.toml` (`nomad.ps1:148-153`, `nomad.sh:28-33`). Клонирования в коде нет вовсе — ветка удалена, и `config.json:6` держит `repoUrl` пустым с комментарием-запретом (`config.json:5`). Vendor не вшит → `exit 120` («устанавливать нечего»), а не ошибка. В dry-run Windows продолжает превью секций 2-4 (`nomad.ps1:165-167`), macOS в dry-run без vendor выходит с 0 (`nomad.sh:38`).

**3. Проверка сети.** TCP-коннект на 443 к `github.com` или `pypi.org` с таймаутом 3 с, без скачиваний (`nomad.ps1:55-66`, `nomad.sh:100-102` — там же, но через `curl -sI`). Ответил хоть один — идём дальше; нет — `exit 120` с текстом «Поставь позже при подключении к интернету». **Порядок разный:** на Windows проверка сети стоит до работы с uv (`nomad.ps1:175-181`), на macOS — после установки uv (`nomad.sh:98-108`).

**4. uv (менеджер Python).** Windows ищет uv цепочкой `Resolve-UvExe` (`nomad.ps1:39-49`): `%LOCALAPPDATA%\Programs\uv\uv.exe` → `Get-Command uv` (строка 40 — это как раз поиск по PATH) → `~/.local/bin` → WinGet Links. Безопасность здесь держится не на отказе от PATH, а на том, что PATH к этому моменту переписан: `Update-Path` (`nomad.ps1:13-33`, вызов на 65) собирает его заново из Machine-PATH и фиксированных админ-owned каталогов, никогда не читая user-PATH, — поэтому user-writable запись в него не попадёт. Не нашёл — ищет вшитый `apps\uv\uv.exe` в `HM_VENDOR`, `HM_VENDOR_BUNDLED` и в `<resources>\vendor` и ставит его через `uv.ps1` с той же SHA-256-логикой (`nomad.ps1:193-227`). И только если и этого нет — **онлайн-фолбэк** `Invoke-RestMethod https://astral.sh/uv/install.ps1 -TimeoutSec 120 | Invoke-Expression` (`nomad.ps1:228-242`). На macOS такого фолбэка нет вообще: единственный источник uv — вшитый архив через `uv.sh`, и если его нет (код 120), Nomad пропускается (`nomad.sh:73-89`). Для lite-издания, где nomad — докачиваемый компонент, а uv остаётся вшитым, блок `if (stagingVendor && id === 'nomad')` (`src/main.js:1290-1300`) докладывает вшитый uv в staging именно этого компонента — иначе Windows уходил бы в онлайн-установку под админом.

**5. Гейт целостности.** Windows делает его внутри шага установки (`nomad.ps1:260-275`), macOS — раньше, сразу после выбора источника (`nomad.sh:48-65`). Содержание одинаковое: (а) манифест `vendor/nomad-src.sha256` сам проверяется против `vendor/checksums.json` (`Confirm-HmArtifact`, `scripts/windows/_verify.ps1:66-106`; `verify_artifact`, `scripts/macos/_lib.sh:254`); (б) `pyproject.toml` дополнительно закреплён там же; (в) детерминированный SHA-256 всего дерева (`Get-HmTreeSha256`, `_verify.ps1:24-45`; `hm_tree_sha256`, `_lib.sh:303`) обязан совпасть с манифестом. Нет манифеста или не совпало — `exit 1`, установка не идёт.

**6. Сборка из копии.** Проверенное дерево копируется в ЗАЩИЩЁННУЮ папку и `uv` получает копию, а не vendor. Windows: `New-HmNomadBuildCopy` создаёт каталог тем же атомарным примитивом, что git/node/pydeps (`New-HmSecureStagingDir -Elevated $true` в `ProgramData`: доступ только у Администраторов и SYSTEM, не `%TEMP%`), копирует туда дерево и ЗАНОВО сверяет сумму уже КОПИИ с манифестом — исполняется ровно то, что проверено; каталог убирает `Remove-HmSecureStagingDir` и после успеха, и после отказа uv. Не удалось создать папку, скопировать или сверить — `exit 1`, запасного пути «из vendor напрямую» нет. macOS: приватный `mktemp -d` (`nomad.ps1:227-242`, `nomad.sh:122-126`). Причина в комментарии `nomad.ps1:217-226`: uv/setuptools кладут `build\` и `*.egg-info\` рядом с исходником, дерево меняется, и при следующем запуске гейт честно скажет «vendor подменён». Windows дополнительно проверяет, что копия не пуста, по наличию `pyproject.toml` (`nomad.ps1:232-234`) — потому что `Copy-Item -LiteralPath "...\*"` в PowerShell 5.1 молча копирует ноль файлов.

**7. Установка.** `uv python install 3.12`, затем `uv tool install --python 3.12 <копия>` (`nomad.ps1:254,300`; `nomad.sh:114,150/149`). Без `--force`. На Intel-маке дополнительно передаётся `-c` с ограничением `cryptography>=46.0.7,<49` (`nomad.sh:143-150`) — на Apple Silicon ограничения нет. Windows проверяет коды возврата обеих команд явно и прерывается с `exit 1` до брендинга и квитанции (`nomad.ps1:255,302`); на macOS ту же роль играет `set -euo pipefail` (`nomad.sh:3`).

**7a. macOS: зависимости без компиляции (Intel, Rosetta, нет Xcode CLT).** Решение принимает `hm_build_policy` (`_lib.sh:492-498`): компилировать разрешено только Apple Silicon с инструментами разработчика — там остаётся прежняя команда из каталога (`nomad.sh:218-221`). Во всех остальных случаях (`nomad.sh:172-217`) сам Nomad, чистый Python, собирается отдельно (`uv build --wheel`), а ставится уже готовый пакет `uv tool install --no-build "nomad-agent @ file://…whl"` — `--no-build` запрещает сборку и корневого каталога, поэтому пакет собирается заранее. uv сам берёт самые новые версии зависимостей с готовой сборкой под этот Mac. Нет готовой сборки (`hm_uv_no_wheel`) — осознанный пропуск `exit 120` с понятной последней строкой; сетевой или иной сбой — красный провал с кодом uv. Живой случай 23.09.2026 (Intel): сборка из исходников докачивала Rust, грела ноутбук, а проверка компилятора CMake вызывала системный `cc` — окно «требуются инструменты разработчика».

**8. Брендинг.** В `HERMES_HOME` (по умолчанию `%LOCALAPPDATA%\hermes` / `~/.hermes`) копируются `SOUL.md`, `skins/nomad.yaml` и, если конфига ещё нет, `config.yaml` из `branding/config.yaml.template` (`nomad.ps1:309-335`, `nomad.sh:160-228`). Каждый файл — только если целевого нет; существующий не трогается. Строка об этом печатается только для двух файлов из трёх: у `SOUL.md` и `nomad.yaml` есть `else`-ветка с сообщением «уже существует — не перезаписываю» (`nomad.ps1:320,326`, `nomad.sh:170,223`), а у `config.yaml` `else`-ветки нет ни на одной платформе (`nomad.ps1:328-334`, `nomad.sh:224-227`) — про существующий конфиг не печатается ничего.

**9. Облачный блок.** Если задан `HM_NOMAD_CLOUD_KEY`, в `config.yaml` в начало файла пишется управляемый блок между маркерами `# >>> nomad-cloud … # <<< nomad-cloud <<<` с `provider: "custom"`, `base_url`, `api_key`, `default` (`nomad.ps1:340-389`, `nomad.sh:243-269`). Перед записью снимаются и прежний управляемый блок, и любой top-level `model:` — чтобы блок был ровно один. Ключа нет — блок не пишется, печатается graceful-строка про `nmd model`.

**10. Тот же блок с финишного экрана.** Человек получает ключ в кабинете уже после установки, поэтому на финише есть поле ввода и кнопка «Сохранить ключ» (`src/renderer/app.js:2435-2443`, обработчик 2350-2382, мост `src/preload.js:37`). IPC `nomad-set-key` остался в `main.js` делегацией из двух строк (`src/main.js:2497-2497`); сама запись — `writeNomadKey` в `src/nomad-key.js:126-192`. Она пишет тот же по содержанию блок, но снимает старое иначе: две замены (`src/nomad-key.js:183-184` — снять прежний управляемый блок и снять top-level `model:`) сделаны через `String.prototype.replace` с регулярками без флага `g` (`src/nomad-key.js:23-24`), то есть убирают только первое вхождение, тогда как `nomad.ps1:357,365` и awk в `nomad.sh:250-256` убирают все (см. инвариант 11). Сам блок не заменяется, а приписывается в начало файла при записи (`src/nomad-key.js:186`). Комментарий рядом с делегацией (`src/main.js:2493`) называет это «тремя регулярками» — в коде их две. `base_url`/`default` берутся из `config.json` (`nomad.cloud.baseUrl`, `nomad.cloud.defaultModel`) и чистятся от кавычек и переводов строк (`src/nomad-key.js:153-157`), из ключа они режутся при санитайзе (`src/nomad-key.js:97`). Поле показывается только если Nomad реально установлен — по `installedEver` или по детекту (`src/renderer/app.js:2421-2444`).

**11. Квитанция и коды.** Скрипт печатает `HM-RECEIPT path …` для созданных шимов, каталога uv-тула и брендинговых файлов — но только тех, которые создал сам (`nomad.ps1:393-419`, `nomad.sh:275-283`); `config.yaml` в квитанцию не попадает намеренно. Код 120 распознаётся как «осознанный пропуск» (`src/install-receipts.js:34-35`; вызов `receipts.isSkipExit(code)` — `src/main.js:1542`), и маркер установки при нём не пишется (`shouldRecordInstall`, `src/install-receipts.js:57-59`; вызов — `src/main.js:1547`). Перед ней, если `~/.local\bin\nmd.exe` на месте, каталог дописывается в PATH пользователя (`Add-HmUserPath` из `scripts/windows/_userpath.ps1`: реестр HKCU и рассылка `WM_SETTINGCHANGE`; PATH самого процесса не трогается, чтобы `Get-Command nmd` под админом не нашёл user-writable шим) — раньше финал обещал «nmd появится в PATH» и PATH не трогал. Финальная проверка на Windows: `Get-Command nmd`, иначе `~/.local/bin/nmd.exe`, иначе `exit 1` (`nomad.ps1:421-430`). macOS печатает результат и завершает `exit 0` в обоих случаях (`nomad.sh:285-286`).

**12. Детект.** `src/main.js:3139-3156` (комментарий — `2673-2676`) считает Nomad установленным, если найден любой из шимов, каталог uv-тула `nomad-agent` или легаси-клон исходников. Голое имя `nomad`/`nomad.exe` намеренно не детектится — это HashiCorp Nomad.

## Инварианты

1. **Источник установки — только вшитый vendor; клонирования нет ни в одной ветке.** `nomad.ps1:148-164`, `nomad.sh:28-40`; `config.json:6` держит `repoUrl` пустым. В скриптах нет ни одного `git clone`.
2. **Ни один файл из nomad-src не попадает в `uv tool install`, пока SHA-256 всего дерева не совпал с манифестом.** `nomad.ps1:260-275` (`Get-HmTreeSha256` + сравнение), `nomad.sh:48-65` (`hm_tree_sha256`). Несовпадение или отсутствие манифеста — `exit 1`.
3. **Сам манифест `nomad-src.sha256` и `pyproject.toml` закреплены в `vendor/checksums.json`.** `Confirm-HmArtifact` (`scripts/windows/_verify.ps1:66-106`) и `verify_artifact` (`scripts/macos/_lib.sh:254`) вызываются на оба файла до сравнения дерева (`nomad.ps1:265-266`, `nomad.sh:54-55`).

## Что ломается, если инвариант нарушить

1. **Вернуть клонирование** — установщик под правами администратора выполнит `build-backend` из чужого репозитория. Именно эта дыра (TOCTOU: подмена `pyproject.toml` между проверкой и клоном) названа причиной удаления ветки в `nomad.ps1:143-147`.
2. **Снять гейт дерева** — вредонос, работающий под тем же пользователем без прав администратора, подменяет любой `.py` в vendor, и его код исполняется при сборке пакета уже с правами администратора. Человек ничего не заметит: установка пройдёт «успешно».
3. **Не проверять сам манифест** — подменивший дерево подменит и `nomad-src.sha256`, и гейт из пункта 2 станет декоративным: он сверит подделку с подделкой.
4. **Переставить copy перед verify** — проверяться будет одна копия, а ставиться другая; окно подмены открывается ровно между этими двумя шагами. **Вернуть копию в `%TEMP%`** — процесс обычного пользователя подменит файл в ней за минуты, пока `uv` резолвит и качает зависимости, и его код (сборочный бэкенд проекта) выполнится у нас с правами администратора; именно поэтому копия лежит в защищённой папке и сверяется после копирования.
5. **Собирать прямо в vendor** — после первой же установки дерево изменится (`build\`, `*.egg-info\`), и при следующем запуске установщика гейт скажет «vendor подменён/повреждён». Для человека это выглядит так: компонент, который вчера встал, сегодня отказывается ставиться навсегда, и текст говорит о взломе.
6. **Разрешить перезапись** — у человека, который уже поставил Nomad или собственный пакет с именем `nomad-agent`, установщик затрёт рабочий инструмент чужой версией. Восстановить нечем: авто-удаления у компонента нет (инвариант 13).
7. **Копировать брендинг с `-Force`** — человек, настроивший `SOUL.md` под себя, потеряет правки при повторном запуске установщика молча.
8. **Записать в квитанцию `config.yaml` или чужие файлы** — деинсталлятор унесёт пользовательский конфиг с ключами вместе с компонентом.
9. **Вшить ключ владельца** — ключ уедет в каждую сборку, попадёт в руки любому, кто её распакует, и оплачивать чужой трафик будет владелец.
10. **Пустить эти переменные из renderer** — скомпрометированный renderer (он работает без прав администратора) подменит `HM_NOMAD_SRC` на свой каталог и получит исполнение кода под администратором, а `base_url` — уведёт запросы и ключ на чужой сервер.
11. **Оставить два блока `model:`** — YAML-парсер возьмёт последний, и агент пойдёт не туда, куда пользователь только что сохранил ключ. Симптом: «ключ сохранил, а всё равно не работает».
12. **Сделать пропуск нулевым кодом** — установщик запишет маркер «установлено» для того, чего на диске нет: финиш скажет «Агент Nomad уже установлен», человек уйдёт в кабинет за платным ключом и вставит его в конфиг несуществующего агента.
13. **Включить авто-удаление** — придётся писать перечень целей с нуля: сейчас его не существует, `case 'nomad'` возвращает пустой массив (`src/uninstall-targets.js:280`). На строках 242-250 лежит только комментарий прозой, объясняющий, почему авто-удаление отключено: TOCTOU-нора при сносе venv, шимов и клона исходников плюс риск затереть одноимённый чужой uv-tool и потерять данные пользователя.
14. **Показывать поле ключа всегда** — человек вставляет платный ключ туда, где агента нет; конфиг создастся, эффекта не будет, и понять почему по экрану невозможно.
15. **Писать BOM** — YAML-парсер агента не прочитает конфиг, и агент не стартует с сообщением про синтаксис, а не про ключ.

## Границы

- **Не работает офлайн.** Вшит только исходник агента; Python и зависимости тянутся из сети (~300 МБ). Полностью офлайн-машина получает пропуск с кодом 120, а не установку.
- **Не выбирает и не оплачивает модель.** Без ключа облачный блок не пишется вообще; подключение любой нейросети своим API-ключом делается уже внутри агента командой `nmd model` — установщик этот путь только называет в тексте (`nomad.ps1:340`, `nomad.sh:244`).
- **Не удаляется установщиком.** Осознанное решение v1 (`src/uninstall-targets.js:270-278`): компонент ставится, но авто-удаления у него нет ни на одной платформе.
- **Не открывает и не проверяет дашборд.** `config.json:17-20` объявляет `dashboard.url = http://127.0.0.1:9119`, но поиск по `src/`, `scripts/`, `templates/`, `assets/` не нашёл ни одного чтения этого поля — единственное упоминание вне `config.json` это тест, проверяющий, что поле есть и что адрес локальный. Панель поднимает сам агент командой `nmd dashboard`; установщик её не запускает и не проверяет. Что важнее: собранного интерфейса панели (`nomad_cli/web_dist`) и текстового чата (`nomad_cli/tui_dist`) в Nomad от установщика, судя по коду, нет. Оба каталога — CI-артефакты (в `.gitignore` репозитория агента; их собирает workflow публикации: `npm ci` в корне монорепо и `npm run build --workspace web` / `--workspace ui-tui`, затем копия `entry.js` в `tui_dist`), а `vendor/nomad-src` делается `git archive` (`tools/fetch-vendor-mac.sh`, `tools/fetch-vendor.ps1`) и их не содержит; ни один скрипт сборки установщика их не собирает (`grep tui_dist|web_dist` по `tools/`, `scripts/`, `src/` пуст). Запуском Nomad от установщика на чистой машине это не проверено. Сборка обоих каталогов при выпуске установщика — отдельное решение (тяжёлый шаг: корневой `npm ci` и две сборки на раннере); сейчас его нет.
- **Версия Python зафиксирована — 3.12** (`nomad.ps1:254,300`, `nomad.sh:114,150/149`). Причина именно этой цифры в коде не зафиксирована: комментарий над пином говорит «pyproject требует `<3.14`» (`nomad.ps1:244`, `nomad.sh:110`), но `vendor/nomad-src/pyproject.toml:20` объявляет `requires-python = ">=3.11,<3.14"` — диапазон допускает 3.11, 3.12 и 3.13, так что «`<3.14`» объясняет только верхнюю границу, а не выбор 3.12. Почему из трёх разрешённых версий взята средняя — **не подтверждено кодом**.
- **На Intel-маках `cryptography` сознательно не свежайшая** (`<49`, `nomad.sh:143-147`): у более новых версий нет колёс под macOS x86_64, и сборка ушла бы в Rust/OpenSSL. Это уступка, а не баг. С `--no-build` uv выбрал бы такую версию и сам; пин оставлен как явное намерение.
- **`Confirm-HmArtifact` ищет запись в `checksums.json` по базовому имени файла** (`scripts/windows/_verify.ps1:69`), то есть на весь установщик действует одна запись `pyproject.toml`. Код об этом знает — прямо сказано в комментарии `src/main.js:1288`, — но это означает, что имя файла — часть контракта манифеста.
- **На Windows компонент не де-элевируется** — `nomad.ps1` подключает только `_verify.ps1` (строка 9), и uv/Python/шимы ставятся в `$env:USERPROFILE` того процесса, который прошёл UAC.
- **`vendor/nomad-src` в git не хранится** (приватный код агента, `.gitignore`) — на чистом клоне без развёрнутого vendor компонент честно пропускается кодом 120.

## Риски и открытые вопросы

1. **Функционального прогона `nomad.ps1` целиком нет.** Исключение — установочная часть (копия в защищённой папке → `uv tool install` → уборка): её исполняет тест «u3-D: nomad.ps1 — сборка исполняется: uv получает путь КОПИИ в защищённой папке, vendor не пачкается, папка убирается и после успеха, и после отказа uv, нет папки — нет uv» с поддельным `uv`. Остальной Windows-скрипт покрыт только регулярками по исходному тексту (тесты на 3108, 3172, 3205, 3246, 5460, 6973 читают файл как строку). Живьём гоняется только `nomad.sh`, и то под условием `if (bashAvailable())` — иначе печатается «bash недоступен — функциональные прогоны nomad.sh пропущены». То есть на Windows-машине разработчика вся живая проверка компонента может не выполниться вовсе, а регексы по тексту не поймают ошибку поведения (пример такой ошибки уже был — молчаливое копирование нуля файлов, `nomad.ps1:223-226`).
2. **IPC `nomad-set-key` долго не был покрыт ни одним тестом — закрыто выносом логики в `src/nomad-key.js`.** Пока запись жила внутри `ipcMain.handle` в `main.js`, из теста её было не позвать: `main.js` требует `electron`. Теперь `writeNomadKey` гоняется живьём (`test/run-tests.js:10595-10674`: отказы без записи на диск, замена блока вместо второго `model:`, чужие ключи целы, маркеры совпадают с `nomad.ps1`), а отдельный тест сторожит, что в `main.js` осталась делегация без копии логики (`test/run-tests.js:10740-10749`). Это по-прежнему **единственный реальный путь ввода ключа**: см. пункт 3.
3. **`HM_NOMAD_CLOUD_KEY` не задаётся нигде в коде.** Оба скрипта его читают (`nomad.ps1:338`, `nomad.sh:235`), но во всём `src/` есть только комментарий (`src/main.js:2487`) — присвоения нет нигде, а `src/install-env.js:14` явно запрещает приходить ему из renderer. Значит, при обычной установке секция 5 всегда идёт по graceful-ветке «ключ не задан», и облачный блок появляется только через финишное поле. Осталось неподтверждённым, задаётся ли эта переменная снаружи (сборочный скрипт, ручной запуск) — в репозитории такого места я не нашёл.
4. **Catch-фолбэк копирования убран (закрыто, u3-D).** Раньше при ошибке `Copy-Item` `uv tool install` собирал пакет прямо в vendor, загрязнял дерево и ломал гейт целостности при следующем запуске. Теперь любая неудача подготовки копии в защищённой папке — `exit 1` (`nomad.ps1:227-242`), как на macOS (`nomad.sh:125-126`). Остаётся то, что вне этого пункта: сам `uv` и его кэш по-прежнему работают под администратором в пользовательском профиле (находка F3 разбора безопасности), а `Test-Path` защищённой папки зависит от того, что `ProgramData` доступна.
5. **Асимметрия сети между платформами.** Windows проверяет доступность сети до работы с uv (`nomad.ps1:175-181`), macOS — после его установки (`nomad.sh:98-108`). На офлайн-маке uv будет установлен как побочный эффект компонента, который затем сам себя пропустит.
6. **Асимметрия источника uv.** Windows допускает последний онлайн-фолбэк `irm https://astral.sh/uv/install.ps1 | iex` (`nomad.ps1:237`), исполняемый в процессе с правами администратора; доверие здесь держится только на TLS (`nomad.ps1:4-6`). macOS такого пути не имеет вовсе и в этой ситуации пропускает компонент (`nomad.sh:76-79`). Тестом онлайн-ветка не покрыта.
7. **Асимметрия финальной проверки.** Windows требует увидеть `nmd` и иначе завершает `exit 1` (`nomad.ps1:426-435`); macOS после успешного `uv tool install` завершает `exit 0` в любом случае, печатая «команда nmd появится в PATH после перезапуска терминала» (`nomad.sh:232-233`). PATH для `nmd` (каталог `~/.local/bin` в профиль оболочки входа) пишет не `nomad.sh`, а always-run `touchup-claude-path.sh`: если новое окно Терминала `nmd` не находит, он дописывает строку PATH и проверяет снова (и после свежей установки, и у тех, у кого Nomad уже стоит). На Windows проверка по файлу смотрит только `nmd.exe` (строка 350) — расширения без `.exe` в этой ветке нет, хотя guard на входе (строки 75-80) проверяет оба варианта.
8. **Детект считает установленным легаси-клон, которого установщик больше не создаёт.** `src/main.js:3152-3154` засчитывает `%LOCALAPPDATA%\nomad-src\pyproject.toml` (и `~/.nomad-src/pyproject.toml`). На машине со следами старой версии финиш скажет «уже установлен» и покажет поле ключа, хотя шимов может не быть.
9. **`defaultModel` не подтверждён.** `config.json:11` — `claude-opus-4-6`, и комментарий рядом (`config.json:9`) сам требует: «defaultModel MUST be a model id that cp.nomadnet.ai/v1/models actually serves — confirm and adjust». Проверить это кодом нельзя; тест (строка 3273) убеждается только в том, что поле непустое.
10. **Копирование вшитого uv в staging lite-издания не покрыто тестами.** `src/main.js:1290-1300` и ветка `HM_VENDOR_BUNDLED` в `nomad.ps1:200-207` — поиск по тестам на `HM_VENDOR_BUNDLED` и «staging nomad» пуст. Именно этот путь удерживает lite-издание от онлайн-установки uv под администратором.
11. **Размер компонента заявлен числом.** `components.json:202-205`: 115 092 078 байт на Windows и 173 468 667 на macOS. Тест сверки размеров существует (строка 8693), но пропускает проверку при отсутствии развёрнутого vendor и при исчерпании бюджета времени — то есть зелёный прогон не всегда означает, что цифру сверяли.
