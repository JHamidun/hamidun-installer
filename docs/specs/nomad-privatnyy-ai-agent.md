## Что обещает человеку

Человек ставит галочку «Nomad — приватный AI-агент» (она стоит по умолчанию: `components.json:185` — `"default": true`) и получает на машине автономного агента с командами `nmd`, `nomad-agent`, `nomad-acp`. Обещание из карточки (`components.json:183-184`): доступ к нейросети двумя способами — своим API-ключом к любой модели или ключом из кабинета Nomad, и во втором случае «без VPN и без зарубежной карты», потому что запросы идут через облако владельца `https://cp.nomadnet.ai/v1` (`config.json:10`). Плюс локальная панель управления на `127.0.0.1`.

Честная часть обещания, которую видно в самой карточке: компонент «докачивает Python и библиотеки из интернета (~300 МБ) — нужен доступ к сети» (`components.json:183`, `sizeNote` в 188). Без сети он не поставится, и установщик скажет это словами, а не упадёт (см. «Как работает», шаг 3). После установки на финишном экране есть поле «Ключ из кабинета (начинается с `nmd_`)» — вставленный туда ключ записывается в конфиг агента без единой команды в терминале (`src/renderer/app.js:2214-2222`, `src/nomad-key.js:68-94`).

## Как работает

Обе платформы идут одним и тем же каркасом: `scripts/windows/nomad.ps1` и `scripts/macos/nomad.sh`. Ниже — по шагам, с местами, где пути расходятся.

**0. Что запускает скрипт.** `src/main.js:1140` кладёт в окружение дочернего процесса `HM_NOMAD_SRC = vendorPick('nomad-src')`; `vendorPick` (`src/main.js:1111-1117`) берёт путь из staging докачки, если он там есть, иначе из вшитого vendor. `HM_VENDOR` ставится туда же (`src/main.js:1137`). Renderer подставить эти переменные не может: `src/install-env.js:20-28` — явный allowlist, и в комментарии (`src/install-env.js:12-15`) прямо сказано, что `HM_NOMAD_CLOUD_BASEURL/KEY` в него не входят намеренно. На Windows весь установщик работает с правами администратора (`package.json:115` — `"requestedExecutionLevel": "requireAdministrator"`), и `nomad.ps1` де-элевацию не делает: он подключает только `_verify.ps1` (`scripts/windows/nomad.ps1:9`), в отличие от соседей вроде `bridge.ps1`, которые дот-сорсят `_deelev.ps1`.

**1. Guard на чужое.** До всего остального скрипт смотрит, не занято ли имя: каталог uv-тула `nomad-agent` (в `%APPDATA%\uv\tools` и `~/.local/share/uv/tools`) и шимы `nmd`/`nomad-agent`/`nomad-acp` в `~/.local/bin` (`nomad.ps1:71-86`, `nomad.sh:12-21`). Нашлось хоть что-то — `exit 120`, без перезаписи и без `--force`.

**2. Источник — только вшитый vendor.** `$src = $env:HM_NOMAD_SRC`; источник считается доверенным, только если в нём лежит `pyproject.toml` (`nomad.ps1:93-98`, `nomad.sh:28-33`). Клонирования в коде нет вовсе — ветка удалена, и `config.json:6` держит `repoUrl` пустым с комментарием-запретом (`config.json:5`). Vendor не вшит → `exit 120` («устанавливать нечего»), а не ошибка. В dry-run Windows продолжает превью секций 2-4 (`nomad.ps1:105-107`), macOS в dry-run без vendor выходит с 0 (`nomad.sh:38`).

**3. Проверка сети.** TCP-коннект на 443 к `github.com` или `pypi.org` с таймаутом 3 с, без скачиваний (`nomad.ps1:53-64`, `nomad.sh:100-102` — там же, но через `curl -sI`). Ответил хоть один — идём дальше; нет — `exit 120` с текстом «Поставь позже при подключении к интернету». **Порядок разный:** на Windows проверка сети стоит до работы с uv (`nomad.ps1:115-121`), на macOS — после установки uv (`nomad.sh:98-108`).

**4. uv (менеджер Python).** Windows ищет uv цепочкой `Resolve-UvExe` (`nomad.ps1:37-47`): `%LOCALAPPDATA%\Programs\uv\uv.exe` → `Get-Command uv` (строка 40 — это как раз поиск по PATH) → `~/.local/bin` → WinGet Links. Безопасность здесь держится не на отказе от PATH, а на том, что PATH к этому моменту переписан: `Update-Path` (`nomad.ps1:11-31`, вызов на 65) собирает его заново из Machine-PATH и фиксированных админ-owned каталогов, никогда не читая user-PATH, — поэтому user-writable запись в него не попадёт. Не нашёл — ищет вшитый `apps\uv\uv.exe` в `HM_VENDOR`, `HM_VENDOR_BUNDLED` и в `<resources>\vendor` и ставит его через `uv.ps1` с той же SHA-256-логикой (`nomad.ps1:133-167`). И только если и этого нет — **онлайн-фолбэк** `Invoke-RestMethod https://astral.sh/uv/install.ps1 -TimeoutSec 120 | Invoke-Expression` (`nomad.ps1:168-182`). На macOS такого фолбэка нет вообще: единственный источник uv — вшитый архив через `uv.sh`, и если его нет (код 120), Nomad пропускается (`nomad.sh:73-89`). Для lite-издания, где nomad — докачиваемый компонент, а uv остаётся вшитым, блок `if (stagingVendor && id === 'nomad')` (`src/main.js:1126-1136`) докладывает вшитый uv в staging именно этого компонента — иначе Windows уходил бы в онлайн-установку под админом.

**5. Гейт целостности.** Windows делает его внутри шага установки (`nomad.ps1:200-215`), macOS — раньше, сразу после выбора источника (`nomad.sh:48-65`). Содержание одинаковое: (а) манифест `vendor/nomad-src.sha256` сам проверяется против `vendor/checksums.json` (`Confirm-HmArtifact`, `scripts/windows/_verify.ps1:64-104`; `verify_artifact`, `scripts/macos/_lib.sh:219`); (б) `pyproject.toml` дополнительно закреплён там же; (в) детерминированный SHA-256 всего дерева (`Get-HmTreeSha256`, `_verify.ps1:24-43`; `hm_tree_sha256`, `_lib.sh:268`) обязан совпасть с манифестом. Нет манифеста или не совпало — `exit 1`, установка не идёт.

**6. Сборка из копии.** Проверенное дерево копируется во временный каталог и `uv` получает копию, а не vendor (`nomad.ps1:226-241`, `nomad.sh:122-126`). Причина в комментарии `nomad.ps1:216-225`: uv/setuptools кладут `build\` и `*.egg-info\` рядом с исходником, дерево меняется, и при следующем запуске гейт честно скажет «vendor подменён». Windows дополнительно проверяет, что копия не пуста, по наличию `pyproject.toml` (`nomad.ps1:231-233`) — потому что `Copy-Item -LiteralPath "...\*"` в PowerShell 5.1 молча копирует ноль файлов.

**7. Установка.** `uv python install 3.12`, затем `uv tool install --python 3.12 <копия>` (`nomad.ps1:194,240`; `nomad.sh:114,147/149`). Без `--force`. На Intel-маке дополнительно передаётся `-c` с ограничением `cryptography>=46.0.7,<49` (`nomad.sh:143-147`) — на Apple Silicon ограничения нет. Windows проверяет коды возврата обеих команд явно и прерывается с `exit 1` до брендинга и квитанции (`nomad.ps1:195,242`); на macOS ту же роль играет `set -euo pipefail` (`nomad.sh:3`).

**8. Брендинг.** В `HERMES_HOME` (по умолчанию `%LOCALAPPDATA%\hermes` / `~/.hermes`) копируются `SOUL.md`, `skins/nomad.yaml` и, если конфига ещё нет, `config.yaml` из `branding/config.yaml.template` (`nomad.ps1:249-273`, `nomad.sh:157-175`). Каждый файл — только если целевого нет; существующий не трогается. Строка об этом печатается только для двух файлов из трёх: у `SOUL.md` и `nomad.yaml` есть `else`-ветка с сообщением «уже существует — не перезаписываю» (`nomad.ps1:260,266`, `nomad.sh:166,170`), а у `config.yaml` `else`-ветки нет ни на одной платформе (`nomad.ps1:268-272`, `nomad.sh:171-174`) — про существующий конфиг не печатается ничего.

**9. Облачный блок.** Если задан `HM_NOMAD_CLOUD_KEY`, в `config.yaml` в начало файла пишется управляемый блок между маркерами `# >>> nomad-cloud … # <<< nomad-cloud <<<` с `provider: "custom"`, `base_url`, `api_key`, `default` (`nomad.ps1:285-315`, `nomad.sh:190-216`). Перед записью снимаются и прежний управляемый блок, и любой top-level `model:` — чтобы блок был ровно один. Ключа нет — блок не пишется, печатается graceful-строка про `nmd model`.

**10. Тот же блок с финишного экрана.** Человек получает ключ в кабинете уже после установки, поэтому на финише есть поле ввода и кнопка «Сохранить ключ» (`src/renderer/app.js:2214-2222`, обработчик 2350-2382, мост `src/preload.js:37`). IPC `nomad-set-key` остался в `main.js` делегацией из двух строк (`src/main.js:1968-1969`); сама запись — `writeNomadKey` в `src/nomad-key.js:68-94`. Она пишет тот же по содержанию блок, но снимает старое иначе: две замены (`src/nomad-key.js:85-86` — снять прежний управляемый блок и снять top-level `model:`) сделаны через `String.prototype.replace` с регулярками без флага `g` (`src/nomad-key.js:21-22`), то есть убирают только первое вхождение, тогда как `nomad.ps1:298,300` и awk в `nomad.sh:197-203` убирают все (см. инвариант 11). Сам блок не заменяется, а приписывается в начало файла при записи (`src/nomad-key.js:88`). Комментарий рядом с делегацией (`src/main.js:1963`) называет это «тремя регулярками» — в коде их две. `base_url`/`default` берутся из `config.json` (`nomad.cloud.baseUrl`, `nomad.cloud.defaultModel`) и чистятся от кавычек и переводов строк (`src/nomad-key.js:73-77`), из ключа они режутся при санитайзе (`src/nomad-key.js:44`). Поле показывается только если Nomad реально установлен — по `installedEver` или по детекту (`src/renderer/app.js:2202-2223`).

**11. Квитанция и коды.** Скрипт печатает `HM-RECEIPT path …` для созданных шимов, каталога uv-тула и брендинговых файлов — но только тех, которые создал сам (`nomad.ps1:324-344`, `nomad.sh:222-230`); `config.yaml` в квитанцию не попадает намеренно. Код 120 распознаётся как «осознанный пропуск» (`src/install-receipts.js:33-34`; вызов `receipts.isSkipExit(code)` — `src/main.js:1332`), и маркер установки при нём не пишется (`shouldRecordInstall`, `src/install-receipts.js:36-38`; вызов — `src/main.js:1337`). Финальная проверка на Windows: `Get-Command nmd`, иначе `~/.local/bin/nmd.exe`, иначе `exit 1` (`nomad.ps1:346-355`). macOS печатает результат и завершает `exit 0` в обоих случаях (`nomad.sh:232-233`).

**12. Детект.** `src/main.js:2589-2606` (комментарий — `2673-2676`) считает Nomad установленным, если найден любой из шимов, каталог uv-тула `nomad-agent` или легаси-клон исходников. Голое имя `nomad`/`nomad.exe` намеренно не детектится — это HashiCorp Nomad.

## Инварианты

1. **Источник установки — только вшитый vendor; клонирования нет ни в одной ветке.** `nomad.ps1:93-104`, `nomad.sh:28-40`; `config.json:6` держит `repoUrl` пустым. В скриптах нет ни одного `git clone`.
2. **Ни один файл из nomad-src не попадает в `uv tool install`, пока SHA-256 всего дерева не совпал с манифестом.** `nomad.ps1:200-215` (`Get-HmTreeSha256` + сравнение), `nomad.sh:48-65` (`hm_tree_sha256`). Несовпадение или отсутствие манифеста — `exit 1`.
3. **Сам манифест `nomad-src.sha256` и `pyproject.toml` закреплены в `vendor/checksums.json`.** `Confirm-HmArtifact` (`scripts/windows/_verify.ps1:64-104`) и `verify_artifact` (`scripts/macos/_lib.sh:219`) вызываются на оба файла до сравнения дерева (`nomad.ps1:205-206`, `nomad.sh:54-55`).
4. **Порядок всегда verify → copy → install.** `nomad.ps1`: гейт на 200-215, копия на 226-241, установка на 240. `nomad.sh`: гейт 48-65, копия 122-126, установка 147/149.
5. **На macOS uv всегда получает копию; на Windows — только на happy-path, безусловным инвариантом это не является.** `nomad.sh`: неудача `cp -R` — сразу `exit 1` (`nomad.sh:125-126`), в `uv tool install` уходит только `$BUILD_SRC` (`nomad.sh:147/149`). `nomad.ps1`: `$srcForInstall = $src` при инициализации (`nomad.ps1:227`), на `$buildSrc` он переприсваивается лишь после успешного `Copy-Item` и проверки, что копия не пуста (`nomad.ps1:234`); в `catch` (`nomad.ps1:235-239`) переприсваивания нет — при любой ошибке копирования `uv tool install --python 3.12 "$srcForInstall"` (`nomad.ps1:240`) получает путь ВНУТРИ vendor. Последствия — «Риски», п.4. Копия удаляется после установки (`nomad.ps1:241`, `trap` в `nomad.sh:124`).
6. **Существующий uv-тул `nomad-agent` или любой из шимов `nmd`/`nomad-agent`/`nomad-acp` останавливает установку кодом 120, а не перезаписывается.** `nomad.ps1:71-86`, `nomad.sh:12-21`. Флага `--force` в обоих скриптах нет.
7. **Брендинговый файл копируется только при отсутствии целевого.** `nomad.ps1:256-266`, `nomad.sh:163-170`; у `Copy-Item` для `SOUL.md` и `nomad.yaml` нет `-Force`.
8. **В квитанцию попадают только пути, созданные этим запуском; `HERMES_HOME/config.yaml` в неё не попадает никогда.** `nomad.ps1:320-344` (флаги `$wroteSoul`/`$wroteSkin`), `nomad.sh:218-230` (`WROTE_SOUL`/`WROTE_SKIN`).
9. **Ключ владельца нигде не вшит: в `config.yaml` пишется только ключ друга.** `config.json:9` (комментарий-инвариант), `nomad.ps1:282`, `nomad.sh:182`, `src/main.js:1968-1969` и `src/nomad-key.js:68-71` — ключ приходит либо из env, либо из поля на финише.
10. **Renderer не может подставить ни источник, ни облачные параметры.** `src/install-env.js:20-28` — `hm_nomad_*` в allowlist отсутствуют; `HM_NOMAD_SRC` ставит только main (`src/main.js:1140`).
11. **После записи облачного блока в `config.yaml` остаётся ровно один top-level `model:` — но на пути финишного поля только при условии, что во входном файле такой блок был не больше одного.** В трёх местах снимаются прежний управляемый блок и top-level `model:`, однако охват замен РАЗНЫЙ: `nomad.ps1:298,300` — статический `[regex]::Replace(...)`, снимающий все совпадения; `nomad.sh:197-203` — awk, вырезающий все блоки за один проход; `src/nomad-key.js:85-86` — `String.prototype.replace` с регулярками БЕЗ флага `g` (только `/m`), то есть снимается лишь ПЕРВОЕ вхождение. Условие «не более одного `model:` во входном файле» в коде нигде не проверяется. Третий шаг — не замена, а приписывание блока в начало файла при записи: `nomad.ps1:310`, `nomad.sh:205-214`, `src/nomad-key.js:88`.
12. **«Нечего ставить» — это код 120, а не 0 и не 1; маркер установки при нём не пишется.** `src/install-receipts.js:33-38`, `src/main.js:1332,1337`.
13. **Nomad не удаляется установщиком: план удаления пуст на всех платформах.** `src/uninstall-targets.js:53` (`UNINSTALL_DISABLED`), ветка `case 'nomad'` на 241+; кнопка «Удалить» для него не рендерится, потому что `nomad` отсутствует в множестве `REMOVABLE` (`src/renderer/app.js:43`; строки 40-42 — только комментарий, поведения он не несёт).
14. **Поле ввода ключа на финише показывается только при реально установленном агенте.** `src/renderer/app.js:2202-2223`: `installedEver` или детект, а не галочка выбора.
15. **`config.yaml` пишется без BOM.** `nomad.ps1:312` (`New-Object Text.UTF8Encoding $false`), `src/nomad-key.js:88` (`fs.writeFileSync(cfgY, buildBlock(san.key, url, model, nl) + text, { encoding: 'utf8' })`).

## Что ломается, если инвариант нарушить

1. **Вернуть клонирование** — установщик под правами администратора выполнит `build-backend` из чужого репозитория. Именно эта дыра (TOCTOU: подмена `pyproject.toml` между проверкой и клоном) названа причиной удаления ветки в `nomad.ps1:88-92`.
2. **Снять гейт дерева** — вредонос, работающий под тем же пользователем без прав администратора, подменяет любой `.py` в vendor, и его код исполняется при сборке пакета уже с правами администратора. Человек ничего не заметит: установка пройдёт «успешно».
3. **Не проверять сам манифест** — подменивший дерево подменит и `nomad-src.sha256`, и гейт из пункта 2 станет декоративным: он сверит подделку с подделкой.
4. **Переставить copy перед verify** — проверяться будет одна копия, а ставиться другая; окно подмены открывается ровно между этими двумя шагами.
5. **Собирать прямо в vendor** — после первой же установки дерево изменится (`build\`, `*.egg-info\`), и при следующем запуске установщика гейт скажет «vendor подменён/повреждён». Для человека это выглядит так: компонент, который вчера встал, сегодня отказывается ставиться навсегда, и текст говорит о взломе.
6. **Разрешить перезапись** — у человека, который уже поставил Nomad или собственный пакет с именем `nomad-agent`, установщик затрёт рабочий инструмент чужой версией. Восстановить нечем: авто-удаления у компонента нет (инвариант 13).
7. **Копировать брендинг с `-Force`** — человек, настроивший `SOUL.md` под себя, потеряет правки при повторном запуске установщика молча.
8. **Записать в квитанцию `config.yaml` или чужие файлы** — деинсталлятор унесёт пользовательский конфиг с ключами вместе с компонентом.
9. **Вшить ключ владельца** — ключ уедет в каждую сборку, попадёт в руки любому, кто её распакует, и оплачивать чужой трафик будет владелец.
10. **Пустить эти переменные из renderer** — скомпрометированный renderer (он работает без прав администратора) подменит `HM_NOMAD_SRC` на свой каталог и получит исполнение кода под администратором, а `base_url` — уведёт запросы и ключ на чужой сервер.
11. **Оставить два блока `model:`** — YAML-парсер возьмёт последний, и агент пойдёт не туда, куда пользователь только что сохранил ключ. Симптом: «ключ сохранил, а всё равно не работает».
12. **Сделать пропуск нулевым кодом** — установщик запишет маркер «установлено» для того, чего на диске нет: финиш скажет «Агент Nomad уже установлен», человек уйдёт в кабинет за платным ключом и вставит его в конфиг несуществующего агента.
13. **Включить авто-удаление** — придётся писать перечень целей с нуля: сейчас его не существует, `case 'nomad'` возвращает пустой массив (`src/uninstall-targets.js:252`). На строках 242-250 лежит только комментарий прозой, объясняющий, почему авто-удаление отключено: TOCTOU-нора при сносе venv, шимов и клона исходников плюс риск затереть одноимённый чужой uv-tool и потерять данные пользователя.
14. **Показывать поле ключа всегда** — человек вставляет платный ключ туда, где агента нет; конфиг создастся, эффекта не будет, и понять почему по экрану невозможно.
15. **Писать BOM** — YAML-парсер агента не прочитает конфиг, и агент не стартует с сообщением про синтаксис, а не про ключ.

## Границы

- **Не работает офлайн.** Вшит только исходник агента; Python и зависимости тянутся из сети (~300 МБ). Полностью офлайн-машина получает пропуск с кодом 120, а не установку.
- **Не выбирает и не оплачивает модель.** Без ключа облачный блок не пишется вообще; подключение любой нейросети своим API-ключом делается уже внутри агента командой `nmd model` — установщик этот путь только называет в тексте (`nomad.ps1:286`, `nomad.sh:191`).
- **Не удаляется установщиком.** Осознанное решение v1 (`src/uninstall-targets.js:242-250`): компонент ставится, но авто-удаления у него нет ни на одной платформе.
- **Не открывает и не проверяет дашборд.** `config.json:17-20` объявляет `dashboard.url = http://127.0.0.1:9119`, но поиск по `src/`, `scripts/`, `templates/`, `assets/` не нашёл ни одного чтения этого поля — единственное упоминание вне `config.json` это тест, проверяющий, что поле есть и что адрес локальный. Панель поднимает сам агент командой `nmd dashboard`; установщик её не запускает и не проверяет.
- **Версия Python зафиксирована — 3.12** (`nomad.ps1:194,240`, `nomad.sh:114,147/149`). Причина именно этой цифры в коде не зафиксирована: комментарий над пином говорит «pyproject требует `<3.14`» (`nomad.ps1:184`, `nomad.sh:110`), но `vendor/nomad-src/pyproject.toml:20` объявляет `requires-python = ">=3.11,<3.14"` — диапазон допускает 3.11, 3.12 и 3.13, так что «`<3.14`» объясняет только верхнюю границу, а не выбор 3.12. Почему из трёх разрешённых версий взята средняя — **не подтверждено кодом**.
- **На Intel-маках `cryptography` сознательно не свежайшая** (`<49`, `nomad.sh:143-147`): у более новых версий нет колёс под macOS x86_64, и сборка ушла бы в Rust/OpenSSL. Это уступка, а не баг.
- **`Confirm-HmArtifact` ищет запись в `checksums.json` по базовому имени файла** (`scripts/windows/_verify.ps1:67`), то есть на весь установщик действует одна запись `pyproject.toml`. Код об этом знает — прямо сказано в комментарии `src/main.js:1124`, — но это означает, что имя файла — часть контракта манифеста.
- **На Windows компонент не де-элевируется** — `nomad.ps1` подключает только `_verify.ps1` (строка 9), и uv/Python/шимы ставятся в `$env:USERPROFILE` того процесса, который прошёл UAC.
- **`vendor/nomad-src` в git не хранится** (приватный код агента, `.gitignore`) — на чистом клоне без развёрнутого vendor компонент честно пропускается кодом 120.

## Риски и открытые вопросы

1. **Функционального прогона `nomad.ps1` нет ни одного.** Windows-скрипт покрыт только регулярками по исходному тексту (тесты на 3108, 3172, 3205, 3246, 5460, 6973 читают файл как строку). Живьём гоняется только `nomad.sh`, и то под условием `if (bashAvailable())` — иначе печатается «bash недоступен — функциональные прогоны nomad.sh пропущены». То есть на Windows-машине разработчика вся живая проверка компонента может не выполниться вовсе, а регексы по тексту не поймают ошибку поведения (пример такой ошибки уже был — молчаливое копирование нуля файлов, `nomad.ps1:222-225`).
2. **IPC `nomad-set-key` долго не был покрыт ни одним тестом — закрыто выносом логики в `src/nomad-key.js`.** Пока запись жила внутри `ipcMain.handle` в `main.js`, из теста её было не позвать: `main.js` требует `electron`. Теперь `writeNomadKey` гоняется живьём (`test/run-tests.js:9804-9881`: отказы без записи на диск, замена блока вместо второго `model:`, чужие ключи целы, маркеры совпадают с `nomad.ps1`), а отдельный тест сторожит, что в `main.js` осталась делегация без копии логики (`test/run-tests.js:9947-9956`). Это по-прежнему **единственный реальный путь ввода ключа**: см. пункт 3.
3. **`HM_NOMAD_CLOUD_KEY` не задаётся нигде в коде.** Оба скрипта его читают (`nomad.ps1:282`, `nomad.sh:182`), но во всём `src/` есть только комментарий (`src/main.js:1957`) — присвоения нет нигде, а `src/install-env.js:14` явно запрещает приходить ему из renderer. Значит, при обычной установке секция 5 всегда идёт по graceful-ветке «ключ не задан», и облачный блок появляется только через финишное поле. Осталось неподтверждённым, задаётся ли эта переменная снаружи (сборочный скрипт, ручной запуск) — в репозитории такого места я не нашёл.
4. **Catch-фолбэк копирования возвращает ровно ту поломку, ради которой копию и завели.** `nomad.ps1:235-239`: если `Copy-Item` не удался, `$srcForInstall` остаётся равен `$src`, и `uv tool install` собирает пакет прямо в vendor. Это загрязнит дерево артефактами сборки, и при следующем запуске гейт целостности скажет «vendor подменён» — то есть компонент перестанет ставиться навсегда. На macOS такого фолбэка нет: там неудача `cp` — это `exit 1` (`nomad.sh:125-126`).
5. **Асимметрия сети между платформами.** Windows проверяет доступность сети до работы с uv (`nomad.ps1:115-121`), macOS — после его установки (`nomad.sh:98-108`). На офлайн-маке uv будет установлен как побочный эффект компонента, который затем сам себя пропустит.
6. **Асимметрия источника uv.** Windows допускает последний онлайн-фолбэк `irm https://astral.sh/uv/install.ps1 | iex` (`nomad.ps1:177`), исполняемый в процессе с правами администратора; доверие здесь держится только на TLS (`nomad.ps1:4-6`). macOS такого пути не имеет вовсе и в этой ситуации пропускает компонент (`nomad.sh:76-79`). Тестом онлайн-ветка не покрыта.
7. **Асимметрия финальной проверки.** Windows требует увидеть `nmd` и иначе завершает `exit 1` (`nomad.ps1:346-355`); macOS после успешного `uv tool install` завершает `exit 0` в любом случае, печатая «команда nmd появится в PATH после перезапуска терминала» (`nomad.sh:232-233`). На Windows проверка по файлу смотрит только `nmd.exe` (строка 350) — расширения без `.exe` в этой ветке нет, хотя guard на входе (строки 75-80) проверяет оба варианта.
8. **Детект считает установленным легаси-клон, которого установщик больше не создаёт.** `src/main.js:2602-2604` засчитывает `%LOCALAPPDATA%\nomad-src\pyproject.toml` (и `~/.nomad-src/pyproject.toml`). На машине со следами старой версии финиш скажет «уже установлен» и покажет поле ключа, хотя шимов может не быть.
9. **`defaultModel` не подтверждён.** `config.json:11` — `claude-opus-4-6`, и комментарий рядом (`config.json:9`) сам требует: «defaultModel MUST be a model id that cp.nomadnet.ai/v1/models actually serves — confirm and adjust». Проверить это кодом нельзя; тест (строка 3273) убеждается только в том, что поле непустое.
10. **Копирование вшитого uv в staging lite-издания не покрыто тестами.** `src/main.js:1126-1136` и ветка `HM_VENDOR_BUNDLED` в `nomad.ps1:140-147` — поиск по тестам на `HM_VENDOR_BUNDLED` и «staging nomad» пуст. Именно этот путь удерживает lite-издание от онлайн-установки uv под администратором.
11. **Размер компонента заявлен числом.** `components.json:189-192`: 115 092 078 байт на Windows и 173 468 667 на macOS. Тест сверки размеров существует (строка 8693), но пропускает проверку при отсутствии развёрнутого vendor и при исчерпании бюджета времени — то есть зелёный прогон не всегда означает, что цифру сверяли.
