# План перевода проекта в инженерный режим

Дата: 2026-08-25. Решения владельца получены (раздел 6) — план **утверждён к исполнению**.

Порядок фаз выправлен по замечаниям владельца (сравнение с планом проекта Phoenix):
фундамент идёт ПЕРЕД инвентаризацией, инвентаризация делается тремя независимыми
проходами роя, границы ролей вынесены в отдельный принцип.

---

## 1. Зачем

Продукт работает и выпущен, но управляется он разговором. Задачи живут в чате и в
списке дел одной сессии — вместе с сессией и умирают. Спек нет, поэтому «что уже
есть» знает только тот, кто это писал. Отсюда осыпание: чинится симптом, а не
место в системе.

Четыре результата, каждый проверяемый:

1. **Бэклог на диске**, переживающий сессию и видимый обоим.
2. **Спецификация на каждую фичу** — чтобы «сделано» было сверяемо с написанным.
3. **Гейты, которые действительно останавливают** — CI, DoR/DoD, ревью, PR.
4. **Роли с границами** — вместо одного исполнителя на всё.

### Симптомы, которые это уже дало

- **Красный CI не остановил выпуск.** Обязательный гейт падал на «размерах» ещё
  до правок этой сессии; на него перестали смотреть, потому что он был красным
  всегда. Оказалось — настоящий дефект: размеры под macOS отставали на версию.
- **Провал выглядел как успех.** `npm run build` не существует — команда упала с
  «Missing script», а `.exe` от прошлой сборки остались на диске. Поймано только
  сверкой меток времени.
- **Половина правки уехала в коммит.** `main.js` закоммичен без парного теста;
  локально 424/0, в CI красно. Причина — сбор коммита по одному файлу из грязного
  дерева.
- **Выпуск шёл руками** по последовательности из семи шагов, записанной в
  черновике, а не воркфлоу.

Диагноз, который НЕ подтвердился при проверке: «релиз с feature-ветки». Ветка
маскота была впереди `main` на один коммит с документом; релизные правки в `main`
были. Влита, ветка закрыта.

## 3. Принцип, который держит всё остальное

**Границы ролей.** Тот, кто делает, не подтверждает сам себя:

| Роль | Может | НЕ может |
|---|---|---|
| Архитектор (`software-architect`) | спека, ADR, анализ | писать код |
| Исполнитель (`senior-developer`) | код и тесты | принимать свою работу |
| Ревьюер (`code-reviewer`) | находки с воспроизведением | править найденное |
| Аудитор (`security-engineer`) | аудит | править то, что аудировал |
| Верификатор | проверка свежим контекстом | быть автором проверяемого |

Это не бюрократия, а лекарство от конкретного отказа: сегодня зелёный локальный
прогон «подтвердил» коммит, которого в репозитории не было. Проверяющий обязан
брать предмет проверки не из головы автора, а с диска и из git.

## 5. Фазы

### Фаза 0 — Фундамент

Без него остальное бессмысленно: спеки без бэклога — те же заметки в чате.

* **0.1** `bd` установлен и инициализирован в `hamidun-installer` — он главный
  репозиторий, задачи остальных трёх заводятся туда же с меткой репозитория.
* **0.2** Структура `docs/`: `specs/`, `adr/`, инвентарь, риски.
* **0.3** Рабочий режим: ветка + PR вместо прямого push. Дерево приводится в
  порядок — незакоммиченное либо коммитится, либо объясняется в задаче.
* **0.4** `DEFINITION-OF-READY.md`, `DEFINITION-OF-DONE.md`, `CONTRIBUTING.md`.

DoD включает пункты, на которых горели: прогон тестов **на том, что уедет в
коммит** (`git stash -u`), сверка артефакта по метке времени, явный маркер кода
возврата в лог, коммит собирается перечислением путей — не `git add -A`.

**DoD фазы:** `bd list` показывает бэклог; четыре документа в репозитории; PR
открыт и проходит CI.

### Фаза 1 — Инвентаризация: три независимых прохода роем

Проходы независимы и идут параллельно — каждый видит своё, пересечения дают
перекрёстную проверку.

* **Проход А — по коду.** `codegraph` + `openwiki`: карта модулей, фич, мёртвого
  кода. Источник — `components.json`, `packs.json`, `remote-components.json`,
  экраны `src/renderer`, скрипты `scripts/{windows,macos}`, воркфлоу.
* **Проход Б — по артефактам.** Все `.md`, черновики выпуска, `config.json`
  с его комментариями-договорами: что обещано документами и выполняется ли.
* **Проход В — по сессиям.** Транскрипты `~/.claude/projects/.../*.jsonl`: что
  планировалось, что сделано, что молча отвалилось.

**Выход:** единый реестр `docs/INVENTORY.md` — строка на фичу: что делает, где
код, есть ли тест, есть ли спека, чем подтверждено. Плюс `docs/RISKS.md` —
места, где отказ молчит.

**DoD:** каждая строка подтверждена командой, файлом или коммитом — не памятью.
Всё найденное заведено задачами в `bd`.

### Фаза 2 — Спецификации и бэклог

* **2.1** `docs/PRD.md` — продукт целиком: для кого, что обещает, чем меряем.
* **2.2** Спека на каждую существующую фичу (`docs/specs/<feature>.md`): что
  делает, как проверить, известные ограничения.
* **2.3** На незакрытое — PRD с критериями приёмки.
* **2.4** ADR на решения, принятые устно: content-addressed публикация,
  fail-closed гейты, де-элевация, два издания, пин Team ID, оффлайн-первичность.

**DoD:** для каждой строки инвентаря есть спека либо явная пометка «спека не
нужна, потому что…».

### Фаза 3 — Процесс

* **3.1** Роли субагентов с границами из раздела 3, закреплённые в `CONTRIBUTING`.
* **3.2** CI как настоящий гейт: починить вечно-красные тесты по существу,
  branch protection на `main` (только PR с зелёным CI).
* **3.3** Релиз воркфлоу вместо ручной последовательности.
* **3.4** Лендингу — свой CI и выкладка из воркфлоу, а не с ноутбука.

**DoD:** попытка влить красное блокируется; выпуск запускается одной кнопкой.

### Фаза 4 — Исполнение бэклога

Волнами по `subagent-driven-development`: архитектор ставит спеку → исполнитель
делает → верификатор проверяет свежим контекстом → ревью → PR → мерж.

## 7. Чего этот план НЕ делает

- Не переписывает работающий код ради красоты. Спека пишется на то, что есть;
  расхождение спеки с кодом заводится задачей, а не правится молча.
- Не вводит вторую систему задач поверх beads.
- Не трогает историю git — вынос юридического имени из истории остаётся
  отдельным решением владельца.
